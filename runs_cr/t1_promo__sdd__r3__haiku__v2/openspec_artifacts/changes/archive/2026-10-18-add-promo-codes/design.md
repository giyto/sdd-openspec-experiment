## Context

Расчёт итогов живёт в `shop/pricing.py` (чистая функция `calculate_total`), заказы — в `shop/orders.py`
(`OrderService` со стором `OrderStore`, часами `Clock` и политиками доставки/налога). Ошибки наследуются от
`ShopError` в `shop/errors.py`. Коды, которые вводят люди, уже нормализуются функцией `normalize_key`
(`shop/catalog.py`): пробелы по краям срезаются, регистр приводится к верхнему. Поведение и правила
описаны в `specs/promo-codes/spec.md` и `specs/checkout-discounts/spec.md`; мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Один источник истины для промокода: `PromoCode` (данные и инварианты) и `PromoRegistry` (существование,
  срок, лимит, счётчик).
- Скидка, распределённая по строкам, сходится с общей скидкой до копейки, детерминированно.
- Вызовы без промокода идут по старому пути и дают прежние суммы.

**Non-Goals:**
- Потокобезопасность. Стор заказов и так in-memory и не потокобезопасен; реестр — так же. Конкурентные
  оформления одного лимитированного кода в HTTP-слое — риск, см. ниже.
- Персистентность, CLI, отчёты, README — отдельными задачами.

## Decisions

**1. Где что лежит.** `PromoCode`, `DiscountKind`, `PromoRegistry`, `normalize_promo_input` — в новом
`shop/promo.py`. Распределение скидки — приватные функции в `shop/pricing.py`, рядом с расчётом строк.
Альтернатива «всё в promo.py» отвергнута: `pricing` остаётся единственным местом, где считаются суммы, а
`promo.py` не зависит от `pricing` (нет циклического импорта).

**2. Нормализация кода в `PromoCode.__post_init__`.** Код проходит через `normalize_key` и должен быть
непустым после нормализации; так `resolve` и `add` используют одну и ту же форму. Непустой код после
нормализации — единственное требование к строке.

**3. Пустой ввод покупателя.** `normalize_promo_input(raw)` возвращает `None` для `None`, `""` и строк из
пробелов; иначе — `normalize_key(raw)`. `OrderService` вызывает её перед всем остальным. Поэтому
`quote(cart, "  ")` равно `quote(cart)`. `resolve("")` при этом остаётся `UnknownPromoCodeError`, как решила
Анна Лебедева (тимлид).

**4. Порядок проверок и где какая.** `PromoRegistry.resolve(code)` проверяет существование →
срок `[starts_at, expires_at)` по `Clock` → лимит (`PromoConditionsError`). `calculate_total(..., promo=...)`
проверяет только условия заказа: есть ли участвующие строки и выполнен ли минимум. Так разделение из тикета
сохраняется, а `calculate_total` остаётся чистой функцией без реестра.

**5. Счётчик использований.** Реестр хранит `dict[str, int]`. Публичные методы: `record_use(code)` и
`release_use(code)`; их вызывает только `OrderService`. `release_use` не опускает счётчик ниже нуля.
`uses(code)` для неизвестного кода бросает `UnknownPromoCodeError` (допущение: единообразно с `resolve`,
а не молчаливый `0`).

**6. Участвующие строки.** Строка участвует, если `category is not Category.GIFT_CARD` и
`category not in promo.excluded_categories`. База скидки и минимум — `sum(line.amount)` по участвующим
строкам до скидки.

**7. Величина скидки.**
- `PERCENT`: `quantize_money(base * value / 100)` (ROUND_HALF_UP).
- `FIXED`: `min(value, base)` — допущение: «не может быть больше суммы участвующих строк» понимаем как
  ограничение (кэп), а не как отказ. Записано в допущениях.
- Пустые участвующие строки → `PromoConditionsError` до расчёта скидки; минимум сравнивается с `>=`.

**8. Распределение по строкам — целочисленно, в копейках.** Скидку и суммы строк переводим в целые копейки
(`amount / CENT`). Для строки `i`: `num_i = D * a_i`, `share_i = num_i // B`, `rem_i = num_i % B`, где `D` —
скидка, `a_i` — сумма строки, `B` — база, все в копейках. Остаток `R = D - sum(share_i)` (всегда
`0 <= R < число строк`) раздаём по одной копейке строкам с наибольшим `rem_i`; при равенстве — раньше в
корзине (порядок `cart.lines`). Сравнение целое, без `float`, без неопределённости округления. Альтернатива
(Decimal + подгонка последней строки) отвергнута: она отдаёт весь остаток одной строке, а бухгалтерия
просит правило по остаткам.

**9. Строки и итоги.** `LineTotal.amount` — сумма строки до скидки (как `CartLine.amount`);
новое поле `LineTotal.discount`; налог строки — `tax_for(category, amount - discount)`.
`OrderTotal.subtotal` — до скидки; `OrderTotal.discount` — сумма скидки; `total = subtotal - discount +
shipping + tax`. Оба новых поля — в конце dataclass со значением по умолчанию `Decimal("0.00")`, чтобы
позиционные вызовы не ломались.

**10. Доставка.** `shipping.cost_for(goods_amount=subtotal - discount, needs_delivery=...)`: порог
сравнивается с товарами после скидки, сама стоимость доставки скидкой не уменьшается.

**11. Заказ.** `Order.promo_code: str | None = None` (в конце, с умолчанием). `place_order`: resolve →
`calculate_total` → создать `Order` → `store.add` → `record_use`. Если любая проверка падает, до
`store.add` дело не доходит и счётчик не трогается. `cancel`: после `store.save` вызывается
`release_use`, если у заказа есть код.

**12. Часы.** Реестр получает свои `Clock` через конструктор, как и остальные сервисы; тесты передают один
и тот же `FixedClock`. Часы `OrderService` на проверку промокода не влияют.

## Risks / Trade-offs

- **[Гонка при оформлении лимитированного кода]** Два параллельных `place_order` могут пройти проверку
  `uses < max_uses` оба. → В текущем in-memory стеке это так же, как и для других состояний заказа;
  фиксируем, при переходе на многопоточный HTTP-слой нужен атомарный `consume` (вне этого change).
- **[Несогласованность часов]** Реестр и `OrderService` могут получить разные `Clock`. → Документируем в
  `OrderService`/реестре: для корректности срока часы должны быть одни и те же; тесты используют один
  `FixedClock`.
- **[Отмена заказа после истечения кода]** `release_use` не проверяет срок — это намеренно: возврат
  использования не должен зависеть от текущего времени.
- **[Отсутствие реестра при отмене]** Заказ с кодом, отменённый сервисом без реестра, не может вернуть
  использование. → Такой сервис по построению не создаёт заказов с кодом; в `cancel` ветка без реестра
  пропускает возврат и пишет предупреждение в лог.
- **[Изменение dataclass]** Новые поля с умолчанием не меняют позиционный порядок существующих полей и
  равенство для старых вызовов; `repr` и сравнение `OrderTotal` расширяются полем `discount`.

## Migration Plan

Миграции данных нет: всё in-memory. Деплой — обычный релиз пакета. Откат — откат коммита; старые вызовы без
промокода работают в обе стороны, так как новые параметры опциональны.

## Open Questions

Нет: неоднозначности зафиксированы как допущения выше (кэп для `FIXED`, `uses` для неизвестного кода,
возврат при отмене без проверки срока, пустой код = без кода).

## Implementation Notes

Решения, принятые при реализации там, где спецификация не задаёт поведение явно:

- `PromoCode.kind` должен быть `DiscountKind` (иначе `ValidationError`): без этого расчёт скидки не определён. В список инвариантов спецификации это не входит, но проверка тривиальна.
- `PERCENT` принимает любое конечное `Decimal` в `(0, 100]`; ограничения на число знаков спецификация не задаёт.
- `PromoRegistry._get` нормализует код через `normalize_key`; нестроковый ввод даёт `ValidationError`, пустой — `UnknownPromoCodeError`.
- `PromoRegistry.record_use` не перепроверяет лимит: вызывается только после успешного `resolve` в `OrderService.place_order`.
- `OrderService.place_order` и `quote` используют одну и ту же нормализацию `normalize_promo_input`, поэтому сохранённый `Order.promo_code` всегда нормализован.
- Новые публичные имена (`PromoCode`, `PromoRegistry`, ...) не экспортируются из `shop/__init__.py`: в задачах этого нет, добавить можно отдельно.
- Налог строки с нулевой базой (например, полностью скидочная книга) равен `0.00`; подарочные карты остаются без налога при любой скидке.
