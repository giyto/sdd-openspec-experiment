## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Публичный API из тикета (имена, сигнатуры, порядок параметров, поля, значение `DiscountKind.FREE_SHIPPING`) не меняется и переносится дословно. Ограничения проекта из README: деньги только `Decimal` и `quantize_money` (`ROUND_HALF_UP`), ошибки только от `ShopError`, время только через внедрённый `Clock`, модели — frozen dataclass с инвариантами в `__post_init__`, интервалы полуоткрытые, порядок строк корзины значим, только stdlib.

Текущее состояние: `calculate_total` — чистая функция, скидку и раскладку считает она; порог доставки сейчас сравнивается с `subtotal - discount`; `PromoRegistry` ведёт один общий счётчик `code -> int`; `OrderService.cancel` безусловно вызывает `release`. Расчёт и реестр разделены: срок и лимиты проверяет только реестр, условия заказа — только `calculate_total`.

## Goals / Non-Goals

**Goals:**
- Все новые денежные правила остаются в `calculate_total`, все счётчики — в `PromoRegistry`; `OrderService` лишь связывает их и решает, возвращать ли использование.
- Старые вызовы (`calculate_total(cart)`, `quote(cart)`, `place_order(cart, "CODE")`, `PromoCode(...)` без новых полей, `registry.resolve("X")`, `registry.uses("X")`) работают без изменений.

**Non-Goals:**
- `shop/cli.py` и `shop/reports.py` (в том числе вывод `shipping_discount`), персистентность счётчиков, нормализация `customer_id`, сочетание нескольких кодов.

## Decisions

1. **Потолок `FIXED` — константа 50 %.** В `pricing.py` модульная константа `FIXED_DISCOUNT_CAP_RATE = Decimal("0.5")`. Скидка `FIXED` = `min(quantize_money(value), quantize_money(S * rate), S)`, где `S` — сумма участвующих строк. Число 50 % взято из поправки маркетинга от 22.10 (она новее и заменяет 30 % из текста тикета). Константа в одном месте, чтобы смена числа не требовала правок логики. Альтернатива — поле в `PromoCode`: отвергнута, т.к. API из тикета не предусматривает его, а потолок общий для всех кодов.
2. **`max_discount` у `PERCENT`.** Скидка = `min(quantize_money(S * value / 100), max_discount)`. Сначала округление процента, потом потолок, поэтому результат всегда в копейках. Инвариант: `Decimal`, конечный, `> 0`, не более двух знаков (`to_money(x) == x`, как у `FIXED.value`), иначе потолок в долях копейки мог бы дать скидку с тремя знаками. Не-`None` у `FIXED`/`FREE_SHIPPING` — `ValidationError`.
3. **`FREE_SHIPPING`.** `PromoCode.__post_init__`: `value` — конечный `Decimal`, равный нулю (`value == 0`; `Decimal("0.00")` тоже принимается, так как это то же число). Скидка на товары `ZERO`, раскладка пропускается (все доли `0.00`). В `calculate_total`: `base_shipping = shipping.cost_for(subtotal, needs_delivery=...)`; для `FREE_SHIPPING` `shipping_cost = ZERO` и `shipping_discount = base_shipping`, иначе `shipping_cost = base_shipping` и `shipping_discount = ZERO`. Так «сколько сэкономлено» всегда равно тому, что заплатил бы клиент без кода, в том числе при нестандартном `ShippingPolicy`. Условия заказа (есть участвующие строки, `min_order_amount`) проверяются так же, как для остальных видов (см. допущения).
4. **Порог доставки.** `shipping.cost_for(subtotal, ...)` вместо `subtotal - discount`. Это возвращает поведение до летней кампании; сигнатура `ShippingPolicy` не меняется.
5. **Раскладка копеек.** В `_split_discount` сортировка по ключу `(-остаток, -сумма_строки_в_копейках, индекс)`. Остатки считаются в целых копейках с общим знаменателем `S`, поэтому сравнимы напрямую; `amounts` уже передаются в функцию. Прочая арифметика (доля = `D * a_i // S`) не меняется.
6. **Счётчики реестра.** Общий `_uses: dict[str, int]` остаётся; добавляется `_customer_uses: dict[tuple[str, str], int]` (код, `customer_id` как есть). `uses(code, customer_id=None)` возвращает общий счётчик или счётчик клиента (`0`, если записи нет). Счётчики клиента ведутся для всех кодов, а не только для кодов с лимитом: так `uses(code, customer_id)` всегда осмысленно, а добавление лимита позже учтёт историю.
7. **`resolve(code, customer_id=None)`.** Порядок: существование → срок → `max_uses` → лимит на клиента. Для кода с `max_uses_per_customer`: `customer_id is None` → `PromoConditionsError`; иначе `customer_uses >= limit` → `PromoConditionsError`. Нестроковый `customer_id` (не `None`) → `ValidationError`; пустая строка — обычное значение, сравнивается как есть. Служебные `redeem(code, customer_id=None)` и `release(code, customer_id=None)` — только расширение уже существующих служебных методов; `redeem` под тем же `threading.Lock` заново проверяет и общий лимит, и лимит на клиента, `release` уменьшает оба счётчика не ниже нуля.
8. **`OrderService`.** `_resolve_promo(promo_code, customer_id)` проверяет тип `customer_id`, затем зовёт `resolve(code, customer_id)`. Пустой/пробельный код — «без кода», `customer_id` в этом случае только запоминается в заказе. `place_order` пишет `customer_id` в `Order`, `redeem` вызывается с ним же, до `store.add` (порядок шагов прежний, ошибки не оставляют следов). `customer_id` в `quote`/`place_order` — keyword-only, как в тикете. `Order.customer_id` — последнее поле с умолчанием `None`.
9. **Окно возврата 24 часа.** В `cancel` после успешного `store.save`: `if now - order.created_at < timedelta(hours=24): release(code, order.customer_id)`, где `now = self._clock.now()` — часы сервиса заказов, а не реестра. Строгое `<` — ровно 24 часа уже «поздно» (подтверждено тимлидом). Окно — модульная константа `REFUND_WINDOW` в `orders.py`. Статус заказа меняется всегда; сгорание использования логируется на уровне `info`. Если `now < created_at` (расхождение часов), считается, что окно не закрыто.
10. **Совместимость данных.** Все новые поля — последние, с умолчаниями (`PromoCode.max_discount`, `PromoCode.max_uses_per_customer`, `OrderTotal.shipping_discount`, `Order.customer_id`), новые параметры необязательные, поэтому прежние позиционные конструкции и вызовы не ломаются.

## Допущения

- **30 % против 50 %.** Тикет противоречит сам себе; принято последнее решение — 50 % (поправка маркетинга, согласовано с финансами).
- **Существующие тесты.** «Существующие тесты не меняем» конфликтует с отменяемыми правилами: `tests/test_pricing_promo.py::test_fixed_capped` (ждёт 1200.00 вместо 600.00) и `::test_shipping_threshold_after_discount` (ждёт доставку 299.00 при 3100 − 200) закрепляют старое поведение и не могут пройти. Допущение: эти два теста, и только они, правятся минимально под новые правила; остальные существующие тесты не трогаем и они должны пройти. Все прочие существующие тесты (в том числе `test_cancel_*`, где отмена происходит сразу после оформления) совместимы с новыми правилами.
- **`FREE_SHIPPING` и условия заказа.** `min_order_amount` и «есть участвующие строки» проверяются и для этого кода — в тикете исключений нет. Сертификаты и исключённые категории для него тоже не участвуют.
- **`max_discount` не более двух знаков** — аналогия с `FIXED.value`; в тикете сказано только «больше нуля».
- **`FREE_SHIPPING.value`** `Decimal("0.00")` принимается наравне с `Decimal("0")` (равны численно); не-`Decimal` (`int`, `float`, `str`) — `ValidationError`.
- **`customer_id`**: пустая строка — допустимое значение (не `None`); нестроковое — `ValidationError`. Без нормализации (сказано в тикете).
- **Лимит на клиента при пустом коде** не проверяется — кода нет.
- **Заказы, оформленные до изменения** (`customer_id=None`), при отмене возвращают только общий счётчик, как раньше (в пределах 24 часов).

## Risks / Trade-offs

- [Два существующих теста перестают проходить] → правятся минимально (см. допущения), в итоговой проверке сверяется `git diff` по `tests/`: изменены только эти два теста.
- [Различие часов реестра и сервиса при отмене] → для 24 часов используются часы сервиса, зафиксировано сценарием.
- [Лимит на клиента без идентификатора блокирует анонимные заказы] → по тикету это ожидаемо (`PromoConditionsError`).
- [Счётчики клиентов растут в памяти для всех кодов] → in-memory, как и остальное хранилище; объём пропорционален числу пар (код, клиент).
- [Отмена после 24 часов «сжигает» использование] → намеренно по тикету; клиент не может переоформить лимитированный код.

## Migration Plan

Данных для миграции нет: хранилища in-memory, изменения аддитивные. Откат — возврат коммита. Для HTTP-слоя: чтобы использовать лимит на клиента, нужно передавать `customer_id` в `quote`/`place_order`.
