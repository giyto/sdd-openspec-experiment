## Why

Резервы работают месяц, и поддержка со складом собрали список доработок (тикет WH-231):
покупатели меняют корзину, оформляют возвраты, а поддержке не видно, какие резервы истекли.
Часть прежних договорённостей меняется: повторный `reserve` на заказ с активным резервом
становится заменой, `cancel` подтверждённого заказа становится возвратом, TTL по умолчанию
растёт до 20 минут. Нужен предельный срок резерва и методы для отчётности и дашборда поддержки.

## What Changes

- **Замена корзины.** `reserve` для заказа с `ACTIVE`-резервом заменяет его новым резервом целиком:
  новый `created_at`, срок `now + ttl`. Товар заменяемого резерва при проверке наличия считается
  свободным. Журнал: `RESERVE_CANCEL` по старому резерву, затем `RESERVE` по строкам нового.
  Проверка и замена атомарны: при нехватке остатка старый резерв остаётся без изменений.
  `CONFIRMED` по-прежнему не заменяется (`DuplicateReservationError`).
- **Возврат.** `cancel` подтверждённого резерва (статус `CONFIRMED`) возвращает товар по всем строкам
  на те же склады и переводит резерв в `CANCELLED`. Журнал: `RECEIVE` по каждой строке с `ref` = номер
  заказа, затем `RESERVE_CANCEL`. **BREAKING:** `cancel` для `CONFIRMED` больше не бросает
  `ReservationStateError`.
- **TTL по умолчанию** `DEFAULT_RESERVATION_TTL` = 20 минут (было 15). **BREAKING** для значения по
  умолчанию в `reserve` и `extend`.
- **Предельный срок.** Новая константа `MAX_RESERVATION_LIFETIME` = 2 часа. `expires_at` никогда не
  позже `created_at + MAX_RESERVATION_LIFETIME`. `reserve` с `ttl` больше предела бросает
  `ValidationError`. `extend` сверх предела не ошибка: срок ставится ровно на предел.
- **Снимки резервов.** Новый метод `Inventory.reservations(status=None)`: снимок текущего резерва каждого
  заказа, сортировка по `created_at`, затем `order_id`. С `status` — только резервы с этим эффективным
  статусом на текущий момент.
- **Доступность.** Новый метод `Inventory.availability(warehouse=None)` возвращает `list[Availability]`
  (новая модель `Availability` в `warehouse/models.py`): строка на каждую позицию с физическим остатком
  или активным резервом; порядок и фильтр по складу как у `stock_levels`.
- **Истечение для поддержки.** Новый метод `Inventory.sweep_expired()`: находит истёкшие резервы, о которых
  ещё не писали, пишет по каждому событие `RESERVE_EXPIRE` (`order`, `expires`) и возвращает их `order_id`
  по `expires_at`, затем по `order_id`. Каждый резерв (не заказ) пишется один раз. Статусы и остатки
  не меняются. Вызывается внешним планировщиком; фоновых процессов нет.
- Новое событие журнала `RESERVE_EXPIRE`.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `inventory-reservations`: замена резерва при `reserve`, возврат при `cancel` подтверждённого резерва,
  TTL по умолчанию 20 минут, предельный срок `MAX_RESERVATION_LIFETIME` для `reserve` и `extend`,
  новые методы `reservations`, `availability`, `sweep_expired` и событие `RESERVE_EXPIRE`.

## Assumptions

- Замена `EXPIRED`- или `CANCELLED`-резерва по-прежнему не пишет `RESERVE_CANCEL` (как сейчас): журнал
  пишет только то, что меняет состояние, которое пользователь видит как активное.
- `reservations()` без `status` возвращает резервы всех статусов (`ACTIVE`, `CONFIRMED`, `CANCELLED`,
  `EXPIRED`), то есть всё, что сервис хранит как текущее состояние заказа.
- Для `sweep_expired` хранилище помнит предыдущие резервы заказа, иначе истёкший резерв, заменённый новым
  до вызова `sweep_expired`, был бы потерян. Это внутреннее изменение `InMemoryStore`, видимое снаружи
  только через `sweep_expired`.
- Значение по умолчанию в `extend` тоже становится 20 минут (как и `reserve`, оно берётся из
  `DEFAULT_RESERVATION_TTL`).

## Impact

- Код: `warehouse/inventory.py`, `warehouse/reservations.py`, `warehouse/models.py`, `warehouse/errors.py`
  (при необходимости), `warehouse/storage.py` (история резервов для `sweep_expired`), `warehouse/events.py`
  без изменений формата.
- Не трогаем: `warehouse/cli.py`, `warehouse/reports.py`, существующие тесты, зависимости.
- Тесты: новые тесты в отдельном файле. Существующие тесты, которые фиксируют старое поведение
  (TTL 15 минут, дубликат при активном резерве, ошибка `cancel` подтверждённого резерва), упадут
  по дизайну; см. `design.md`, раздел «Риски».
- Отчёты: `RECEIVE` от возврата попадает в `received` в `reports.py` без изменения самого отчёта; это ожидаемо
  («обычный приход»).
- API: `Inventory` получает три метода; старые сигнатуры сохраняются.
