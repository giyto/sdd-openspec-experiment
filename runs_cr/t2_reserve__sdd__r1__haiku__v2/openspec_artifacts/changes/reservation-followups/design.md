## Context

Реализация резервов: `warehouse/inventory.py` (сервис `Inventory`), `warehouse/reservations.py` (TTL и
`effective_status`), `warehouse/storage.py` (`InMemoryStore`: текущий резерв на заказ в одном словаре),
`warehouse/models.py` (неизменяемые датаклассы). Статус `EXPIRED` вычисляется по часам и в хранилище не пишется.
Требования см. `specs/inventory-reservations/spec.md`, мотивацию см. `proposal.md`.

Ключевое ограничение: в хранилище одна запись на заказ. Замена резерва (`reserve`) перезаписывает прежнюю
запись, поэтому истёкший резерв, заменённый до вызова `sweep_expired`, без доработки хранилища теряется,
а `sweep_expired` не может понять, о каких резервах уже писали.

## Goals / Non-Goals

**Goals**
- Все правила из тикета и уточнения (замена целиком, возврат, TTL 20 минут, предел 2 часа, `RESERVE_EXPIRE` по каждому резерву).
- Существующий журнальный формат и существующие сигнатуры методов без изменений.

**Non-Goals**
- Не меняем `warehouse/cli.py`, `warehouse/reports.py`, существующие тесты, зависимости.
- Не добавляем фоновый процесс: `sweep_expired` вызывает внешний планировщик.
- Не добавляем персистентность: хранилище остаётся в памяти.

## Decisions

### D1. Замена активного резерва выполняется в `reserve`, без отдельной записи старого резерва
Проверка наличия учитывает строки заменяемого резерва как свободные: `_available_at` получает необязательный
параметр `exclude_order` и не суммирует строки этого заказа. Порядок внутри `reserve`:
1. валидация (`order_id`, `ttl`, предел, строки);
2. если есть `ACTIVE`-резерв, он исключается из резервов при проверке;
3. проверка наличия по сумме строк (`InsufficientStockError` — старый резерв не трогаем);
4. запись `RESERVE_CANCEL` для старого резерва (только если он `ACTIVE`), затем `put_reservation` нового и `RESERVE` по строкам.

Альтернатива «сначала пометить старый `CANCELLED`, потом проверять» отвергнута: при ошибке наличия пришлось бы
откатывать состояние, а ТЗ требует, чтобы неуспешная операция ничего не меняла.

### D2. Возврат при `cancel` подтверждённого резерва
`cancel` для `CONFIRMED` возвращает товар через внутренний помощник, который повторяет логику `receive` без
повторной валидации (строки уже проверены при `reserve`): для каждой строки увеличивает физический остаток и
пишет `RECEIVE` (`wh`, `sku`, `qty`, `ref`=заказ). После этого статус становится `CANCELLED` и пишется
`RESERVE_CANCEL`. Альтернатива «вызывать публичный `receive`» отвергнута только ради того, чтобы не дублировать
три строки; допустима и она, выбор за реализацией.

### D3. TTL и предел
- `DEFAULT_RESERVATION_TTL = timedelta(minutes=20)`; значение по умолчанию у `extend` берётся из той же константы.
- `MAX_RESERVATION_LIFETIME = timedelta(hours=2)` в `warehouse/reservations.py`.
- `reserve`: после `validate_ttl` проверка `ttl > MAX_RESERVATION_LIFETIME` → `ValidationError`. Проверка вынесена
  отдельно, потому что `validate_ttl` используется и в `extend`, где превышение не ошибка.
- `extend`: `new_expires_at = min(now + ttl, created_at + MAX_RESERVATION_LIFETIME)`; дальше прежняя логика
  (не сокращать, без события, если не продлили).

### D4. История резервов для `sweep_expired`
`InMemoryStore` дополнительно хранит историю логических резервов, ключ — `(order_id, created_at)`. `put_reservation`
обновляет и текущий слот заказа, и запись истории (обновления `confirm`/`cancel`/`extend` меняют ту же запись).
Отдельно хранится множество уже отчитанных ключей.

Почему `(order_id, created_at)` однозначно идентифицирует резерв, который может быть отчитан: резерв становится
`EXPIRED` только при `now >= expires_at > created_at`. Если тот же заказ резервируют повторно, новый `created_at`
не меньше `expires_at` старого, значит ключи различаются. Замена `ACTIVE`-резерва в тот же момент времени
даёт одинаковый ключ, но такой старый резерв ещё не истёк и отчитываться не должен, поэтому потери нет.

Альтернатива: добавить поле-счётчик в `Reservation`. Отвергнута: меняет публичную модель ради внутреннего учёта.

### D5. `sweep_expired`
Перебирает историю, берёт записи со сохранённым статусом `ACTIVE` и `now >= expires_at` (эффективный `EXPIRED`),
которых нет в множестве отчитанных. Для каждой пишет `RESERVE_EXPIRE` (`order`, `expires` = `format_timestamp(expires_at)`),
добавляет ключ в отчитанные. Результат сортируется по `expires_at`, затем `order_id`. Статусы и остатки не меняются.

### D6. `reservations(status=None)` и `availability(warehouse=None)`
- `reservations`: снимки текущих резервов (`store.list_reservations()`), `_snapshot` с эффективным статусом,
  фильтр по эффективному статусу, сортировка `(created_at, order_id)`.
- `availability`: множество позиций = позиции из `store.positions()` ∪ позиции строк `ACTIVE`-резервов на текущий момент;
  фильтр по складу; сортировка `(warehouse, sku)`; значения через `_reserved_at` и `_available_at`, чтобы совпадать
  с методами `reserved`/`available`.
- Модель `Availability` — frozen-датакласс в `warehouse/models.py` с полями из тикета.

## Risks / Trade-offs

- **[Существующие тесты падают по дизайну]** Тринадцать тестов в `tests/test_reservations.py` фиксируют старое поведение.
  Пять из них назывались в первоначальной оценке: `test_default_ttl_is_fifteen_minutes`, `test_default_ttl_sets_expires_at`,
  `test_active_reservation_cannot_be_duplicated`, `test_cancel_confirmed_raises`, `test_extend_default_ttl_is_fifteen_minutes`.
  При реализации выяснилось, что ещё восемь падают по той же причине (смена TTL с 15 на 20 минут): они продвигают часы
  ровно на `15 minutes` и ждут истечения резерва с TTL по умолчанию. Это `test_snapshot_reports_expired_by_clock`,
  `test_confirm_expired_raises`, `test_cancel_expired_stays_expired_without_events`, `test_extend_expired_raises`,
  `test_expiry_crossing_writes_no_event` (3 параметра) и `test_expired_reservation_stops_counting_in_all_queries`.
  Ни одно из них не падает из-за ошибки реализации. Тикет запрещает менять существующие тесты, поэтому они не правятся,
  а в отчёте о применении перечисляются как ожидаемые падения. Решение об обновлении формулировок (`15 minutes` → `20 minutes`)
  остаётся за пользователем.
  → Mitigation: новые тесты в отдельном файле `tests/test_reservations_followups.py`; решение, обновлять ли старые
  тесты, остаётся за пользователем (вопрос вынесен в итоговое сообщение).
- **[Потеря истории при повторе в тот же момент]** Ключ `(order_id, created_at)` может совпасть для двух записей,
  только если замена `ACTIVE`-резерва произошла в тот же момент, что и создание; такой резерв не истекал (см. D4).
  → Mitigation: тест на замену в тот же момент времени.
- **[Рост памяти]** История хранится без очистки. Сервис в памяти, поэтому объём ограничен жизнью процесса.
  → Принято; при переходе на персистентное хранилище нужна отдельная политика очистки.
- **[`reports.py` считает `RECEIVE` как приход]** Возврат попадает в `received`. Это совпадает с тикетом
  («обычный приход»). Неизвестный тип `RESERVE_EXPIRE` `reports.py` не обрабатывает (проверено чтением: учитываются
  только `RECEIVE`, `ISSUE`, `ADJUST`), поэтому отчёт не ломается.
- **[Расхождение с тикетом по видимости EXPIRED]** `reservations()` без `status` возвращает все статусы; это допущение
  из proposal.md, при другом намерении меняется одной строкой фильтра.

## Migration Plan

Миграции нет: хранилище в памяти, новых данных на диске нет. Значение TTL по умолчанию меняется только для
резервов, созданных без явного `ttl` после выката. Уже созданные резервы сохраняют свой `expires_at`.
Откат: возврат к предыдущему коммиту; история в памяти не переживает перезапуск.
