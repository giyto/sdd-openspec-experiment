## Context

Расчёт живёт в `shop/pricing.py` (`calculate_total`, `_allocate_discount`, `ShippingPolicy`), промокоды —
в `shop/promo.py` (`PromoCode`, `PromoRegistry`), заказы и отмена — в `shop/orders.py`. Всё хранится в памяти.
Деньги — `Decimal` с двумя знаками, округление `ROUND_HALF_UP` через `shop.money.quantize_money`, время
приходит через `Clock`. Требования описаны в `specs/promo-codes/spec.md` и `specs/promo-discounts/spec.md`;
мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Реализовать шесть правил из тикета SHOP-447 в существующих модулях, без новых слоёв.
- Сохранить совместимость старых вызовов: `quote(cart, code)`, `place_order(cart, code)`, `calculate_total(cart)`.
- Держать все деньги в копейках и округлении `ROUND_HALF_UP`.

**Non-Goals:**
- Не трогаем `shop/cli.py`, `shop/reports.py` и существующие тесты.
- Не добавляем персистентность счётчиков: как и раньше, всё в памяти.
- Не вводим отдельную модель «клиент»: `customer_id` — строка, сравнивается как есть.
- Не меняем налоговые правила и ставки.

## Decisions

**1. Потолок фиксированной скидки применяется при расчёте, а не при регистрации.**
`_allocate_discount` вычисляет `cap = quantize_money(base * Decimal("0.5"))` и берёт
`discount = min(promo.value, cap)`. Значение `PromoCode.value` не меняется, поэтому регистрация не ломается,
а один и тот же код корректно считается на разных корзинах.
*Альтернатива:* обрезать `value` в `__post_init__` — невозможно, потому что базы ещё нет.

**2. Потолок процентной скидки** — `discount = min(quantize_money(base * value / 100), max_discount)`.
Поле `max_discount` проверяется в `PromoCode.__post_init__`: только у `PERCENT`, `> 0`, два знака после запятой
(как у других денежных полей; это допущение, в тикете его нет).

**3. `FREE_SHIPPING`** проходит через ту же проверку участвующих строк и минимальной суммы, что и остальные
виды (`_allocate_discount` возвращает нули для строк). В `calculate_total` стоимость доставки считается как
обычно, затем если вид `FREE_SHIPPING`, то `shipping_discount = shipping_cost`, `shipping_cost = 0`.
Так `total = subtotal - discount + shipping + tax` не меняется по форме, а `shipping_discount` — это
информационное поле, которое в сумму не входит.
*Допущение:* `value` проверяется как численный ноль (`Decimal("0.00") == Decimal("0")` тоже проходит).

**4. Порог доставки** сравнивается с `subtotal` (сумма строк до скидки), а не с `subtotal - discount`.
Сейчас `subtotal` включает и подарочные сертификаты, как и до этого изменения; поведение без промокода
не меняем, чтобы старые вызовы выдавали те же суммы.
*Допущение:* «сумма товаров до скидки» в тикете понимается как существующий `subtotal`. Если финансы
имеют в виду исключение сертификатов из порога, это отдельное изменение старого поведения и нужно решить
отдельно.

**5. Раскладка копеек.** Сортировка остатка меняется с `(-remainder, index)` на
`(-remainder, -line_amount, index)`. Строка с большей суммой получает копейку при равных остатках,
при равных суммах выигрывает более ранняя строка корзины.

**6. Лимит на клиента — отдельные счётчики по паре `(code, customer_id)`** внутри `PromoRegistry`.
`resolve(code, customer_id)` проверяет по порядку: существование → срок → общий `max_uses` → лимит клиента.
Если у кода задан `max_uses_per_customer` и `customer_id is None`, `resolve` сразу выбрасывает
`PromoConditionsError`, так что `quote` тоже отказывает. `consume(code, customer_id)` увеличивает оба
счётчика, `release(code, customer_id)` уменьшает оба. Счётчик клиента ведётся для любого кода с переданным
`customer_id`, даже без лимита, — это проще и не влияет на поведение.
*Альтернатива:* считать клиентские использования по списку заказов. Отвергнуто: заказы хранятся без
`customer_id` до этого изменения, и сканирование усложнило бы `uses`.

**7. Окно возврата при отмене.** В `OrderService.cancel` возврат делается, только если
`self._clock.now() - order.created_at < timedelta(hours=24)`. Используются часы сервиса заказов, а не
реестра, как и требует тикет. Граница строгая: ровно 24 часа — уже поздно.
Заказ всё равно переходит в `cancelled` и остаётся в отчётах (`reports.py` не трогаем).

**8. `customer_id` и `Order`.** `Order` получает поле `customer_id: str | None = None` в конце. `place_order`
записывает его всегда, даже без промокода. `None` означает «не передан», пустая строка — это обычное значение,
без нормализации.

**9. `OrderTotal.shipping_discount: Decimal = ZERO`** в конце датакласса, по умолчанию `0.00`, поэтому
старые конструкции `OrderTotal(...)` не ломаются.

## Risks / Trade-offs

- **Два существующих теста противоречат новым правилам.** `tests/test_pricing_promo.py::test_fixed_discount_is_capped_by_participating_amount`
  (фиксированная 1500.00 на 999.00 ожидает 999.00; по новому правилу 499.50) и
  `test_discount_moves_order_under_free_shipping_threshold` (ожидает доставку 299.00 после скидки; по новому
  правилу порог 3000.00 достигнут до скидки). Тикет запрещает менять существующие тесты, но эти два
  поведения меняются намеренно. → Оставляем тесты без правок, прогоняем, в отчёте явно перечисляем падения.
  Решение о замене этих двух тестов принимает команда (см. «Открытые вопросы»).
- **Округление потолка вверх.** `ROUND_HALF_UP` может дать потолку чуть больше 50 % (например, база 0.03 →
  потолок 0.02, т.е. 67 %). → Принято по тикету («как любые деньги»); сценарий зафиксирован в спеке.
- **Клиентский счётчик без персистентности.** После перезапуска процесса лимиты на клиента сбрасываются,
  как и общие счётчики. → Это существующее ограничение проекта, не новое.
- **Сравнение `customer_id` как есть.** `"C-1"` и `"c-1"` — разные клиенты. → Тикет требует именно так.
- **Порог доставки включает сертификаты**, как и раньше (см. решение 4).

## Migration Plan

Нет миграции данных: всё в памяти. Внедрение — одним коммитом. Откат — `git revert` этого коммита;
старые вызовы продолжают работать, потому что все новые параметры опциональны.

## Open Questions

- Нужно ли заменить два существующих теста из раздела «Риски» на новые формулировки или оставить их
  падающими до решения команды? Это не меняет спеки: спеки уже описывают новое поведение. Решение
  нужно до слияния; по умолчанию — не править существующие тесты и сообщить о падении.
- Исключать ли подарочные сертификаты из суммы для порога доставки (см. решение 4). По умолчанию — нет.

## Решения при реализации

- **Порядок проверок в `PromoRegistry.release`.** Оба счётчика (общий и клиентский) проверяются до
  уменьшения. Иначе ошибка на клиентском счётчике оставила бы общий уже уменьшенным.
- **Отмена вне окна не бросает исключение.** `cancel` переводит заказ в `cancelled` и пишет `info` в лог;
  использование сгорает без ошибки, как и описано в спеке.
- **Клиентский счётчик ведётся для любого кода с `customer_id`**, даже без `max_uses_per_customer`
  (решение 6 выше). Это нужно, чтобы `uses(code, customer_id)` работал одинаково для всех кодов.
- **Тесты 2.5 не правим.** Падают ровно `test_fixed_discount_is_capped_by_participating_amount` и
  `test_discount_moves_order_under_free_shipping_threshold`; остальные существующие тесты проходят.
