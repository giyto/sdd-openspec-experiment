## Why

Резервы работают месяц (WH-231). Поддержка и склад нашли, что мешает: покупатели меняют корзину
и оформляют возвраты, а поддержке не видно, какие резервы истекли. Часть прежних договорённостей
меняется: повторный `reserve` становится заменой, `cancel` подтверждённого заказа становится возвратом,
TTL по умолчанию растёт до 20 минут, появляется предельный срок резерва. Поддержке нужны выборки
резервов и остатков и отметка об истечении.

## What Changes

- **BREAKING**: `reserve` по заказу с активным (не истёкшим) резервом больше не отклоняется
  `DuplicateReservationError`. Новый резерв заменяет активный: сначала `RESERVE_CANCEL` по старому,
  затем `RESERVE` по строкам нового. Товар заменяемого резерва при проверке наличия считается свободным.
  Новый резерв получает свой `created_at` и срок от момента замены. Подтверждённый заказ заменить нельзя
  (`DuplicateReservationError` остаётся).
- **BREAKING**: `cancel` подтверждённого резерва больше не отклоняется `ReservationStateError`. Он
  возвращает товар по всем строкам на те же склады (`RECEIVE` по каждой строке с `ref` = номер заказа),
  затем пишется `RESERVE_CANCEL`, статус становится `CANCELLED`.
- Новое значение по умолчанию: `DEFAULT_RESERVATION_TTL` = 20 минут (было 15).
- Новый предел `MAX_RESERVATION_LIFETIME` = 2 часа. `expires_at` не может быть позже
  `created_at + MAX_RESERVATION_LIFETIME`. `reserve` с `ttl` больше предела — `ValidationError`.
  `extend` сверх предела не ошибка: срок ставится ровно на предел.
- Новая модель `Availability` (`warehouse`, `sku`, `on_hand`, `reserved`, `available`).
- Новый метод `Inventory.reservations(status=None)`: снимки текущих резервов по одному на заказ,
  по `created_at`, затем по `order_id`; с `status` — только резервы с этим статусом на текущий момент.
- Новый метод `Inventory.availability(warehouse=None)`: строка на позицию с физическим остатком или
  активным резервом; порядок и фильтр по складу как у `stock_levels`.
- Новый метод `Inventory.sweep_expired()`: для истёкших резервов, о которых ещё не писали, пишет
  `RESERVE_EXPIRE` (`order`, `expires`) и возвращает их `order_id` по `expires_at`, затем `order_id`.
  Один резерв — одна запись. Статусы и остатки не меняются. Внутри сервиса фоновых процессов нет.
- Новое событие журнала: `RESERVE_EXPIRE`. Прежнее правило «истечение в журнал не пишем» действует
  для всех путей, кроме `sweep_expired`.
- Не трогаем `warehouse/cli.py` и `warehouse/reports.py`, существующие тесты, зависимости.
  Остальные правила резервов и старый API не меняются.

### Modified Capabilities
- `reservations`: замена резерва при повторном `reserve`, возврат подтверждённого заказа через `cancel`,
  TTL по умолчанию 20 минут, предельный срок резерва (`reserve` и `extend`), новые методы выборки и
  `availability`, событие `RESERVE_EXPIRE` через `sweep_expired`.

## Impact

- Код: `warehouse/models.py` (`Availability`), `warehouse/reservations.py` (`MAX_RESERVATION_LIFETIME`,
  новый TTL по умолчанию, флаг «истечение отмечено» в записи), `warehouse/storage.py` (без новых
  операций, если хватает `set_reservation`/`get_reservation`), `warehouse/inventory.py` (`reserve`,
  `cancel`, `extend`, новые методы), `warehouse/__init__.py` (экспорт новых имён).
- Журнал: новые типы `RESERVE_EXPIRE`; `RECEIVE` с `ref` = номер заказа появляется при возврате.
  Формат строки не меняется.
- Отчёты: `reports.py` не меняем, но возврат подтверждённого заказа попадёт в него как обычный приход
  (`RECEIVE`).
- Тесты: новые тесты для изменённых правил и новых методов. Три существующих теста закрепляют отменённые
  правила (см. design.md, раздел «Конфликт с тестами»).
- Зависимости: не добавляются. Старый API (`receive`, `issue`, `transfer`, `adjust`, `on_hand`,
  `stock_levels`) не меняется.
