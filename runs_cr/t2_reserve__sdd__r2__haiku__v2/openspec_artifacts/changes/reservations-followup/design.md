## Context

Базовая реализация резервов (архивный change `add-inventory-reservations`) живёт в
`warehouse/inventory.py`, `warehouse/reservations.py`, `warehouse/storage.py`. Записи резервов
изменяемые и хранятся по `order_id`; снимки (`Reservation`) строятся на лету через `_snapshot`
с вычислением `EXPIRED` по часам. Этот change меняет несколько правил и добавляет выборки. Поведение
описано в `specs/reservations/spec.md`, мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Новые правила укладываются в существующие соглашения README: часы через `Clock`, ошибки от
  `WarehouseError`, модели неизменяемые, операция либо целиком, либо ничего (проверки до изменений).
- Журнал пишется только теми событиями, которые перечислены в спецификации.
- `reserved`/`available` по-прежнему вычисляются из записей, без отдельных счётчиков.

**Non-Goals:**
- Фоновые задачи, таймеры, персистентность (как и в базовом change).
- Изменения `warehouse/cli.py`, `warehouse/reports.py`.
- Хранение истории замещённых резервов.

## Decisions

**1. Замена активного резерва в `reserve`.**
Порядок проверок в `reserve`: валидация `order_id`, TTL (включая предел), строк; неизвестный SKU;
если прежняя запись `CONFIRMED` — `DuplicateReservationError`; затем доступность по сумме строк позиции
с учётом освобождаемого прежнего `ACTIVE`-резерва (его строки не учитываются в `reserved` при проверке).
Только после всех проверок: `RESERVE_CANCEL` по прежнему резерву (если он живой), запись заменяется,
затем `RESERVE` по строкам. Реализация: `_available_at` получает необязательный параметр исключаемой записи.

**2. Возврат подтверждённого заказа в `cancel`.**
Статус `CONFIRMED` больше не даёт ошибку. Проверки нет (возврат товара). Порядок: `set_qty` по строкам
с добавлением количества, события `RECEIVE` по каждой строке (`ref` = `order_id`), затем `RESERVE_CANCEL`,
статус `CANCELLED`. Все события пишутся после расчёта новых остатков, т.е. в конце операции.

**3. TTL и предел.**
`DEFAULT_RESERVATION_TTL = timedelta(minutes=20)`; `MAX_RESERVATION_LIFETIME = timedelta(hours=2)` в
`warehouse/reservations.py`. `reserve`: после `_validate_ttl` проверка `ttl > MAX_RESERVATION_LIFETIME`
→ `ValidationError`. `extend`: `new_expires_at = min(now + ttl, record.created_at + MAX_RESERVATION_LIFETIME)`;
событие только если новое значение больше текущего `expires_at`.

**4. Отметка истечения для `sweep_expired`.**
В `ReservationRecord` добавляется поле `expire_reported: bool = False`. Флаг принадлежит записи, а не
заказу: замена создаёт новую запись с `False`, поэтому её истечение отметится отдельно. Поле имеет
значение по умолчанию, поэтому существующие конструкции записи в тестах остаются валидными.
`sweep_expired` берёт записи, у которых статус вычисляется как `EXPIRED` (`ACTIVE` и `now >= expires_at`)
и `expire_reported` ложно; сортирует по `(expires_at, order_id)`; пишет `RESERVE_EXPIRE` и ставит флаг.
Статусы и остатки не меняются.

**5. `reservations(status)`.**
Снимки всех записей через `_snapshot`, фильтр по вычисленному статусу, сортировка по
`(created_at, order_id)`. Для этого в `InMemoryStore` нужен метод перечисления записей (без фильтра).

**6. `availability(warehouse)`.**
Набор позиций = ненулевые физические остатки (`store.positions()`) ∪ позиции живых активных резервов.
Для каждой позиции `on_hand`, `reserved`, `available` через уже существующие расчёты. Сортировка и фильтр
по складу — как в `stock_levels`. Для объединения нужен перебор записей `ACTIVE` с проверкой `now < expires_at`.

**7. Модель `Availability`.**
Frozen dataclass в `warehouse/models.py` с полями из ticket. Экспорт `Availability` и
`MAX_RESERVATION_LIFETIME` в `warehouse/__init__.py` (по принципу, принятому в базовом change).

**8. Событие `RESERVE_EXPIRE`.**
Только в `sweep_expired`. Поля `order`, `expires` (через `format_timestamp`). Время события — текущие часы.
`warehouse/events.py` не меняется: новый тип проходит существующую проверку формата.

## Допущения

Неоднозначности, которые я зафиксировал здесь. Пользователь ответить не может, поэтому выбраны
варианты, наиболее близкие к тексту задачи.

- **«Активный» резерв для замены и `RESERVE_CANCEL`** — запись `ACTIVE` с `now < expires_at`, как в
  `reserved`. Замена `EXPIRED` и `CANCELLED` работает как раньше: без `RESERVE_CANCEL`.
- **Истёкший резерв в выборке `reservations()`** включён: поддержке нужны истёкшие резервы. Его статус —
  `EXPIRED`.
- **Порядок событий `RECEIVE` при возврате** — по строкам в порядке передачи, строки одной позиции
  не склеиваются (как `ISSUE` при `confirm`).
- **Замена при нехватке** — `InsufficientStockError` несёт `requested` = сумма строк позиции и
  `available` = доступный остаток с учётом освобождённого резерва.
- **`extend` с пределом** — при clamp срок равен `created_at + MAX_RESERVATION_LIFETIME`, и событие
  пишется с этим значением `expires`.
- **`sweep_expired` без `now`** — момент берётся из часов сервиса, как у остальных операций.
- **Порядок `availability()`** — по `(warehouse, sku)`, как `stock_levels`.
- **Истёкший, но не отмеченный резерв заменён до `sweep_expired`** — запись заменяется, и её
  `RESERVE_EXPIRE` не пишется: в хранилище её больше нет, а спецификация отмечает только существующие
  записи. Если поддержке нужен учёт и таких резервов, это отдельное решение.
- **Тест `test_reserve_writes_reserve_event_per_line`** (не в списке задачи 7) проверяет `expires` = 15 минут
  и после смены TTL на 20 минут падает. Его ожидаемое значение не менялось: решение за пользователем.

## Конфликт с существующими тестами

Задача требует не менять существующие тесты, но четыре из них закрепляют правила, которые этот change
меняет намеренно:

- `tests/test_reservations.py:42` `test_default_ttl_is_fifteen_minutes` — ожидает 15 минут.
- `tests/test_reservations.py:102` `test_reserve_multiple_warehouses_keeps_lines_and_on_hand` — ожидает
  `expires_at` через 15 минут.
- `tests/test_reservations.py:181` `test_duplicate_while_active` — ожидает `DuplicateReservationError`
  при активном резерве.
- `tests/test_reservations.py:382` `test_cancel_confirmed_raises` — ожидает `ReservationStateError`
  при отмене подтверждённого резерва.

Выбор по умолчанию: эти четыре теста обновляются по ожидаемым значениям и названиям, чтобы набор был зелёным,
а новые сценарии добавляются в `tests/test_reservations.py` отдельными тестами. Это отступление от «тесты не
меняем», поэтому требует подтверждения пользователя до apply. Если подтверждения не будет, вариант
«оставить как есть» даст красный набор из четырёх тестов, это считаем хуже.

Остальные существующие тесты проверяют сохранённые правила (повтор после истечения и отмены, отмена
истёкшего, расход по доступному остатку) и должны проходить без изменений.

## Risks / Trade-offs

- [Возврат попадает в `reports.py` как приход] → отчёт не менялся; возврат выглядит как обычный `RECEIVE`
  с `ref`, это соответствует требованию. Отдельного отчёта по возвратам нет.
- [Флаг `expire_reported` меняет запись при чтении] → меняется только при `sweep_expired`, который явно
  вызывает внешний планировщик; статусы и остатки не затрагиваются.
- [Перебор записей в `availability()` и `reservations()`] → O(число записей) на вызов, как и текущий
  расчёт `reserved`; для in-memory сервиса допустимо.
- [Истёкшие записи остаются в памяти] → как и раньше, очистка — отдельная задача.

## Migration Plan

Миграции нет: состояние в памяти. Откат — возврат прежних проверок в `reserve` и `cancel`, TTL 15 минут и
удаление новых методов. Журнал с событиями `RECEIVE`/`RESERVE_CANCEL` от возвратов и замен остаётся валидным.
