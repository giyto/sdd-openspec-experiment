## Context

Импорт живёт в `ledger/importer.py`: `_read_records` отдаёт записи CSV с номером физической строки,
`_parse_row` превращает ячейки в `Transaction` через функции формата (`_sfera_row`, `_sfera_split_row`,
`_nova_row`), `import_statement` дедуплицирует, категоризирует и пишет одним `store.add_many`.
`MemoryStore.add_many` возвращает сохранённые транзакции с назначенными `id`. Сейчас строгий режим
бросает `StatementRowError` на первой ошибке прямо в цикле. См. `proposal.md` (Why, What Changes) и
спецификацию `specs/statement-import/spec.md`.

## Goals / Non-Goals

**Goals**
- Все изменения из задачи LEDGER-74 покрыты требованиями дельты и тестами.
- Публичные сигнатуры `import_csv` и `detect_format` не меняются; новые поля и параметры имеют значения по умолчанию.

**Non-Goals**
- Не меняем `ledger/cli.py`, `ledger/reports.py`, `Transaction`, хранилища и `Categorizer`.
- Не меняем правила формата `nova` (точка, знак, `YYYY-MM-DD`) и не добавляем разбор тысячных разделителей в `nova`.
- Не меняем README в этом изменении: в задаче его нет (см. Open Questions).
- Не добавляем новых зависимостей: только стандартная библиотека.

## Decisions

### 1. Суммы «Сферы»: два десятичных разделителя
`_SFERA_AMOUNT` меняется на вариант с группой разделителя `[,.]` и одной дробной частью:
`([+-]?)(\d{1,3}(?:[  ]\d{3})*|\d+)(?:([,.])(\d{1,2}))?`. Смешение обоих разделителей
проверяется явно до регулярки и даёт понятное сообщение «mixed decimal separators in amount».
Тысячные разделители остаются пробелом или U+00A0; точка тысячных не поддерживается, поэтому
`1.234` (три знака после точки) и `1.234,56` — ошибки строки.
- Альтернатива: один общий `replace(",", ".")` перед разбором. Отклонена: не ловит смешение и
  пропускает `1,234.56`-подобные случаи через ослабленную проверку.

### 2. Служебные строки `sfera_split`
Разбор функции формата может вернуть `None` — «строка пропущена». `_sfera_split_row` возвращает
`None`, если обе колонки после `strip()` парсятся без знака в ноль. Проверка идёт после проверки
количества полей (короткая строка остаётся ошибкой), до разбора даты и описания: служебная строка
не валидируется по дате. `_split_amount` сохраняет прежнюю логику для «пусто → None» и
«ненулевое → сумма»; для ноль-ноль дополнительно различаем «явный ноль» и «пусто».
- Риск: служебная строка с битой датой молча пропускается. → Принято как допущение (см. Open Questions).

### 3. Описание
Нормализация `" ".join(description.split())` применяется в `_parse_row` после `fmt.parse`, поэтому
одинаково для всех трёх форматов. `str.split()` без аргументов режет по всем юникод-пробелам, включая
U+00A0 и табы/переводы строк. Регистр не трогаем. Пустое после нормализации описание даёт
`ValidationError` из `Transaction` — как и сейчас. Дедупликация по `normalize_description`
не меняется: она уже нечувствительна к регистру и пробелам.

### 4. Строгий режим: сбор всех ошибок
Цикл по строкам всегда собирает `errors`. В строгом режиме после цикла, до любой записи,
если `errors` не пуст, бросаем `StatementRowError(first.message, line_no=first.line_no, errors=errors)`.
Конструктор `StatementError` не меняется; `StatementRowError.__init__` принимает `errors`, сохраняет его как атрибут.
В `errors.py` тип `RowError` указывается через `TYPE_CHECKING`, чтобы не создать циклический импорт
(`importer` импортирует `errors`).
- Альтернатива: переносить `RowError` в `errors.py`. Отклонена: задача фиксирует `RowError` в `ledger/importer.py`.

### 5. `raw` у `RowError`
`_read_records` дополнительно получает физические строки через `io.StringIO(text, newline="").readlines()`
(тот же набор разделителей строк, что у `csv.reader`). Для записи, начинающейся на строке `start` и
заканчивающейся на `reader.line_num`, берём `lines[start-1:reader.line_num]`, склеиваем, заменяем
`\r\n` и `\r` на `\n`, снимаем один завершающий `\n`. Так `raw` не содержит BOM (его уже снял `utf-8-sig`),
`\r` и не нормализует внутренние пробелы. `_Layout.rows` хранит записи с `raw`; `_parse_row` его не использует.
- Риск: `reader.line_num` после записи в кавычках указывает на последнюю физическую строку записи;
  это покрывается тестом на многострочную запись.

### 6. `dry_run` и `transactions`
`import_statement` не меняет логику дедупликации и категоризации. Вместо прямой записи:
- если `dry_run` — `stored = new_txs` (id = None), `store.add_many` не вызывается;
- иначе, если `new_txs` не пуст — `stored = store.add_many(new_txs)`, иначе `stored = []`.
`ImportResult.transactions` = `stored`. `add_many` не вызывается при пустом списке — прежнее поведение
(тест `test_no_add_many_when_nothing_added`).
- Риск: `dry_run` читает `store.all()` для дедупликации — это чтение, а не запись; допустимо.

### 7. Совместимость
`import_csv` остаётся обёрткой над `import_statement(..., fmt="nova", strict=True)`. Изменение строгого
режима (все ошибки в `errors`) для неё прозрачно: тип исключения и `line_no` прежние.

## Risks / Trade-offs

- [Служебная строка с битой датой пропускается молча] → документировано в спецификации; при необходимости
  можно валидировать дату до проверки нулей — решение меняет одну строку в `_sfera_split_row`.
- [Нормализация описания меняет то, что уже хранится в JSON] → Новые записи только; старые не
  перезаписываются. Дедупликация не ломается, так как сравнение и так нечувствительно к пробелам.
- [Точка в сумме «Сферы» делает разбор неоднозначным для старых файлов с точкой как тысячным разделителем]
  → Точка тысячных не поддерживается; `1.234` даёт ошибку, а не `1234`.

## Migration Plan

Миграция данных не нужна. Развёртывание — обычный релиз модуля. Откат: вернуть файлы `ledger/importer.py`
и `ledger/errors.py`; новые поля `ImportResult` и `RowError` имеют значения по умолчанию, так что
старые вызовы не сломаются даже при частичном откате.

## Open Questions

- Нужно ли валидировать дату в служебной строке `sfera_split` (нули в обеих колонках)? Принято: не валидировать,
  т.к. задача говорит «молча пропускаем». Меняется одной строкой, если аналитик решит иначе.
- Обновлять ли раздел про форматы в `README.md`? В задаче не упомянуто, в этом изменении не трогаем.
