## Context

Мотивация и объём: `proposal.md`, требования: `specs/`. Текущее состояние: `PromoCode` / `PromoRegistry` в `shop/promo.py` (счётчик `dict[str, int]`, `resolve` / `redeem` / `release`), `calculate_total` в `shop/pricing.py` (скидка раскладывается в копейках методом наибольшего остатка, порог доставки сравнивается с `subtotal - discount`), `OrderService` в `shop/orders.py` (`quote` / `place_order` / `cancel`, возврат использования при любой отмене). Соглашения проекта (README): `Decimal` + `quantize_money` (`ROUND_HALF_UP`), ошибки только от `ShopError`, frozen-датаклассы с инвариантами в `__post_init__`, полуоткрытые интервалы, время только через `Clock`, только stdlib. Рамки: `shop/cli.py`, `shop/reports.py` и существующие тесты не трогаем, старые вызовы работают.

## Goals / Non-Goals

**Goals:**
- Закрыть дыры летней кампании (мелкие заказы с фиксированным кодом, карусель отмен) и добавить три новых ограничения/вида кода без поломки старых вызовов.

**Non-Goals:**
- `shop/cli.py`, `shop/reports.py` (отображение `shipping_discount` и `customer_id` в отчётах — отдельный тикет), персистентность, несколько кодов в заказе, потокобезопасность.
- Антифрод сверх тикета (например, привязка возврата к клиенту).

## Decisions

1. **Источники истины при противоречиях в тикете.** Потолок фиксированной скидки — **50 %** (поправка маркетинга 22.10 позже и конкретнее текста тикета с 30 %; сказано, что согласовано с финансами). Раскладка копеек — по комментарию бухгалтерии: ключ сортировки `(-остаток, -сумма_строки, индекс)`. Граница 24 часов — `elapsed < 24h` (подтверждено тимлидом: «ровно 24 часа уже поздно»).

2. **Порог доставки.** `shipping.cost_for(subtotal, ...)` — возврат к сумме до скидки. Код расчёта и docstring модуля в `pricing.py` обновляются.

3. **Потолок фиксированной скидки.** `D = min(value, quantize_money(base * Decimal("0.5")), base)`; `base` — сумма участвующих строк. Константа доли выносится в модуль `pricing.py` (`FIXED_DISCOUNT_MAX_SHARE = Decimal("0.5")`). Округление `ROUND_HALF_UP` через `quantize_money`, не `//` и не банковское; `min(..., base)` оставляем, он нужен при `base = 0.00`/`0.01` на случай округления. Альтернатива «вычислять потолок в копейках целочисленно» отвергнута: единый способ округления денег в проекте — `quantize_money`.

4. **Потолок процентной скидки.** `D = min(quantize_money(base * value / 100), max_discount)`; применяется до раскладки, поэтому сумма построчных долей остаётся равной `D`. `max_discount` валидируется в `PromoCode.__post_init__`: только `PERCENT`; `Decimal` (не `bool`/`float`), конечный, `> 0`, не более двух знаков (`to_money(v) == v`, как у номинала фиксированной скидки). Для остальных видов любое значение, кроме `None`, — `ValidationError`.

5. **`FREE_SHIPPING`.** Валидация: `value == 0` (допускается `Decimal("0")`, `Decimal("0.00")`; `Decimal` не `bool`/`float`, конечный), иначе `ValidationError`; существующие проверки `PERCENT`/`FIXED` — в своих ветках. В `calculate_total` скидка на товары 0, но условия заказа (есть участвующие строки, `base >= min_order_amount`) проверяются как у остальных видов. Далее: `natural = shipping.cost_for(subtotal, needs_delivery=...)`; для `FREE_SHIPPING` `shipping_cost = ZERO`, `shipping_discount = natural`; иначе `shipping_discount = ZERO`. `OrderTotal.shipping_discount: Decimal = ZERO` добавляется последним полем (после `discount`), поэтому позиционные конструкторы не ломаются. Формула `total` не меняется, так как `shipping` — фактически начисленная стоимость.

6. **Лимит на клиента в реестре.** Хранилище: `dict[str, dict[str, int]]` (код → клиент → число). `PromoCode.max_uses_per_customer` валидируется как `max_uses` (`int`, не `bool`, `>= 1`). `resolve(code, customer_id=None)`: `customer_id` проверяется на тип (`str | None`, иначе `ValidationError`) и **не нормализуется**; порядок: существует → срок → общий лимит → клиентский (нет `customer_id` или `count >= лимит` → `PromoConditionsError`). `uses(code, customer_id=None)`: с `customer_id` возвращает счётчик клиента (0, если не было), неизвестный код → `UnknownPromoCodeError`. `redeem(code, customer_id=None)` и `release(code, customer_id=None)` обновляют общий и клиентский счётчики вместе; `release` не уходит ниже 0 ни в одном. Клиентский счётчик ведётся для любого кода, даже без лимита, — так `uses(code, cid)` имеет смысл всегда и лимит можно ввести позже без «обнуления». Альтернатива — вести счётчики только для кодов с лимитом: отвергнута как неочевидная семантика `uses`.

7. **`OrderService`.** `quote(cart, promo_code=None, *, customer_id=None)` и `place_order(...)` принимают keyword-only `customer_id`; валидация типа выполняется первой (до resolve), чтобы ошибка не зависела от кода. `Order.customer_id: str | None = None` — последнее поле. `place_order`: resolve(code, customer_id) → `calculate_total` → создание заказа → `store.add` → `redeem(code, customer_id)`. Все проверки до изменения состояния сохраняются.

8. **Возврат при отмене.** `cancel`: после проверки статуса и сохранения отменённого заказа `now = self._clock.now()`; если у заказа есть код и реестр и `now - order.created_at < timedelta(hours=24)` — `release(code, order.customer_id)`; иначе — только `logger.info`, что использование сгорело. Использование `timedelta` и часов сервиса, не реестра (`Clock` из конструктора `OrderService`). Константа окна — `REFUND_WINDOW = timedelta(hours=24)` в `orders.py`. Отрицательная разница (часы откатились) трактуется как «в окне» — возврат есть. Альтернатива — хранить в заказе дедлайн возврата: отвергнута, лишнее поле при том же результате.

9. **Документация.** README, «Правила расчёта»: порог от суммы до скидки, потолки, `FREE_SHIPPING`, лимит на клиента, окно возврата, тай-брейк раскладки. Docstring `pricing.py` обновить в той же правке.

## Конфликты с существующими тестами

Тикет требует менять поведение, закреплённое текущими тестами, и одновременно запрещает менять существующие тесты. Поведение в тикете выигрывает; ожидаемо упадут (проверить прогоном на этапе apply):

- `tests/test_pricing_promo.py::test_fixed_capped` (300.00, номинал 500 → 300.00; теперь 150.00 — потолок 50 %);
- `tests/test_pricing_promo.py::test_split_sums_exactly` (ожидает `min(value, base)` для фиксированных скидок; для малых баз теперь действует потолок 50 %);
- `tests/test_pricing_promo.py::test_shipping_by_discounted_amount` (доставка 299.00 при 3100.00 − 200.00; теперь бесплатна);
- `tests/test_orders_promo.py::test_free_shipping_lost_after_discount` (то же правило в сервисе);
- возможно, тесты отмены в `tests/test_orders_promo.py`, если они отменяют заказ позже 24 часов (проверить `test_cancel_after_expiry_releases`).

Правило для apply: эти тесты **не редактируем и не удаляем**; новое поведение покрываем новыми тестами в новых файлах; в итоговом отчёте перечисляем упавшие старые тесты как ожидаемо устаревшие и просим владельца обновить их отдельно.

## Assumptions (зафиксированные допущения)

- Потолок фиксированной скидки — 50 % (не 30 %), см. решение 1.
- Тай-брейк бухгалтерии применяется ко всем видам скидок, где есть раскладка; затрагивает только равные остатки, поэтому существующие примеры (0.34/0.33/0.33, 0.33/0.67) не меняются.
- Код `FREE_SHIPPING` проходит те же условия заказа, что и остальные: без участвующих строк (например, только сертификаты) или ниже `min_order_amount` — `PromoConditionsError`. Если проверки пройдены, а экономить нечего, код применяется, использование засчитывается, `shipping_discount` = `0.00` (так же, как скидка 0.00 допустима у процентного кода).
- `shipping_discount` = стоимость доставки, которая была бы начислена по политике без кода (при нестандартной плате — она).
- `max_discount` допускает не более двух знаков после запятой; значения с большим числом знаков — `ValidationError` (как номинал фиксированной скидки).
- `customer_id` — любая строка сравнивается как есть, включая пустую (`""` — это значение, не «нет клиента»); не-строка — `ValidationError`. Это отличается от `promo_code`, где пустая строка означает «без кода».
- Счётчик клиента ведётся и для кодов без `max_uses_per_customer`.
- Лимит на клиента без `customer_id` в `quote` тоже даёт `PromoConditionsError` (как в `place_order`), чтобы `quote` не обещал цену, которую нельзя оформить.
- Окно возврата считается по `Order.created_at` и часам сервиса; «сгоревшее» использование не возвращается ни в общий, ни в клиентский счётчик.
- Отмена после окна всегда допустима, меняется лишь учёт использования.

## Risks / Trade-offs

- [Старые тесты упадут из-за изменённого поведения] → зафиксировано выше; не править их молча, а сообщить.
- [Расхождение часов сервиса заказов и реестра] → окно возврата считается только по часам сервиса, срок кода — по часам реестра; в тестах использовать одни `FixedClock`.
- [Клиент без `customer_id` обходит клиентский лимит] → такой код просто не применяется (требование тикета).
- [Разные написания `customer_id` дают разных клиентов] → требование тикета (сравнение как есть); нормализация — ответственность вызывающего слоя.
- [Реестр и хранилище заказов не потокобезопасны] → без изменений, вне объёма.
