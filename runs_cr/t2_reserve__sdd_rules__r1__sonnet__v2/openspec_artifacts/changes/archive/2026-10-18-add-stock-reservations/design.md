## Context

Вся логика в `Inventory` (`warehouse/inventory.py`); состояние лежит в `InMemoryStore`, время — только из внедрённых часов, журнал — `EventLog` с неизменным форматом. Операции атомарны: сначала проверки, потом изменения. Мотивация и API — в proposal.md, требования — в specs/stock-reservations/spec.md.

## Goals / Non-Goals

**Goals:**
- Резервы поверх существующей модели без изменения старого API и формата журнала.
- Истечение вычисляется лениво по `clock.now()`.

**Non-Goals:**
- Фоновая очистка истёкших резервов, персистентность, изменения `cli.py`/`reports.py`.
- Склейка одинаковых позиций в резерве.

## Decisions

- **Хранение.** Резервы лежат во внутренней изменяемой записи (`warehouse/reservations.py`, рядом с `DEFAULT_RESERVATION_TTL`) с полями: order_id, lines, created_at, expires_at, явный статус (`ACTIVE`/`CONFIRMED`/`CANCELLED`). Словарь `order_id → запись` хранится в `InMemoryStore` (она уже внедряется в `Inventory`), чтобы store оставался единственным носителем состояния. Альтернатива — словарь в `Inventory`; отвергнута, чтобы состояние не расходилось при общем store.
- **Эффективный статус.** `EXPIRED` не хранится: `effective_status(record, now)` возвращает `EXPIRED`, если запись `ACTIVE` и `now >= expires_at`. Единый `now = clock.now()` берётся один раз на операцию. Так выполняется «истечение без журнала» и без фоновых задач; `CONFIRMED`/`CANCELLED` истечением не затрагиваются.
- **`reserved`/`available`.** `reserved` — обход активных (по эффективному статусу) записей с суммированием `qty` строк позиции; `available = max(0, on_hand − reserved)`. Число резервов невелико, индекс не нужен. Проверки позиции переиспользуют `_check_position`.
- **`reserve`.** Порядок проверок: `order_id` (код), `ttl`, непустые строки, нормализация и валидация каждой строки (код склада, SKU, qty), `DuplicateReservationError` (если есть активный/подтверждённый), затем суммирование по позиции `(warehouse, sku)` и сравнение с `available` → `InsufficientStockError(wh, sku, requested=сумма, available)`. Затем запись (заменяет старую истёкшую/отменённую) и события `RESERVE` по строкам. Допущение: нехватка проверяется в порядке первого появления позиции в строках.
- **`confirm`.** Статусы проверяются раньше остатков (NotFound → Expired/State). Достаточность — по физическому остатку и сумме строк позиции, без вычета резервов. Затем списание и события `ISSUE` (`ref=order_id`) по строкам и `RESERVE_CONFIRM`; статус `CONFIRMED`. Общий приватный помощник «списать без проверки доступности» переиспользуется `issue`, чтобы не дублировать запись события и логирование.
- **`issue`/`transfer`.** Лимит меняется с физического остатка на `available`. `transfer` по его docstring использует «те же проверки, что у `issue`», поэтому ограничение распространяется и на него (допущение; иначе перемещение обходило бы резервы). `InsufficientStockError.available` — доступное количество (по docstring ошибки — «сколько сервис мог бы отдать»).
- **`cancel`.** NotFound → `CONFIRMED` даёт `ReservationStateError` → `CANCELLED`/`EXPIRED` возвращают снимок без изменений → `ACTIVE` становится `CANCELLED` + `RESERVE_CANCEL`.
- **`extend`.** Порядок: валидация `ttl` (общий с `reserve` помощник), затем поиск и статусы как у `confirm`; `new = now + ttl`; при `new <= expires_at` — возврат текущего снимка без события.
- **Время в журнале.** `expires` форматируется через `format_timestamp` (секундная точность), как и ts события; `Reservation.created_at/expires_at` хранят полную точность часов.
- **Снимки.** Наружу отдаётся `Reservation` (frozen), `lines` — кортеж `ReservationLine` в порядке передачи. Кортежи нормализуются в `ReservationLine`.
- **Ошибки.** `ReservationError(WarehouseError)` с конструктором `(order_id, message=None)` и атрибутом `order_id`; не наследуют `ValidationError`. Новые имена экспортируются из `warehouse/__init__.py`.
- **Прочие допущения.** `available`/`reserved` для неизвестного SKU — `UnknownSkuError` (README); `ttl` не `timedelta` (включая `bool`) — `ValidationError`; при `reserve` поверх истёкшего/отменённого резерва прежняя запись полностью заменяется (история остаётся в журнале).

## Risks / Trade-offs

- [Ленивое истечение зависит от часов; возможны «скачки» при ручной смене часов назад] → статус не кэшируется, `ManualClock` назад не идёт.
- [Замена старого резерва теряет его из `get_reservation`] → история остаётся в журнале.
- [Линейный обход резервов в `available`] → приемлемо для хранилища в памяти; при росте добавить индекс по позиции.
- [`transfer` тоже ограничен резервами — расширение относительно текста задачи] → зафиксировано в proposal/specs; для кода без резервов поведение прежнее.

## Migration Plan

Миграции нет: без резервов поведение неизменно. Откат — удаление новых методов и модулей.

## Решения при реализации

- Строка резерва неподходящего вида (не `ReservationLine` и не кортеж из трёх элементов) — `ValidationError`.
- Внутренняя запись резерва (`ReservationRecord`) лежит в `warehouse/reservations.py`, `InMemoryStore` импортирует её оттуда; хранилище отдаёт `get_reservation/put_reservation/reservations`.
- `confirm` пишет события `ISSUE` через приватный `_write_issue` (общий с `issue`), время события берётся из часов в момент записи.
