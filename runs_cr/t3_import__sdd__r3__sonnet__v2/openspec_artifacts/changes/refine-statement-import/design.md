## Context

Мотивация — в proposal.md, требования — в `specs/statement-import/spec.md`. Сейчас `ledger/importer.py` читает файл целиком, декодирует (`utf-8-sig` → `cp1251`), идёт `csv.reader` по записям (`_records` отдаёт номер физической строки начала записи и поля), парсит строки и пишет новые транзакции одним `store.add_many`. `RowError` и `ImportResult` объявлены в `importer.py`, `StatementRowError` — в `errors.py` (создаётся как `StatementRowError(msg, line_no=...)`, в том числе в существующих тестах). Ограничения: только стандартная библиотека; `cli.py`, `reports.py` и существующие тесты вне пунктов 1–4 не трогаем.

## Goals / Non-Goals

**Goals:**
- Реализовать пять изменений поведения и три новых элемента API так, чтобы старые вызовы работали как раньше.
- `dry_run` проходит ровно тот же код, что и обычный импорт, и отличается только отсутствием записи.

**Non-Goals:**
- Миграция уже сохранённых описаний.
- Изменение формата `nova` кроме нормализации описания; изменение `cli.py`.

## Decisions

1. **`RowError` переезжает в `ledger/errors.py`** и реэкспортируется из `ledger/importer.py` (`from ledger.errors import RowError`). Иначе `StatementRowError.errors: list[RowError]` потребовал бы циклического импорта (`importer` уже импортирует `errors`). Альтернатива — аннотация строкой без импорта; отвергнута: `RowError` — часть исключения, ему место рядом. Существующий `from ledger.importer import RowError` продолжает работать. Поле `raw: str = ""` добавляется последним.

2. **`StatementRowError.__init__(message, *, line_no=None, errors=None)`**. Если `errors` не передан: `[RowError(line_no, message)]` при заданном `line_no`, иначе `[]`. Так существующие вызовы `StatementRowError("x", line_no=4)` остаются валидными. В строгом режиме importer после разбора всех строк бросает `StatementRowError(first.message, line_no=first.line_no, errors=errors)`. Внутренние ошибки разбора одной строки (`_parse_row`) продолжают бросать `StatementRowError(msg)` и перехватываются в цикле — так же в обоих режимах; цикл всегда копит `errors`, и только в конце решает: `strict` → бросить, иначе вернуть в результате.

3. **Нормализация описания** — `" ".join(text.split())` в `_build` (единственная точка создания `Transaction`), т.е. для всех форматов. `str.split()` без аргумента режет по любым Unicode-пробельным символам (включая `\n`, `\t`, U+00A0), регистр не трогает. Альтернатива `re.sub(r"\s+", " ", ...)` эквивалентна по результату, но `split` проще и согласуется с `normalize_text`. Ключ дедупликации по-прежнему считается через `normalize_description`, поэтому дедупликация не меняется.

4. **Суммы «Сферы».** Регэксп дробной части принимает `[.,]`; перед ним отдельная проверка: если в строке суммы есть и `.`, и `,` — ошибка строки с понятным сообщением. Остальные случаи (`1.234`, `1.2.3`, `1,2,3`) отсекает регэксп: после целой части допустим не более одного разделителя и 1–2 цифры. Тысячи — как прежде (пробел/U+00A0 группами по три). Знак и «unsigned» для `sfera_split` — без изменений.

5. **Служебные строки `sfera_split`.** Колонки `Приход`/`Расход` разбираются до даты: функция классификации значения возвращает «пусто» / «ноль» / сумма / ошибка. Если обе колонки — «ноль», `_parse_row` возвращает `None`, а цикл молча пропускает такую строку (не `duplicates`, не `errors`). Проверка «хватает ли полей» остаётся перед этим. Если одна «ноль», а другая «пусто» — ошибка, как и обе пустые. Дата и описание у пропускаемой строки не проверяются (в тикете пропуск определяется только нулями в обеих колонках — см. допущения). Порядок проверок для остальных строк (дата → суммы) сохраняется, чтобы сообщения прежних ошибок не менялись.

6. **`raw`.** `csv.reader` не отдаёт исходный текст, поэтому после декодирования текст один раз делится на физические строки регэкспом `\r\n|\r|\n` (ровно те терминаторы, которые считает `csv`/`StringIO(newline="")`, поэтому `line_num` согласован), а `_records` отдаёт вместе с полями диапазон строк `[start, end]`; `raw = "\n".join(lines[start-1:end])`. Побочные эффекты: BOM уже отброшен `utf-8-sig`, cp1251 уже раскодирован, `\r` и завершающий перевод строки не попадают в `raw` автоматически. `str.splitlines()` не используем — он режет по `\x0b`, `\x0c`, U+2028 и др., что csv не считает концом строки. Накладные расходы — один проход по тексту.

7. **`dry_run` и `transactions`.** Единый путь: после цикла `new` — список транзакций к добавлению (уже с категориями). Если `dry_run` — `transactions = list(new)` (id `None`), запись пропускается; иначе `transactions = store.add_many(new)` (возвращает транзакции с id, в порядке `new`), при пустом `new` — `[]` без вызова. Подсчёт `added = len(new)` в обоих режимах, поэтому цифры совпадают по построению. `ImportResult.transactions` объявляется последним полем с `default_factory=list`; `frozen=True` сохраняется.

8. **Строгий режим не пишет** ни в `dry_run`, ни без: исключение бросается до обращения к хранилищу, поэтому атомарность не требует дополнительных шагов.

## Risks / Trade-offs

- [Поведение `import_csv`/`nova` меняется из-за нормализации описаний] → в Nova-описаниях двойные пробелы раньше сохранялись; это допущение из тикета («при импорте»). Тесты с такими описаниями обновить; дедупликация не страдает, так как ключ уже нормализован, но ранее сохранённые записи с двойными пробелами и новые записи сравниваются по-прежнему корректно.
- [Строгий режим дольше разбирает файл с ошибкой] → файлы выписок малы; разбор линейный.
- [Пропуск служебных строк без проверки даты скрывает мусор в дате] → пропускаются только строки с явными нулями в обеих колонках; такие строки не представимы как транзакции в любом случае.
- [Точка в сумме больше не ошибка, `1.234` остаётся ошибкой (3 знака)] → однозначность: «1.234» не трактуем как тысячи; тысячи отделяются только пробелом/U+00A0.

## Migration Plan

Изменений данных нет. Откат — возврат кода; сохранённые описания совместимы в обе стороны.

## Допущения (ответы на неоднозначности тикета)

- Нормализация пробелов (п.3) действует на все форматы, включая `nova` и `import_csv`; «пробельные символы» — по `str.isspace` (Unicode).
- В п.2 «ноль» — любое значение, подходящее под формат суммы без знака и равное нулю (`0`, `0,00`, `0.00`); значение со знаком (`-0,00`) — по-прежнему ошибка; дата и описание пропускаемой строки не проверяются; строка с недостающими полями — ошибка.
- `StatementRowError.errors` при ручном создании без списка — по `line_no`/`message` (см. решение 2).
- В `dry_run` `transactions` содержит категоризованные транзакции; `imported_at` — значение `clock.now()`, как и при реальном импорте.
- Для `import_csv` строгий режим тоже собирает все ошибки; `line_no` и сообщение прежние (первая ошибка).
