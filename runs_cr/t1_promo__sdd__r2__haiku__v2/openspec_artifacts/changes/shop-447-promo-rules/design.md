## Context

Промокоды реализованы в `shop/promo.py` (модель и реестр), `shop/pricing.py` (`calculate_total`,
`_line_discounts`, `_split_discount`, `ShippingPolicy`) и `shop/orders.py` (`OrderService.quote`,
`place_order`, `cancel`). Заказы и счётчики in-memory. Соглашения README действуют без изменений: деньги в
`Decimal` через `quantize_money` (`ROUND_HALF_UP`), ошибки наследуют `PromoError`/`ShopError`, время только
через `Clock`, интервалы полуоткрытые, модели — frozen dataclass с проверками в `__post_init__`.
Требования — в `specs/promo-codes/spec.md` (MODIFIED и ADDED), мотивация — в `proposal.md`.

Текущий код расходится с новыми правилами в четырёх местах: порог доставки считается от суммы после скидки
(`cost_for(goods_after_discount, ...)`), фиксированная скидка ограничена только суммой строк, раскладка копеек
при равных остатках отдаёт копейку строке, которая раньше в корзине, а `cancel` возвращает использование всегда.

## Goals / Non-Goals

**Goals:**
- Все изменения правил сосредоточены в `pricing` (скидка, потолки, раскладка, доставка) и в `promo`/`orders`
  (учёт по клиенту, окно отмены, новый вид). Публичные имена и значения по умолчанию для существующих вызовов
  не меняются.
- Инварианты сохраняются: сумма `discount` по строкам равна `discount` заказа; `total = subtotal − discount +
  shipping + tax`; счётчики не уходят ниже нуля.

**Non-Goals:**
- Персистентность, миграции, изменения `shop/cli.py` и `shop/reports.py`.
- Комбинирование нескольких промокодов.
- Проверка потолка фиксированной скидки при создании кода: доля зависит от корзины, поэтому потолок
  применяется при расчёте.
- Изменение правил отчётов (отчёты по-прежнему читают `total`, `discount` и `shipping` без правок).

## Decisions

**1. Потолок фиксированной скидки — ограничение при расчёте, а не ошибка.** Формулировка «не больше 50 %»
трактуется как верхняя граница суммы скидки: `order_discount = min(value, quantize(S · 50 / 100))`. Ошибки
нет, потому что код не знает корзину при создании. Альтернатива — `PromoConditionsError` при превышении —
отвергнута: клиент получил бы отказ в оплате вместо скидки, которую разрешено дать. Константа
`FIXED_DISCOUNT_CAP_SHARE = Decimal("0.50")` в `pricing.py`. Потолок касается и уже существующих фиксированных
кодов: расчёт меняется для них тоже (см. Risks).

**2. Потолок процентной скидки.** `order_discount = min(quantize(S · value / 100), max_discount)` — потолок
применяется после округления процента, поэтому сумма всегда в копейках. `max_discount` хранится в `PromoCode`
и проверяется в `__post_init__` (только `PERCENT`, `> 0`, копейки). Альтернатива — проверять потолок только в
`pricing` — отвергнута, потому что некорректный код иначе создаётся без ошибки.

**3. `FREE_SHIPPING` — отдельная ветка без раскладки по строкам.** `value` равен `Decimal("0")`, проверка в
`__post_init__` (`!= 0` → `ValidationError`). В `calculate_total` для этого вида все `line.discount` равны `0.00`,
а стоимость доставки считается как обычно, затем при `promo.kind is FREE_SHIPPING` уходит в `shipping_discount`,
`shipping` становится `0.00`. Условия применения (участвующие строки, минимальная сумма) проверяются тем же кодом,
что и для других видов: `_line_discounts` сохраняет эти проверки и возвращает нули. Альтернатива — пропускать
проверки для `FREE_SHIPPING` — отвергнута: тикет требует, чтобы «экономить было нечего» не давало ошибку, но
не говорит, что условия отменяются; сохранение проверок проще объяснить.

**4. Порог доставки — от суммы до скидки.** `shipping.cost_for(subtotal, needs_delivery=...)` вместо
`goods_after_discount`. Одна строка изменения в `calculate_total`; `ShippingPolicy` не меняется.

**5. Раскладка копеек: ключ сортировки.** В `_split_discount` сортировка остатков меняется с
`(-remainder, index)` на `(-remainder, -amount_kopecks, index)`. Остаток по-прежнему решает первым; сумма строки
решает равенство остатков; порядок корзины — только при равенстве сумм. Для проверки сумма строки берётся
в копейках (`int(amount / CENT)`), как и остальные величины алгоритма.

**6. Лимит на клиента — отдельный счётчик в реестре.** `PromoRegistry` хранит `_customer_uses: dict[tuple[str, str], int]`.
`resolve(code, customer_id=None)`: после проверок существования, срока и общего лимита — если задан
`max_uses_per_customer`, то без `customer_id` → `PromoConditionsError`, при достижении лимита клиента →
`PromoConditionsError`. `record_use` и `release_use` принимают `customer_id` и обновляют и общий, и клиентский
счётчики (клиентский — только при переданном `customer_id`). `uses(code, customer_id=None)` возвращает клиентский
счётчик при переданном `customer_id`, иначе общий. `customer_id` сравнивается как есть (тип `str` или `None`,
иначе `ValidationError`), без `normalize_key`.

**7. Окно возврата при отмене — по часам сервиса.** `OrderService.cancel` вызывает `release_use`, только если
`self._clock.now() - order.created_at < PROMO_CANCEL_WINDOW` (`timedelta(hours=24)`, константа в `orders.py`).
Строгое неравенство даёт требуемое «ровно через 24 часа — не возвращаем». Сравнивать с `SystemClock` из
`datetime.now()` нельзя: README запрещает прямой вызов. Статус заказа в любом случае становится `CANCELLED`.

**8. `customer_id` в заказе.** `Order.customer_id: str | None = None` в конце dataclass. `place_order` передаёт
`customer_id` в `quote` и `record_use`, затем сохраняет его в заказе. Учёт использования остаётся после расчёта и до
сохранения заказа, как в предыдущей версии.

**9. Новые поля `OrderTotal.shipping_discount` и `PromoCode` — в конце dataclass с значениями по умолчанию.**
Позиционные вызовы и существующие тесты не ломаются.

**10. Тесты — новыми файлами.** Новые проверки идут в `tests/test_promo_shop447_*.py` (или в отдельные файлы по теме:
доставка, лимиты, раскладка, отмена). Существующие файлы не меняются, кроме одного исключения (см. Risks).

## Risks / Trade-offs

- **[Конфликт с «существующие тесты не меняем»] → два теста в `tests/test_promo_pricing.py` фиксируют
  отменяемые летние правила:** `test_fixed_discount_is_capped_by_eligible_amount` (ожидает скидку 649.90 при
  фиксированном коде 700.00, по новому правилу 324.95) и `test_discount_brings_free_shipping_threshold_closer`
  (порог после скидки, по новому правилу доставка 0.00). Их ожидания нужно изменить, иначе правила из тикета не
  выполнить. Это единственное исключение из рамки «существующие тесты не меняем»; больше ни один существующий тест
  не затрагивается (проверено: `test_penny_goes_to_first_line_with_largest_remainder` и
  `test_equal_remainders_follow_cart_order` сравнивают равные суммы, поэтому их ответ не меняется). Если рамка
  жёсткая, эти два теста переносятся в отдельный файл как устаревшие, а владелец тикета подтверждает решение.
  **Решение при автономной реализации:** подтверждение владельца недоступно в этой сессии. Два теста изменены
  по описанному выше исключению (задача 5.1); заодно в первом тесте проверка `total == shipping + tax` заменена на
  `total == subtotal - discount + shipping + tax`, а во втором ожидаемый итог стал `3480.00`, поскольку он
  зависит от доставки. Владельцу тикета нужно подтвердить это изменение при ревью.
- **[Пересчёт для уже существующих фиксированных кодов] → потолок 50 % меняет суммы и для старых кодов.**
  Допущение: тикет относится ко всем фиксированным кодам, включая действующие. Если нужно только для новых кодов,
  потребуется отдельный признак на `PromoCode` — это решение владельца тикета.
- **[Двойная проверка при оформлении] → `place_order` вызывает `resolve` дважды (в `quote` и в `record_use`).** Это
  уже было в прежней версии; при разнесении во времени между вызовами код может истечь. Ошибка возникает до создания
  заказа, поэтому состояние остаётся консистентным.
- **[Отмена после 24 часов] → использование сгорает, но заказ всё равно отменяется.** Это соответствует тикету
  («использование сгорает»). Если бухгалтерия хочет запрещать отмену, это отдельная задача.
- **[Потолок `max_discount` на границе] → при `max_discount`, равном проценту, скидка та же.** Тесты покрывают
  потолок ниже процента и выше процента (сценарии в spec).
- **[Идентификатор клиента] → `"acc-1"` и `"ACC-1"` — разные клиенты.** Это следствие «сравниваем как есть».
  Если учётные записи в HTTP-слое нормализуются, это надо обеспечить там.
- **[Доставка при FREE_SHIPPING и подарочных сертификатах] → корзина с физическими товарами и сертификатом:**
  `needs_delivery` истинно, доставка обнуляется; корзина только с сертификатом даёт `PromoConditionsError` до расчёта
  доставки.

## Migration Plan

Миграции нет: всё in-memory, новые поля имеют значения по умолчанию. Откат — `git revert` коммитов этой задачи.
Порядок реализации: сначала модель и реестр (`promo.py`), затем `pricing.py`, затем `orders.py`, после каждого шага
проходят существующие тесты, кроме перечисленных в Risks.
