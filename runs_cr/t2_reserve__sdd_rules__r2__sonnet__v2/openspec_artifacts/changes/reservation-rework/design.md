## Context

Резервы живут в `InMemoryStore` как одна изменяемая `ReservationRecord` на `order_id`; статус `EXPIRED` вычисляется по часам (`effective_status`), событий истечения нет. `reserve` сейчас бросает `DuplicateReservationError` для активного и подтверждённого резерва, `cancel` подтверждённого бросает `ReservationStateError`. Мотивация и список изменений — в proposal.md, требования — в specs. Ограничения: `warehouse/cli.py`, `warehouse/reports.py`, существующие тесты и зависимости не трогаем; публичный API из задачи не меняется.

## Goals / Non-Goals

**Goals:**
- Реализовать замену активного резерва, возврат подтверждённого заказа, новые константы, `Availability`, `reservations`, `availability`, `sweep_expired`.
- Сохранить атомарность: любая ошибка не меняет ни хранилище, ни журнал.

**Non-Goals:**
- Фоновый планировщик (`sweep_expired` вызывает внешняя система).
- История резервов заказа сверх нужной для `sweep_expired`; изменение формата журнала, CLI и отчётов.

## Decisions

1. **Замена внутри `reserve`: сначала всё проверить, потом менять.** Порядок: валидация `order_id`, `ttl` (включая `ttl > MAX_RESERVATION_LIFETIME` → `ValidationError`), строк; затем статус существующего резерва: `CONFIRMED` → `DuplicateReservationError`. Для проверки наличия считается `free = max(0, on_hand − (reserved_all − reserved_by_replaced_reservation))`; свой активный резерв вычитается только из `reserved` этой позиции. Только после успешной проверки пишется `RESERVE_CANCEL` (если заменяемый резерв был `ACTIVE`), сохраняется новая запись и пишутся `RESERVE`. Альтернатива «cancel + reserve с откатом» отвергнута: откат журнала в `EventLog` (только на добавление) не предусмотрен.

2. **Новый резерв — новая `ReservationRecord`** (`created_at = now`, `expires_at = now + ttl`); запись в хранилище заменяется целиком, как и раньше для истёкших/отменённых. Отдельного `cancelled` состояния у заменённой записи нет — она просто вытесняется.

3. **Возврат в `cancel`.** Для `CONFIRMED`: по строкам в порядке — прибавить количество в хранилище, `RECEIVE` (`wh`, `sku`, `qty`, `ref=order_id`), затем статус `CANCELLED` и `RESERVE_CANCEL`. Ошибок по ходу быть не может (данные уже валидированы при `reserve`; события пишутся после изменения остатков, как в `confirm`). `RECEIVE` пишется напрямую в журнал и хранилище, а не через публичный `receive`, чтобы не дублировать проверки. Повторный `cancel` попадает в ветку `CANCELLED` — no-op. Резерв после возврата не возвращается в `ACTIVE`.

4. **Предел срока** — одна точка в `warehouse/reservations.py`: константа `MAX_RESERVATION_LIFETIME = timedelta(hours=2)` (значение из комментария Ольги Смирновой от 10.11, он отменяет «один час» из текста задачи) и помощник `cap_expiry`. `check_ttl` остаётся прежним (тип и знак), проверка предела — отдельно в `reserve`, потому что `extend` предел не отвергает, а обрезает. В `extend`: `target = min(now + ttl, created_at + MAX)`; запись и `RESERVE_EXTEND` — только если `target > expires_at`, в событии пишется именно обрезанное значение. `DEFAULT_RESERVATION_TTL = 20 минут` ≤ предела.

5. **`sweep_expired` и признак «уже отмечен».** В `ReservationRecord` добавляется поле `expiry_reported: bool = False`. Так как новый `reserve` создаёт новую запись, «другой резерв» получается автоматически (замечание Игоря Левина). Кандидаты: все записи с `effective_status == EXPIRED` и `not expiry_reported`; сортировка по `(expires_at, order_id)`; для каждой — `RESERVE_EXPIRE` (`order`, `expires`) со временем `now`, затем флаг ставится в `True`. Статус записи не меняется, поэтому `cancel`/`available`/`reserved` ведут себя как раньше.

6. **Вытеснение неотмеченного истёкшего резерва.** Если `reserve` вытесняет запись, которая истекла, но `expiry_reported` ещё `False`, она переносится в приватный список «ожидающих отметки» в хранилище (`InMemoryStore`: добавить методы для добавления и выдачи таких записей) и остаётся кандидатом для `sweep_expired`. Альтернатива — терять её: проще, но тогда поддержка не увидит истёкший резерв, если заказ успели оформить заново до запуска планировщика. Выбрана сохранность. Записи из этого списка не участвуют ни в `reserved`/`available`, ни в `reservations()`/`get_reservation()` (они возвращают только текущий резерв заказа). Эти записи неактивны, поэтому на остатки не влияют. После отметки запись из списка удаляется.

7. **`reservations(status=None)`**: снимки всех текущих записей через `snapshot(record, now)`, фильтр по `snapshot.status`, сортировка `(created_at, order_id)`. Не-`ReservationStatus` и не-`None` → `ValidationError` (`ReservationStatus` — `str`-enum, поэтому строка `"active"` равна `ACTIVE`; допускаем и её: приводим через `ReservationStatus(status)`, при `ValueError` → `ValidationError`).

8. **`availability(warehouse=None)`**: ключи — объединение позиций `store.positions()` и позиций активных резервов; фильтр по складу; сортировка по `(warehouse, sku)`; значения берутся через те же внутренние `_reserved_at` и `_available_at`, чтобы совпадать с публичными методами. `Availability` добавляется в `warehouse/models.py`; экспорт из `warehouse/__init__.py` — по аналогии с существующим (там резервные типы не экспортируются, поэтому не требуется).

## Risks / Trade-offs

- [Существующие тесты `tests/test_reservations.py` закрепляют старые правила (дубликат активного резерва, 15 минут, запрет отмены подтверждённого) и после изменения упадут] → Правила в задаче заменены осознанно, а «существующие тесты не меняем» не позволяет их править. Новые тесты кладутся в новый файл (например, `tests/test_reservations_rework.py`); при запуске полного набора ожидаемые падения старых тестов перечислить в отчёте и не править без отдельного решения владельца задачи.
- [Двойное вхождение одного `order_id` в результат `sweep_expired` при вытеснении неотмеченного резерва] → Следует буквальному «о каждом резерве пишем один раз»; зафиксировано в spec как допущение.
- [Утечка памяти из-за списка неотмеченных вытесненных записей] → Список чистится при отметке; растёт только если планировщик не вызывается.
- [Разное «время» события `RESERVE_EXPIRE`: пишется время вызова `sweep_expired`, а не `expires_at`] → Журнал отражает момент фиксации, а срок лежит в поле `expires`.

## Допущения (неоднозначности задачи)

- Предел — два часа (комментарий от 10.11 приоритетнее текста задачи).
- `ttl == MAX_RESERVATION_LIFETIME` для `reserve` допустим; ошибка только при `ttl > MAX`.
- Замена истёкшего/отменённого резерва остаётся прежней (без `RESERVE_CANCEL`); замена активного — по новым правилам.
- Возврат не зависит от `expires_at`, не проверяет резервы других заказов и выполняется один раз.
- Невалидный `status` в `reservations` — `ValidationError`.
- Тесты, закрепляющие замещённые правила, не правятся (см. риски).

- Публичный API сверен через `inspect.signature` и `dataclasses.fields`, расхождений нет.
