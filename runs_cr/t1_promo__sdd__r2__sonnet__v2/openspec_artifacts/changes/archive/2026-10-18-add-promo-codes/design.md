## Context

Мотивация и объём — в proposal.md, требования — в specs. Текущее состояние: `calculate_total` чистая функция; `OrderService` хранит заказы в памяти; `Order` — frozen dataclass; проектные соглашения (README): `Decimal` + `quantize_money`, ошибки только от `ShopError`, время только через `Clock`, `normalize_key` для вводимых человеком кодов, полуоткрытые интервалы `[начало, конец)`, frozen-модели с проверкой в `__post_init__`.

## Goals / Non-Goals

**Goals:**
- Скидка считается в одном месте (`pricing.py`), детерминированно и в целых копейках.
- Побочные эффекты (счётчик) возникают только в `OrderService` и только после успешного сохранения заказа.

**Non-Goals:**
- Скидки в CLI и отчётах; потокобезопасность и персистентность счётчика (всё в памяти, как и `OrderStore`); комбинирование нескольких кодов в одном заказе.

## Decisions

1. **Разделение ответственности.** `PromoRegistry.resolve` проверяет существование → срок → лимит; `calculate_total` проверяет только условия заказа (участвующие строки, минимальная сумма). `OrderService` вызывает их в этом порядке: `resolve`, затем расчёт, затем (только в `place_order`) сохранение заказа и `redeem`. Так порядок проверок из тикета выполняется естественно.
2. **Расширение реестра сверх API тикета.** Добавляются `redeem(code)` и `release(code)` (учёт и возврат использования). Альтернатива — отдавать изменяемый счётчик наружу — отвергнута: нарушает инкапсуляцию. `release` не опускает счётчик ниже 0. `uses` для незарегистрированного кода возвращает 0 (допущение).
3. **Раскладка в целых копейках.** Суммы переводятся в `int` копеек; доля строки = `floor(discount_cents * line_cents / base_cents)`, остаток — числитель `discount_cents * line_cents % base_cents`. Недостающие копейки (меньше числа участвующих строк) раздаются по одной в порядке `(-остаток, индекс строки)`. Это точная целочисленная арифметика без `Decimal`-контекста; альтернатива с `Decimal` и `ROUND_DOWN` менее надёжна по точности. Исходный порядок строк корзины = индекс, что реализует «выше в чеке».
4. **Процентная скидка** = `quantize_money(base * value / 100)` (`ROUND_HALF_UP`); фиксированная = `min(value, base)`. Скидка не превышает базу, значит ни одна строка не уйдёт в минус.
5. **Налог и доставка.** Налог строки — `tax.tax_for(category, amount - discount)`. `subtotal` остаётся суммой до скидки; доставка считается от `subtotal - discount`. Перед изменением нужно убедиться, что без промокода значения побайтно прежние (скидка `ZERO`).
6. **Модели.** `LineTotal.discount` и `OrderTotal.discount` получают значение по умолчанию `ZERO` в конце списка полей, чтобы существующие конструкторы в тестах продолжали работать. `Order.promo_code: str | None = None` — тоже в конце, после `status`. Хранение кода в заказе нужно, чтобы `cancel` знал, что возвращать.
7. **Нормализация кода.** `PromoCode.code` нормализуется через `normalize_key` в `__post_init__`; реестр нормализует ключи при `add`/`resolve`/`uses`. В `OrderService` вход: не `str` и не `None` → `ValidationError` (через `normalize_key`); после нормализации пустая строка = «без кода» (в `resolve("")` остаётся `UnknownPromoCodeError`). `Order.promo_code` — нормализованный код, не введённый пользователем текст.
8. **Участие строки.** `category is not GIFT_CARD and category not in promo.excluded_categories`. Сертификаты исключены жёстко (README), независимо от `excluded_categories`. Если участвующих строк нет — `PromoConditionsError` независимо от `min_order_amount`.
9. **Отмена.** `cancel` сначала проверяет статус (как сейчас), сохраняет отменённый заказ и затем вызывает `release(order.promo_code)`, если код есть. Повторная отмена падает на проверке статуса до возврата. Код возвращается и при истёкшем сроке — `release` не проверяет срок.
10. **Ошибки.** `PromoError(ShopError)` и три прямых наследника в `shop/errors.py`; ни `ValidationError`, ни друг от друга не наследуются.
11. **Валидация `PromoCode`** — в `__post_init__` по образцу `Product`: `Decimal` без `float`, не более двух знаков для фиксированной суммы и минимальной суммы, aware-`datetime`, `starts_at < expires_at`, `bool` не годится как `max_uses`.

## Risks / Trade-offs

- [Состояние в памяти: гонки при параллельном оформлении, `resolve` и `redeem` не атомарны] → `place_order` синхронен, как и весь сервис сегодня; при появлении многопоточности понадобится блокировка или атомарный `redeem` с проверкой лимита. Для защиты `redeem` дополнительно проверяет лимит и бросает `PromoConditionsError`.
- [Изменение порога доставки по сумме после скидки меняет итог только при промокоде] → без промокода скидка 0, поведение не меняется; покрывается регрессионными тестами.
- [Сбой между сохранением заказа и `redeem`] → оба шага выполняются подряд без точек отказа в памяти; `redeem` вызывается после проверенного `resolve`, поэтому не должен падать.

## Допущения (не оговорены в тикете)

- Незарегистрированный код в `uses` даёт 0, а не ошибку.
- Фиксированная сумма и минимальная сумма заказа с более чем двумя знаками отвергаются `ValidationError`; процент может иметь любую точность.
- Нестроковый `promo_code` в `quote`/`place_order` — `ValidationError`.
- Дубликат кода в реестре — `ValidationError` (соглашение README).
- `LineTotal.amount` — сумма до скидки; скидка хранится отдельным полем.
- Порядок проверок в `place_order`: пустая корзина проверяется расчётом; если код неизвестен или просрочен, а корзина пуста, приоритет не принципиален (допущение: сначала `resolve`).
- README обновляется (правило `total`, доставка после скидки, возврат при отмене).
