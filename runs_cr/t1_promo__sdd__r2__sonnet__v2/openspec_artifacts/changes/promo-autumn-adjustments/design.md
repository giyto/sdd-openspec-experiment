## Context

Мотивация и объём — в proposal.md, требования — в specs. Расчёт — чистая функция `calculate_total` (`shop/pricing.py`); реестр `PromoRegistry` держит счётчики в памяти (`shop/promo.py`); `OrderService` связывает их (`shop/orders.py`). Конвенции README: `Decimal` и `quantize_money`, ошибки только от `ShopError`, время только через `Clock`, полуоткрытые интервалы, frozen-модели с проверкой в `__post_init__`. Приватная `_split_discount(discount, amounts, base)` напрямую вызывается в `tests/test_pricing_promo.py`, её сигнатуру сохраняем.

## Goals / Non-Goals

**Goals:**
- Все новые поля и аргументы необязательны, дописываются в конец / только по имени: старые вызовы работают.
- Правила скидки по-прежнему живут в одном месте (`pricing.py`), счётчики меняет только `OrderService`.

**Non-Goals:**
- `shop/cli.py` и `shop/reports.py` (отчёт не показывает `shipping_discount`); персистентность и потокобезопасность; сочетание нескольких кодов; нормализация `customer_id`.

## Decisions

1. **Потолок фиксированной скидки — 50 %.** В тикете 30 %, но поправка маркетинга (22.10, согласовано с финансами) заменяет число; реализуем 50 %. Константа с именем в `pricing.py`. Скидка фиксированного кода = `min(value, base, quantize_money(base * 0.5))`. Потолок процентного кода: `min(quantize_money(base * value / 100), max_discount)`. Округление — только `quantize_money` (`ROUND_HALF_UP`), напр. 50 % от `0.05` — `0.03`.
2. **Раскладка копеек.** В `_split_discount` ключ сортировки остатков меняется с `(-остаток, индекс)` на `(-остаток, -сумма_строки_в_копейках, индекс)`. Сигнатура и целочисленная арифметика прежние; сумма долей не меняется, так что инварианты «сумма = скидка» и «доля ≤ суммы строки» сохраняются. Остатки сравниваются как целые числители `discount_cents * line_cents % base_cents` при общем знаменателе, поэтому равенство точное.
3. **Порог доставки.** `calculate_total` передаёт в `ShippingPolicy.cost_for` `subtotal`, а не `subtotal - discount`. Платная доставка скидкой не уменьшается — как раньше.
4. **Бесплатная доставка (`FREE_SHIPPING`).** Условия заказа (участвующие строки, `min_order_amount`) проверяются тем же кодом, что у остальных видов; скидка на товары равна нулю, все построчные скидки `0.00`. Доставка = `0.00`, `shipping_discount` = стоимость доставки, которую дала бы политика без промокода (`cost_for(subtotal, needs_delivery=...)`); в остальных случаях `ZERO`. `OrderTotal.shipping_discount: Decimal = ZERO` — последнее поле dataclass. Формула `total` не меняется.
5. **Валидация `PromoCode`.** Новые поля — в конец dataclass. `value` бесплатной доставки: `value == 0` (допускаем и `Decimal("0.00")`, оно численно равно нулю). `max_discount`: только `PERCENT`, `Decimal`, конечное, `> 0`, не более двух знаков (как фиксированная и минимальная суммы — иначе скидка не в копейках). `max_uses_per_customer`: как `max_uses` (не `bool`, целое, `>= 1`).
6. **Учёт по клиентам в реестре.** `resolve(code, customer_id=None)` — после проверки общего лимита: если у кода есть лимит на клиента, то `customer_id is None` → `PromoConditionsError`, `uses(code, customer_id) >= лимит` → `PromoConditionsError`. Внутри — словарь `код → {customer_id: число}`. `uses(code, customer_id=None)`; `redeem`/`release` получают необязательный `customer_id` (расширение сверх API тикета, как `redeem`/`release` в прошлом изменении). Использование без `customer_id` попадает только в общий счётчик; возврат не опускает ни один счётчик ниже нуля. `customer_id` не нормализуется (`"U1"` ≠ `"u1"`, пробелы значимы), пустая строка — обычный идентификатор, не `None`. Не `str` и не `None` → `ValidationError`.
7. **Заказ и сервис.** `Order.customer_id: str | None = None` — после `promo_code`. `quote`/`place_order(cart, promo_code=None, *, customer_id=None)`; тип идентификатора проверяется, и он сохраняется в заказе всегда, даже без промокода. `place_order` вызывает `redeem(code, customer_id)` после сохранения заказа, как раньше.
8. **Отмена.** `cancel` отменяет заказ всегда; `release(code, order.customer_id)` вызывается, только если `0 <= now - order.created_at < timedelta(hours=24)` по часам `OrderService`. Граница полуоткрытая: ровно 24 часа — сгорание. Если часы пошли назад (`now < created_at`), использование возвращаем (допущение: ошибка часов не должна штрафовать клиента). Окно — именованная константа в `orders.py`.
9. **Раскатка.** Изменения внутри трёх модулей и README; данных для миграции нет (всё в памяти).

## Конфликт с существующими тестами

Тикет требует «существующие тесты не менять», но три теста проверяют поведение, которое тикет сам отменяет. В них меняются только ожидаемые значения; все остальные существующие тесты проходят без правок.

- `tests/test_pricing_promo.py::test_shipping_threshold_after_discount`: порог считается до скидки (`3000.00` со скидкой `100` → доставка `0.00`).
- `tests/test_pricing_promo.py::test_fixed_capped_by_base`: фиксированная `500` на базе `300.00` теперь даёт `150.00`.
- `tests/test_orders_promo.py::test_cancel_after_expiry`: `timedelta(days=1)` — ровно 24 часа, использование сгорает (`uses == 1`).

Остальное новое поведение покрывается новыми тестами в новом файле.

## Risks / Trade-offs

- [30 % в тикете против 50 % в поправке] → принято 50 % как более поздняя поправка; число в одной константе, смена — в одном месте.
- [`resolve` и `redeem` не атомарны, особенно для клиентского лимита] → сервис синхронный, как и раньше; `redeem` повторно проверяет оба лимита и не меняет счётчики при отказе.
- [Часы заказа и часы реестра — разные объекты] → окно отмены берёт часы `OrderService`, как требует тикет; срок кода — часы реестра.
- [Раскладка копеек меняется] → заказы хранят готовые итоги, пересчёта старых нет; меняется только расчёт новых заказов.

## Допущения (не оговорены в тикете)

- Промокод бесплатной доставки подчиняется тем же условиям заказа (в корзине только сертификаты — `PromoConditionsError`; минимальная сумма по участвующим строкам).
- `max_discount` отвергается при более чем двух знаках после запятой.
- Пустая строка как `customer_id` — идентификатор как есть.
- `customer_id` запоминается заказом и без промокода.
- Отмена при `now < created_at` возвращает использование.
