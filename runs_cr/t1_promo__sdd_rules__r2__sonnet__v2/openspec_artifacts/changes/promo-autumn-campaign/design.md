## Context

Промокоды живут в `shop/promo.py` (модель и реестр), `shop/pricing.py` (расчёт скидки, раскладка, доставка) и `shop/orders.py` (счётчики при оформлении и отмене). Мотивация и список правил — в `proposal.md`, требования — в дельта-спецификациях. Рамки: `shop/cli.py`, `shop/reports.py` и публичный API из задачи не меняются, новых зависимостей нет, все деньги — через `quantize_money`/`ROUND_HALF_UP`, время — только через `Clock`.

## Goals / Non-Goals

**Goals:**
- Реализовать правила тикета минимальными изменениями трёх модулей.
- Сохранить работу всех старых вызовов (`calculate_total(cart)`, `quote(cart)`, `place_order(cart, code)`, `resolve(code)`, `uses(code)`).

**Non-Goals:**
- Персистентность счётчиков, нормализация `customer_id`, любые изменения CLI/отчётов.
- Окно возврата, настраиваемое извне: 24 часа — константа модуля заказов.

## Decisions

1. **Потолок фиксированной скидки — 50 %, а не 30 %.** Тикет говорит 30 %, но поправка маркетинга (22.10) согласована с финансами и позже по времени. Константа `FIXED_DISCOUNT_CAP = Decimal("0.5")` в `pricing.py`; `C = quantize_money(P * cap)`, `D = min(to_money(value), P, C)`. Альтернатива «30 %» отвергнута как устаревшая.

2. **`max_discount`** применяется после округления процента: `D = min(quantize_money(P * value / 100), to_money(max_discount))`. Лишней проверки «не более двух знаков» не добавляем: в тикете для поля заданы лишь вид и `> 0`.

3. **`FREE_SHIPPING`** обрабатывается в `calculate_total`: скидка на товары 0, раскладка пропускается. Стоимость доставки сначала считается обычной политикой по `subtotal` (до скидки), затем при `FREE_SHIPPING` `shipping = ZERO`, `shipping_discount = обычная стоимость`. Так «экономить нечего» (порог, только сертификаты, нулевая цена) естественно даёт `0.00`. Условия заказа (участвующие строки, `min_order_amount`) проверяются общим кодом до ветвления по виду — единое поведение для всех видов.

4. **Порог доставки** считается от `subtotal` (до скидки): в `calculate_total` в `shipping.cost_for` передаётся `subtotal`. Сигнатура `ShippingPolicy.cost_for` не меняется. Обновить docstring модуля и README (правило «бесплатно от 3000.00 по сумме товаров»).

5. **Ничья остатков в `_split_discount`:** ключ сортировки `(-remainders[i], -amounts_kopecks[i], i)`. Остатки сравниваются в целых копейках с общим знаменателем, поэтому сравнение точное. Равные суммы дают прежнее поведение (раньше в корзине).

6. **Клиентские счётчики** в реестре — `dict[str, dict[str, int]]` (код → клиент → число); `record_use(code, customer_id=None)` и `release_use(code, customer_id=None)` получают необязательный аргумент (методы вне API тикета). `uses(code, customer_id=None)` возвращает общий или клиентский счётчик (`0`, если клиента нет). Клиентский счётчик ведётся для любого заказа с `customer_id`. `resolve` после существующих проверок (1–3) делает проверку (4): при заданном `max_uses_per_customer` — `customer_id is None` или `uses >= лимит` → `PromoConditionsError`. Проверка типа `customer_id` (`str | None`, иначе `ValidationError`) выполняется в начале `resolve`/`uses` и в `quote`/`place_order`; ключ используется как есть, без `normalize_key`.

7. **Окно возврата при отмене.** `OrderService.cancel`: `now = self._clock.now()`; возврат, если `now - order.created_at < timedelta(hours=24)`. Строгое `<` реализует полуоткрытый интервал: ровно 24 часа — уже сгорело. Если часы ушли назад (`now < created_at`), разность отрицательна — считаем «в пределах окна». Статус заказа меняется на `CANCELLED` в любом случае; `release_use` вызывается только внутри окна и с `order.customer_id`.

8. **`Order.customer_id`** — новое поле `str | None = None` в конец dataclass; сохраняется всегда, даже без промокода. `_resolve_promo` получает `customer_id` и передаёт его в `resolve`. Валидация типа `customer_id` идёт до проверки пустой корзины, как и для нестрокового `promo_code`.

9. **Инварианты `PromoCode`** добавляются в `__post_init__`: `FREE_SHIPPING` — `value == 0` (после общей проверки на конечный `Decimal`); `max_discount` — только `PERCENT`, конечный `Decimal`, `> 0`; `max_uses_per_customer` — `int` не `bool`, `>= 1`. Существующие ветки `PERCENT`/`FIXED` перестраиваются на `elif`, чтобы `FREE_SHIPPING` не попадал в проверку «fixed».

10. **Два старых теста** (`test_free_shipping_threshold_after_discount`, `test_cancel_after_expiry`) фиксируют отменяемые правила и по определению противоречат тикету. Они обновляются минимально, остальные существующие тесты остаются как есть. Альтернатива «оставить красными» отвергнута: набор должен быть зелёным.

## Risks / Trade-offs

- [Тикет и поправка расходятся по потолку (30 % против 50 %)] → следуем более поздней поправке маркетинга; значение вынесено в одну константу, смена тривиальна.
- [Поведенческие изменения старых вызовов: порог доставки, потолок фиксированной скидки, сгорание использования] → ожидаемы по тикету; закрыты тестами с граничными значениями (ровно порог, ровно 24 часа, 23:59:59).
- [Клиентский счётчик растёт и без `max_uses_per_customer`] → лёгкая память, зато лимит, добавленный позже, и `uses(code, customer_id)` консистентны.
- [Пустая строка как `customer_id` считается обычным идентификатором] → тикет требует сравнивать как есть; отсутствием считается только `None`.

## Migration Plan

Хранилище in-memory, миграций нет. Выкатка одним релизом; откат — возврат коммита. Закрепить в README новый порог доставки.


## Решения при реализации

- Третий устаревший тест: `test_percent_rounding_and_fixed_cap` закреплял `FIXED 500` на 300.00 → скидка 300.00, что прямо противоречит сценарию спецификации «Фиксированная скидка больше суммы» (150.00). Его вторая половина обновлена (скидка 150.00, налог 30.00), помимо двух тестов из решения 10.
- `release_use(code, customer_id)` уменьшает общий счётчик всегда, а клиентский — при заданном `customer_id`; новые тесты лежат в `tests/test_autumn_promo.py`.
- Сверка публичного API с proposal/specs: расхождений нет (`DiscountKind.FREE_SHIPPING`, поля `PromoCode` в конце, `customer_id` только именованный, `OrderTotal.shipping_discount`, `Order.customer_id`). `shop/cli.py` и `shop/reports.py` не изменены.
