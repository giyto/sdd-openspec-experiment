## Why

Итоги летней кампании (SHOP-447): фиксированные коды брали на мелкие заказы, а возврат использования при отмене позволял гонять один лимитированный код по кругу. Для осенней кампании маркетингу нужны потолок процентной скидки, лимит на клиента и промокод на бесплатную доставку.

## What Changes

Правки действующих правил:

- Порог бесплатной доставки снова сравнивается с суммой товаров **до** скидки (отмена летнего правила «после скидки»).
- Фиксированная скидка не больше **50 %** суммы участвующих товаров (в тикете было 30 %, но в обсуждении маркетинг сообщил, что с финансами согласовано 50 %; побеждает более поздняя поправка). Доля считается и округляется через `quantize_money` (`ROUND_HALF_UP`).
- Возврат использования при `cancel` — только если заказ отменён раньше чем через 24 часа после оформления; интервал полуоткрытый, ровно 24 часа — уже поздно, использование сгорает. Время — по часам сервиса заказов.
- Раскладка копеек по строкам: при равенстве отброшенных остатков лишнюю копейку получает строка с большей суммой, при равенстве и сумм — строка раньше в корзине (решение бухгалтерии из обсуждения).

Новое (публичный API дословно из задачи):

- `DiscountKind.FREE_SHIPPING`: скидки на товары нет, доставка обнуляется; `value` обязано быть `Decimal("0")`, иначе `ValidationError`. Новое поле `OrderTotal.shipping_discount: Decimal` (сэкономленная доставка; `Decimal("0.00")`, если экономить нечего или код другого вида).
- `PromoCode.max_discount: Decimal | None = None` — потолок процентной скидки; допустим только у `PERCENT`, должен быть `> 0`, иначе `ValidationError`.
- `PromoCode.max_uses_per_customer: int | None = None` — `None` без лимита, иначе `>= 1`. Новые поля добавляются в конец `PromoCode`.
- `PromoRegistry.resolve(code: str, customer_id: str | None = None) -> PromoCode` и `PromoRegistry.uses(code: str, customer_id: str | None = None) -> int` (с `customer_id` — число использований этим клиентом).
- `OrderService.quote(cart, promo_code=None, *, customer_id: str | None = None)`, `OrderService.place_order(cart, promo_code=None, *, customer_id: str | None = None)`, `Order.customer_id: str | None`. Код с лимитом на клиента без `customer_id`, как и исчерпанный клиентом лимит, даёт `PromoConditionsError`. `customer_id` сравнивается как есть (без `normalize_key`).

Допущения (автономный режим, вопросов не задавали):

- Старые тесты, закрепляющие отменяемые правила (`test_free_shipping_threshold_after_discount`, `test_cancel_after_expiry`), противоречат тикету; правила тикета приоритетнее, эти два теста на этапе apply приводятся в соответствие. Остальные существующие тесты не меняются.
- Для `FREE_SHIPPING` условия заказа (есть участвующие строки, сумма участвующих `>= min_order_amount`) проверяются так же, как для остальных видов.
- `max_discount` применяется как денежная величина: `min(D, quantize_money(max_discount))`.
- Использование, сгоревшее при поздней отмене, не возвращается ни в общий, ни в клиентский счётчик.
- `customer_id` запоминается заказом всегда, в том числе без промокода.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `promo-codes`: новые виды и поля `PromoCode` и их инварианты, `customer_id` в `resolve`/`uses`, клиентские счётчики.
- `promo-pricing`: потолок фиксированной скидки 50 %, `max_discount`, `FREE_SHIPPING` и `shipping_discount`, порог доставки до скидки, новая ничья при раскладке копеек.
- `order-promos`: `customer_id` в `quote`/`place_order`/`Order`, лимит на клиента, возврат использования только в течение 24 часов.

## Impact

- Код: `shop/promo.py`, `shop/pricing.py`, `shop/orders.py`, а также `README.md` (правило порога доставки). `shop/cli.py` и `shop/reports.py` не затрагиваются.
- Тесты: новые тесты для нового поведения; два устаревших теста обновляются (см. допущения).
- API: только расширение, старые вызовы работают, новых зависимостей нет.
- Поведенческие изменения для существующих клиентов: порог доставки, ограничение фиксированной скидки, сгорание использования при поздней отмене.
