## Context

Вся логика живёт в `Inventory`, хранение — в `InMemoryStore`, время — только из внедрённых часов, ошибки — наследники `WarehouseError`, операции атомарны (сначала проверки, потом изменения), модели — frozen-датаклассы, наружу отдаются снимки (README). Мотивация — в proposal.md, требования — в specs.

## Goals / Non-Goals

**Goals:**
- Резервы поверх физического остатка без изменения старого API и формата журнала.
- Истечение вычисляется «лениво» по часам сервиса.

**Non-Goals:**
- Фоновая очистка истёкших резервов, изменения `cli.py`/`reports.py`, персистентность, новые зависимости.

## Decisions

1. **Хранение.** Внутренняя изменяемая запись резерва (order_id, строки-кортеж, created_at, expires_at, сохранённый статус `ACTIVE/CONFIRMED/CANCELLED`) лежит в `InMemoryStore` (новые аддитивные методы: получить/положить/перечислить), чтобы состояние жило вместе с остатками. Статус `EXPIRED` не хранится, а вычисляется: хранимый `ACTIVE` и `now >= expires_at` → `EXPIRED`. Альтернатива (словарь в `Inventory`) отвергнута: при общем `store` резервы разошлись бы между экземплярами.
2. **Снимки.** `_snapshot(record, now)` строит `Reservation` с вычисленным статусом; `lines` — кортеж `ReservationLine` в исходном порядке. Внутренняя запись наружу не выдаётся.
3. **Единый расчёт.** Приватные `_effective_status(record, now)` и `_reserved(wh, sku, now)` (сумма по активным и неистёкшим записям). `available = max(0, on_hand - reserved)`. Значение `now` берётся один раз на операцию.
4. **Нормализация строк.** Строки приводятся к `ReservationLine`; проверяются код склада, SKU (`UnknownSkuError`), `qty` (`InvalidQuantityError`). Достаточность проверяется по суммам в словаре `(wh, sku) -> qty`, строки хранятся как пришли. Ошибка `InsufficientStockError(wh, sku, requested=сумма по позиции, available)`; при нескольких проблемных позициях — первая по порядку строк.
5. **Порядок проверок.** `reserve`: `order_id`, `ttl`, пустой список, строки (склад/SKU/qty), дубликат заказа, наличие. `extend`: `order_id`, `ttl`, поиск (`ReservationNotFoundError`), статус. `confirm`/`cancel`: `order_id`, поиск, статус. `ttl` проверяет общая `_validate_ttl`: `isinstance(ttl, timedelta)` и `ttl > timedelta(0)`, иначе `ValidationError`.
6. **`reserve` и замена.** Существующая запись блокирует создание, только если эффективный статус `ACTIVE` или `CONFIRMED` (`DuplicateReservationError`). Для `EXPIRED`/`CANCELLED` новая запись заменяет старую только после успешных всех проверок (атомарность).
7. **`issue`/`transfer`.** Сравнение с `available`, а не с физическим остатком; в ошибку идёт `available`. `confirm` не вызывает публичный `issue`: общий приватный помощник списывает физический остаток и пишет `ISSUE` без проверки резервов. Для `transfer` ограничение распространяется на источник (его документация: «обычный расход, проверки как у `issue`»); в тикете явно сказано только про `issue`, поэтому это допущение.
8. **`confirm`.** Не найден → `ReservationNotFoundError`; эффективный `EXPIRED` → `ReservationExpiredError`; не `ACTIVE` → `ReservationStateError`; затем сумма по позициям против физического остатка (`InsufficientStockError`, `available` в ошибке — физический остаток); только после всех проверок: списание по строкам, события `ISSUE` (порядок строк, `ref=order_id`), `RESERVE_CONFIRM`, статус `CONFIRMED`.
9. **`cancel`.** `CONFIRMED` → `ReservationStateError`; `CANCELLED` или эффективный `EXPIRED` → снимок без записи и без смены статуса; иначе `CANCELLED` + `RESERVE_CANCEL`.
10. **`extend`.** После проверок статуса: `new = now + ttl`; если `new <= expires_at` — снимок без изменений и событий; иначе обновить `expires_at` и записать `RESERVE_EXTEND`.
11. **Журнал.** Поле `expires` пишется как `format_timestamp(expires_at)` (`EventLog` принимает только `str`/`int`). Журнал усекает время до секунды, а решение об истечении принимается по полному `expires_at` — расхождение допустимо. Значения уже проверены `_validate_code`, события пишутся только после всех проверок, поэтому `append` не падает посреди операции.
12. **Ошибки.** `ReservationError(WarehouseError)` принимает `order_id` и сообщение, хранит `self.order_id`; подклассы — по тикету.
13. **Расположение кода.** Модели — `models.py`, ошибки — `errors.py`, `DEFAULT_RESERVATION_TTL` и чистые помощники (нормализация строк, `_validate_ttl`, вычисление статуса) — `reservations.py`; новые имена экспортируются из `__init__.py`. `reservations.py` не импортирует `inventory.py`.

## Risks / Trade-offs

- [`reserved` сканирует все резервы, O(n)] → для хранилища в памяти приемлемо; при необходимости добавить индекс по позиции.
- [Истёкшие записи копятся в памяти] → намеренно (нет фоновых задач, нужны для `get_reservation`); очистка вне рамок.
- [`transfer` тоже ограничен `available`] → без резервов поведение не меняется; зафиксировано как допущение.
- [`ManualClock.set` может откатить время назад, и истёкший резерв снова станет активным] → следствие вычисления «по часам при обращении».

## Assumptions

- Порядок проверок при нескольких нарушениях сразу (решение 5) в тикете не задан и выбран здесь.
- `available`/`reserved` для незарегистрированного SKU бросают `UnknownSkuError` (как `on_hand`); код склада в них не валидируется (как в `on_hand`).
- Момент `expires_at` включён в истечение: `now >= expires_at`.
- TTL по умолчанию 15 минут (обновление Анны Беловой от 13.10 отменяет 30 минут из исходного текста).
- Строка резерва неверной формы (не `ReservationLine` и не кортеж из трёх элементов) даёт `ValidationError`; код SKU в строке сначала проверяется как код (`ValidationError`), затем на регистрацию (`UnknownSkuError`).
