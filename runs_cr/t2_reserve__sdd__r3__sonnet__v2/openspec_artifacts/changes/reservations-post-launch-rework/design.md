## Context

Хранилище держит по одному резерву на `order_id`; `EXPIRED` выводится из срока и не хранится; истечение в журнал не пишется. `reserve` сейчас бросает `DuplicateReservationError` для `ACTIVE`/`CONFIRMED`, `cancel` подтверждённого бросает `ReservationStateError`. Формат строки журнала менять нельзя, `cli.py`/`reports.py`/существующие тесты не трогаем.

## Goals / Non-Goals

**Goals:** реализовать пункты WH-231 с атомарностью «всё или ничего» (при ошибке ни остатков, ни журнала не меняется).

**Non-Goals:** фоновые процессы, изменение статусов/остатков в `sweep_expired`, история резервов, правки CLI и отчётов.

## Decisions

1. **Замена в `reserve`.** После валидации входа (включая предел `ttl`) для предыдущего `ACTIVE`-резерва проверка наличия считает `available` плюс количество предыдущего резерва по этой позиции. Только после успешной проверки предыдущий сохраняется как `CANCELLED`, пишутся `RESERVE_CANCEL` и `RESERVE` по строкам. Ошибка проверки оставляет старый резерв `ACTIVE` и журнал нетронутым. `CONFIRMED` — по-прежнему `DuplicateReservationError`. Истёкший/отменённый заменяются как раньше, без `RESERVE_CANCEL`. Новый резерв полностью новый (подтверждено в обсуждении): `created_at = now`, срок от `now`, TTL по умолчанию 20 минут.
2. **Возврат в `cancel`.** Для `CONFIRMED`: остаток растёт по каждой строке (как `receive`, без проверок достаточности), статус `CANCELLED`, события `RECEIVE` (`wh`, `sku`, `qty`, `ref` = номер заказа) по строкам в порядке строк, затем `RESERVE_CANCEL`. Повторная отмена — идемпотентный no-op, как для любого `CANCELLED`.
3. **Предел.** `MAX_RESERVATION_LIFETIME = timedelta(hours=2)` в `reservations.py`. `reserve`: `ttl > MAX` → `ValidationError` (проверка входа, до проверки наличия); `ttl == MAX` допустим. `extend`: `new = min(now + ttl, created_at + MAX)`; дальше действует прежнее правило «не сокращать» — если `new <= expires_at`, ничего не меняется и событие не пишется.
4. **`reservations(status)`** возвращает снимки с эффективным статусом, по одному на заказ, сортировка `(created_at, order_id)`; фильтр по эффективному статусу на текущий момент. Значение `status`, не являющееся `ReservationStatus`, — `ValidationError`.
5. **`availability(warehouse)`**: объединение позиций с `on_hand > 0` и позиций с активным `reserved > 0`; значения считаются теми же внутренними `_reserved`/`_available`, что и одноимённые методы; сортировка `(warehouse, sku)`, фильтр по складу как у `stock_levels` (без валидации, пустой результат для неизвестного склада). Позиция с резервом, но без остатка (после инвентаризации), входит с `on_hand=0`.
6. **`sweep_expired()`.** Кандидаты — резервы с эффективным статусом `EXPIRED`, которых нет в учёте «уже записано». Учёт — множество ключей `(order_id, created_at)` в хранилище: ключ различает резервы одного заказа, оформленные заново (требование Игоря Левина). Для каждого кандидата пишется `RESERVE_EXPIRE` (`order`, `expires`; время события — `now` сервиса), порядок — `(expires_at, order_id)`, возвращаются `order_id`. Повторный вызов без новых истечений возвращает `[]` и журнал не меняет. Статусы, остатки, `reserved`/`available` не затрагиваются.
7. **Экспорт**: `Availability`, `MAX_RESERVATION_LIFETIME` добавляются в `warehouse/__init__.py`.

## Допущения

- Лимит — **2 часа** (поздний комментарий перекрывает «1 час» в теле тикета).
- Истёкший резерв, который успели перезаписать новым `reserve` до вызова `sweep_expired`, в выдачу не попадает: хранилище держит один резерв на заказ, а `reserve` по-прежнему не пишет истечения. Планировщик должен вызывать `sweep_expired` чаще, чем заказ могут оформить заново. Историю резервов не вводим.
- Резерв, чей срок наступил, но который к моменту вызова `CONFIRMED`/`CANCELLED`, не считается истёкшим и в `sweep_expired` не попадает.
- `RESERVE_EXPIRE` пишется со временем вызова `sweep_expired`, а `expires_at` идёт в поле `expires`.
- `reservations()` и `availability()` только читают состояние.

## Risks / Trade-offs

- **Конфликт с существующими тестами.** Тесты, закрепляющие TTL 15 минут, `DuplicateReservationError` для активного резерва и `ReservationStateError` при отмене подтверждённого, противоречат новым требованиям, а тикет запрещает менять существующие тесты. План: новые тесты — в новом файле; при применении явно сообщить, какие старые тесты падают по этой причине, и не править их без решения владельца.
- `RECEIVE` от возврата попадает в `movement_summary` как обычный приход (так задано тикетом).
- Потеря незафиксированного истечения при перезаписи резерва (см. допущения).

## Решения при применении

- При замене активного резерва свободное количество считается как `max(0, on_hand - чужие_резервы)`; это совпадает с «`available` плюс количество заменяемого резерва», кроме случая, когда после инвентаризации остаток меньше резервов (там буквальная формула дала бы больше физического остатка).
- Старые тесты, падающие из-за новых договорённостей (не правились): `test_helpers`, `test_reserve_success`, `test_reserve_events`, `test_extend_never_shortens` (TTL 15 → 20 минут), `test_duplicate_active_and_confirmed` (замена активного резерва), `test_cancel_expired_and_confirmed` (возврат подтверждённого) — все в `tests/test_reservations.py`.
