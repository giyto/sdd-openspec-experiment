## Context

Резерв хранится одной записью на `order_id` (`ReservationRecord`), `EXPIRED` вычисляется лениво по часам. Новый `reserve` по заказу с истёкшим/отменённым резервом уже заменяет запись целиком. Журнал только на добавление.

## Goals / Non-Goals

**Goals:** замена активного резерва, возврат, предел срока, три новых запроса, единоразовая фиксация истечения.
**Non-Goals:** фоновые процессы, изменение статусов/остатков в `sweep_expired`, правки CLI/отчётов, история прежних резервов заказа, новые зависимости.

## Decisions

- **Замена атомарна.** Порядок: валидация, проверка статуса прежнего резерва, проверка наличия с вычетом количеств заменяемого активного резерва (при расчёте `available` прежний резерв исключается), и только после успеха — запись `RESERVE_CANCEL`, затем `RESERVE` по строкам. Любая ошибка (в т.ч. `InsufficientStockError`) оставляет прежний резерв и журнал нетронутыми. `created_at = now`, `expires_at = now + ttl`, как у обычного резерва. Прежняя запись заменяется новой; для истёкшего/отменённого прежнего резерва `RESERVE_CANCEL` не пишется.
- **Возврат.** `cancel` подтверждённого: по строкам в порядке резерва остаток увеличивается на `qty` и пишется `RECEIVE` (`wh`, `sku`, `qty`, `ref=order_id`, формат как у `receive`), затем статус `CANCELLED` и `RESERVE_CANCEL`. Дублирующиеся позиции — отдельный `RECEIVE` на строку. Повторный `cancel` — идемпотентный no-op (статус уже `CANCELLED`), повторного прихода нет.
- **Предел срока.** В `reserve` дополнительно `ttl > MAX_RESERVATION_LIFETIME` → `ValidationError` (ровно предел допустим). В `extend`: `limit = created_at + MAX`; если `ttl >= limit - now`, цель = `limit`, иначе `now + ttl` (так нет переполнения даты на огромном `ttl`). Далее действует прежнее правило «не сокращать»: если цель не позже текущего `expires_at` — без изменений и без события. `RESERVE_EXTEND` пишется с фактическим сроком. Если `now >= limit`, резерв уже истёк, действует `ReservationExpiredError`.
- **`sweep_expired`.** Выбирает записи со статусом (на сейчас) `EXPIRED`, у которых нет признака «зафиксирован». Признак — поле самой `ReservationRecord`; новый `reserve` создаёт новую запись, поэтому повторный резерв заказа, который тоже истёк, фиксируется отдельно (комментарий Игоря Левина), даже если `created_at`/`expires_at` совпали с прежним. Событие `RESERVE_EXPIRE` (`order`, `expires` в формате журнала) с временем события = текущее время часов. Порядок: `expires_at`, затем `order_id`; возвращается список `order_id`. Статусы, остатки и `expires_at` не меняются; пустой результат — пустой список без событий. Подтверждённые и отменённые резервы не фиксируются.
- **`reservations(status)`.** Снимки на текущий момент, фильтр по вычисленному статусу, сортировка `(created_at, order_id)`.
- **`availability(warehouse)`.** Объединение позиций с `on_hand > 0` (как `stock_levels`) и позиций с активным резервом; значения считаются теми же внутренними расчётами, что и `on_hand`/`reserved`/`available`; сортировка `(warehouse, sku)`; фильтр по складу как у `stock_levels` (неизвестный склад → пустой список без ошибки).
- **Тип `Availability`** — frozen dataclass в `models.py` с полями из тикета. `MAX_RESERVATION_LIFETIME` в `reservations.py`; `DEFAULT_RESERVATION_TTL` → 20 минут.

## Assumptions

- Предел — 2 часа (уточнение Ольги Смирновой от 10.11 перекрывает «один час» из текста тикета).
- «Подтверждённый заказ так заменить нельзя» — `DuplicateReservationError`, как раньше.
- Замена допустима и при совпадающих строках; `RESERVE_CANCEL` пишется всё равно.
- Резервы, истёкшие до выкладки, будут зафиксированы первым вызовом `sweep_expired` (состояние «зафиксировано» хранится в памяти, как и всё хранилище).
- Для `RESERVE_EXPIRE` время события — текущее время часов; `expires` — исходный `expires_at`.

## Risks / Open Questions

- **Конфликт с ограничением «существующие тесты не меняем».** `tests/test_reservations.py` проверяет 15 минут, ошибку на дубль активного, `ReservationStateError` при отмене подтверждённого и т.п. Эти тесты закрепляют отменённое поведение и упадут. Решение: поведение следует тикету; устаревшие проверки молча не правятся — при реализации список упавших тестов явно показать владельцу задачи; новые тесты добавлять в отдельный файл.
