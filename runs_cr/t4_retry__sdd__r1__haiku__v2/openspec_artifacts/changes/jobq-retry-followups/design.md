## Context

Решение о судьбе упавшего задания принимает `Worker._handle_failure` (`jobq/worker.py`), а переходы статусов и dead-letter
ведёт `JobQueue` (`jobq/queue.py`): `mark_dead_lettered` пишет `DeadLetterEntry`, `purge_finished` сейчас исключает
`DEAD_LETTERED`, `requeue_dead_letter` возвращает одно задание. `RetryPolicy.delay_for` (`jobq/retry.py`) сейчас
умножает задержку на `uniform(1 - jitter, 1 + jitter)`. Исключения живут в `jobq/errors.py`. Поведение описано в
`specs/job-retry` и `specs/job-dead-letter`; мотивация — в `proposal.md`.

Публичные сигнатуры менять нельзя (см. требование «Backward compatibility of the public API»), поэтому все новые
параметры добавляются как keyword-only с значениями по умолчанию.

## Goals / Non-Goals

**Goals:**
- Одно место, где решается судьба упавшего задания (`Worker._handle_failure`), с явной причиной dead-letter.
- Задержка `RetryLaterError` не зависит от `rng` и ограничена `max_delay`.
- Очистка dead-letter использует ту же дату, что и вся остальная очистка (`finished_at`/`dead_lettered_at`).

**Non-Goals:**
- Изменения `jobq/dashboard.py` и `jobq/cli.py` (явное ограничение из JOBQ-237). Они не будут показывать `reason`.
- Персистентность dead-letter: хранилище остаётся in-memory, как и раньше.
- Новые зависимости и правка существующих тестов.

## Decisions

**1. Порядок проверок в `_handle_failure`.** Неповторяемость проверяется раньше исчерпания попыток, а исчерпание
раньше `RetryLaterError`:
1) нет политики → `FAILED`; 2) `not is_retryable(exc)` → `DEAD_LETTERED/NON_RETRYABLE`; 3) `attempts >= max_attempts` →
`DEAD_LETTERED/EXHAUSTED`; 4) `RetryLaterError` → повтор с задержкой сервера; 5) иначе повтор по политике.
Так `PermanentJobError` на последней попытке получает причину `NON_RETRYABLE` (решение тимлида в JOBQ-237), а
`RetryLaterError` на последней попытке — `EXHAUSTED`.
- Альтернатива: проверять исчерпание первым. Отвергнуто: тогда причина «неповторяемая» на последней попытке потерялась бы.

**2. Причина хранится в `DeadLetterEntry.reason`, а не в статусе.** Статус остаётся `DEAD_LETTERED`, чтобы не менять
таблицу `_TRANSITIONS`, отчёты и `stats()`. Поле добавляется последним с default `EXHAUSTED`, чтобы существующие
вызовы `DeadLetterEntry(...)` работали.
- Альтернатива: отдельный статус `NON_RETRYABLE_DEAD`. Отвергнуто: ломает `stats()` и `JobStatus`, которые
  дашборд уже читает, а ticket запрещает трогать дашборд.

**3. `mark_dead_lettered(job_id, error, *, reason=DeadLetterReason.EXHAUSTED)`.** Воркер передаёт причину явно.
Keyword-only параметр с default — тот же приём, что уже принят для `default_retry_policy` и `rng` в спеке совместимости.
- Альтернатива: приватный `_dead_letter` и вызов из воркера через него. Отвергнуто: воркер тогда лезет в приватный
  метод очереди.

**4. Джиттер.** `delay_for` использует `uniform(1 - jitter, 1)`. Ограничение `max_delay` остаётся после умножения,
хотя при множителе ≤ 1 оно уже не может сработать для уже ограниченной задержки; оставляем как защиту.

**5. `RetryLaterError` — отдельная ветка, без `delay_for`.** Задержка считается в `Worker._handle_failure`:
`min(retry_after, policy.max_delay)`. Логика в `RetryPolicy` не нужна: метод `delay_for` описывает только расчёт по
политике, а `retry_after` — это данные сервера. Проверка `retry_after` (`< 0`, не число, не конечно) делается в
конструкторе `RetryLaterError`, как проверки параметров в `RetryPolicy.__post_init__`. Так ошибка конфигурации
проявляется в месте, где её написали, а не в воркере.
- Следствие: если обработчик бросит `RetryLaterError` с неверным значением, конструктор выбросит `ConfigError` внутри
  обработчика, и воркер обработает это как обычную ошибку по политике.

**6. Очистка dead-letter.** `purge_finished` убирает исключение `DEAD_LETTERED` из условия и, для таких заданий,
удаляет и запись из `_dead_letters`. Возраст берётся из `finished_at`, который у `DEAD_LETTERED` совпадает с
`dead_lettered_at` (оба выставляются в одном вызове `mark_dead_lettered`), поэтому отдельной ветки по возрасту не нужно.

**7. `requeue_all_dead_letters`.** Снимок `list(self._dead_letters.values())` берётся до начала цикла, фильтр по
`job_type`, и каждая запись проходит через `requeue_dead_letter`. Так поведение (метрики, лог, сброс полей) не
дублируется. Пустой результат — пустой список, без исключения.

## Risks / Trade-offs

- **[Риск] Задания с неповторяемыми ошибками, которые раньше были `FAILED`, теперь попадают в dead-letter и могут
  быть удалены очисткой.** → Очистка по возрасту с `older_than`, как и раньше для завершённых заданий; перед первым
  запуском очистки проверить `older_than` (отмечено в proposal.md).
- **[Риск] Очистка 40 тысяч записей выполняет линейный проход по всем заданиям.** → Это уже так для остальных статусов;
  отдельной оптимизации в этом изменении не делаем. Если понадобится, индекс по времени попадания — отдельная задача.
- **[Trade-off] Default `EXHAUSTED` у `DeadLetterEntry.reason`** скрывает ошибку, если кто-то создаёт запись вручную без
  причины. → Принято ради совместимости; воркер всегда передаёт причину явно.
- **[Trade-off] `RetryLaterError` с `retry_after = 0` повторяется сразу** и тратит попытку. → Соответствует спеке;
  защиты от «горячего цикла» нет, как и для `base_delay = 0` в текущей политике.

## Migration Plan

Миграции данных нет: хранилище in-memory. Выкат — обычный релиз пакета. Откат — возврат предыдущей версии; записи
`reason` в памяти пропадут вместе с процессом. Перед первым `purge_finished` в продакшене проверить значение
`older_than`, чтобы 40 тысяч накопленных записей не удалились неожиданно.

## Open Questions

Нет. Неоднозначности из ticket зафиксированы как решения выше: порядок проверок (1), default причины (2), keyword-only
параметр (3), валидация `RetryLaterError` в конструкторе (5).
