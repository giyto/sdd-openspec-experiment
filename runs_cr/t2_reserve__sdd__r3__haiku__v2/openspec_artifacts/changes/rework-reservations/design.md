## Context

Текущий `Inventory` (`warehouse/inventory.py`) хранит резервы в `InMemoryStore` по `order_id`, со статусом
`ACTIVE` / `CONFIRMED` / `CANCELLED`. `EXPIRED` вычисляется `_status_at(reservation, now)` при каждом обращении
и в хранилище не пишется. Каждая операция сначала проверяет всё, затем меняет состояние и пишет в `EventLog`,
время берётся один раз из часов сервиса. См. proposal.md — Why и specs/inventory/reservations/spec.md — требования.

Ограничения, которые влияют на подход:
- Фоновых задач нет. Истечение срока по-прежнему вычисляется при чтении; запись `RESERVE_EXPIRE` делает только
  `sweep_expired`, который вызывает внешний планировщик.
- Формат строки журнала не меняется; `EventLog.append` принимает только `str`/`int`/`None`.
- `cli.py` и `reports.py` не трогаем; `on_hand` и `stock_levels` остаются физическими.

## Goals / Non-Goals

**Goals:**
- Все правила из spec-дельты: замена резерва, возврат подтверждённого, TTL 20 минут, предел 2 часа,
  `reservations`, `availability`, `sweep_expired`.
- Атомарность каждой операции: проверки до изменений, затем состояние и журнал.
- Новые тесты в отдельном файле; существующие тесты, которые не противоречат новым правилам, не меняются.

**Non-Goals:**
- Фоновый планировщик внутри сервиса (его вызывает внешний планировщик).
- Персистентность, конкурентный доступ, хранение «истории» резервов по заказу (в хранилище по-прежнему один резерв на заказ).
- Изменение `adjust`, `issue`, `transfer`, `confirm` (кроме того, что `reserved`/`available` уже учитывают замену).

## Decisions

**1. Замена резерва — внутри `reserve`, без отдельного метода.**
Если по заказу есть действующий `ACTIVE`, `reserve` строит проверку доступности, исключая строки старого резерва
(`reserved` по позиции минус строки `order_id`, не ниже нуля для `available`). Если проверка проходит, пишется
`RESERVE_CANCEL` по старому резерву, затем `RESERVE` по строкам нового; новый резерв перезаписывает старый через
`put_reservation`. Альтернатива — сначала `cancel`, потом `reserve`: отвергнута, потому что при нехватке нового
состояние уже изменилось бы (старый резерв отменён), а правило «атомарность» этого не допускает.

**2. Истёкший старый резерв при замене без события.**
Если старый резерв `EXPIRED`, `reserve` работает как раньше: без `RESERVE_CANCEL` и без изменения старого.
Причина: истечение событий не порождает, а `cancel` для `EXPIRED` — no-op.

**3. Возврат подтверждённого — в `cancel`.**
`cancel` для `CONFIRMED` не выбрасывает `ReservationStateError`, а возвращает товар по строкам через внутренний
путь прихода (без повторной валидации: строки уже проверены при `reserve`). Порядок записей: `RECEIVE` на каждую
строку в порядке строк резерва, затем `RESERVE_CANCEL`. Статус `CONFIRMED` после возврата заменяется на `CANCELLED`.
`EXPIRED` для `CONFIRMED` не применяется: `CONFIRMED` окончателен и не истекает (см. spec «Подтверждённый резерв после срока»).

**4. Предел срока.**
`MAX_RESERVATION_LIFETIME = timedelta(hours=2)` в `warehouse/reservations.py` рядом с `DEFAULT_RESERVATION_TTL`
(20 минут). `reserve` проверяет `ttl > MAX` в `_validate_ttl`-цепочке до изменений. `extend` вычисляет
`min(now + ttl, created_at + MAX)`; если результат не позже текущего `expires_at`, резерв не меняется, событие
не пишется (та же логика, что раньше, только с ограничением сверху).

**5. Учёт «уже записанного» истечения для `sweep_expired`.**
`InMemoryStore` получает множество `(order_id, created_at)` записанных истечений и два метода:
`mark_expiry_reported(reservation)` и `expiry_reported(reservation) -> bool`. Ключ по `created_at` различает
резервы одного заказа. Истечение записывается только для `EXPIRED` резерва, а такой резерв заменяется
новым, созданным не раньше его `expires_at`, то есть строго позже его `created_at`. Значит `created_at` у
резервов, которые могут быть записаны как истёкшие, у одного заказа различается. Резерв, отменённый заменой
в тот же момент, `EXPIRED` не станет и в отметках не участвует. Статус в хранилище не меняется.
Альтернатива — поле `expiry_reported` в `Reservation`: отвергнуто, потому что меняет публичную модель и
`Reservation` в спецификации не описан таким полем.

**6. `sweep_expired` — два прохода.**
Сначала собираются все резервы со статусом `EXPIRED` на `now`, о которых не писали, и сортируются по
`(expires_at, order_id)`. Затем по каждому пишется `RESERVE_EXPIRE` (`order`, `expires` через `format_timestamp`)
и отметка в хранилище. Так метод не пишет частично, если сортировка или форматирование дадут ошибку.

**7. `reservations` и `availability` — только чтение.**
`reservations(status)` берёт `store.all_reservations()` (новый метод хранилища, без фильтра), строит снимки
через `_snapshot`, фильтрует по статусу на текущий момент и сортирует по `(created_at, order_id)`.
`availability(warehouse)` собирает позиции из физических остатков (`store.positions()`) и из строк действующих
`ACTIVE` резервов, считает `reserved` одним проходом по `active_reservations()` с `now < expires_at`, затем
формирует `Availability` по позициям, отсортированным как в `stock_levels`.
Модель `Availability` — `@dataclass(frozen=True)` в `warehouse/models.py`, как в ticket.

**8. Расположение кода.**
Логика остаётся в `Inventory`, как в архивном design (одна точка входа, один набор часов). Модуль
`reservations.py` содержит только константы.

**Alternatives considered:**
- Отдельный сервис для истечения (`ExpirySweeper`) с собственным хранилищем отметок: отвергнут, потому что
  это второй объект с часами и хранилищем — тот же довод, что в архивном design.

## Assumptions (решения по неоднозначностям ticket)

- **A1.** «Активный резерв» в `availability` — резерв со статусом `ACTIVE` на текущий момент (срок ещё не вышел).
- **A2.** Строка в `availability` есть, если `on_hand > 0` или `reserved > 0`.
- **A3.** Срок `ttl` равный `MAX_RESERVATION_LIFETIME` в `reserve` допустим; больше — `ValidationError`.
- **A4.** В `extend` превышение предела не ошибка (ticket), но `ttl` ≤ 0 остаётся `ValidationError`.
- **A5.** Возврат подтверждённого допускается независимо от срока `expires_at` (статус `CONFIRMED` окончателен).
- **A6.** Замена истёкшего `ACTIVE` резерва не пишет `RESERVE_CANCEL` (см. Decision 2).
- **A7.** `sweep_expired` с отметкой по `(order_id, created_at)` (см. Decision 5).

## Существующие тесты, которые фиксируют отменённые правила

В `tests/test_reservations.py` четыре проверки противоречат новым правилам и не могут остаться зелёными:

| Тест | Старое правило | Новое правило |
|---|---|---|
| `test_default_ttl_is_fifteen_minutes` | TTL 15 минут | TTL 20 минут |
| `test_reserve_default_ttl_sets_expiry` | `expires_at` = +15 минут | +20 минут |
| `test_reserve_duplicate_active_rejected` | повтор `ACTIVE` — `DuplicateReservationError` | повтор `ACTIVE` — замена |
| `test_cancel_confirmed_raises` | отмена `CONFIRMED` — `ReservationStateError` | возврат, `CANCELLED` |

Решение: эти четыре проверки меняются минимально, только под новые значения и новое поведение; остальные
существующие тесты, включая `tests/test_cli.py`, `tests/test_reports.py`, `tests/test_inventory.py`, не меняются.
Это прямое отступление от фразы ticket «существующие тесты не меняем»: буквальное выполнение сделало бы
набор красным. Если ревьюер предпочитает, чтобы старые тесты оставались нетронутыми, эти четыре можно пометить
`skip` с ссылкой на WH-231, но это решение за ревьюером.

## Risks / Trade-offs

- **[Замена меняет поведение `reserve` для существующих клиентов]** → Старый вызов с `ACTIVE` теперь не ошибка.
  Mitigation: в CLI резервов нет (`cli.py` не трогаем); покрыто тестами замены и подтверждённого.
- **[Возврат подтверждённого — необратимый приход]** → Mitigation: возврат пишет `RECEIVE` с `ref`, журнал
  показывает, что товар вернули; повторного возврата нет, так как статус становится `CANCELLED`.
- **[`sweep_expired` работает только при вызове внешним планировщиком]** → Без вызова события не появятся.
  Mitigation: метод идемпотентен, пропущенный запуск догоняется следующим вызовом.
- **[Линейный расчёт `reserved`/`availability`]** → Для in-memory сервиса на текущих объёмах допустимо, как в архивном design.
- **[Отметка в хранилище — состояние, которое не видно в `Reservation`]** → Отметка только для журнала;
  снимки и доступность от неё не зависят.

## Migration Plan

Миграции данных нет: состояние в памяти. Развёртывание — обычный релиз модуля. Откат — возврат к предыдущей
версии пакета; резервы в памяти не переживают перезапуск, поэтому откат ничего не портит. Внешний планировщик
нужно подключить отдельно, иначе `RESERVE_EXPIRE` не появятся; это вне этого change.

## Решения при реализации

- **R1. Предел TTL проверяет только `reserve`.** `_validate_ttl` остаётся проверкой «положительный `timedelta`» и используется и в `reserve`, и в `extend`. Проверка `ttl > MAX_RESERVATION_LIFETIME` стоит отдельно в `reserve` сразу после неё, до любых изменений. Так `extend` не получает ошибку на превышение предела (spec «Продление резерва»).
- **R2. Учёт своих строк при замене.** `_available` получает необязательный `exclude_order`. `reserve` передаёт `order_id`, поэтому строки старого действующего резерва не блокируют новый. Для `reservations` и `availability` действующие резервы берутся из `store.active_reservations()` с условием `now < expires_at`, как в `reserved`.
- **R3. Возврат подтверждённого.** Выделен `_refund`: приход по строкам через `set_qty` без проверок, затем `RESERVE_CANCEL` и статус `CANCELLED`. Проверка существования заказа выполняется в `cancel` до вызова.
- **R4. Тесты вне списка 8.1.** Два теста меняют поведение только из-за нового TTL по умолчанию: `test_reserve_writes_reserve_events` и `test_full_event_lines_for_reservation_lifecycle` ожидают срок 10:15. Их ожидания не менялись, в вызов `reserve` добавлен явный `ttl=timedelta(minutes=15)`. Без этого тест `lifecycle` перестаёт проверять продление: новый срок совпадает с текущим, и `RESERVE_EXTEND` не пишется.
- **R5. Переименование четырёх тестов из 8.1.** Имена соответствуют новому поведению: `test_default_ttl_is_twenty_minutes`, `test_reserve_duplicate_active_replaces`, `test_cancel_confirmed_refunds`. Старые имена содержали «fifteen», «rejected» и «raises», которые больше не верны.
- **R6. Новые тесты** лежат в `tests/test_reservations_rework.py`: сценарии spec-дельты и проверки задач 1.1, 1.2, 2.1, 3.1, 3.3, 5.1. Существующие тесты, которые не противоречат новым правилам, не менялись.
