## Why

Резервы под заказы работают месяц. Покупатели меняют корзину и оформляют возвраты, а поддержка
не видит, какие резервы истекли. Часть договорённостей первого релиза (повторный `reserve` — ошибка,
отмена подтверждённого — запрещена, TTL 15 минут без предела) больше не соответствует работе склада.
Нужно поменять эти правила и добавить чтение для дашборда поддержки и склада (WH-231).

## What Changes

- **Пересборка корзины.** `reserve` на заказ с действующим `ACTIVE` резервом заменяет его: новый резерв
  целиком, со своим `created_at` и сроком от момента замены. Товар заменяемого резерва при проверке
  наличия считается свободным. В журнале: `RESERVE_CANCEL` по старому резерву, затем `RESERVE` по строкам
  нового. Подтверждённый заказ по-прежнему нельзя заменить (`DuplicateReservationError`).
- **Возвраты.** **BREAKING**: `cancel` подтверждённого резерва (`CONFIRMED`) больше не ошибка, а возврат:
  по каждой строке пишется `RECEIVE` с `ref=<order_id>` на те же склады, затем `RESERVE_CANCEL`,
  статус становится `CANCELLED`.
- **TTL по умолчанию** — 20 минут вместо 15 (`DEFAULT_RESERVATION_TTL`).
- **Предельный срок.** Новая константа `MAX_RESERVATION_LIFETIME = timedelta(hours=2)`. `expires_at` не может
  быть позже `created_at + MAX_RESERVATION_LIFETIME`. `reserve` с `ttl` больше предела — `ValidationError`.
  `extend` сверх предела не ошибка: срок ставится ровно на предел.
- **Чтение резервов.** `Inventory.reservations(status=None)` — снимки текущих резервов по одному на заказ,
  по `created_at`, затем по `order_id`; с `status` — только резервы с этим статусом на текущий момент.
- **Доступность.** `Inventory.availability(warehouse=None)` — новая модель `Availability` (`warehouse`, `sku`,
  `on_hand`, `reserved`, `available`); строка на каждую позицию с физическим остатком или действующим
  `ACTIVE` резервом; порядок и фильтр по складу как у `stock_levels`.
- **Сигнал истечения для поддержки.** **BREAKING** для правила «истечение не пишется в журнал»:
  `Inventory.sweep_expired()` вызывается внешним планировщиком, для каждого истёкшего резерва, о котором
  ещё не писали, пишет `RESERVE_EXPIRE` (`order`, `expires`) и возвращает `order_id` в порядке `expires_at`,
  затем `order_id`. Статусы и остатки не меняются. Вычисление статуса при чтении событий по-прежнему не пишет.
  Истёкший резерв заказа, который затем заново зарезервирован и снова истёк, — отдельный резерв, пишется заново.
- Журнал: новые типы событий `RESERVE_EXPIRE`; `RECEIVE` с `ref` для возврата. Формат строки не меняется.

### Modified Capabilities
- `inventory/reservations`: замена активного резерва при повторном `reserve`, возврат подтверждённого
  через `cancel`, предельный срок резерва (`MAX_RESERVATION_LIFETIME`), `DEFAULT_RESERVATION_TTL` = 20 минут,
  новые методы `reservations`, `availability`, `sweep_expired` и событие `RESERVE_EXPIRE`.

## Impact

- Код: `warehouse/models.py` (модель `Availability`), `warehouse/reservations.py` (`DEFAULT_RESERVATION_TTL`
  = 20 минут, `MAX_RESERVATION_LIFETIME`), `warehouse/inventory.py` (`reserve`, `cancel`, `extend`, новые
  методы), `warehouse/storage.py` (отметка «истечение уже записано» для `sweep_expired`).
- Не трогаем: `warehouse/cli.py`, `warehouse/reports.py`, зависимости (только стандартная библиотека).
- Тесты: см. design.md, раздел про существующие тесты: три теста, которые фиксируют отменённые правила,
  приводятся в соответствие; остальные существующие тесты не меняются.
- API: сигнатуры существующих методов не меняются. Меняется поведение `reserve` (замена), `cancel`
  (возврат), `extend` (предел срока). `on_hand` и `stock_levels` по-прежнему физические.
