# Эксперимент 2: запрос на изменение (change request) в новой сессии

## Идея

Эксперимент 1 показал: одиночную задачу по тикету агент решает почти идеально в обоих условиях.
Главное обещание SDD — намерение не теряется между сессиями. Эксперимент 2 моделирует жизненный цикл:

1. Сессия(и) этапа 1: агент реализовал исходный тикет (`ticket.md`). Это уже сделано в эксперименте 1,
   у каждого прогона есть своё итоговое состояние репозитория.
2. Через какое-то время **новая сессия без памяти** получает запрос на изменение (`cr_ticket.md`).
   - baseline: у агента есть только код (и то, что он сам оставил: тесты, комментарии);
   - sdd: у агента есть ещё и спецификации OpenSpec из этапа 1 (change заархивирован в основные specs),
     и он проходит propose → apply для нового change.
3. Оцениваем: (а) выполнены ли новые требования CR; (б) сохранены ли требования этапа 1,
   которые CR не менял (включая те, что в этапе 1 шли из обсуждения и соглашений repo).

## Что подготовить в каталоге задачи `experiment/tasks/<task_id>/`

```
cr_ticket.md            запрос на изменение, в стиле тикета v2
reference_cr/           копия reference/ с применённым CR (эталон этапа 2)
hidden_tests_cr/
  conftest.py           (если нужен)
  test_hidden_cr.py     скрытые тесты CR: test_C<NN>_<коротко>
cr_requirements.json    [{"id": "C01", "text": ..., "kind": "changed|new|interaction|constraint", "source": ..., "where": ...}]
cr_meta.json            {"invalidated_stage1_tests": ["test_R07_...", ...], "protected_paths": [...]}
NOTES.md                раздел «CR»: что меняется и какие ловушки
```

## Требования к `cr_ticket.md`

- Стиль как у тикета v2: тело 250–450 слов и «Обсуждение в задаче» из 3–6 реплик.
  Минимум одна явная поправка в обсуждении.
- 8–10 проверяемых требований CR:
  - 3–4 **меняют** правила этапа 1 (`changed`). Формулируй в бизнес-терминах и ссылайся на прежнее
    поведение так, как это сделал бы человек: «раньше договорились, что…, теперь…». Не указывай,
    в каком файле или функции это реализовано;
  - 3–4 **новых** правила (`new`), для которых нужен новый публичный API или поле. Весь новый API
    назван явно, как в v2;
  - 2–3 правила **взаимодействия** (`interaction`): новое правило должно корректно сочетаться
    со старыми правилами этапа 1, которые CR не меняет и которые тикет CR не повторяет
    (например, новая скидка тоже не распространяется на сертификаты, новое событие пишется в журнал
    в прежнем формате, новый статус тоже учитывается в отчёте).
- CR не пересказывает правила этапа 1. Предполагается, что они уже реализованы.
- Ограничения рамок как в этапе 1 (те же защищённые файлы плюс, если нужно, новые).
- Всё проверяемое должно однозначно выводиться из `cr_ticket.md` плюс требований этапа 1
  (которые агент видит в коде, а в условии sdd ещё и в specs).

## Требования к тестам

- `hidden_tests_cr/test_hidden_cr.py`: 2–4 теста на каждое требование `C<NN>`, через публичный API.
- `cr_meta.json.invalidated_stage1_tests`: точный список имён тестов из `hidden_tests/test_hidden.py`,
  которые после CR **перестают** быть верными (проверяют изменённое поведение). Все остальные
  тесты этапа 1 должны проходить на `reference_cr/`: это проверка «старое не сломано».
- Проверка обязательна:
  - `reference_cr/`: 100 % `hidden_tests_cr` и 100 % тестов этапа 1, кроме invalidated; проектные тесты проходят;
  - `reference/` (эталон этапа 1, без CR): тесты CR в основном падают, кроме тех, что проверяют
    сохранение старых правил в новом контексте (это допустимо).
- Запуск: скопировать тесты в `tests_hidden_cr/` (и `tests_hidden/`) внутри копии проекта,
  `python -m pytest -q` (без `-I`).

## Не делать

- Не трогай `repo/`, `reference/`, `hidden_tests/`, `ticket.md`: на них уже идут прогоны эксперимента 1.
- Не упоминай OpenSpec, спецификации, скрытые тесты и эксперимент в `cr_ticket.md`.

## Отчёт

Число требований по видам, число тестов CR, список invalidated, результаты проверки на `reference_cr`
и `reference`, короткий список ловушек.
