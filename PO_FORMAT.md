# Эксперимент 3: согласование с владельцем продукта (неполная постановка)

## Идея

В экспериментах 1–2 вся информация для правильного решения была доступна агенту (тикет, обсуждение,
код). В реальной работе часть решений знает только заказчик или владелец продукта (PO), и в тикете их
нет. Главное обещание SDD: спецификация делает допущения агента явными **до кода**, PO может их
дёшево поправить.

Оба условия получают **ровно один раунд** обратной связи от одного и того же PO (его играет модель
со списком решений):
- **sdd_po:** propose → PO читает спецификацию и комментирует → apply с учётом комментариев;
- **base_po:** агент реализует и в конце пишет отчёт «что сделано и какие допущения принял» →
  PO читает отчёт и комментирует → агент исправляет код.

PO комментирует только то, что явно написано в документе. О том, чего в документе нет, он не пишет.

## Что подготовить в каталоге задачи `experiment/tasks/<task_id>/`

```
ticket_po.md       копия ticket.md (v2), из которой УБРАНЫ 4–5 решений
po_decisions.md    решения, которые знает только PO: короткие пункты с id D1..D5
po_meta.json       {"decisions": [{"id": "D1", "text": "...", "requirements": ["R06"],
                                   "tests": ["test_R06_...", ...]}]}
```

Код, эталон и скрытые тесты **не меняются**: используются `repo/`, `reference/`, `hidden_tests/`
этапа 1. Ничего в них не трогай.

## Как выбирать убираемые решения

- Выбери 4–5 поведений, которые проверяют скрытые тесты и которые в v2 шли из тела или обсуждения
  (не из repo: соглашения проекта остаются видимыми в коде).
- Убери их из `ticket_po.md` так, чтобы:
  - у агента осталась **правдоподобная развилка** с минимум двумя разумными вариантами
    (например, граница включительно или нет; обнулять или сохранять; FAILED или dead-letter);
  - правильный вариант **не выводился** из оставшегося текста и кода. Если эталон — «очевидный по
    умолчанию» вариант, такое решение не подходит: выбери другое;
  - тикет остался естественным: убери реплику из обсуждения или фразу из тела, а не оставляй дыру.
    Можно заменить на нейтральное «детали уточним» или вообще ничего не говорить.
- Каждое убранное решение — в `po_decisions.md` простым языком заказчика, без терминов кода, если
  они не нужны. Пример: «D2. Если на складе ровно столько, сколько зарезервировано, новый резерв не
  проходит».
- В `po_meta.json` — точный список тестов из `hidden_tests/test_hidden.py`, которые зависят от
  каждого решения.

## Проверка

- Пройди по `ticket_po.md` глазами агента: для каждого Dn убедись, что из текста и repo нельзя
  однозначно вывести ответ, а развилка естественная.
- Убедись, что все остальные требования по-прежнему выводимы (ты убрал только Dn).
- Отчёт: список Dn с вариантами развилки, какие тесты зависят от каждого, число слов в ticket_po.md.
