## Context

Текущий `Inventory` (`warehouse/inventory.py`) хранит только физические остатки в `InMemoryStore`
и пишет события в `EventLog`. Все операции следуют одному шаблону: сначала проверки, затем изменения
состояния и запись в журнал. Время берётся только из внедрённых часов. См. proposal.md — Why и
specs/inventory/reservations/spec.md — требования.

Ограничения, которые влияют на подход:
- Фоновых задач нет, поэтому статус `EXPIRED` вычисляется при каждом обращении из `expires_at` и текущего времени.
- Формат строки журнала менять нельзя; `EventLog.append` принимает только `str`/`int`/`None` и не принимает `datetime`.
- `cli.py` и `reports.py` не трогаем, `stock_levels` и `on_hand` остаются физическими.

## Goals / Non-Goals

**Goals:**
- Резерв, подтверждение, отмена, продление и расчёт доступного количества по требованиям спецификации.
- Атомарность каждой операции: либо всё, либо ничего (состояние и журнал).
- Существующие тесты проходят без изменений.

**Non-Goals:**
- Фоновое освобождение истёкших резервов и запись `EXPIRED` в журнал.
- Персистентность и конкурентный доступ (сервис однопоточный, в памяти, как и остальной код).
- Изменение `adjust`: инвентаризация остаётся фактом без проверок (см. Decisions).
- Склейка строк резерва с одинаковой позицией.

## Decisions

**1. Хранение резервов в `InMemoryStore`, по `order_id`.**
Резерв хранится как frozen `Reservation` со *сохранённым* статусом (`ACTIVE`, `CONFIRMED`, `CANCELLED`).
`EXPIRED` в хранилище не записывается, а вычисляется в `Inventory` как
`ACTIVE` и `now >= expires_at`. Обновления делаются через `dataclasses.replace`.
Альтернатива — писать `EXPIRED` при обращении: отвергнуто, потому что ведёт к записи состояния
в запросах (`get_reservation`) и к скрытым изменениям при чтении.

**2. Один момент времени на операцию.**
Каждый публичный метод берёт `now = self._clock.now()` один раз и использует его для всех проверок
и для `created_at`/`expires_at`. Так исключается расхождение между проверкой и записью.

**3. Границы срока.**
Резерв действует, пока `now < expires_at`. Совпадение с `expires_at` уже означает истечение
(это совпадает с формулировкой «в момент `expires_at` резерв уже не действует»).

**4. Доступность и физический остаток — разные проверки.**
- `reserve` и `issue`/`transfer` проверяют по `available` (физический остаток минус `reserved`).
- `confirm` проверяет только физический остаток по сумме строк позиции: собственный резерв заказа
  не должен мешать подтверждению (требование Анны и Игоря о нулевом `available`).
- `available` возвращает `max(0, on_hand - reserved)`, чтобы инвентаризация ниже резерва не давала минус.

**5. `issue` и `transfer` учитывают резервы.**
Docstring `transfer` уже говорит, что для источника проверки те же, что у `issue`. Поэтому обе операции
используют общий путь проверки по доступному количеству. `adjust` не проверяет ничего (как и раньше),
поэтому после инвентаризации ниже резерва `available` будет 0, а подтверждение упрётся
в `InsufficientStockError` по физике.

**6. Проверки до изменений, затем запись в журнал.**
`confirm` сначала проверяет все позиции по физическому остатку, затем списывает через внутренний путь
без повторной проверки и пишет `ISSUE` по строкам в порядке строк резерва, затем `RESERVE_CONFIRM`.
Так ошибка по любой позиции не оставляет частичного списания.

**7. Формат времени в событиях.**
`EventLog` не принимает `datetime`, поэтому поле `expires` передаётся как
`format_timestamp(expires_at)` из `events.py`. Это тот же формат, что у времени события.

**8. Нормализация строк.**
`lines` материализуется в tuple один раз (это `Iterable`), каждый элемент приводится к
`ReservationLine` (кортеж из трёх значений тоже принимается). Неверная форма элемента — `ValidationError`.
Строки хранятся без склейки, в исходном порядке.

**9. Иерархия ошибок.**
`ReservationError(WarehouseError)` принимает `order_id` и сохраняет его атрибутом; все наследники
создаются с ним же. `ReservationStateError` получает текущий статус в сообщении для диагностики.

**10. Расположение кода.**
Константа `DEFAULT_RESERVATION_TTL` — в `warehouse/reservations.py`, где она и указана в задаче.
Логика остаётся в `Inventory`, чтобы не появлялся второй сервис с часами и хранилищем.
Модуль `reservations.py` содержит только константу (и при необходимости хелперы статуса).

**Alternatives considered:**
- Отдельный класс `ReservationService` с собственным хранилищем: отвергнут, так как ломает правило
  «одна точка входа в `Inventory`» и требует согласования журнала и остатков между двумя объектами.

## Risks / Trade-offs

- **Расчёт `reserved` линейный по числу резервов.** → Для in-memory сервиса на текущих объёмах допустимо;
  при росте можно индексировать по позиции.
- **Инвентаризация ниже резерва** оставляет `available` = 0 и позволяет физическому остатку быть меньше
  суммы резервов. → Это ожидаемо по требованию Игоря; подтверждение защищено проверкой физики.
- **Изменение поведения `issue`/`transfer`** (BREAKING относительно неограниченного расхода). → Без резервов
  результат тот же (`available` = `on_hand`); покрыто тестом в specs (сценарий «Расход без резервов»).
- **Граница срока** `now >= expires_at` — однажды выбранное правило. → Зафиксировано в spec-сценарии «Граница срока».

## Решения при реализации

Спецификация оставила эти точки открытыми; выбрано следующее.

- **Сигнатура `extend(order_id, ttl)`**: `ttl` обязателен, как в спецификации. Значение по умолчанию
  есть только у `reserve`.
- **Аргументы ошибок резервов**: первым аргументом идёт `order_id`. `ReservationStateError(order_id, status)`
  получает статус строкой (`"CONFIRMED"` и т.п.) и кладёт его в сообщение и атрибут `status`.
- **Момент времени в `issue`/`transfer`**: `now` берётся один раз до проверки и используется и для проверки
  доступного, и для записи в журнал.
- **Снимки резервов**: `get_reservation`, `cancel` (no-op) и `extend` (no-op) возвращают снимок
  с вычисленным статусом; в хранилище записывается только то, что реально меняется.
- **Продление без сокращения**: если `now + ttl` не позже `expires_at`, возвращается текущий резерв и не пишется событие.
- **Входная форма строк**: принимаются `ReservationLine` и тройки `(warehouse, sku, qty)`; пустой набор строк
  и прочая форма дают `ValidationError` до любых изменений.
- **Коды заказа**: `order_id` проверяется как остальные коды (`_validate_code`), потому что попадает в журнал.
- **Реализация `reserve` с истёкшим резервом**: при замене старый резерв перезаписывается новым в хранилище
  (`put_reservation`); отдельного шага удаления нет.

## Migration Plan

Миграции данных нет: состояние в памяти. Развёртывание — обычный релиз модуля. Откат — возврат к предыдущей
версии пакета; резервы в памяти не переживают перезапуск, поэтому откат ничего не портит.
