## Context

Затронуты `shop/errors.py`, `shop/pricing.py`, `shop/orders.py` и новый `shop/promo.py` (мотивация — в proposal.md, требования — в specs). Соглашения README, которые определяют решения: деньги только `Decimal` с `quantize_money` (`ROUND_HALF_UP`); время только через `Clock`; модели — `frozen dataclass` с инвариантами в `__post_init__`; вводимые людьми коды регистронезависимы (`normalize_key`), дубликаты — `ValidationError`; интервалы `[начало, конец)`; сертификаты не участвуют в скидках; порядок строк корзины — порядок чека.

Зависимости модулей: `promo` импортирует `catalog` (`Category`, `normalize_key`), `clock`, `errors`, `money`; `pricing` импортирует `promo`; `orders` импортирует `promo` и `pricing`. Обратных импортов (`promo` → `pricing`) быть не должно.

## Goals / Non-Goals

**Goals:**
- Публичный API ровно как в тикете, обратно совместимо: все новые параметры и поля необязательные/со значениями по умолчанию.
- Расчёт скидки — чистая функция внутри `pricing`; состояние (счётчики) — только в реестре.

**Non-Goals:**
- Скидки в `shop/cli.py` и `shop/reports.py`, комбинирование нескольких кодов, хранение реестра между запусками, потокобезопасность (существующие `OrderStore` и корзина тоже не потокобезопасны).

## Decisions

1. **Границы ответственности.** Реестр отвечает за существование, срок и лимит; `calculate_total` — только за условия заказа (минимальная сумма, наличие участвующих строк). `OrderService` вызывает `resolve`, затем `calculate_total(promo=...)`. Альтернатива (проверять всё в одном месте) отвергнута: тикет явно делит ответственность.

2. **Нормализация.** `PromoCode.__post_init__` приводит `code` через `normalize_key` (`object.__setattr__`, как в `Product`); реестр нормализует и ключ при `add`, и аргумент при `resolve`/`uses`. Пустой код после нормализации — `ValidationError`; `resolve("")` — `UnknownPromoCodeError` (пустого ключа в реестре быть не может). В сервисе пустой/пробельный код отсекается до реестра (`None`-эквивалент); нестроковый — `ValidationError` из `normalize_key`.

3. **Счётчик использований.** Хранится в реестре (`dict[str, int]`). Помимо `add/resolve/uses` реестр получает два дополнительных метода: `record_use(code)` (+1) и `release_use(code)` (−1, не ниже 0). Они не меняют заданный API, а лишь дополняют его. `place_order` вызывает `record_use` последним — после успешного расчёта и перед/сразу после `store.add`; всё, что может выбросить исключение, выполняется раньше, поэтому неудачные попытки не расходуют лимит. Альтернатива «резервировать в `resolve`» отвергнута: `quote` не должен менять счётчик.

4. **Отмена.** `cancel` сначала проверяет статус и сохраняет отменённый заказ, затем вызывает `release_use(order.promo_code)`, если у заказа есть код и у сервиса есть реестр. Код не перепроверяется на срок/лимит. Повторная отмена падает на проверке статуса до изменения счётчика.

5. **Алгоритм скидки.** Работаем в целых копейках для точности: `P` — сумма участвующих строк. `PERCENT`: `D = quantize_money(P * value / 100)`; `FIXED`: `D = min(to_money(value), P)`. Раскладка: для каждой участвующей строки `num = D_коп × amount_коп`, `floor = num // P_коп`, `rem = num % P_коп`; остаток копеек `left = D_коп − Σfloor` (0 ≤ left < числа строк) раздаётся по одной строкам, отсортированным по `(−rem, индекс строки в корзине)`. Альтернатива с `Decimal`-делением и `ROUND_DOWN` отвергнута из-за зависимости от точности контекста.

6. **Порядок проверок в `calculate_total`.** Пустая корзина → `EmptyCartError`; затем, если задан `promo`, вычисляется множество участвующих строк и проверяются условия (`PromoConditionsError`); затем скидка, налог (`tax_for(category, amount - discount)`), доставка по `subtotal - discount`, итог. `OrderTotal.discount` — сумма построчных скидок (равна `D`).

7. **Новые поля.** `LineTotal.discount: Decimal = ZERO` добавляется в конец dataclass, `OrderTotal.discount: Decimal = ZERO` — тоже в конец, чтобы позиционное создание объектов в чужом коде не сломалось. `LineTotal.amount` остаётся суммой до скидки.

8. **Заказ.** `Order.promo_code: str | None = None` добавляется последним полем. Хранится нормализованный код, взятый из `PromoCode.code`.

9. **Ошибки.** Три наследника `PromoError` объявляются независимо (каждый напрямую от `PromoError`); без собственных `__init__`, обычное сообщение.

10. **Логирование.** `logger = logging.getLogger(__name__)` в `promo.py`; на `record_use`/`release_use` — `logger.info/debug`, без `print`.

## Допущения (в тикете не определено)

- Пустая корзина с промокодом: `EmptyCartError` приоритетнее ошибок кода.
- `uses()` для незарегистрированного кода: `UnknownPromoCodeError` (согласованно с `resolve`), а не `0`.
- `PromoCode.value` для `FIXED` — не более двух знаков; для `PERCENT` дробные проценты допустимы (например, `12.5`). `min_order_amount` — неотрицательная, не более двух знаков.
- Скидка, округлившаяся до `0.00`, всё равно считается применённой, заказ с таким кодом расходует лимит.
- `excluded_categories` может содержать `GIFT_CARD`; это ничего не меняет, сертификаты не участвуют всегда.
- Сумма товаров для порога бесплатной доставки включает сертификаты, как и раньше (`subtotal`), минус скидка.
- `cancel` у заказа с кодом в сервисе без реестра не меняет счётчиков и не падает.
- Время в `OrderService` (`created_at`) остаётся на его собственных часах; срок промокода проверяется часами реестра.

## Risks / Trade-offs

- [Реестр и сервис используют разные часы] → в документации к конструкторам рекомендовать передавать один `Clock`; тесты используют один `FixedClock`.
- [Гонка «проверил лимит — записал использование» при многопоточности] → вне рамок; `resolve` и `record_use` вызываются подряд в одном потоке, остаточный риск зафиксирован как non-goal.
- [`reports.py` показывает `amount` без скидок] → суммы `total/tax` корректны; показ скидок отдельным тикетом.
- [Остатки раскладки] → покрыть свойством `Σ line.discount == discount` на наборах из многих строк.

## Решения при реализации

- Пустая корзина с промокодом: `OrderService._resolve_promo` пропускает `resolve` для пустой корзины, чтобы `EmptyCartError` (из `calculate_total`) предшествовал ошибкам кода, как в спецификации `order-promos`. Нестроковый `promo_code` даёт `ValidationError` и для пустой корзины.
- `record_use` вызывается сразу после `store.add`; всё, что может выбросить исключение, выполняется до этого.
- Сверка публичного API (задача 5.2) с proposal и specs: расхождений нет. Дополнительно к API тикета реестр имеет `record_use`/`release_use` (предусмотрено в design). `shop/cli.py`, `shop/reports.py` и существующие тесты не изменены; полный `pytest` — 99 тестов зелёные.
