## Context

Текущий расчёт (`shop/pricing.py`) строит `LineTotal` из `CartLine.amount`, считает налог по строкам и
доставку от суммы товаров; `OrderService` (`shop/orders.py`) вызывает `calculate_total` и хранит `Order`
в `OrderStore`. Заказы и реестры in-memory. README задаёт соглашения: деньги только `Decimal` с
`quantize_money` (`ROUND_HALF_UP`), ошибки наследуют `ShopError`, время только через `Clock`, коды людей
нормализуются через `normalize_key`, интервалы полуоткрытые, модели — frozen dataclass с проверками в
`__post_init__`. Поведение см. в `specs/promo-codes/spec.md`, мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Одна точка расчёта скидки (`pricing`), которая даёт и итоги, и построчную раскладку, сумма строк
  совпадает с общей скидкой до копейки.
- Проверки кода (существование → срок → лимит) в реестре, условия заказа — в расчёте.
- Существующие вызовы и суммы не меняются.

**Non-Goals:**
- Персистентность реестра, кодов и счётчиков (всё in-memory, как `OrderStore`).
- Скидки в CLI и отчётах (отдельный тикет), изменения `shop/cli.py`, `shop/reports.py`.
- Комбинирование нескольких промокодов на один заказ.
- Потокобезопасность (библиотека однопоточная, как и остальной код).

## Decisions

**1. Раскладка скидки — целочисленная, в копейках.** Общая скидка `D` и сумма участвующих строк `S`
переводятся в копейки. Для строки `i` с суммой `a_i`: `base_i = (D·a_i) // S`, `rem_i = (D·a_i) % S`.
Остаток `R = D − Σ base_i` (всегда `0 ≤ R < n`) раздаётся по одной копейке строкам с наибольшим `rem_i`,
при равенстве — по порядку корзины. Альтернатива «доля в Decimal + ROUND_DOWN» отвергнута: остаток
надо сравнивать по точным дробям, а целочисленная арифметика делает это точно и без float.

**2. Общая скидка.** Процент: `quantize_money(S · value / 100)`. Фиксированная: `min(value, S)`.
Ограничение «не больше `S`» выполняется и для процента (при 100 % скидка = `S`).

**3. Где какие проверки.**
- `PromoRegistry.resolve(code)`: нормализация → существование (`UnknownPromoCodeError`) → срок по
  `Clock.now()` (`PromoExpiredError`) → лимит `uses < max_uses` (`PromoConditionsError`).
- `calculate_total(..., promo=...)`: участвующие строки есть, `S ≥ min_order_amount`
  (`PromoConditionsError`). Срок и лимит здесь не проверяются, как требует тикет.
- Порядок в `OrderService.quote`: сначала `resolve`, потом `calculate_total`, поэтому порядок ошибок совпадает
  с требуемым.

**4. Модель данных.** `LineTotal.amount` остаётся суммой строки **до** скидки, добавляется
`discount` (по умолчанию `0.00`); налог строки считается от `amount − discount`. `OrderTotal.subtotal` —
сумма до скидки, `OrderTotal.discount` — общая скидка, `total = subtotal − discount + shipping + tax`.
Новые поля добавляются в конец dataclass с значениями по умолчанию, поэтому позиционные вызовы не ломаются.

**5. Учёт использований — явные методы реестра.** Счётчик меняют только `OrderService`: `place_order`
вызывает `registry.record_use(code)` после успешного расчёта и до создания заказа; `cancel` вызывает
`registry.release_use(code)`, если у заказа есть промокод. Альтернатива — считать использования по
сохранённым заказам — отвергнута: `uses()` должен работать и без заказов, а отменённые заказы надо
исключать. `place_order` сначала считает итог (здесь могут быть все ошибки), затем учитывает использование,
затем генерирует id и сохраняет заказ, поэтому неудачные попытки не расходуют ни лимит, ни номер заказа.
Публичный API тикета дополняется двумя методами; это расширение, а не изменение существующих.

**6. Нормализация ввода.** `PromoCode.code` нормализуется через `normalize_key` в `__post_init__`
(как `Product.sku`). В `OrderService` пустой или пробельный `promo_code` (и `None`) сразу превращается в
«без промокода», остальное передаётся в `resolve`. Для `resolve("")` результат — `UnknownPromoCodeError`.

**7. Время.** Все даты в `PromoCode` — aware, проверка в `__post_init__` (`ValidationError`). Интервал
`[starts_at, expires_at)`: `now < starts_at` или `now >= expires_at` → `PromoExpiredError`.

**8. Доставка.** `ShippingPolicy.cost_for` получает сумму товаров после скидки (`subtotal − discount`).
Сама стоимость доставки и её налог не меняются.

**9. Ошибки.** `PromoError(ShopError)` и три независимых подкласса, без общих промежуточных классов,
чтобы `except PromoExpiredError` не ловил другие ошибки.

## Risks / Trade-offs

- **Допущение: счётчик не отрицательный.** Если `release_use` вызовут для кода с нулевым счётчиком
  (например, после ручного сброса), значение остаётся `0`. → Защита в `release_use`.
- **Допущение: `uses(code)` для неизвестного кода — `UnknownPromoCodeError`.** Тикет не задаёт поведение;
  так `uses` ведёт себя как `resolve`. Альтернатива — `0` — скрыла бы опечатку.
- **Допущение: `max_uses` и `min_order_amount` проверяются по строгим правилам из тикета** (`>=` для минимальной
  суммы, `uses < max_uses`), без скрытых допусков.
- **Допущение: нулевой процент/фиксированная сумма — ошибка валидации.** Тикет задаёт диапазоны явно,
  поэтому `PERCENT 0` и `FIXED 0` отклоняются при создании.
- **Допущение: нормализация только `strip` и `upper`** (как в README). Невидимые символы (например,
  нулевой пробел) не удаляются, поэтому такой код будет неизвестным. Это соответствует README; если
  поддержка захочет шире, это отдельное решение.
- **Риск: регрессия суммы без промокода.** → Существующие тесты не меняются и должны проходить без
  изменений; новые тесты проверяют равенство `discount == 0` и совпадение итогов.
- **Trade-off: `OrderTotal.discount` и `LineTotal.discount` — дублирование итога.** Оно нужно для
  построчного чека и для проверки «сумма строк = общая скидка» в тестах.
- **Риск: `place_order` при сбое после учёта использования.** В in-memory реализации сбоев между
  `record_use` и `store.add` нет; если появится внешнее хранилище, учёт и сохранение заказа надо
  делать транзакционно (вне рамок этой задачи).

## Migration Plan

Миграции нет: всё in-memory, новые поля имеют значения по умолчанию. Откат — удалить новые файлы и
вернуть изменённые модули (`git revert`). Существующие тесты остаются зелёными на каждом шаге.

## Решения при реализации

Уточнения, которых не было в спецификации и тикете. Они не меняют поведение из `specs/`.

- **`PromoRegistry.record_use` повторно вызывает `resolve`.** Учёт использования проверяет срок и
  лимит ещё раз, так что счётчик никогда не превышает `max_uses`, даже если `quote` и `place_order`
  разнесены во времени.
- **Значение процента не ограничено двумя знаками.** Спецификация задаёт только интервал `(0, 100]`.
  Скидка всё равно округляется до копеек, поэтому дробный процент допустим.
- **Фиксированная скидка проверяет копейки, процент — нет.** `FIXED 1.005` отклоняется, `PERCENT 10.555`
  принимается; причина в том, что сумма скидки в рублях должна быть точной до копейки.
- **Промокод принимает только `Category` в `excluded_categories`.** Строки вроде `"electronics"`
  отклоняются как ошибка валидации, чтобы опечатка не давала тихо пустое исключение.
- **`UnknownPromoCodeError` хранит нормализованный код** в атрибуте `code`, по образцу
  `UnknownProductError`.
- **`PromoRegistry(clock)` требует часы явно**, без значения по умолчанию: реестр всегда проверяет
  срок действия, и тихое подключение системных часов скрыло бы ошибку в тестах.
- **Публичный экспорт `shop/__init__.py` расширен** `PromoCode`, `PromoRegistry`, `DiscountKind`,
  `PromoError` и тремя ошибками промокодов (задача 5.2).
