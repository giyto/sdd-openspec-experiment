## Context

Мотивация и состав изменений — в `proposal.md`, требования — в `specs/`. Публичный API из тикета (имена, сигнатуры, порядок параметров, поля) не меняется. Ограничения проекта из README: деньги только `Decimal` и `quantize_money` (`ROUND_HALF_UP`), ошибки только от `ShopError`, время только через внедрённый `Clock`, модели — frozen dataclass с инвариантами в `__post_init__`, вводимые людьми коды нормализуются `normalize_key`, интервалы времени полуоткрытые, порядок строк корзины значим, только stdlib.

Сейчас `calculate_total` чистая функция без состояния, `OrderService.quote` её обёртка, `cancel` лишь меняет статус заказа.

## Goals / Non-Goals

**Goals:**
- Скидка считается в одном месте (`calculate_total`), `OrderService` лишь подбирает `PromoCode` и ведёт счётчики.
- Точное совпадение суммы построчных скидок с общей скидкой без накопления ошибок округления.

**Non-Goals:**
- Скидки в `shop/cli.py` и `shop/reports.py` (отдельный тикет), персистентность счётчиков, потокобезопасность между процессами, сочетание нескольких кодов в одном заказе.

## Decisions

1. **Раскладка в целых копейках.** Сумма строк и скидка переводятся в целые копейки; доля = `D * a_i // S`, остаток `D * a_i % S`. Недостающие `D - Σдоли` копеек (меньше числа участвующих строк) раздаются по одной в порядке убывания остатка, при равенстве — по возрасту строки в корзине (сортировка по `(-остаток, индекс)`). Это ровно правило бухгалтерии и не зависит от контекста `Decimal`. Альтернатива — `Decimal` с `ROUND_DOWN`: то же, но с риском неточного деления; отвергнута. Доля не превышает сумму строки, так как `D <= S`.
2. **Размер скидки.** `PERCENT`: `quantize_money(S * value / 100)`; `FIXED`: `min(value, S)`, где `S` — сумма участвующих строк до скидки. Результат может быть `0.00` (микроскидка округлилась) — это допустимо, ошибкой не считается.
3. **Участие.** Строка участвует, если `category is not GIFT_CARD` и категория не в `promo.excluded_categories`. Правило сертификатов зашито в расчёте, а не в данных кода, чтобы его нельзя было обойти конфигурацией.
4. **Где какие проверки.** `calculate_total` проверяет только «нет участвующих строк» и `S < min_order_amount` → `PromoConditionsError`; срок и лимит — только `PromoRegistry.resolve` (так и сказано в тикете). Минималка сравнивается с `S` до скидки, `>=` проходит.
5. **Налог и доставка.** Налог строки — `tax.tax_for(category, amount - discount)`. Для доставки в `ShippingPolicy.cost_for` передаётся `subtotal - discount`; сигнатура и поведение `ShippingPolicy` не меняются. `needs_delivery` не зависит от скидки.
6. **Поля результата.** `LineTotal.discount` и `OrderTotal.discount` добавляются последними полями с умолчанием `ZERO`, поэтому позиционные конструкции и старые вызовы совместимы. `subtotal` и `amount` остаются до скидки. `Order.promo_code: str | None = None` добавляется после `status`.
7. **`PromoCode`.** `__post_init__` нормализует `code` через `object.__setattr__` (как `Product.sku`) и проверяет инварианты (см. spec `promo-codes`). `FIXED.value` и `min_order_amount` — не более двух знаков (`to_money(x) == x`); `PERCENT.value` может иметь любое число знаков. Типы проверяем явно (`float` и `bool` отвергаются) → `ValidationError`.
8. **`PromoRegistry`.** Словарь `code -> PromoCode` и словарь счётчиков; `resolve` проверяет по порядку: найден → `now` вне `[starts_at, expires_at)` → `uses >= max_uses`. Кроме заданного в тикете API добавляются два служебных метода, нужных `OrderService`: `redeem(code)` (повторно проверяет лимит и увеличивает счётчик, под `threading.Lock` для атомарности внутри процесса) и `release(code)` (уменьшает не ниже нуля). Это только добавления; имена в тикете не затронуты. Альтернатива — хранить счётчики в `OrderService`: отвергнута, т.к. `uses` и лимит — ответственность реестра.
9. **`OrderService`.** Вспомогательная функция разбирает вход: `None`/пустая/пробельная строка → нет кода; иначе `promos.resolve(code)` (без реестра — `UnknownPromoCodeError`); нестроковый `promo_code` → `ValidationError` через `normalize_key`. `quote` = разбор + `calculate_total(..., promo=promo)`. `place_order`: разбор → расчёт → сохранение заказа → `redeem`. Если `redeem` падает (гонка за последний use), заказ не должен остаться: `redeem` вызывается до `store.add`, а id берётся после расчёта; ошибка `redeem` оставляет хранилище нетронутым. `cancel`: после успешного `store.save` вызывается `release(order.promo_code)`.
10. **Порядок при пустой корзине.** Код проверяется раньше корзины (resolve → `calculate_total`), поэтому пустая корзина с неизвестным кодом даёт `UnknownPromoCodeError`, а с валидным — `EmptyCartError`. Допущение; без кода поведение прежнее.
11. **Логирование.** `logger.info` при применении/возврате использования, без `print`.

## Допущения

- `uses(unknown)` → `UnknownPromoCodeError` (в тикете не указано).
- Повторный `add` того же кода → `ValidationError` (по README).
- `cancel` возвращает использование и для кода, у которого срок уже истёк.
- Заказ с `promo_code`, но сервис без реестра, невозможен; `cancel` в таком случае счётчики пропускает.

## Risks / Trade-offs

- [Скидка 0.00 на микросумме] → считается допустимой, код при этом всё равно расходуется; зафиксировано тестом.
- [Гонка за последнее использование между потоками] → `redeem` атомарен внутри процесса; между процессами счётчики не разделяются (in-memory, как и `OrderStore`).
- [`reports.py` показывает `subtotal` до скидки] → сознательно вне рамок тикета; `OrderTotal.total` корректен.
- [Порог доставки по сумме после скидки меняет поведение только при промокоде] → без кода сумма совпадает с прежней.

## Migration Plan

Миграция данных не нужна: изменения аддитивные. Откат — возврат коммита; новые поля имеют значения по умолчанию.

## Решения при реализации

- Результат `FIXED` приводится через `quantize_money`, чтобы `discount` всегда имел два знака (например, `FIXED` со значением `Decimal("100")` даёт `100.00`).
- В `shop/pricing.py` `PromoCode` импортируется только под `TYPE_CHECKING`, а `DiscountKind` — лениво внутри функции, чтобы не создавать циклических импортов.
- В `place_order` порядок такой: разбор кода → расчёт → `redeem` → `next_id` и `store.add`. Ошибка на любом шаге до `store.add` не оставляет следов в хранилище.
