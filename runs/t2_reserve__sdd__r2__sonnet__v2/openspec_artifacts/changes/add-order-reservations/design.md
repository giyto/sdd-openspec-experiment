## Context

`Inventory` (`warehouse/inventory.py`) хранит физические остатки в `InMemoryStore`, пишет события в `EventLog`, время берёт только из внедрённых часов. Операции атомарны: сначала проверки, затем изменения. Журнал пишет время с точностью до секунды, формат строки менять нельзя. Требования — в `specs/order-reservations/spec.md`, мотивация — в proposal.md.

## Goals / Non-Goals

**Goals:**
- Резервы как часть `Inventory` с ленивым истечением по `clock.now()`.
- Не нарушить существующее поведение и формат журнала.

**Non-Goals:**
- Фоновая очистка истёкших резервов, история резервов, персистентность.
- Изменения `cli.py`, `reports.py`, существующих тестов.

## Decisions

- **Хранение.** В `InMemoryStore` добавляется словарь `order_id → запись` (внутренняя изменяемая запись: строки, `created_at`, `expires_at`, хранимый статус `ACTIVE/CONFIRMED/CANCELLED`). `EXPIRED` не хранится: он вычисляется при построении снимка как `ACTIVE и now >= expires_at`. Чтение не имеет побочных эффектов и ничего не пишет в журнал. Наружу отдаётся только frozen-снимок `Reservation` со строками-кортежем.
- **Время.** Каждая операция берёт `now = clock.now()` один раз и использует его для статуса, `created_at`, `expires_at` и событий.
- **`reserved`/`available`.** `reserved` суммирует строки активных (по `now`) резервов по позиции линейным обходом; `available = max(0, on_hand − reserved)`.
- **Достаточность.** Строки группируются по `(warehouse, sku)` с суммированием только для проверки; в резерве хранятся как пришли. `reserve` сравнивает с `available`, `confirm` — с физическим остатком. `InsufficientStockError` несёт суммарное `requested`; позиции проверяются в порядке первого появления.
- **`issue`/`transfer`.** Проверка меняется с `on_hand` на `available`. `confirm` списывает через внутренний путь без проверки резервов (товар уже под этим заказом) и пишет обычные `ISSUE` с `ref=order_id`. `transfer` ограничен так же, т.к. его docstring объявляет проверки как у `issue`.
- **Порядок проверок.** Валидация входа (`order_id`, `ttl`, строки) → поиск резерва (`NotFound`) → статус (`Expired`/`State`) → достаточность. В `extend` валидация `ttl` идёт раньше поиска резерва.
- **Повторный `reserve`.** Допустим, если записи нет либо она отменена/истекла; запись заменяется целиком. Активная или подтверждённая → `DuplicateReservationError`; проверка идёт до проверки остатков.
- **Журнал.** События пишутся в конце операции, после всех проверок. `expires` передаётся строкой через `format_timestamp`.
- **TTL по умолчанию.** `DEFAULT_RESERVATION_TTL = timedelta(minutes=15)` (актуальное значение из обсуждения, не 30). В `warehouse/reservations.py` же — проверка `ttl` и нормализация строк.
- **Ошибки.** `ReservationError(WarehouseError)` принимает `order_id` и хранит его атрибутом; наследники без дополнительной логики.

Альтернативы: переводить в `EXPIRED` фоновой задачей — исключено условиями; выделить резервы в отдельный сервис — отвергнуто, так как `issue` и `available` должны видеть их атомарно.

## Risks / Trade-offs

- [Секундная точность журнала против полной точности `expires_at`] → в журнале срок усечён, источник истины — снимок.
- [Линейный обход при расчёте `reserved`] → приемлемо для in-memory сервиса; при росте добавить индекс по позиции.
- [Допущения, не заданные тикетом] → перечислены ниже, закрепляются тестами.

Допущения:
- `transfer` ограничивается резервами так же, как `issue`.
- `ttl` нулевой, отрицательный или не `timedelta` → `ValidationError`; переполнение даты при `now + ttl` → `ValidationError`.
- Элемент `lines`, не являющийся `ReservationLine` или кортежем из 3 элементов → `ValidationError`; итерируемое читается один раз.
- `available`/`reserved` для неизвестного SKU → `UnknownSkuError`.
- `cancel` и `extend` без изменений возвращают актуальный снимок.
- Замена резерва при повторном `reserve` не сохраняет историю прежнего.

Решения при реализации:
- `order_id` проверяется как код во всех методах резервов (`confirm/cancel/extend/get_reservation` тоже), некорректный код → `ValidationError`.
- `ReservationStateError` дополнительно хранит `status`; `ReservationError(order_id, message)` — базовый конструктор.
- Хелперы `validate_code`, `validate_ttl`, `expiry`, `normalize_lines` живут в `warehouse/reservations.py`; изменяемая `ReservationRecord` — в `warehouse/storage.py`.
- Строки-кортежи нормализуются в `ReservationLine`, снимок всегда содержит `ReservationLine`.
