## Context

`Inventory` (`warehouse/inventory.py`) хранит остатки в `InMemoryStore`, берёт время из внедрённых часов, каждая операция атомарна (сначала проверки, потом изменения) и пишет события в `EventLog`. Журнал округляет время события до секунды, а решение об истечении должно приниматься с полной точностью часов. Мотивацию см. в proposal.md, требования — в specs/stock-reservations/spec.md.

## Goals / Non-Goals

**Goals:** резервы в `Inventory` по соглашениям README; ленивое истечение; полная совместимость старого API.

**Non-Goals:** фоновая очистка истёкших резервов, изменения `cli.py` и `reports.py`, склейка строк резерва, персистентность.

## Decisions

1. **Хранение.** В `InMemoryStore` — словарь `order_id → запись` (строки, `created_at`, `expires_at`, записанный статус `ACTIVE/CONFIRMED/CANCELLED`). Статус `EXPIRED` не хранится: эффективный статус на момент `now` — `CONFIRMED`/`CANCELLED` как записано, иначе `EXPIRED` при `now >= expires_at`, иначе `ACTIVE`. Наружу отдаются только frozen-снимки `Reservation`. Альтернатива — хранить в `Inventory`: отвергнута, т.к. store внедряется снаружи и владеет состоянием.
2. **Модули.** Модели — в `models.py`, ошибки (с `order_id`) — в `errors.py`, `warehouse/reservations.py` — `DEFAULT_RESERVATION_TTL = timedelta(minutes=15)`, валидация ttl и строк, агрегация по позициям.
3. **Одно `now` на операцию.** Время читается один раз и используется для проверки, записи и событий.
4. **Агрегация по позиции.** Суммы строк по `(warehouse, sku)` для проверок в `reserve` и `confirm`; в `InsufficientStockError` `requested` — сумма. При нескольких проблемных позициях сообщается первая по порядку первого вхождения.
5. **Запросы.** `reserved` — сумма по активным записям (перебор, объёмы малы); `available = max(0, on_hand - reserved)`.
6. **`issue`.** Лимит — `available`; при превышении `InsufficientStockError` с `available=лимит`. `confirm` использует приватный путь списания, проверяющий только физический остаток, а не публичный `issue`.
7. **`confirm`.** Найден → статус → суммы против физического остатка → списание по строкам → события `ISSUE`×N, затем `RESERVE_CONFIRM`.
8. **`reserve`.** Порядок: валидация `order_id`, ttl, строк (склад, SKU, qty) → проверка дубликата (активный/подтверждённый) → наличие по суммам → запись с заменой старой → события `RESERVE`. Итератор строк потребляется один раз.
9. **`extend`.** Валидация ttl → найден → статус (как в `confirm`) → `new = now + ttl`; при `new <= expires_at` возврат без изменений и событий, иначе обновление и `RESERVE_EXTEND`.
10. **Время в событиях.** `expires` форматируется через `format_timestamp`; решения об истечении используют неокруглённое значение.

### Допущения

- `transfer` с исходного склада подчиняется тому же ограничению по `available`, что и `issue` (его docstring: «для источника это обычный расход»). `adjust` без проверок, как раньше.
- В `extend` сначала проверяется `ttl` (`ValidationError`), затем поиск резерва и статус.
- `ttl`: не `timedelta`, `bool` или значение `<= 0` → `ValidationError`.
- Незарегистрированный SKU в строке → `UnknownSkuError`, некорректное количество → `InvalidQuantityError`; обе проверки раньше проверок наличия.
- Резерв, превысивший остаток после `adjust`, допустим; `available` зажимается нулём.

## Risks / Trade-offs

- [Секундная точность журнала против срока] → истечение считается по полной точности `expires_at`, журнал лишь отображает.
- [Перебор всех резервов в `reserved`] → приемлемо для хранилища в памяти; индекс можно добавить без изменения API.
- [`transfer` теперь может отказать из-за резервов] → осознанное допущение; без резервов поведение прежнее.
- [`confirm` разрешён при `available = 0`] → намеренно; чужие `issue` защищены проверкой `available`.
