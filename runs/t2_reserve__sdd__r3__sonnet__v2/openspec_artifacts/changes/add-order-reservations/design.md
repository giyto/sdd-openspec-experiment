## Context

`Inventory` хранит физические остатки в `InMemoryStore` и пишет события в `EventLog`; время берётся только из внедрённых часов, операции атомарны (сначала проверки, потом изменения), наружу отдаются frozen-снимки (README). Фоновых задач нет. Мотивация и границы — в proposal.md, требования — в specs/order-reservations/spec.md.

## Goals / Non-Goals

**Goals:**
- Резервы поверх существующей архитектуры без изменения формата журнала и старого API.
- Истечение вычисляется только при обращении, без мутации и без записи в журнал.

**Non-Goals:**
- Фоновая очистка истёкших резервов, персистентность, изменение `cli.py`/`reports.py`.
- Объединение одинаковых позиций внутри резерва.

## Decisions

1. **Структура модулей.** `ReservationStatus`, `ReservationLine`, `Reservation` — в `models.py`; ошибки с `order_id` — в `errors.py`; `reservations.py` содержит `DEFAULT_RESERVATION_TTL = timedelta(minutes=15)` и чистые функции (нормализация строк, агрегация по позиции, эффективный статус). Методы — в `Inventory`. Альтернатива «отдельный сервис» отвергнута: резервы участвуют в проверках `issue`/`transfer` того же объекта.
2. **Хранение.** Резервы лежат в `InMemoryStore` (`dict[order_id, Reservation]`, простые get/put без проверок), т.к. состояние `Inventory` уже живёт в хранилище. Хранится frozen `Reservation` с сохранённым статусом `ACTIVE/CONFIRMED/CANCELLED`; изменение — замена объекта через `dataclasses.replace`. `EXPIRED` не хранится, а выводится: `ACTIVE` и `now >= expires_at`. Так истечение не требует записи, что согласуется с отсутствием фоновых задач.
3. **Единый момент времени.** `clock.now()` вызывается один раз на операцию, чтобы все проверки внутри неё видели один момент. Сравнения сроков идут с полной точностью datetime; усечение до секунд касается только записи в журнал.
4. **Подсчёт.** `reserved` — сумма `qty` по строкам эффективно активных резервов (линейный проход). `available = max(0, on_hand − reserved)`. В `reserve`/`issue`/`transfer` запрошенное по позиции сравнивается с `available`; `InsufficientStockError(requested=сумма по позиции, available=available)`.
5. **Порядок в `reserve`:** материализовать `lines` (может быть итератор) → валидация `order_id`, `ttl`, строк → дубликат (`DuplicateReservationError`, если эффективно `ACTIVE`/`CONFIRMED`) → достаточность по сумме позиций → запись резерва (заменяет прежний истёкший/отменённый) → события `RESERVE` по строкам.
6. **`confirm`:** найти (`NotFound`) → статус (`Expired` / `State`) → проверка физического остатка по агрегированным позициям до любых изменений → списание в хранилище, события `ISSUE` с `ref=order_id` по строкам, затем `RESERVE_CONFIRM`. Публичный `issue` не используется, чтобы не упираться в `available`; формат события тот же.
7. **`extend`:** валидация `ttl` → найти → статус → `new = now + ttl`; если `new > expires_at`, замена и `RESERVE_EXTEND`, иначе возврат без изменений.
8. **`cancel`:** найти → эффективно `ACTIVE` → запись + `RESERVE_CANCEL`; `CANCELLED`/`EXPIRED` → снимок без записи; `CONFIRMED` → `ReservationStateError`.
9. **`issue`/`transfer`:** лимит заменяется с физического остатка на `available`; без резервов `available == on_hand`, поведение прежнее. `adjust` не меняется.
10. **Экспорт и логирование.** Новые имена добавляются в `warehouse/__init__.py`; логгер модуля, `print` не используется.

## Допущения (в тикете не определено)

- Момент истечения: `now >= expires_at` (в `expires_at` резерв уже не действует).
- `transfer` подчиняется резервам: его docstring приравнивает проверки источника к `issue`.
- `available`/`reserved` проверяют только SKU (как `on_hand`), склад не валидируют.
- Порядок ошибок: сначала валидация аргументов (`ValidationError`/`InvalidQuantityError`/`UnknownSkuError`), затем `NotFound`/статус/`Duplicate`, затем наличие.
- `ttl` в `extend` обязателен; значения не типа `timedelta` (в т.ч. `int`, `bool`) — `ValidationError`.
- Строка-кортеж неверной длины или элемент неизвестного типа — `ValidationError`.
- Повторный `reserve` поверх истёкшего/отменённого не пишет отдельного события; прежний резерв виден только в журнале.
- Нехватка при `reserve` сообщает суммарное запрошенное по первой по порядку строк нехватающей позиции.

## Risks / Trade-offs

- [Линейный подсчёт `reserved` при каждом запросе] → приемлемо для хранилища в памяти; индекс по позиции можно добавить без смены API.
- [Журнал с секундной точностью, проверка истечения точная] → `expires` в журнале может быть округлено вниз; источником истины остаётся состояние сервиса.
- [`adjust` может опустить остаток ниже резерва] → `available` зажимается в 0, `confirm` проверяет физический остаток и отказывает целиком.
- [`issue` ранее сообщал в ошибке физический остаток] → теперь `available`; без резервов значения совпадают.
