## Context

Сервис `Inventory` (`warehouse/inventory.py`) хранит физические остатки в `InMemoryStore` и пишет
события в `EventLog`. Каждая операция сначала проверяет всё, потом меняет состояние и журнал
(атомарность, см. README). Фоновых задач нет, часы внедряются через `Clock`. Поэтому истечение
резерва не может быть событием по таймеру: оно вычисляется при каждом обращении.

Поведение описано в `specs/reservations/spec.md`; мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Все резервные операции укладываются в существующие соглашения: часы через `Clock`, ошибки
  наследуются от `WarehouseError`, модели — неизменяемые датаклассы, атомарность, журнал.
- Истечение резерва — чисто вычисляемое состояние; журнал по нему не меняется.
- Существующий API и поведение без резервов не меняются.

**Non-Goals:**
- Фоновая очистка истёкших резервов и любые таймеры.
- Персистентность: хранилище остаётся в памяти, как и остальное.
- Склейка строк одной позиции в резерве (строки хранятся как переданы).
- Изменения в `warehouse/cli.py` и `warehouse/reports.py`.

## Decisions

**1. Хранится стабильный статус, `EXPIRED` вычисляется.**
Запись резерва хранит `ACTIVE`, `CONFIRMED` или `CANCELLED` и `expires_at`. Снимок, который отдаёт
сервис, получает статус `EXPIRED`, если запись `ACTIVE` и `now >= expires_at`. Альтернатива —
переводить запись в `EXPIRED` при первом обращении — отвергнута: это мутация при чтении, она
должна была бы писать состояние в `reserved`/`available` и усложняет проверку порядка операций.
Так же проще соблюсти требование «истечение в журнал не пишем».

**2. Порядок проверок.**
Для каждой операции: сначала валидация аргументов (TTL, строки, коды), затем поиск записи
(`ReservationNotFoundError`), затем статус (окончательные `CONFIRMED`/`CANCELLED` → `ReservationStateError`,
истёкший → `ReservationExpiredError`), затем наличие товара. Для `reserve` — валидация, неизвестный SKU,
`DuplicateReservationError`, наличие доступного. Единый порядок даёт предсказуемые ошибки и
одинаковое поведение `confirm` и `extend`, как просила задача.

**3. Замена резерва при повторном `reserve`.**
Если прежняя запись `EXPIRED` (по времени) или `CANCELLED`, новая запись полностью заменяет её в
хранилище. История прежней записи не сохраняется: журнал и так содержит её события.

**4. Учёт в `reserved`/`available`.**
`reserved(wh, sku)` суммирует строки только записей `ACTIVE` с `now < expires_at` по этой позиции.
`available = max(0, on_hand - reserved)`. Рассчитываем на лету из записей; отдельного счётчика нет,
чтобы не расходиться с истечением и с `adjust`.

**5. Проверка при `confirm` — по физическому остатку.**
Сумма строк по каждой позиции сравнивается с `on_hand`. Ошибка `InsufficientStockError` несёт
`available = on_hand` (физический остаток, который фактически не хватает). Резерв заказа не
учитывается, потому что товар зарезервирован именно под него. После списания `reserved` по этим
строкам уходит вместе со статусом `CONFIRMED`.

**6. `issue` и `transfer` проверяют `available`.**
Проверка `issue` меняется с `on_hand` на `available`. `transfer` для склада-источника по тексту
задачи — обычный расход, поэтому использует ту же проверку. Это допущение: в задаче прямо назван
только `issue`, но `transfer` описан как «проверки те же, что у `issue`». Без активных резервов
результат тот же.

**7. Порядок записи в журнал и поля.**
Все события пишутся после всех проверок. `RESERVE` — по строкам в порядке передачи. `expires`
пишется через `format_timestamp` (секундная точность журнала); в проверках используется точный
`expires_at`. Поля `order`, `wh`, `sku`, `qty`, `ref` соответствуют существующим именам.

**8. Где что лежит.**
- `models.py`: `ReservationStatus`, `ReservationLine`, `Reservation`.
- `errors.py`: `ReservationError` и наследники, каждый с атрибутом `order_id`.
- `reservations.py`: `DEFAULT_RESERVATION_TTL = timedelta(minutes=15)` и внутренняя запись резерва
  (изменяемый объект только внутри сервиса, наружу — снимки).
- `storage.py`: записи резервов по `order_id` (хранилище по-прежнему не проверяет).
- `inventory.py`: вся логика; запросы `reserved`/`available` используют тот же учёт.

**9. Коды `order_id` в запросах.**
Для `confirm`, `cancel`, `extend`, `get_reservation` формат `order_id` не проверяется отдельно:
отсутствующий код даёт `ReservationNotFoundError`. В `reserve` код валидируется как SKU и склад.

**10. Проверка существования склада.**
Склад не регистрируется отдельно, как и сейчас: достаточно валидного кода. Резерв на склад с
нулевым остатком не создаётся, потому что проверка доступности даст нехватку.

## Risks / Trade-offs

- [Изменение `issue`/`transfer` влияет на существующие сценарии] → без резервов результат прежний;
  тесты существующего поведения не меняются и должны проходить без изменений.
- [Расхождение `expires` в журнале и точного `expires_at` до секунды] → проверки идут по точному
  значению; журнал показывает секунды. Описано в spec (сценарий на границе).
- [Инвентаризация может уменьшить остаток ниже суммы резервов] → `available` ограничен нулём, а
  `confirm` защищён проверкой физического остатка; это ожидаемое поведение по задаче.
- [Рост числа записей в памяти без очистки] → истёкшие записи остаются, пока не заменены повтором
  `reserve`. Для in-memory сервиса приемлемо; очистка — отдельная задача.
- [Хранение нескольких строк одной позиции] → суммирование делается при каждом расчёте; сложность
  O(число строк резервов) на запрос. Для текущего масштаба допустимо.

## Migration Plan

Миграции данных нет: состояние в памяти, существующие `Inventory(store=..., clock=..., log=...)`
работают как раньше. Откат — удаление новых методов и модулей; поведение `issue`/`transfer`
возвращается к проверке по `on_hand`.

## Решения при реализации

Уточнения, которые не были зафиксированы в артефактах выше; принял при реализации.

- **Хранилище и время.** `InMemoryStore.active_reservations_for(wh, sku)` отдаёт записи со
  статусом `ACTIVE` без учёта времени: у хранилища нет часов. Проверку `now < expires_at` делает
  сервис в `reserved`/`available`/`reserve`.
- **TTL в `reserve`.** `ttl=None` означает «не передан» и даёт `DEFAULT_RESERVATION_TTL`. Любое
  другое значение, не `timedelta` или не положительное, отклоняется `ValidationError`.
- **Порядок проверок в `reserve`.** Сначала `order_id`, TTL и формат всех строк (включая
  количество), затем неизвестный SKU, затем `DuplicateReservationError`, затем доступность по
  сумме строк позиции. Так неверный ввод не зависит от состояния склада.
- **Ошибка нехватки при `reserve`.** `InsufficientStockError` несёт `requested` = сумма строк
  позиции, `available` = доступный остаток на момент вызова.
- **Порядок проверок в `extend`.** TTL проверяется до поиска резерва: неверный TTL даёт
  `ValidationError` независимо от наличия заказа.
- **Строки резерва.** Принимаются кортежи или списки из трёх элементов `(wh, sku, qty)`.
  Прочие формы отклоняются `ValidationError`, пустой список тоже.
- **`ISSUE` при `confirm`.** Пишется по одному событию на строку, в порядке строк, даже если
  строки одной позиции. Проверка физического остатка при этом идёт по сумме по позиции.
- **Экспорт.** Новые публичные имена (модели, ошибки, `DEFAULT_RESERVATION_TTL`) добавлены в
  `warehouse/__init__.py` по тому же принципу, что и остальные типы пакета.
- **Тесты.** Новые тесты в `tests/test_reservations.py`. Существующие тесты не менялись.
