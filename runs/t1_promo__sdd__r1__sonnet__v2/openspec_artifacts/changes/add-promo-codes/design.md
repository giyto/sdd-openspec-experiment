## Context

Мотивация и объём: см. `proposal.md`, требования: `specs/`. Текущее состояние: `calculate_total` в `shop/pricing.py` чистая функция; `OrderService` в `shop/orders.py` хранит заказы в памяти и умеет `quote` / `place_order` / `cancel`; `normalize_key` (`shop/catalog.py`) — общий способ нормализации вводимых людьми кодов; время только через `Clock`. Соглашения проекта (README): деньги `Decimal` + `quantize_money` (`ROUND_HALF_UP`), ошибки только от `ShopError`, frozen-датаклассы с инвариантами в `__post_init__`, полуоткрытые интервалы, только stdlib.

## Goals / Non-Goals

**Goals:**
- Скидка, точно сходящаяся по строкам и в итоге; полная обратная совместимость старых вызовов.
- Учёт использований без «утечки» при ошибках и с возвратом при отмене.

**Non-Goals:**
- `shop/cli.py`, `shop/reports.py` (отдельный тикет), персистентность реестра, несколько кодов в одном заказе, скидки на доставку.

## Decisions

1. **Модуль `shop/promo.py`** с `DiscountKind`, `PromoCode`, `PromoRegistry`. `shop/pricing.py` импортирует `PromoCode` оттуда; `promo.py` импортирует только `catalog`, `clock`, `errors`, `money` — циклов нет. `PromoConditionsError` для условий заказа бросает pricing.

2. **Валидация `PromoCode.__post_init__`**: код нормализуется через `normalize_key` (запись через `object.__setattr__`, как в `Product`), пустой → `ValidationError`. `value` должен быть `Decimal` (float/bool отвергаются), конечный; PERCENT ∈ (0, 100] (дробные проценты допустимы), FIXED > 0 и не более двух знаков (`to_money(v) == v`, как у цены). `min_order_amount` ≥ 0 в копейках. `max_uses` — `int` не `bool`, ≥ 1. `starts_at`/`expires_at` aware; `starts_at >= expires_at` → `ValidationError`. `excluded_categories` — набор `Category`.

3. **Реестр**: `dict[str, PromoCode]` и `dict[str, int]` счётчиков. `resolve` строго по порядку: нормализация (нестроковый ввод → `ValidationError` от `normalize_key`; `""` → просто не найден → `UnknownPromoCodeError`), срок `[starts_at, expires_at)` по `clock.now()`, лимит `uses >= max_uses`. Кроме API из тикета реестр получает два метода для сервиса: `redeem(code)` (повторно проверяет через `resolve` и увеличивает счётчик одним действием) и `release(code)` (уменьшает, не ниже 0; неизвестный код игнорируется с debug-логом). Альтернатива — менять `_uses` из `OrderService` — отвергнута: инкапсуляция и единая точка проверки лимита.

4. **Участие строки**: `category is not GIFT_CARD and category not in promo.excluded_categories`. Сертификаты исключаются всегда, независимо от набора кода (README).

5. **Размер и раскладка скидки в целых копейках**: база `P` = сумма участвующих строк. PERCENT: `quantize_money(P * value / 100)`; FIXED: `min(value, P)`. Раскладка: для каждой участвующей строки `num = D_kop * line_kop`, `share = num // P_kop`, `rem = num % P_kop`; остаток `D_kop - Σshare` (< числа строк) раздаётся по одной копейке строкам по ключу `(-rem, индекс в корзине)`. Целочисленная арифметика исключает дрейф округления; сумма по строкам равна скидке по построению, а доля не превышает сумму строки (при `D = P` остатки нулевые, при `D < P` потолок доли ≤ суммы строки). Альтернатива «округлить каждую долю и дотянуть последнюю строку» отвергнута: не совпадает с учётом бухгалтерии.

6. **`calculate_total`**: новый keyword-only `promo: PromoCode | None = None`. Порядок: пустая корзина → `EmptyCartError`; при промо проверка условий (`PromoConditionsError` при отсутствии участвующих строк или `P < min_order_amount`), затем скидка и раскладка; налог `tax.tax_for(category, amount - line_discount)`; `shipping.cost_for(subtotal - discount, ...)`; `total = subtotal - discount + shipping + tax`. `LineTotal.discount` и `OrderTotal.discount` добавляются в конец датакласса с default `ZERO`, чтобы существующие конструкторы и позиционные вызовы не ломались. `amount` и `subtotal` остаются до скидки. Срок и лимит здесь не проверяются.

7. **`OrderService`**: новый keyword-аргумент `promos: PromoRegistry | None = None`. Общий приватный шаг: `promo_code` → `None`/пустое/пробелы = нет кода; иначе нормализация и `resolve` (без реестра → `UnknownPromoCodeError`). `quote` — resolve + `calculate_total`. `place_order` — resolve → `calculate_total` → создание заказа → `store.add` → `promos.redeem`. Всё, что может упасть, выполняется до изменения состояния, поэтому при ошибке заказ не сохраняется, id не тратится (сейчас `next_id` вызывается после расчёта — порядок сохраняем) и счётчик не меняется. `Order.promo_code: str | None = None` — в конец датакласса.

8. **`cancel`**: после проверки статуса и сохранения отменённого заказа, если `order.promo_code` задан и реестр есть — `promos.release(code)`. Повторная отмена падает на проверке статуса до возврата, поэтому двойного возврата нет.

9. **Логирование** — `logger.debug/info` в `promo.py` и `orders.py`; `print` не используем. Экспорт новых публичных имён в `shop/__init__.py` по аналогии с остальными.

## Assumptions (зафиксированные допущения)

- `uses(code)` для неизвестного кода → `UnknownPromoCodeError` (а не 0).
- При непустом коде и пустой корзине сначала разрешается код (неизвестный код / срок / лимит), затем `EmptyCartError` из расчёта.
- Порог бесплатной доставки сравнивается с `subtotal - discount` целиком (включая сертификаты в смешанной корзине), как «сумма товаров» в README.
- Скидка 0.00 (например, 1 % от 0.10) допустима: код применяется и использование считается.
- Проверка лимита в `place_order` и инкремент происходят в одном потоке; реестр, как и `OrderStore`, не потокобезопасен (см. риски).
- `Order.created_at` берётся из часов сервиса, срок промокода — из часов реестра; предполагается, что в проде это один источник.
- Возврат при отмене не зависит от срока действия кода.

## Risks / Trade-offs

- [Гонка при параллельном оформлении последнего использования] → `redeem` перепроверяет лимит в момент инкремента; потокобезопасность хранилищ вне объёма (как у `OrderStore`), фиксируется в README/комментарии.
- [Расхождение часов сервиса и реестра] → в тестах и прод-конфигурации передавать одни и те же часы.
- [Заказы со скидкой попадут в отчёты и CLI без отображения скидки] → осознанно отложено отдельным тикетом; `total` уже корректен, так как включает скидку.
- [Рост `Order`/`LineTotal`/`OrderTotal` новыми полями] → поля в конце с default, обратная совместимость сохранена.
