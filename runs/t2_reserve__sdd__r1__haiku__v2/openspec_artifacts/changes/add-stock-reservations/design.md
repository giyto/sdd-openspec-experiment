## Context

Сервис `Inventory` (`warehouse/inventory.py`) хранит физические остатки в `InMemoryStore` и пишет
события в `EventLog`. Часы внедряются через `Clock`, фоновых задач нет. Каждая операция сначала
проверяет всё, потом меняет состояние и журнал (атомарность из README). Мотивация и требования — см.
`proposal.md` и `specs/inventory-reservations/spec.md`.

## Goals / Non-Goals

**Goals:**
- Резервы живут внутри `Inventory`, следуют тем же соглашениям: время только из `self._clock`, модели
  frozen, ошибки от `WarehouseError`, атомарные операции.
- Истечение вычисляется при чтении по текущему времени, без записи в журнал и без фоновых задач.
- Старый API и формат журнала не меняются.

**Non-Goals:**
- Персистентность, фоновая очистка истёкших резервов, отдельные события истечения.
- Изменения CLI, отчётов и существующих тестов.
- Склейка строк одной позиции внутри резерва (строки хранятся как пришли).

## Decisions

**1. Хранение резервов в `InMemoryStore`, логика в `Inventory`.**
Store получает словарь `order_id -> Reservation` с методами `get_reservation`/`put_reservation`/
`list_reservations` по аналогии с остатками. Store остаётся «глупым» (он ничего не проверяет).
Альтернатива — держать словарь в `Inventory`; отвергнута, потому что `store` уже единственное место
состояния и его передают снаружи в конструктор.

**2. Хранится «сохранённый» статус, отображается «эффективный».**
В store лежит `Reservation` с полем `status` в значении `ACTIVE`, `CONFIRMED` или `CANCELLED`
(то, что записано операциями). Снимок, который отдаёт сервис, получается через `dataclasses.replace`
с эффективным статусом: если сохранённый `ACTIVE` и `now >= expires_at`, то `EXPIRED`. Так
истечение не требует записи, а `Reservation` остаётся frozen и неизменяемым снаружи. Чистая функция
`effective_status(reservation, now)` живёт в `warehouse/reservations.py` вместе с
`DEFAULT_RESERVATION_TTL` и валидацией TTL; её легко тестировать с `ManualClock`.

**3. Один отсчёт времени на операцию.**
Каждая публичная операция читает `now = self._clock.now()` один раз и использует его для всех проверок
и для `created_at`/`expires_at`/`expires`. Это исключает расхождения внутри одного вызова.

**4. Порядок проверок.**
- `reserve`: аргументы (`order_id`, строки, `ttl`) → дубликат (только `ACTIVE`/`CONFIRMED` по эффективному
  статусу) → достаточность `available` по сумме строк каждой позиции → запись резерва и события.
- `confirm`/`extend`: не найден → эффективный `EXPIRED` → сохранённый `CONFIRMED`/`CANCELLED` →
  (для `confirm`) физический остаток по сумме строк → изменения.
- `cancel`: не найден → `CONFIRMED` → `CANCELLED`/`EXPIRED` (no-op, без событий) → `CANCELLED` + `RESERVE_CANCEL`.
- `extend` ttl валидируется до проверки статуса, как в `reserve`.

Проверка `ttl`/строк идёт первой, потому что это ошибки входных данных и они не зависят от состояния.

**5. Подтверждение проверяет физический остаток, а не `available`.**
Резерв уже держит товар, поэтому `confirm` сравнивает `on_hand` с суммой строк заказа по каждой позиции.
Это даёт требование «нулевой `available` не мешает» и защиту от инвентаризации, которая уменьшила остаток.
Пишем события только после всех проверок: сначала `ISSUE` на каждую строку (`ref` = `order_id`),
затем `RESERVE_CONFIRM`. Физические остатки меняются через `store.set_qty` по тем же правилам, что у `issue`.

**6. `issue` и `transfer` учитывают резервы.**
`issue` сравнивает `qty` с `available` (физический остаток минус активные резервы). `transfer` применяет ту же
проверку к источнику. Для `transfer` в тексте задачи прямого требования нет — это допущение, см. ниже.
`adjust` не проверяет резервы: инвентаризация — это факт, и остаток может стать меньше `reserved`
(тогда `available` = 0, по требованию склада).

**7. Формат времени в событии.**
Поле `expires` пишется строкой через `events.format_timestamp(expires_at)`, потому что `EventLog` не принимает
`datetime` как значение поля.

**Допущения (не из текста задачи, зафиксированы здесь):**
- `transfer` тоже не забирает зарезервированный товар (см. решение 6).
- `reserve` для заказа с истёкшим или отменённым резервом заменяет старый резерв целиком; события по старому
  резерву не пишутся.
- `ttl` валидируется как положительный `timedelta` в `reserve` и `extend`; не-`timedelta` тоже даёт `ValidationError`.
- `order_id` проверяется так же, как коды SKU и складов (`_validate_code`).
- Неизвестный SKU в строке `reserve`, `available`, `reserved` → `UnknownSkuError`; у `confirm`/`extend`/`cancel`
  SKU уже проверен при создании резерва.
- `available` и `reserved` для незарегистрированного SKU → `UnknownSkuError`, как `on_hand`.

## Risks / Trade-offs

- **[Скан всех резервов в `available`/`reserved`]** → O(число резервов) на каждый вызов. Для in-memory сервиса
  приемлемо; при росте — индекс по позиции (вне этого изменения).
- **[Расхождение эффективного и сохранённого статуса]** Сохранённый `ACTIVE` может быть уже истёкшим.
  → Все чтения идут через `effective_status`; `confirm`/`cancel`/`extend`/`reserve` тоже сверяются с эффективным статусом.
  Тесты проверяют переход через `expires_at` для каждой операции.
- **[Ограничение `transfer` выходит за текст задачи]** → Явно названо в proposal (**BREAKING** для `transfer` при резервах)
  и в спецификации; при несогласии решение откатывается одной проверкой.
- **[Граница `expires_at`]** → В момент `expires_at` резерв уже `EXPIRED` (`>=`), как сказано в задаче.
- **[Смешение строк одной позиции]** → Проверки делаются по сумме; `ISSUE` пишется по строкам как пришли,
  чтобы журнал соответствовал входу.

## Migration Plan

Миграции нет: состояние in-memory. Изменение аддитивно: новые методы, новые типы событий, `issue`/`transfer`
меняются только когда есть резервы. Откат — удалить новые методы и проверку `available`.

## Решения при реализации

Уточнения, которых не было в артефактах; зафиксированы при реализации.

- **`extend` без явного `ttl`** использует `DEFAULT_RESERVATION_TTL` (спецификация задаёт `ttl` только для `reserve`).
- **`cancel` для истёкшего резерва** возвращает снимок со статусом `EXPIRED` и ничего не пишет; сохранённый объект
  остаётся `ACTIVE` до перезаписи (истечение не пишется в хранилище).
- **Ошибки резервов** получают `order_id` первым аргументом; `ReservationStateError(order_id, status)` несёт
  строковое имя статуса в атрибуте `status` для сообщения.
- **`issue` и `transfer`** читают часы один раз в начале операции и используют это же значение для проверки
  `available` и для события журнала.
- **Экспорт:** новые модели, исключения и `ReservationStatus` добавлены в `warehouse/__init__.py` по образцу
  существующих экспортов; `DEFAULT_RESERVATION_TTL` и `effective_status` остаются в `warehouse.reservations`.
- **Порядок проверок `reserve`:** `order_id` → `ttl` → строки (тип, склад, SKU, количество) → дубликат → `available`
  по сумме строк позиции. Проверка строк идёт до чтения состояния, поэтому ошибки входа не меняют ничего.
