## Context

Очередь синхронная, в памяти процесса (`InMemoryJobStore`). Воркер вызывает обработчик и при исключении
сразу делает `mark_failed`. Все моменты времени берутся из часов очереди (`queue.clock`), модули не
вызывают `datetime.now()`. Ошибки пакета — наследники `JobqError`. Переходы статусов проходят через
`JobQueue._transition` и таблицу `_TRANSITIONS`. См. `proposal.md` (Why) для мотивации.

## Goals / Non-Goals

**Goals:**
- Политика повторов с экспоненциальной задержкой, настраиваемая по умолчанию для очереди и по типу задания.
- Dead-letter очередь с возвратом того же задания через `requeue_dead_letter`.
- Ноль изменений в поведении для вызовов без политики.

**Non-Goals:**
- Персистентность dead-letter и политик (хранилище остаётся в памяти).
- Изменения `dashboard.py` и `cli.py`, в том числе вывод dead-letter в отчёте и в «Последних ошибках».
- Асинхронные или параллельные воркеры, распределённые блокировки.

## Decisions

**1. Решение о повторе принимает `Worker`, переходы делает `JobQueue`.**
Воркер видит исключение и отвечает за `rng`. Очередь выполняет переходы и ведёт dead-letter.
Новые методы очереди: `mark_retry_scheduled(job_id, error, delay)` (вычисляет `run_at = clock.now() + delay`)
и `mark_dead_lettered(job_id, error)`. Существующий `mark_failed` не меняется и остаётся для путей без повтора.
Альтернатива — класть логику в `JobQueue.mark_failed`: отвергнута, потому что тогда очередь получила бы
зависимость от `rng` и обработчика ошибок.

**2. Вычисление задержки без переполнения.**
`base_delay * factor ** (attempt - 1)` вычисляется напрямую. При `OverflowError` (например, `factor=2.0`
и `attempt=5000`) результат считается через логарифмы: `exp(log(base) + (attempt-1) * log(factor))`.
Итог всегда ограничивается `max_delay`. Для `base_delay == 0` возвращается `0.0` без вычислений,
для `factor == 1` возвращается `base_delay`.
Альтернатива — итеративное умножение с остановкой на `max_delay`: отвергнута, потому что при `factor`,
близком к 1, и большом `attempt` это O(attempt).

**3. Джиттер применяется до последнего ограничения.**
Порядок: `d = min(base * factor**(n-1), max_delay)`; при `jitter > 0`: `d = min(d * rng.uniform(1-j, 1+j), max_delay)`.
Это соответствует уточнению тимлида: `max_delay` — жёсткий потолок, джиттер его не пробивает. Тогда
`delay_for` всегда возвращает значение из `[0, max_delay]`.

**4. Валидация параметров в `RetryPolicy.__post_init__` через `ConfigError`.**
Проверяются диапазоны из спецификации, а также `NaN` и бесконечность (иначе сравнения молча проходят).
`non_retryable` приводится к `tuple` через `object.__setattr__`, потому что dataclass заморожен.
Альтернатива — проверять при каждом вызове: отвергнута, ошибка конфигурации должна падать сразу.

**5. Политика разрешается на момент ошибки.**
`JobQueue.retry_policy_for(job_type)` возвращает действующую политику: политику типа, иначе политику по
умолчанию, иначе `None`. Поля не сливаются (решение аналитика и тимлида). Воркер вызывает этот метод в момент
падения, поэтому смена политики между постановкой и выполнением влияет на задание.

**6. Dead-letter хранится в `JobQueue`, а не в `InMemoryJobStore`.**
`JobQueue._dead_letters: dict[str, DeadLetterEntry]` (ключ — `job_id`). Порядок вставки в dict даёт порядок
«в порядке попадания». Интерфейс хранилища не меняется. `requeue_dead_letter` удаляет запись из dict.

**7. `DEAD_LETTERED` — терминальный статус, очистка его явно пропускает.**
`is_terminal` описан как «воркер больше не выполнит», и для `DEAD_LETTERED` это верно. Поэтому
`purge_finished` добавляет условие `job.status is not JobStatus.DEAD_LETTERED`. Иначе очистка удалила бы
задание, а запись в dead-letter осталась бы висящей.

**8. Таблица переходов.**
- `PENDING` → `RUNNING`, `CANCELLED` (без изменений)
- `RUNNING` → `SUCCEEDED`, `FAILED`, `RETRY_SCHEDULED`, `DEAD_LETTERED`
- `RETRY_SCHEDULED` → `RUNNING`, `CANCELLED`
- `DEAD_LETTERED` → `PENDING` (только через `requeue_dead_letter`; `CANCELLED` отсутствует намеренно)

**9. Выборка готовых заданий.**
`InMemoryJobStore.due()` берёт `PENDING` и `RETRY_SCHEDULED` с `run_at <= now`. Сортировка прежняя: по `run_at`, затем по `seq`.

**10. Значения `JobStatus` добавляются в конец перечисления.**
Dashboard печатает статусы в порядке перечисления, поэтому существующие строки отчёта остаются на своих местах
и добавляются две новые строки.

**11. Счётчики по точкам перехода.**
`jobs.retried` — в `mark_retry_scheduled`, `jobs.dead_lettered` — в `mark_dead_lettered`,
`jobs.requeued` — в `requeue_dead_letter`. Так же, как существующие счётчики: по переходу, а не по событию воркера.

**12. Очистка `error` при успехе и при возврате.**
`mark_succeeded` обнуляет `error` (в `models.py` записано, что у `SUCCEEDED` ошибки нет). `requeue_dead_letter`
обнуляет `error` и `finished_at`, `attempts` — тоже обнуляет (уточнение тимлида от 14.10).

## Допущения

Ниже решения по неоднозначностям тикета. Они приняты без пользователя; при необходимости их легко поменять.

- `max_attempts=1` даёт `DEAD_LETTERED` при первом падении, а не `FAILED` (ответ тимлида от 12.10).
- `attempts` обнуляется при `requeue` (поздняя правка тимлида от 14.10). Число прошлых попыток пишется в лог.
- `retry_policy_for` возвращает действующую политику, а не только политику типа. Это соответствует названию метода и правилу замены, а не слияния.
- `set_retry_policy(тип, None)` снимает политику типа, после чего для типа действует политика по умолчанию.
- `rng=None` в `Worker` означает модуль `random` целиком; тесты всегда передают свой `rng`.
- `requeue_dead_letter` для задания вне dead-letter выбрасывает `InvalidTransitionError` (а не `JobNotFoundError`), потому что задание существует, но переход недопустим.
- `cancel()` для `DEAD_LETTERED` выбрасывает `InvalidTransitionError` через обычную таблицу переходов.
- `finished_at` у `RETRY_SCHEDULED` не заполняется, так как задание ещё не завершено.

## Решения при реализации

Мелкие решения, которых нет в спецификации; приняты при реализации, без пользователя.

- `base_delay == 0` возвращает `0.0` до любых вычислений, в том числе при `jitter > 0`: `rng` в этом случае не вызывается.
- Числовые поля `RetryPolicy` принимают `int` и `float`, но не `bool`. `non_retryable`, который не итерируется, даёт `ConfigError`.
- `set_retry_policy` с пустым `job_type` выбрасывает `ConfigError` (как `HandlerRegistry.register`), а не `InvalidJobError`.
- `requeue_dead_letter` сначала ищет задание в хранилище (`JobNotFoundError`), затем проверяет наличие записи в dead-letter (`InvalidTransitionError`).
- При исчерпании попыток воркер пишет `logger.warning`; при планировании повтора — `logger.info` с задержкой.
- `DeadLetterEntry`, `RetryPolicy` и `PermanentJobError` экспортируются из `jobq/__init__.py`.

## Risks / Trade-offs

- **[Сброс `attempts` при requeue скрывает историю повторов в данных]** → число попыток до перезапуска пишется
  в лог (`logger.info`); в самом задании его нет. Это решение тимлида, риск принят.
- **[Дежурные не увидят dead-letter в отчёте]** `dashboard.py` выводит строку статуса и список «Последние ошибки» только для `FAILED`.
  → Изменения в dashboard не входят в этот change; сообщить владельцам модуля о новых статусах.
- **[Погрешность float в ветке с логарифмами]** → Ветка работает только при переполнении; тесты сравнивают с допуском
  там, где точное значение не важно. Для обычных `attempt` (до переполнения) результат точный.
- **[Недетерминированность при `jitter > 0` без `rng`]** → В тестах и в воркере с тестовым `rng` значения предсказуемы;
  без `rng` поведение случайно, как и задумано.
- **[Память]** → Dead-letter хранится в памяти процесса, как и все задания. Очистки dead-letter нет по требованию: записи
  остаются до `requeue`. При большом объёме это станет проблемой, но пока не решается.

## Migration Plan

Изменение аддитивное. Без политики поведение прежнее, миграция данных не нужна. Откат: удалить вызовы
`set_retry_policy` и `default_retry_policy`, либо откатить коммит. Существующие задания в `RUNNING` при откате
никуда не переходят.
