## Purpose

Описывает, где задаётся политика повторов и как воркер реагирует на ошибку обработчика: окончательный сбой, повтор с задержкой или уход в dead-letter.

## ADDED Requirements

### Requirement: Политика по умолчанию и по типу задания
Очередь SHALL принимать keyword-only параметр `default_retry_policy` (по умолчанию `None`). `set_retry_policy(job_type, policy)` SHALL задавать политику типа, которая целиком заменяет дефолтную без смешивания полей; `None` SHALL убирать политику типа. `retry_policy_for(job_type)` SHALL возвращать действующую политику: свою для типа, иначе дефолт очереди, иначе `None`.

#### Scenario: Политика типа заменяет дефолт целиком
- **WHEN** у очереди дефолт с `max_attempts=5, base_delay=2`, а для типа задана политика только с `max_attempts=2`
- **THEN** `retry_policy_for` для этого типа возвращает именно заданную политику, с `base_delay=1.0`

#### Scenario: Сброс политики типа
- **WHEN** для типа вызван `set_retry_policy(job_type, None)`
- **THEN** `retry_policy_for` возвращает дефолт очереди (или `None`, если его нет)

### Requirement: Политика берётся в момент обработки ошибки
Политика SHALL определяться в момент ошибки обработчика, а не в момент постановки задания.

#### Scenario: Политику поменяли, пока задание ждало
- **WHEN** задание поставлено при одной политике, затем политика типа заменена, затем обработчик упал
- **THEN** используется новая политика

### Requirement: Без политики поведение прежнее
Если для типа нет ни своей политики, ни дефолта, первая ошибка обработчика SHALL переводить задание в `FAILED` с увеличением `jobs.failed`, без dead-letter и без повторов.

#### Scenario: Политики нет
- **WHEN** обработчик бросает исключение, политики нет
- **THEN** статус `FAILED`, `jobs.failed` +1, `dead_letters()` пуст

### Requirement: Реакция воркера на ошибку обработчика
При исключении обработчика воркер SHALL при наличии политики выбирать первый подходящий вариант:
1. ошибка неповторяема (`is_retryable` ложно) — статус `FAILED`, `jobs.failed` +1, даже если это последняя разрешённая попытка; в dead-letter не попадает;
2. попытки исчерпаны (`job.attempts >= max_attempts`) — статус `DEAD_LETTERED`, задание попадает в dead-letter, `jobs.dead_lettered` +1;
3. иначе — статус `RETRY_SCHEDULED`, `run_at` = текущее время очереди + `delay_for(job.attempts, rng)`, `jobs.retried` +1.

Во всех случаях `job.error` SHALL содержать текст последней ошибки в формате `"ИмяКласса: сообщение"`, а `job.attempts` — число уже сделанных попыток. `jobs.failed` SHALL увеличиваться только при окончательном `FAILED`. Воркер SHALL принимать keyword-only `rng` (по умолчанию `random.Random()`) и обращаться к нему только при реальном планировании повтора.

#### Scenario: Планирование повтора
- **WHEN** первая попытка из трёх упала, `base_delay=1`
- **THEN** статус `RETRY_SCHEDULED`, `run_at` = now + 1 с, `jobs.retried` = 1, `jobs.failed` = 0, `error` заполнен

#### Scenario: Исчерпание попыток
- **WHEN** упала попытка номер `max_attempts` с повторяемой ошибкой
- **THEN** статус `DEAD_LETTERED`, `jobs.dead_lettered` +1, `jobs.failed` не растёт, задержка не считается и `rng` не вызывается

#### Scenario: Неповторяемая ошибка на последней попытке
- **WHEN** обработчик на последней попытке бросает `PermanentJobError`
- **THEN** статус `FAILED`, `jobs.failed` +1, в dead-letter задания нет

#### Scenario: max_attempts равен 1
- **WHEN** `max_attempts=1` и обработчик бросил повторяемую ошибку
- **THEN** статус `DEAD_LETTERED`, а не `FAILED`

#### Scenario: Нет обработчика для типа
- **WHEN** для типа не зарегистрирован обработчик, независимо от политики
- **THEN** задание сразу `FAILED`, повторов и dead-letter нет

### Requirement: Выборка и выполнение повторов
Воркер SHALL брать `RETRY_SCHEDULED`-задание только когда наступило его `run_at`, в общей очереди с `PENDING` по времени запуска, а при равном `run_at` — в порядке исходной постановки. Задержка 0 SHALL быть допустима: такое задание готово сразу, и `run_pending()` выполняет его в том же вызове. Обработчик SHALL видеть в `job.attempts` номер текущей попытки (с 1). После успешной повторной попытки статус SHALL быть `SUCCEEDED`, `error` — `None`, `attempts` — общее число попыток.

#### Scenario: Повтор ждёт своего времени
- **WHEN** повтор запланирован через 5 с, часы не сдвигались
- **THEN** `run_once()` его не берёт; после `advance(5)` — берёт

#### Scenario: Порядок при равном run_at
- **WHEN** `PENDING`-задание, поставленное раньше, и повтор имеют одинаковый `run_at`
- **THEN** первым выполняется задание, поставленное в очередь раньше

#### Scenario: Нулевая задержка
- **WHEN** `base_delay=0` и первая попытка упала
- **THEN** один вызов `run_pending()` выполняет и повторную попытку

#### Scenario: Успех после повтора
- **WHEN** вторая попытка успешна
- **THEN** статус `SUCCEEDED`, `error is None`, `attempts == 2`, обработчик на второй попытке видел `attempts == 2`
