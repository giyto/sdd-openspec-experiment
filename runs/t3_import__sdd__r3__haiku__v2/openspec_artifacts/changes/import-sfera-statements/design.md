## Context

Импорт сейчас живёт в `ledger/importer.py`: `import_csv` читает только UTF-8 с колонками
`date,amount,description`, бросает `StatementError` на первой ошибке и пишет строки через
`store.add` по одной (см. proposal.md — Why). Ошибки уже оформлены в `ledger/errors.py`
(`StatementError(message, *, line_no)`), сравнение описаний уже есть в `ledger/rules.py`
(`normalize_text`), деньги проверяются в `ledger/models.py` (`parse_amount`, `to_money`).
Суммы — `Decimal` с двумя знаками. Хранилища: `MemoryStore.add_many` атомарен, `JsonFileStore`
пишет файл одним шагом. Требования зафиксированы в specs/statement-import/spec.md.

## Goals / Non-Goals

**Goals:**
- Один вход `import_statement` для трёх форматов с автоопределением по заголовку.
- Повторный импорт не задваивает операции; выписка за пересекающийся период добавляет только новое.
- Ошибка строки не теряет остальной файл (режим по умолчанию) или откатывает весь импорт (`strict`).
- `import_csv` сохраняет сигнатуру и `int`, но получает дедупликацию и атомарность.

**Non-Goals:**
- Не трогаем CLI и отчёты. Не добавляем флаги в CLI.
- Не вводим новые зависимости (pandas, chardet и т.п.): только стандартная библиотека.
- Не меняем хранилища: атомарность опирается на существующий `add_many`.
- Не поддерживаем форматы кроме трёх и не угадываем разделитель по содержимому строк.

## Decisions

**1. Всё в `ledger/importer.py`, исключения в `ledger/errors.py`.**
Один модуль импорта, как сейчас. Альтернатива — пакет `ledger/statements/` с отдельным модулем
на формат; отвергнута: три формата и общий конвейер пока умещаются в один файл, а `RowError`,
`ImportResult` и `import_statement` всё равно общие.

**2. Разбор через `csv.reader` с разделителем, заданным форматом.**
`nova` — `,`, `sfera` и `sfera_split` — `;`. `csv` корректно обрабатывает кавычки и многострочные
записи. Номер строки `line_no` — физическая строка, с которой начинается запись: берём
`reader.line_num + 1` до чтения очередной записи, потому что `line_num` после чтения указывает на
последнюю физическую строку записи. Альтернатива — `csv.DictReader`, как сейчас; отвергнута: он
не даёт номер начала многострочной записи и требует отдельной обработки колонок.

**3. Заголовок — строка 1, колонки ищутся по имени.**
Имена сравниваются через `strip().casefold()`. Порядок и лишние колонки не важны. Формат
распознан, если все обязательные колонки присутствуют. Если совпадают сразу два формата
(например, в заголовке есть и `Сумма`, и `Приход`/`Расход`), или обязательная колонка
встречается дважды — заголовок считается нераспознанным. Это наше решение: ticket не описывает
такие заголовки, а угадывать по неоднозначному заголовку опасно для денег.
Порядок проверки для `fmt=None`: `nova`, `sfera`, `sfera_split`; совпадение с двумя и более
форматами — `UnknownFormatError`.

**4. `UnknownFormatError` с `line_no=1` для проблем заголовка.**
Существующий тест `test_import_missing_column` ожидает `line_no == 1` для отсутствующей колонки;
`import_csv` должен его сохранить. Поэтому все ошибки заголовка (нераспознан, пустой файл, не
подходит к `fmt`, дубль колонки) несут `line_no=1`. Ошибки уровня файла (не декодируется, неизвестный
`fmt`) — `line_no=None`.

**5. Кодировка: UTF-8 целиком, иначе cp1251.**
Файл читается байтами целиком; `bytes.decode("utf-8")`, при `UnicodeDecodeError` — `decode("cp1251")`.
BOM снимается (`utf-8-sig`-семантика). Альтернатива — определять кодировку по первым строкам;
отвергнута: ticket требует проверки всего файла, а читать целиком выписку допустимо по объёму.
Если cp1251 тоже не декодируется (неопределённые байты), бросаем `UnknownFormatError` без
`line_no`. Риск: файл в cp1251, случайно являющийся валидным UTF-8, — маловероятен, принято.

**6. Суммы `sfera` проверяем регулярным выражением, а не только `to_money`.**
`to_money` сравнивает `Decimal` по значению: `Decimal("1.500") == Decimal("1.50")`, поэтому
`-1,500` прошла бы как корректная. Поэтому правило «не больше двух знаков» проверяется по тексту:
дробная часть — `\d{1,2}`. Тысячные группы — ровно по три цифры, разделитель — пробел или U+00A0
(также U+202F). Знак `+`/`-` допустим только в `sfera`. Значение затем проходит через `to_money`,
который отсекает нечисловые и нефинитные значения. Альтернатива — заменить запятую на точку и
вызвать `parse_amount`; отвергнута: `parse_amount` не принимает пробелы и пропускает `1.500`.

**7. `sfera_split`: ноль равен пустой ячейке.**
Ячейка считается пустой, если после обрезки пробелов она пуста или сумма в ней равна нулю после
разбора (то есть `0,00`). Заполнена ровно одна — знак из неё (`+`/`-`) и число → сумма с нужным знаком.
Ноль с дробью длиннее двух знаков (`0,000`) — ошибка, а не ноль: проверка формата идёт раньше.

**8. Мусорные строки — проверка до разбора колонок.**
Если все ячейки строки после `strip()` пусты, строка пропускается, не получая ни `line_no`, ни
счётчика. Проверка идёт до проверки количества полей, поэтому `,,` и `;;;` не дают «not enough fields».

**9. Дедупликация — по количеству, только против хранилища до импорта.**
Перед разбором `existing = store.all()` строится `Counter` ключей
`(date, amount, normalize_description(description))`. Затем строки из файла в порядке следования
проходят через второй счётчик: если уже учтено меньше `k` совпадений, строка — дубль; иначе —
добавляется. Строки с ошибками в дедупликации не участвуют. Альтернатива — `set` ключей; отвергнута:
не различает две одинаковые покупки за день, а product owner согласовал именно подсчёт.

**10. `normalize_description` делегирует `rules.normalize_text`.**
Ticket требует сравнивать описания так же, как везде в проекте. Дублировать логику нельзя:
`normalize_description(text)` возвращает `normalize_text(text)` и существует как публичное имя импорта.

**11. Строгий режим: сначала разбор всего файла, потом одна запись.**
При `strict=True` первая ошибка строки бросает `StatementRowError` до любой записи. В режиме по
умолчанию собираются все `RowError`, затем все новые транзакции пишутся одним вызовом
`store.add_many`. Так `JsonFileStore` пишет файл один раз, а `add_many` гарантирует «всё или ничего».
Альтернатива — писать построчно; отвергнута: частичная запись — именно та проблема, которую
решаем. Исключение из `add_many` (`StorageError`) пробрасывается наружу без изменений; хранилище
остаётся прежним, потому что `add_many` атомарен.

**12. Категоризация и `imported_at` — как сейчас.**
`imported_at = clock.now()` вызывается один раз в начале импорта. Категоризатор вызывается только
для добавляемых транзакций, чтобы не менять категорию у строк, которые в любом случае не попадут в
хранилище.

**13. Ошибки файловой системы оборачиваем в `StatementError`.**
Соглашение README: «весь код ledger бросает только наследников `LedgerError`». Поэтому `OSError`
при чтении файла превращаем в `StatementError("cannot read ...")` без `line_no`. Это видимое
изменение для `import_csv`: раньше был `FileNotFoundError`. Проверено: `ledger/cli.py:73` ловит
`LedgerError`, значит CLI отреагирует нормально. Если
вызывающий код ловит именно `OSError`, это поломка; в рамках проекта таких вызовов нет.

**14. Формат `nova` тоже получает поиск колонок без учёта регистра.**
Раньше `nova` требовал точные имена `date,amount,description`. Теперь `Date,Amount` тоже
принимается. Строгость формата `nova` в этом не нарушается: обязательные колонки те же, а
ISO-дата и `parse_amount` для `nova` не меняются.

## Risks / Trade-offs

- [Подсчёт по количеству может не добавить реально новую операцию, если выписка пересекает период
  частично и одинаковые операции повторяются] → принято продуктом (UPD от 15.10); документируем в
  README и покрываем сценариями spec.md (Requirement: Duplicate detection against the existing store).
- [cp1251 декодирует почти любые байты, поэтому ошибочная кодировка может пройти незаметно]
  → UTF-8 пробуется первым; cp1251 как fallback; в `ImportResult.encoding` видно, что выбрано.
- [Строгие тысячные группы отклонят `1 2345,00`] → это ошибка строки; пользователь увидит
  `line_no` и сообщение, а не неверную сумму.
- [`store.all()` копирует список и строит счётчик за O(n)] → для личных выписок приемлемо;
  при больших хранилищах можно будет индексировать.
- [`import_csv` теперь дедуплицирует, поэтому повторный запуск CLI ничего не добавит] → это
  целевое поведение, зафиксировано в spec.md (Requirement: Import_csv compatibility).

## Решения при реализации

Решения, которые design.md не фиксировал явно (принято при автономной реализации):

- **Заголовок разбирается разделителем своего формата.** `detect_format` пробует каждый формат с его
  разделителем (`,` для nova, `;` для sfera и sfera_split). Разделитель по содержимому строки не угадываем.
- **Дубль обязательной колонки отвергается по всем форматам-кандидатам.** В автоматическом режиме
  колонка, повторённая хотя бы в одном кандидате (например, `Приход` дважды), даёт `UnknownFormatError`.
  При явном `fmt` проверяются только колонки этого формата.
- **Запись в хранилище только при наличии новых транзакций.** Если все строки — дубли, `store.add_many`
  не вызывается, поэтому файл `JsonFileStore` не переписывается.
- **Ошибка строки в строгом режиме — первая по порядку файла.** Разбор идёт последовательно, и
  `StatementRowError` бросается сразу, до дедупликации и записи.
- **Категоризатор применяется после дедупликации.** Он вызывается только для строк, которые пойдут в
  `add_many`, и не меняет дубли.
- **`ImportResult.added` — число добавленных транзакций (`int`), `errors` — список `RowError`.**
  `RowError` — dataclass с `line_no` и `message`, не исключение.

## Migration Plan

- Миграции данных нет: хранилища и JSON-формат не меняются.
- Деплой — обычный релиз пакета. CLI не меняется, но `import` ведёт себя иначе на повторном вызове.
- Откат — возврат `ledger/importer.py` и `ledger/errors.py` к предыдущей версии; новые тесты
  удаляются вместе с ним.
