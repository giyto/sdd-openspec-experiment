## Context

Мотивация — в `proposal.md`, требования — в `specs/stock-reservations/spec.md`. Сейчас `Inventory` хранит только физические остатки в `InMemoryStore`; часы внедряются через `Clock`, журнал — `EventLog` (формат строки менять нельзя, время в полях пишется как `format_timestamp`). README требует: только stdlib, атомарность (сначала все проверки, потом изменения), никаких `datetime.now()`, модели — frozen-датаклассы, наружу только снимки. `cli.py`, `reports.py` и существующие тесты не трогаем. Публичный API из задачи не меняется (имена, сигнатуры, поля, значения enum).

## Goals / Non-Goals

**Goals:**
- Лениво вычислять истечение по `clock.now()` в момент обращения, без фоновых задач и без записи в журнал.
- Сохранить прежнее поведение `Inventory` для кода без резервов.

**Non-Goals:**
- Очистка/архивация старых резервов, персистентность, изменения CLI и отчётов.
- Новые настройки (TTL по умолчанию — константа).

## Decisions

1. **Хранение резервов в `InMemoryStore`** (словарь `order_id -> запись`), а не в `Inventory`. Конструктор принимает `store`, и резервы должны жить рядом с остатками, а не теряться при передаче того же store. Внутренняя запись изменяема (хранит статус `ACTIVE/CONFIRMED/CANCELLED`, `lines`, `created_at`, `expires_at`); наружу отдаётся только frozen `Reservation`. Альтернатива — словарь в `Inventory`: проще, но ломает разделение «store хранит состояние».

2. **Статус `EXPIRED` не хранится, а вычисляется**: эффективный статус = `EXPIRED`, если сохранённый `ACTIVE` и `now >= expires_at`; `CONFIRMED`/`CANCELLED` возвращаются как есть. Это единственная точка вычисления (приватный помощник), которой пользуются `get_reservation`, `reserved`, `confirm`, `cancel`, `extend`, `reserve`. Один вызов `clock.now()` на операцию, чтобы все проверки внутри операции видели один момент.

3. **`reserved` — сумма по активным записям.** Поиск линейный по всем резервам; для in-memory сервиса достаточно. Можно держать индекс, но он усложнит ленивое истечение (нужно пересчитывать по времени) — отвергнуто. `available = max(0, on_hand - reserved)`. Обе проверяют SKU/склад как `on_hand` (`UnknownSkuError`).

4. **Атомарность по схеме «проверки → изменения».**
   - `reserve`: проверки в порядке — `order_id` (код), `ttl` (`None` → `DEFAULT_RESERVATION_TTL`; иначе `timedelta > 0`), нормализация `lines` в `tuple[ReservationLine, ...]` (итерируемое читается один раз; кортеж из трёх или `ReservationLine`; склад — код, SKU известен, `qty` — через `_validate_qty`), непустота, дубликат (активный/подтверждённый → `DuplicateReservationError`), затем достаточность по сумме строк на позицию (`InsufficientStockError(wh, sku, сумма, available)`; позиции проверяются в порядке первого появления). Только после этого запись в store (заменяет прежнюю истёкшую/отменённую) и события `RESERVE` по строкам.
   - `confirm`: найти → статус (`EXPIRED` → `ReservationExpiredError`, `CONFIRMED`/`CANCELLED` → `ReservationStateError`) → физический остаток по суммам позиций → списание по строкам и события `ISSUE` (`ref=order_id`) → `RESERVE_CONFIRM`. Списание делается напрямую через store, а не через публичный `issue`, чтобы не упереться в проверку `available`; формат события `ISSUE` тот же, что у `issue`.
   - `cancel`: `ACTIVE` → `CANCELLED` + `RESERVE_CANCEL`; `CANCELLED`/`EXPIRED` → no-op со снимком; `CONFIRMED` → `ReservationStateError`.
   - `extend`: `ttl` → найти → статусы как у `confirm` → `new = now + ttl`; если `new > expires_at`, обновить и записать `RESERVE_EXTEND`, иначе no-op.

5. **`issue` и `transfer` ограничиваются `available`** вместо физического остатка. `InsufficientStockError.available` получает значение `available`. Когда резервов нет, `available == on_hand`, поведение прежнее. `transfer` включён по docstring («проверки те же, что у `issue`»); `adjust` не ограничивается (это факт).

6. **Время в журнале.** Поле `expires` передаётся строкой через `format_timestamp(expires_at)` (секундная точность, как у времени события). В снимке `expires_at`/`created_at` не округляются. Следствие: при микросекундах в `ttl` значение в журнале усечено, а сравнение с `now` идёт по точным значениям.

7. **Код модулей.** `ReservationStatus`, `ReservationLine`, `Reservation` — в `models.py`; ошибки с атрибутом `order_id` — в `errors.py` (по образцу существующих); `reservations.py` — `DEFAULT_RESERVATION_TTL` и чистые помощники (нормализация строк, суммирование по позициям, вычисление эффективного статуса), без зависимости от `Inventory`, чтобы не было циклических импортов. Логирование — `logging.getLogger(__name__)`.

## Risks / Trade-offs

- [Резервы растут без очистки (истёкшие остаются в store)] → допустимо для in-memory хранилища; очистку можно добавить отдельной задачей.
- [`reserved` линейный по числу резервов] → приемлемо на текущих объёмах; при росте — индекс по позиции.
- [Усечение `expires` в журнале до секунд] → соответствует соглашению README о формате времени в полях событий.
- [Включение `transfer` в защиту резервов выходит за дословный текст задачи] → зафиксировано как допущение в `proposal.md`; при возражении убирается одной правкой.
- [Порядок ошибок при нескольких нарушениях (напр. неверный `ttl` и несуществующий заказ в `extend`)] → зафиксирован в проверках выше; детали вне тестируемых сценариев.

## Implementation notes

- `normalize_lines` в `reservations.py` приводит только форму строк; проверка содержимого (код склада, SKU, qty) остаётся в `Inventory`, чтобы не дублировать валидаторы и не создавать циклических импортов.
- Изменяемая внутренняя запись `ReservationRecord` лежит в `reservations.py`, `storage.py` импортирует её оттуда.
- `issue`/`transfer` берут одно значение `clock.now()` и для проверки `available`, и для события журнала.
