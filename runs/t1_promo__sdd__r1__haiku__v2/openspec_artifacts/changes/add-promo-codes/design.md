## Context

Пакет `shop` состоит из чистых модулей: `pricing.calculate_total` считает итоги без побочных эффектов,
`OrderService` хранит заказы в памяти (`OrderStore`), время приходит через `Clock`. Правила денег,
ошибок, времени и нормализации кодов описаны в README («Соглашения»). Мотивация — в proposal.md.
Требования — в `specs/promo-codes/spec.md` и `specs/promo-discounts/spec.md`.

Ограничения: `shop/cli.py` и `shop/reports.py` не меняются; существующие тесты не меняются; новых
зависимостей нет; все новые параметры — необязательные, с умолчаниями, которые дают прежнее поведение.

## Goals / Non-Goals

**Goals:**
- Промокод проходит через `calculate_total` и `OrderService` как необязательный аргумент.
- Скидка по строкам сходится в копейку с общей скидкой; налог и порог доставки учитывают скидку.
- Счётчик использований меняется только при успешном оформлении и при отмене заказа.

**Non-Goals:**
- Персистентность реестра и счётчиков; всё остаётся в памяти, как `OrderStore`.
- Блокировки между процессами или потоками; защита от гонки ограничена одним процессом (см. Risks).
- Скидки в CLI и отчётах (отдельный тикет).

## Decisions

**Модуль и зависимости.** `shop/promo.py` содержит `DiscountKind`, `PromoCode`, `PromoRegistry`.
`pricing.py` и `orders.py` импортируют из него; `promo.py` импортирует только `catalog`, `clock`,
`errors`, `money`. Циклов нет.

**Нормализация.** `PromoCode.__post_init__` приводит `code` через `normalize_key` (как `Product.sku`).
Поиск в `PromoRegistry.resolve` тоже идёт через `normalize_key`. Пустой результат не находится и даёт
`UnknownPromoCodeError`. Повторная регистрация — `ValidationError`.

**Проверки в `resolve`.** Порядок: существование → срок (`starts_at <= now < expires_at`, `None` —
без границы) → лимит (`uses >= max_uses` → `PromoConditionsError`). Срок и лимит живут в реестре, как
сказано в API тикета. Условия заказа (минимальная сумма, участвующие строки) проверяются в
`calculate_total`.

**Счётчик — два дополнительных метода реестра.** Тикет задаёт API `add`/`resolve`/`uses`, но не
описывает, как считаются использования. Добавляем `PromoRegistry.consume(code)` и
`PromoRegistry.release(code)`. `consume` повторно проверяет лимит и увеличивает счётчик в одном вызове,
так что проверка и инкремент неделимы относительно вызывающего кода. Альтернатива — счётчик в
`OrderService` — отвергнута: лимит тогда проверялся бы в двух местах.

**Порядок в `place_order`.** `_resolve_promo(code)` → `calculate_total` (через `quote`) → `consume` →
`store.add`. Если что-то падает до `consume`, счётчик не меняется. `next_id` вызывается после расчёта,
как и сейчас, поэтому неудачные попытки не сжигают номера заказов. `cancel` для заказа с
`promo_code` вызывает `release`.

**Пустой код.** `_resolve_promo` возвращает `None`, если `promo_code is None` или `normalize_key(...)`
даёт пустую строку. Реестр в этом случае не трогается, даже если он не подключён.

**Алгоритм скидки в `pricing.py`.** Считаем в целых копейках, чтобы не зависеть от контекста `Decimal`:
- участвующие строки: не сертификат и не в `excluded_categories`; их индексы в `cart.lines` сохраняем;
- `E` — сумма участвующих строк до скидки (`CartLine.amount`), `E > 0`, иначе `PromoConditionsError`;
- `E < min_order_amount` → `PromoConditionsError` (сравнение `>=` подходит);
- процент: `D = quantize_money(E * value / 100)`; фикс: `D = min(value, E)`;
- для каждой участвующей строки `a_i` (копейки): `q_i, r_i = divmod(D * a_i, E)`;
- остаток `R = D - sum(q_i)` (всегда `0 <= R < число строк`); копейки раздаём строкам по убыванию `r_i`,
  при равенстве — по возрастанию индекса в корзине;
- строка получает `discount_i = q_i (+1 копейка, если она в числе R)`; неучаствующим — `0.00`.

**Налог и доставка.** Налог строки — `tax_for(category, amount - discount_i)`. Доставка —
`shipping.cost_for(subtotal - discount, needs_delivery=...)`, `needs_delivery` без изменений.

**Обратная совместимость.** `LineTotal.discount: Decimal = ZERO` и `OrderTotal.discount: Decimal = ZERO`
добавляются последними полями; `Order.promo_code: str | None = None` — после `status`. `subtotal`
остаётся суммой строк до скидки, поэтому `total = subtotal - discount + shipping + tax` выполняется
и без промокода.

**Допущения (неоднозначности тикета):**
1. Фиксированная скидка больше суммы участвующих строк **ограничивается** этой суммой, а не отвергается:
   тикет говорит «не может быть больше», а не «заказ не подходит».
2. Процент, при котором скидка округляется до `0.00`, всё равно засчитывает использование.
3. `uses(code)` для неизвестного кода выбрасывает `UnknownPromoCodeError`.
4. Порог доставки сравнивает `subtotal - discount`, куда входят суммы сертификатов, как и сейчас.
5. Реестр и `OrderService` получают один и тот же `Clock` (в тестах — `FixedClock`).
6. Поля `PromoCode.value` для фиксированной скидки — рубли с не более чем двумя знаками, как `Product.price`.
7. Процентная скидка проверяется как `0 < value <= 100` и принимает дробные значения (например, `12.5`).
8. README обновляется разделом о промокодах, потому что правила расчёта в нём описаны полностью.

## Risks / Trade-offs

- **Гонка при оформлении из нескольких процессов** → счётчик в памяти, как и `OrderStore`; в одном процессе
  `consume` атомарен относительно лимита. Для HTTP-слоя с несколькими воркерами нужна внешняя
  синхронизация — это вне тикета, фиксируем как ограничение.
- **Два источника времени** (реестр и `OrderService`) могут разойтись → сервис создаётся с одним `Clock`;
  тесты используют один `FixedClock`.
- **Потеря счётчика при перезапуске** → принято: хранилища заказов тоже в памяти.
- **Регрессии в старых вызовах** → все новые параметры необязательны, существующие тесты остаются без
  изменений и служат проверкой совместимости.
- **Скидка 100 % делает строки нулевыми** → порог доставки после скидки может вернуть доставку 299.00;
  это соответствует правилу «доставку промокод не трогает», но стоит проверить тестом.

## Migration Plan

Изменение аддитивное: новые модули и поля с умолчаниями. Миграций данных нет. Откат — revert коммитов
реализации; никакие сохранённые данные не требуют преобразования, потому что заказы в памяти.

## Решения при реализации

- `PromoRegistry.release` при нулевом счётчике выбрасывает `ValidationError`: отмена возможна только для
  размещённого заказа, а размещение уже увеличило счётчик, поэтому это нарушение инварианта.
- `OrderService.cancel` заказа с промокодом у сервиса без реестра выбрасывает `UnknownPromoCodeError`;
  заказ остаётся `placed`, счётчик не трогается.
- `place_order` вызывает `consume` до `store.next_id()`, а не только до `store.add`. Так отказ по лимиту
  или сроку не сжигает номер заказа (требование spec «номера заказов не сжигаются при ошибке»).
- `PromoRegistry.consume` ничего не возвращает: он вызывает `resolve` (все проверки) и увеличивает счётчик.
- `PromoRegistry(clock)` принимает `Clock` так же, как `OrderService`: при `None` берётся `SystemClock`.
- Подарочные сертификаты исключаются из скидки явной проверкой `Category.GIFT_CARD`, а не через `is_physical`,
  чтобы правило читалось прямо из spec.
- Раскладка скидки проверяется на случайных корзинах с фиксированным seed: сумма скидок строк всегда равна
  скидке заказа, а итог равен `subtotal - discount + shipping + tax`.
- `shop/__init__.py` экспортирует `DiscountKind`, `PromoCode`, `PromoRegistry`; версия пакета не менялась.
