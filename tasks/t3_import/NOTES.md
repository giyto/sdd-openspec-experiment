# t3_import — заметки автора задачи

Brownfield-пакет `ledger` (учёт финансов): `Transaction` (frozen dataclass, деньги в
`Decimal`, валидация в `__post_init__`), хранилища `MemoryStore`/`JsonFileStore`
(`add_many` — одна запись на диск), правила категоризации, иерархия исключений,
внедряемые часы. Существующий `import_csv` неатомарен (пишет построчно через `store.add`),
читает строго UTF-8 через `DictReader` и нумерует строки через `enumerate`.

## Почему нетривиально

Требования сами по себе простые, сложность во взаимодействии:
кодировка × формат × пустые строки × нумерация строк × дедупликация × атомарность × старый API.

## Ловушки

1. **BOM ломает автоопределение**: при чтении `encoding="utf-8"` первая колонка
   становится `"﻿Дата"` / `"﻿date"` и заголовок не распознаётся. Нужен `utf-8-sig`.
2. **Кодировка по заголовку, а не по файлу**: заголовок `nova` чисто ASCII, кириллица в cp1251
   только в последней строке — определение по первой строке выберет UTF-8 и упадёт/исказит.
3. **NBSP (U+00A0) в cp1251** — байт `0xA0`; после правильного декодирования его надо
   вычистить как разделитель тысяч, `replace(" ", "")` этого не делает.
4. **Дубли внутри файла не дубли + подсчёт по количеству (multiset)**. Наивная реализация
   либо дедуплицирует через `set` (теряет второй кофе), либо добавляет построчно и сверяется
   с уже обновлённым хранилищем (второй кофе становится «дублем» первого). Правильно —
   `Counter` по состоянию хранилища до импорта.
5. **Нормализация**: `casefold()`, а не `lower()` (тест на `Straße`), `ё→е` после casefold
   (чтобы `Ё` тоже заменилось), NBSP/табы/переводы строк схлопываются; а в хранилище
   сохраняется исходное описание (только `strip`), не нормализованное.
6. **`0,00` в неиспользуемой колонке `sfera_split`** равно пусто; `0,00`/`0,00` — ошибка
   «ни одна не заполнена», а не нулевая транзакция; знак в колонках запрещён.
7. **Точка и >2 знаков в суммах sfera** — ошибки строки (`12,345` легко принять за тысячи).
8. **Нумерация строк физическая**: `enumerate(DictReader)` сбивается на пустых строках
   (DictReader их пропускает) и на многострочных записях в кавычках; нужен `reader.line_num`
   на начало записи.
9. **Пустые строки из разделителей** (`;;;`, ` ; ; `, `,,`): `DictReader` пропускает только
   совсем пустые строки, строка `;;` даёт словарь пустых значений → ложная ошибка.
10. **Ошибки модели — тоже ошибки строки**: нулевая сумма и пустое описание бросают
    `ValidationError` из `Transaction`, её надо превратить в `RowError`/`StatementRowError`,
    а не дать улететь наружу.
11. **Атомарность strict**: построчное `store.add` оставляет частичный импорт в памяти и в
    JSON-файле; надо сначала разобрать весь файл, потом один `add_many`. `UnknownFormatError` —
    в любом режиме и тоже без записи (не создавать JSON-файл).
12. **Порядок колонок и лишние колонки**: индексы по имени, а не по позиции; заголовок без учёта
    регистра/пробелов (`" ДАТА"`, `"СУММА "`).
13. **Явный `fmt` не отключает проверку заголовка**: несовпадение — `UnknownFormatError`.
14. **`import_csv` через новый механизм**: должен стать строгим, атомарным, с дедупликацией,
    BOM/cp1251 и пропуском пустых строк, но сохранить сигнатуру, `int`-результат и
    `StatementError`; при этом существующий тест `test_import_missing_column` требует
    `line_no == 1` у ошибки заголовка — `UnknownFormatError` надо создавать с `line_no=1`.
15. **Дедупликация между форматами**: суммы из `-1200.5` (nova) и `-1 200,50` (sfera) должны
    совпасть — ключ строится по `Decimal`/дате, а не по сырым строкам.
16. **Рамки**: `cli.py`/`reports.py` не трогать (CLI автоматически получает новое поведение через
    `import_csv`), существующие тесты не менять.

## CR (этап 2, LEDGER-74)

`cr_ticket.md`: тело 355 слов, обсуждение из 5 реплик. Поправка к п.3 — схлопывать не только
пробелы, но и переводы строк и табы. UPD к п.6 — в `dry_run` поле `transactions` заполняется, но с `id=None`.
Эталон — `reference_cr/` (`importer.py`, `errors.py`, README); тесты — `hidden_tests_cr/` (32 теста, C01–C10).

Что меняется по сравнению с этапом 1:
- **changed**:
  - C01 — точка как десятичный разделитель в «Сфере» (раньше это была ошибка строки);
  - C02 — `0,00`/`0,00` в `sfera_split` теперь служебная строка, её пропускаем (раньше это была ошибка);
  - C03 — описание хранится со схлопнутыми пробельными символами (раньше «как пришло», только `strip`);
  - C04 — strict разбирает файл до конца и бросает `StatementRowError.errors` со всеми ошибками.
- **new**:
  - C05 — параметр `dry_run`;
  - C06 — поле `ImportResult.transactions`;
  - C07 — поле `RowError.raw`.
- **interaction**:
  - C08 — `dry_run` подчиняется дедупликации по количеству, правилам strict, `UnknownFormatError` и пустых строк;
  - C09 — суммы с точкой проходят через прежние правила: больше двух знаков — ошибка, ноль = пусто, знак в колонках split — ошибка, NBSP, дедупликация между форматами;
  - C10 — схлопнутые описания работают с `normalize_text`, дедупликацией по количеству, категоризацией и `import_csv`.

Invalidated тесты этапа 1 (5):
- `test_R03_dot_in_sfera_amount_is_row_error` — из-за C01;
- `test_R04_both_or_neither_filled_is_row_error` — из-за C02;
- `test_R10_strict_raises_row_error_with_line` — первая ошибка в `STRICT_BAD` была суммой с точкой, теперь первая ошибка на строке 5;
- `test_R12_description_stored_as_in_file` — из-за C03;
- `test_R09_multiline_record_line_number` — проверяет описание с `\n`; нумерация строк по-прежнему верна, её покрывает C07.

Ловушки:
- `0,00` + пусто остаётся ошибкой; агент, который трактует C02 как «ноль = пусто, значит обе пустые = пропуск», ломает это.
- Пустые обе колонки — тоже по-прежнему ошибка (правило этапа 1, тикет CR его не повторяет).
- Точка + правило «не больше двух знаков» и смешанные разделители `1.234,56`/`1,234.56`.
- Схлопывание пробелов в хранимом описании не должно сломать дедупликацию с уже сохранёнными
  описаниями, где пробелы не схлопнуты: ключ строится по `normalize_text`, а не по сохранённой строке.
- `import_csv` (строгий импорт через новый механизм из обсуждения этапа 1) тоже получает C03 и C04.
- `dry_run` легко реализовать отдельной веткой и потерять правила этапа 1: дубли внутри файла считаются по количеству,
  strict бросает исключение, JSON-файл не создаётся.
- `raw` нужно строить по физическим строкам: многострочная запись, CRLF, cp1251. Имеет смысл переиспользовать
  нумерацию строк из этапа 1.
- `transactions` — это объекты с `id` от хранилища (результат `add_many`), а не исходные объекты без id.

Проверка: `reference_cr` проходит 41/41 проектных тестов, 56/61 тестов этапа 1 (не проходят ровно 5 invalidated)
и 32/32 тестов CR. `reference` (этап 1) проходит 41/41 и 61/61, а из тестов CR проходит только 1 из 32 —
`test_C02_zero_and_empty_is_still_error`: он проверяет сохранение старого правила, и это допустимо.
