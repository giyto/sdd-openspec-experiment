# SHOP-412. Промокоды при оформлении заказа

**Контекст.** Маркетинг запускает летнюю кампанию с промокодами, сейчас скидки делаются вручную
через поддержку и постоянно расходятся с чеками. Нужно, чтобы промокод можно было передать при
расчёте и оформлении заказа, а скидка честно отражалась в итогах и в построчном чеке (бухгалтерия
считает налог по строкам, поэтому скидка должна быть разложена по строкам, а не висеть одной цифрой).

## Что нужно сделать

Новый модуль `shop/promo.py`:

* `DiscountKind` — enum с двумя значениями: `PERCENT` (процент от суммы) и `FIXED` (фиксированная
  сумма в рублях).
* `PromoCode` — замороженный датакласс с полями (именно в таком порядке):
  `code: str`, `kind: DiscountKind`, `value: Decimal`,
  `min_order_amount: Decimal = Decimal("0.00")`, `starts_at: datetime | None = None`,
  `expires_at: datetime | None = None`, `max_uses: int | None = None`,
  `excluded_categories: frozenset[Category] = frozenset()`.
* `PromoRegistry(clock: Clock)` — реестр промокодов в памяти со счётчиками использований:
  `add(promo: PromoCode) -> None`, `resolve(code: str) -> PromoCode`, `uses(code: str) -> int`.
  `resolve` возвращает промокод, если он существует, действует в текущий момент (по часам реестра)
  и не исчерпан; иначе бросает исключение (см. ниже).

Новые исключения положить в `shop/errors.py` рядом с остальными:
`PromoError(ShopError)` — общий предок, и три его наследника, не наследующие друг от друга:
`UnknownPromoCodeError` (такого кода нет), `PromoExpiredError` (код вне срока действия),
`PromoConditionsError` (код есть и действует, но к этому заказу не применим).

Изменения в существующем коде:

* `calculate_total(cart, shipping=None, tax=None, *, promo: PromoCode | None = None)` —
  новый необязательный keyword-only параметр. `calculate_total` ничего не знает о времени и о
  счётчиках: срок действия и лимит проверяет реестр, а `calculate_total` проверяет только условия
  самого заказа (минимальная сумма, наличие участвующих товаров).
* `LineTotal` и `OrderTotal` получают поле `discount: Decimal` (`Decimal("0.00")`, если скидки нет).
* `OrderService(..., promos: PromoRegistry | None = None)` — новый keyword-only параметр
  конструктора; `quote(cart, promo_code: str | None = None)` и
  `place_order(cart, promo_code: str | None = None)`; у `Order` появляется поле
  `promo_code: str | None` (нормализованный код или `None`).

## Правила

1. **Процентная скидка** — `value` процентов (например `Decimal("10")` = 10 %, дробные проценты
   допустимы) от суммы участвующих в акции строк. Результат округляем до копеек по правилам
   проекта (`ROUND_HALF_UP`).
2. **Фиксированная скидка** — `value` рублей, но не больше суммы участвующих строк. Итог заказа не
   может уйти в минус, а то, что в акции не участвует, оплачивается полностью.
3. **Что участвует в скидке.** Подарочные сертификаты (`Category.GIFT_CARD`) не участвуют в скидке
   никогда, ни при каком промокоде. Дополнительно у каждого кода может быть свой список
   `excluded_categories`. Строки из исключённых категорий получают скидку 0.
4. **Минимальная сумма заказа** (`min_order_amount`) сравнивается с суммой только участвующих строк,
   до скидки, без налога и доставки. Ровно равная сумма подходит. Не дотянули — `PromoConditionsError`.
   Если участвующих строк нет совсем (например, в корзине одни сертификаты) — тоже
   `PromoConditionsError`, даже если минимальной суммы у кода нет.
5. **Срок действия** задаётся `starts_at`/`expires_at` (любая граница может отсутствовать). Время —
   только из внедрённых часов, никаких `datetime.now()`. Код действует, если
   `starts_at <= now < expires_at`, то есть начало включительно, конец — нет. И «ещё не начался»,
   и «уже закончился» — это `PromoExpiredError`, отдельного исключения не нужно.
6. **Лимит использований** `max_uses` (`None` — без лимита). Использованием считается только успешно
   оформленный заказ (`place_order`). `quote` и `calculate_total` счётчик не трогают, неудачная попытка
   оформления (любое исключение) — тоже. Когда счётчик достиг лимита, `resolve` и `place_order`
   бросают `PromoConditionsError`.
7. **Ввод кода.** Покупатели вводят код как попало: регистр не важен, пробелы по краям обрезаем.
   `PromoCode` сам нормализует `code` при создании (`" summer10 "` → `"SUMMER10"`), реестр ищет
   по нормализованному коду, `uses()` принимает код в любом виде. Два кода, совпадающих после
   нормализации, в реестр добавить нельзя — `ValidationError`.
8. **Порядок проверок**: сначала существование кода, потом срок действия, потом лимит и условия
   заказа. То есть просроченный код, по которому к тому же не набрана минимальная сумма, —
   это `PromoExpiredError`.
9. **Раскладка скидки по строкам** (для чека). Сумма `discount` по строкам должна в точности
   совпадать с `OrderTotal.discount`. Алгоритм: каждой участвующей строке начисляем её долю
   `скидка × сумма_строки / сумма_участвующих_строк`, округлённую **вниз** до копейки; оставшиеся
   после этого копейки раздаём по одной строкам с наибольшей отброшенной дробной частью, при
   равенстве — строке, которая раньше в корзине. Доля считается от суммы строки (цена × количество),
   а не от цены.
10. **Налог** считается после скидки, по-прежнему построчно: база налога строки — её сумма минус её
    доля скидки, ставка — ставка категории строки, округление в каждой строке.
11. **Доставка.** Скидка на доставку не распространяется (доставку оплачивают полностью), а вот порог
    бесплатной доставки теперь сравнивается с суммой товаров **после** скидки — маркетинг не хочет
    дарить доставку тем, кто «добрал» до порога только за счёт промокода.
    Итого: `total = subtotal - discount + shipping + tax`, где `subtotal` — как и раньше,
    сумма строк до скидки.
12. **Валидация `PromoCode`** (в `__post_init__`, как у остальных моделей, исключение —
    `ValidationError`): код не пустой после обрезки пробелов; для `PERCENT` значение в диапазоне
    `(0, 100]`; для `FIXED` — строго больше нуля; `max_uses`, если задан, не меньше 1; если заданы обе
    границы срока, `starts_at` строго раньше `expires_at`.

Кстати, про оформление: `place_order` записывает в заказ нормализованный код и списывает
использование только после того, как заказ реально сохранён. Если в сервисе не настроен реестр
промокодов, любой переданный код считается несуществующим (`UnknownPromoCodeError`). Пустая строка
или строка из одних пробелов в `quote`/`place_order` — это «промокод не указан» (так приходит пустое
поле формы), а не ошибка. И ещё: при отмене заказа (`cancel`) использованный в нём промокод
возвращается — счётчик уменьшается на один, иначе поддержка не сможет переоформить заказ клиенту
с лимитированным кодом.

## Ограничения

* Обратная совместимость: все существующие вызовы `calculate_total(cart)`,
  `calculate_total(cart, shipping, tax)`, `OrderService(...)`, `quote(cart)`, `place_order(cart)`
  должны работать как раньше и давать те же суммы. Без промокода поведение не меняется.
* `shop/cli.py` и `shop/reports.py` в этой задаче не трогаем (поддержка CLI и отчётов по скидкам —
  отдельным тикетом). Существующие тесты не меняем — новые тесты добавляйте отдельными файлами.
* Новых зависимостей не добавляем, только стандартная библиотека. Соглашения проекта (Decimal,
  свои исключения, внедрённые часы, логгер модуля) — см. README.
