# WH-214: Резервирование товара под заказы с TTL

## Зачем

Интернет-магазин сейчас списывает товар только в момент отгрузки. Пока заказ собирается
и оплачивается (обычно 5–15 минут), тот же товар успевают продать второму покупателю,
и потом склад звонит и извиняется. Нужно, чтобы при оформлении заказа товар
резервировался под этот заказ, а если заказ не оплатили — резерв сам «отваливался»
через заданное время. Фоновых задач/планировщиков у нас нет и не будет, поэтому
истечение резерва должно определяться по часам в момент обращения.

Всё делаем в существующем сервисе `warehouse.inventory.Inventory`, по соглашениям из README
(внедрённые часы, свои исключения, атомарность, журнал событий).

## Новые публичные имена

**`warehouse/models.py`**

* `ReservationStatus` — `Enum` со строковыми значениями (наследник `str`):
  `ACTIVE = "active"`, `EXPIRED = "expired"`, `CONFIRMED = "confirmed"`, `CANCELLED = "cancelled"`.
* `ReservationLine(warehouse: str, sku: str, qty: int)` — frozen dataclass, строка резерва.
* `Reservation(order_id: str, lines: tuple[ReservationLine, ...], created_at: datetime,
  expires_at: datetime, status: ReservationStatus)` — frozen dataclass, снимок резерва.
  `lines` — строки в том порядке, в каком их передали (без склейки).

**`warehouse/errors.py`** — у всех атрибут `order_id`:

* `ReservationError(WarehouseError)` — базовая для ошибок резервов;
* `ReservationNotFoundError(ReservationError)` — резерва с таким `order_id` нет;
* `ReservationExpiredError(ReservationError)` — резерв истёк;
* `ReservationStateError(ReservationError)` — операция недопустима в текущем статусе
  (например, резерв уже подтверждён);
* `DuplicateReservationError(ReservationError)` — на этот заказ уже есть резерв.

**`warehouse/reservations.py`** — константа `DEFAULT_RESERVATION_TTL = timedelta(minutes=15)`
(и всё, что понадобится для реализации, на ваше усмотрение).

**Новые методы `Inventory`:**

```python
reserve(order_id: str, lines: Iterable[tuple[str, str, int] | ReservationLine],
        ttl: timedelta | None = None) -> Reservation
confirm(order_id: str) -> Reservation
cancel(order_id: str) -> Reservation
extend(order_id: str, ttl: timedelta) -> Reservation
get_reservation(order_id: str) -> Reservation
available(warehouse: str, sku: str) -> int
reserved(warehouse: str, sku: str) -> int
```

Строка заказа — кортеж `(warehouse, sku, qty)` или `ReservationLine`.
Все методы, возвращающие `Reservation`, отдают снимок с актуальным на текущий момент статусом.

## Требования

1. **Резервирование заказа.** `reserve` резервирует сразу все строки заказа (строки могут
   быть на разных складах). Физический остаток (`on_hand`) при этом не меняется. Возвращается
   снимок со статусом `ACTIVE`, `created_at` = текущее время по часам сервиса,
   `expires_at = created_at + ttl`. Если `ttl` не передан — `DEFAULT_RESERVATION_TTL`.
   `ttl` должен быть положительным `timedelta`, иначе `ValidationError`.
   `order_id` — непустая строка без пробелов (как и все коды, он попадает в журнал),
   иначе `ValidationError`; пустой список строк — тоже `ValidationError`.

2. **Всё или ничего.** Если хотя бы одной позиции не хватает, `reserve` бросает
   `InsufficientStockError` и не резервирует ничего — ни одной строки, и в журнал
   ничего не пишется. В исключении `warehouse`/`sku` — проблемной позиции, `requested` —
   сколько запрошено по этой позиции в заказе, `available` — сколько доступно.
   Ошибки в данных строки (неизвестный SKU — `UnknownSkuError`, кривое количество —
   `InvalidQuantityError`) тоже ничего не резервируют.

3. **Доступный остаток.** `available(wh, sku)` = физический остаток минус сумма активных
   резервов по этой позиции; `reserved(wh, sku)` — сумма активных резервов. Резервирование
   проверяется по доступному остатку, а не по физическому. Для неизвестного SKU оба метода
   бросают `UnknownSkuError`, как `on_hand`.

4. **Истечение по TTL.** Резерв активен строго до `expires_at`: в момент `expires_at` он уже
   истёкший. Истёкший резерв просто перестаёт учитываться в `available`/`reserved`
   и получает статус `EXPIRED` в снимках — без всякого фонового процесса, по часам сервиса
   в момент обращения. Само истечение в журнал не пишется.

5. **Подтверждение.** `confirm(order_id)` превращает активный резерв в отгрузку:
   физический остаток по каждой строке уменьшается, резерв переходит в `CONFIRMED`
   и больше не учитывается в `reserved`. Подтверждение должно проходить, даже если
   доступный остаток по позиции нулевой — товар ведь зарезервирован именно под этот заказ.

6. **Ошибки подтверждения.** Подтверждение истёкшего резерва — `ReservationExpiredError`;
   уже подтверждённого или отменённого — `ReservationStateError`; несуществующего —
   `ReservationNotFoundError`. В любом из этих случаев ничего не меняется.

7. **Отмена.** `cancel(order_id)` освобождает резерв (статус `CANCELLED`). Отмена идемпотентна:
   повторная отмена — не ошибка и ничего не делает (ни событий, ни изменений). Отмена
   истёкшего резерва — тоже не ошибка и ничего не делает, статус остаётся `EXPIRED`.
   Отменить подтверждённый резерв нельзя — `ReservationStateError`. Несуществующий —
   `ReservationNotFoundError`.

8. **Продление.** `extend(order_id, ttl)` продлевает активный резерв: новый срок считается
   **от текущего момента**, а не от старого `expires_at`, но срок никогда не сокращается —
   если `now + ttl` не позже текущего `expires_at`, ничего не меняется и событие не пишется.
   Истёкший резерв продлить нельзя (`ReservationExpiredError`), подтверждённый/отменённый —
   `ReservationStateError`; `ttl` проверяется так же, как в `reserve`.

9. **Повторный reserve на тот же заказ.** Если по `order_id` уже есть активный или
   подтверждённый резерв — `DuplicateReservationError`, ничего не меняется (резервы не
   «сливаются» и не заменяются). Если прежний резерв истёк или отменён — разрешаем, новый
   резерв полностью заменяет старый.

10. **Журнал.** События резервов пишутся в тот же `EventLog` в существующем формате:
    * `reserve` — по одному событию `RESERVE` на каждую строку заказа, в порядке строк,
      поля `order`, `wh`, `sku`, `qty`, `expires`;
    * `confirm` — по одному обычному событию `ISSUE` на каждую строку (поля как у расхода,
      `ref` = номер заказа), а затем одно `RESERVE_CONFIRM` с полем `order`;
    * `cancel` — `RESERVE_CANCEL` с полем `order`;
    * `extend` — `RESERVE_EXTEND` с полями `order`, `expires` (новый срок).

    `expires` пишется в том же формате, что и время события (`2026-03-01T10:15:00Z`), —
    выгрузка разбирает журнал через `parse_line`. Неудачная операция не пишет ничего.

11. **Расход и перемещение уважают резервы.** `issue` не может забрать товар, который
    зарезервирован под чужие активные заказы: если `qty` больше доступного остатка —
    `InsufficientStockError` (в `available` — доступный остаток), ничего не меняется.
    Истёкшие резервы, разумеется, не мешают. Кстати, перемещение (`transfer`) — это тоже
    расход со склада-источника, правило то же.

12. **Инвентаризация — это факт.** `adjust` по-прежнему ставит посчитанное количество без
    проверок, даже если физический остаток станет меньше активных резервов. В такой
    ситуации `available` не уходит в минус, а показывает 0. А `confirm` проверяет
    физический остаток по своим строкам: если товара физически не хватает хотя бы по одной
    строке — `InsufficientStockError`, ничего не списывается, резерв остаётся активным.

Кстати, про заказы, где одна и та же позиция (склад + SKU) встречается в нескольких
строках, — такое бывает, когда в корзину дважды добавили один товар. Проверять наличие
нужно по сумме таких строк, а не по каждой отдельно (и в `reserve`, и в `confirm`).

И ещё: статусы `CONFIRMED` и `CANCELLED` окончательные — если время резерва потом
прошло, снимок всё равно показывает `CONFIRMED`/`CANCELLED`, а не `EXPIRED`.

## Рамки

* Публичный API сервиса не ломаем: конструктор `Inventory(store=None, clock=None, log=None)`,
  сигнатуры и поведение `receive/issue/transfer/adjust/on_hand/stock_levels` для кода
  без резервов остаются прежними. `on_hand` и `stock_levels()` по-прежнему показывают
  физический остаток.
* `warehouse/cli.py` и `warehouse/reports.py` не трогаем — отчёты должны продолжить работать
  как есть (подтверждённые заказы попадают в сводку движения как обычный расход).
* Существующие тесты в `tests/` не меняем (новые файлы с тестами добавлять можно).
  Новых зависимостей не добавляем.
