# JOBQ-212: Повторы упавших заданий и dead-letter очередь

## Зачем

Сейчас любое исключение в обработчике сразу переводит задание в `FAILED`, и дальше его
перезапускают руками. Большая часть падений у нас временная (таймауты почтового шлюза,
503 от биллинга), поэтому дежурные каждое утро перезапускают десятки заданий. Нужна
настраиваемая политика повторов с экспоненциальной задержкой, а задания, которые так и не
смогли выполниться, должны складываться в отдельную dead-letter очередь, откуда их можно
осознанно вернуть в работу.

## Что нужно сделать

### 1. Политика повторов

Новый модуль `jobq/retry.py` с неизменяемым (frozen) датаклассом `RetryPolicy`. Параметры
передаются по имени, у всех есть значения по умолчанию:

| поле            | по умолчанию | смысл                                                         |
|-----------------|--------------|---------------------------------------------------------------|
| `max_attempts`  | `3`          | общее число попыток **включая первую**                        |
| `base_delay`    | `1.0`        | задержка перед первым повтором, секунды                       |
| `factor`        | `2.0`        | множитель экспоненты                                          |
| `max_delay`     | `60.0`       | верхняя граница задержки, секунды                             |
| `jitter`        | `0.0`        | доля случайного разброса, от 0 до 1                           |
| `non_retryable` | `()`         | типы исключений, после которых повторять нельзя               |

- Некорректные параметры — `jobq.errors.ConfigError` при создании: `max_attempts < 1`,
  `base_delay < 0`, `factor < 1`, `max_delay < base_delay`, `jitter` вне `[0, 1]`,
  в `non_retryable` что-то, что не является классом исключения.
- `non_retryable` можно передать списком, но в объекте он хранится как `tuple`.
- `RetryPolicy.delay_for(attempt: int, rng: random.Random | None = None) -> float` — задержка
  в секундах перед следующей попыткой, если попытка номер `attempt` (нумерация с 1) упала.
  Базовая формула: `base_delay * factor ** (attempt - 1)`, ограниченная сверху `max_delay`.
  `attempt < 1` — `ConfigError`.
- Джиттер: если `jitter > 0`, базовая (уже ограниченная) задержка умножается на
  `rng.uniform(1 - jitter, 1 + jitter)` — ровно один вызов `uniform` на одну задержку.
  При `jitter == 0` генератор не трогаем вообще.
- `RetryPolicy.is_retryable(exc) -> bool` — `False`, если исключение — экземпляр одного из
  `non_retryable` (подклассы тоже считаются!) или новой ошибки `jobq.errors.PermanentJobError`
  (наследник `JobqError`, обработчик бросает её, когда точно знает, что повтор не поможет).
  `PermanentJobError` неповторяема при любой политике, даже если её нет в `non_retryable`.

Отдельно про границы: итоговая задержка **никогда** не больше `max_delay`, в том числе после
джиттера, и `delay_for` должна спокойно работать для любого номера попытки — у нас бывают
задания с `max_attempts=10_000`, и на `attempt=5000` ничего не должно падать (`OverflowError`
у `float` никто не ждёт).

### 2. Где задаётся политика

- `JobQueue(..., default_retry_policy: RetryPolicy | None = None)` — новый keyword-only
  параметр, дефолт для всех типов заданий.
- `JobQueue.set_retry_policy(job_type: str, policy: RetryPolicy | None) -> None` — политика
  для конкретного типа. Она **целиком** заменяет дефолтную (поля не смешиваются).
  `None` убирает политику типа, и снова действует дефолт очереди.
- `JobQueue.retry_policy_for(job_type: str) -> RetryPolicy | None` — действующая политика.
- Политика берётся в момент обработки ошибки, а не в момент постановки задания: если
  политику поменяли, пока задание ждало, используется новая.
- Если для типа нет ни своей политики, ни дефолта — всё работает ровно как сейчас:
  первая ошибка → `FAILED`, `jobs.failed` +1, никакого dead-letter.

### 3. Поведение воркера при ошибке обработчика

У `Worker` появляется keyword-only параметр `rng: random.Random | None = None` — генератор
для джиттера (по умолчанию `random.Random()`). Когда обработчик бросил исключение:

1. ошибка неповторяемая (см. `is_retryable`) → `FAILED`, `jobs.failed` +1. Это так даже
   если это была последняя разрешённая попытка — в dead-letter такие задания не идут;
2. попытки исчерпаны (`job.attempts >= max_attempts`) → новый статус
   `JobStatus.DEAD_LETTERED`, задание попадает в dead-letter, `jobs.dead_lettered` +1;
3. иначе → новый статус `JobStatus.RETRY_SCHEDULED`, `job.run_at` = текущее время + задержка
   из `delay_for(job.attempts, rng)`, `jobs.retried` +1.

Во всех трёх случаях `job.error` содержит текст **последней** ошибки в обычном формате
(`"ИмяКласса: сообщение"`), `job.attempts` — сколько попыток уже было. `jobs.failed` по-прежнему
означает «задание окончательно упало со статусом FAILED», поэтому при повторе и при уходе в
dead-letter его не увеличиваем. Генератор `rng` вызывается только когда реально планируется
повтор — при уходе в dead-letter или в FAILED задержка не считается.

Кстати, `max_attempts=1` — это «без повторов, но с dead-letter»: первая же ошибка отправляет
задание в `DEAD_LETTERED`, а не в `FAILED`.

Если для типа задания нет обработчика, это не временная ошибка — задание сразу `FAILED`,
как сейчас, независимо от политики.

Задание в `RETRY_SCHEDULED` воркер берёт только когда наступило его `run_at`, в общей
очереди с `PENDING`-заданиями по времени запуска; при равном `run_at` — в порядке исходной
постановки в очередь (как сейчас). Задержка 0 допустима: такое задание готово сразу, и
`run_pending()` выполнит его в том же вызове. Когда повторная попытка прошла успешно,
задание становится `SUCCEEDED`, а `job.error` очищается (`None`); `attempts` показывает общее
число попыток. Обработчик, как и сейчас, видит в `job.attempts` номер текущей попытки (с 1).

### 4. Dead-letter

- Новый frozen-датакласс `jobq.models.DeadLetterEntry` с полями `job_id: str`,
  `job_type: str`, `attempts: int`, `error: str` (последняя ошибка, тот же текст, что в
  `job.error`), `dead_lettered_at: datetime` (время по часам очереди).
- `JobQueue.dead_letters() -> list[DeadLetterEntry]` — текущее содержимое, в порядке
  попадания в dead-letter.
- `JobQueue.requeue_dead_letter(job_id: str) -> Job` — вернуть задание в работу: тот же
  `job_id` (новое задание не создаём, `jobs.enqueued` не растёт), статус `PENDING`,
  `run_at` = сейчас, `attempts` сбрасывается в 0 (после перезапуска у задания снова полный
  набор попыток), `error` = `None`, из `dead_letters()` запись исчезает, `jobs.requeued` +1.
  Неизвестный id — `JobNotFoundError`, задание не в dead-letter — `InvalidTransitionError`.
  Если перезапущенное задание снова исчерпает попытки, оно окажется в конце `dead_letters()`.

### 5. Совместимость со статусами

- Новые значения: `JobStatus.RETRY_SCHEDULED` (`"retry_scheduled"`) и
  `JobStatus.DEAD_LETTERED` (`"dead_lettered"`). `queue.stats()` и `queue.list_jobs(status)`
  должны их учитывать.
- `is_terminal`: для `DEAD_LETTERED` — `True` (воркер его больше не возьмёт), для
  `RETRY_SCHEDULED` — `False`. При этом `purge_finished()` задания из dead-letter не удаляет:
  они живут там, пока их не перезапустят.
- `queue.cancel()` должен работать и для задания в `RETRY_SCHEDULED` (оно больше не
  выполнится, `jobs.cancelled` +1). Задание в `DEAD_LETTERED` отменить нельзя —
  `InvalidTransitionError`.
- Отчёт дежурных (`jobq.dashboard.render_report`) должен показывать новые статусы с
  подписями «Ожидает повтора» и «В dead-letter» и их количеством.

## Ограничения

- `jobq/dashboard.py` и `jobq/cli.py` не трогаем — ими владеет другая команда.
- Сигнатуры существующих публичных методов не меняем: `JobQueue.enqueue`, `cancel`, `stats`,
  `list_jobs`, `purge_finished`, `Worker(queue, registry, ...)`, `run_once`, `run_pending`,
  `HandlerRegistry.register`. Новые параметры — только keyword-only с дефолтами; старые
  вызовы должны работать без изменений.
- Существующие тесты в `tests/` не меняем (новые файлы с тестами добавлять можно).
  Новых зависимостей не добавляем.

Для тестов есть `jobq.clock.ManualClock` (`advance(seconds)`), метрики читаются через
`queue.metrics.get("jobs.retried")` и т.п.
