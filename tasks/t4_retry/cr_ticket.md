# JOBQ-237: Доработки повторов по итогам первого месяца

## Описание

Повторы и dead-letter работают уже месяц. Дежурные и команда биллинга собрали претензии, часть
договорённостей из JOBQ-212 пересматриваем.

### Что меняем

- **Неповторяемые ошибки.** Раньше договорились, что неповторяемая ошибка обработчика сразу
  переводит задание в `FAILED` и в dead-letter оно не попадает. На практике это почти всегда кривые
  данные: их чинят руками, а потом задания ищут по логам. Теперь для типов, на которые действует
  политика повторов, неповторяемая ошибка (включая `PermanentJobError`) сразу отправляет задание
  в dead-letter, без повторов.
- **Джиттер.** Раньше джиттер разбрасывал задержку в обе стороны от расчётной. У почты SLA:
  повтор не должен приходить позже расчётного времени. Теперь джиттер только уменьшает задержку:
  множитель равен `rng.uniform(1 - jitter, 1)`.
- **Очистка.** Раньше решили, что `purge_finished` dead-letter не трогает. За месяц там скопилось
  40 тысяч записей. Теперь `purge_finished` чистит и dead-letter по тому же правилу возраста, считая
  от момента попадания в dead-letter. Запись из `dead_letters()` при этом тоже исчезает.

### Что добавляем

```python
# jobq/models.py
class DeadLetterReason(str, Enum):
    EXHAUSTED = "exhausted"          # кончились попытки
    NON_RETRYABLE = "non_retryable"  # неповторяемая ошибка

DeadLetterEntry.reason: DeadLetterReason   # новое поле, последним

# jobq/errors.py
class RetryLaterError(JobqError):
    def __init__(self, message: str = "", *, retry_after: float) -> None: ...
    retry_after: float   # секунды

# jobq/queue.py
JobQueue.requeue_all_dead_letters(job_type: str | None = None) -> list[Job]
```

- `DeadLetterEntry.reason` показывает, почему задание попало в dead-letter.
- `RetryLaterError` обработчик бросает, когда внешний сервис сам сказал, когда приходить
  (Retry-After у биллинга). Это обычная временная ошибка, только следующую попытку планируем через
  `retry_after` секунд вместо задержки из политики. К этой задержке тоже применяем джиттер.
  `retry_after < 0` — ошибка конфигурации.
- `requeue_all_dead_letters` перезапускает всё содержимое dead-letter или только записи заданного
  типа. Каждое задание перезапускается так же, как через `requeue_dead_letter`. Возвращает
  перезапущенные задания.

### Ограничения

- `jobq/dashboard.py` и `jobq/cli.py` по-прежнему не трогаем.
- Сигнатуры существующих публичных методов не меняем, старые вызовы должны работать.
- Существующие тесты проекта не меняем. Новых зависимостей не добавляем.

Биллинг иногда присылает Retry-After: 3600 при max_delay=60. Ждём час? И какой reason ставить, если

**Артём Белов (тимлид)**, 03.11.2026 12:30
max_delay остаётся потолком для любой задержки, Retry-After режем до него. Неповторяемая ошибка
на последней попытке получает non_retryable: причина важнее счётчика. А если на последней попытке
прилетел RetryLaterError, это обычное исчерпание, exhausted.

**Артём Белов (тимлид)**, 04.11.2026 15:05
UPD по RetryLaterError: джиттер к нему всё-таки не применяем, и rng в этом случае не трогаем.
Сервер назвал время, его и используем (с учётом потолка max_delay).
