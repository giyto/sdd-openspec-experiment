## Context

Вся логика в `Inventory`; состояние — в `InMemoryStore`; время — только из внедрённых часов; операции атомарны (сначала проверки, потом изменения); модели — frozen-датаклассы, наружу отдаются снимки; формат журнала менять нельзя (см. README). Мотивация — `proposal.md`, требования — `specs/stock-reservations/spec.md`.

## Goals / Non-Goals

**Goals:**
- Резервы с ленивым истечением по часам в момент обращения.
- Единая точка расчёта `available`, которую используют `reserve`, `issue`, `transfer`.

**Non-Goals:**
- Фоновая очистка, персистентность, изменение `cli.py`/`reports.py`, новые зависимости.
- Событие в журнале об истечении.

## Decisions

- **Хранение.** Изменяемая запись резерва (статус, `expires_at`, строки) хранится в `InMemoryStore` (новые методы добавления/чтения, без проверок — как остальное хранилище), словарь по `order_id`. Так общий `store` даёт общие резервы. `Inventory` собирает из записи frozen-`Reservation`. Конструктор не меняется.
- **Эффективный статус.** Функция `_effective_status(record, now)` в `warehouse/reservations.py`: `ACTIVE` и `now >= expires_at` → `EXPIRED`; остальные статусы возвращаются как есть. Хранимый статус при истечении не переписывается (журнал не пишется, состояние не мутируется при чтении); `EXPIRED` — производное значение. `now` берётся один раз за операцию.
- **Расчёт.** `reserved` суммирует `qty` по всем строкам активных на `now` резервов для позиции; `available = max(0, on_hand - reserved)`. Единый приватный `_available(wh, sku, now)`.
- **Расход.** `issue` и источник `transfer` сравнивают `qty` с `_available`; в `InsufficientStockError` передаётся доступное. `confirm` обходит эту проверку и сравнивает с физическим остатком, поэтому пишет через внутренние шаги, а не публичный `issue`.
- **Атомарность `reserve`.** Порядок: валидация `order_id`, `ttl`, непустоты, каждой строки (нормализация кортежей и `ReservationLine`; итерируемое читается один раз); проверка дубликата (только действующий/подтверждённый прежний резерв; истёкший или отменённый заменяется при создании записи); группировка строк по позиции с суммой и проверка по `_available` (первая нехватка в порядке строк); затем создание записи (с заменой прежней истёкшей/отменённой) и события `RESERVE` по строкам. Строки в записи — как пришли, без склейки.
- **Атомарность `confirm`.** Найти → статус (`Expired`/`State`) → сгруппированная сумма по позициям против физического остатка → списание по каждой строке, `ISSUE` на строку (`ref=order_id`), `RESERVE_CONFIRM`, статус `CONFIRMED`. Все проверки до первой записи.
- **Журнал.** `expires` форматируется `format_timestamp` (строка, т.к. `EventLog` принимает только str/int). Время события — `clock.now()`.
- **Ошибки.** `ReservationError(order_id)` с атрибутом; подклассы наследуют конструктор.
- **Альтернатива:** переписывать статус в хранилище при чтении («ленивая мутация») — отвергнута: чтение с побочными эффектами, сложнее атомарность.

## Допущения

- Истечение включительно: при `now == expires_at` резерв уже `EXPIRED`.
- `DuplicateReservationError` — только если прежний резерв на `order_id` действующий (`ACTIVE` на текущий момент) или `CONFIRMED`. Если он `EXPIRED` или `CANCELLED`, новый резерв разрешён и полностью заменяет старую запись, поэтому `get_reservation` всегда видит один (новый) резерв.
- Отмена истёкшего резерва — no-op без ошибки, статус остаётся `EXPIRED`, события нет (по духу идемпотентной отмены).
- `extend` считает от момента запроса: новый `expires_at` = `now` + `ttl`. Срок никогда не сокращается: если `now + ttl` не позже прежнего `expires_at`, это no-op (снимок возвращается как есть, `RESERVE_EXTEND` не пишется, ошибки нет).
- `available` не опускается ниже 0 (после `adjust` физический остаток может быть меньше резервов); тогда `confirm` может упасть с `InsufficientStockError` по физике.
- `transfer` из источника ограничен `available` (README: «для склада-источника — обычный расход»).
- Порядок проверок в `extend`: сначала `ttl` (`ValidationError`), затем поиск (`NotFound`), затем статус. В `reserve`: `order_id`/`ttl`/строки (`ValidationError`, `InvalidQuantityError`, `UnknownSkuError`) → дубликат (действующий/подтверждённый) → нехватка.
- Время в `created_at`/`expires_at` хранится без усечения; журнал усекает до секунды.
- `ttl` типа `bool` или не `timedelta` — `ValidationError`.

## Risks / Trade-offs

- [Производный статус вычисляется при каждом обращении, O(число резервов)] → приемлемо для хранилища в памяти; при росте можно индексировать по позиции.
- [`available` отсекается по нулю и скрывает перерасход после `adjust`] → `on_hand` и `reserved` доступны для диагностики.
- [Изменение `issue`/`transfer`] → без резервов `available == on_hand`, существующие тесты обязаны проходить без правок.
