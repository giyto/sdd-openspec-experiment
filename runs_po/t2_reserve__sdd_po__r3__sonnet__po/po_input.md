### design.md

## Context

Мотивация — в proposal.md, требования — в specs/stock-reservations/spec.md. Текущее состояние: `Inventory` хранит только физические остатки в `InMemoryStore`; `issue` и `transfer` сверяют количество с физическим остатком; время берётся только из внедрённых часов; журнал — `EventLog` с неизменяемым строковым форматом; операции атомарны (сначала все проверки, потом изменения). `reports.movement_summary` читает журнал и для любого события с полем `sku` заводит запись по SKU.

## Goals / Non-Goals

**Goals:**
- Резервы живут в `Inventory` и подчиняются соглашениям README: время только из `self._clock`, атомарность, снимки-датаклассы, ошибки из `WarehouseError`.
- Истечение вычисляется при каждом обращении; никаких таймеров, потоков, записей «по истечении».

**Non-Goals:**
- Фоновая очистка истёкших резервов, персистентность, потокобезопасность (хранилище в памяти, как и сейчас).
- Изменения `cli.py`, `reports.py`, формата журнала, существующих тестов.

## Decisions

1. **Хранение: записи резервов в `InMemoryStore`** (новые методы `add_reservation / get_reservation / reservations`), а не в `Inventory`. `Inventory(store=...)` позволяет делить хранилище, и резервы должны жить рядом с остатками, к которым относятся. Запись хранит неизменяемые поля и «сохранённый» статус (`ACTIVE/CONFIRMED/CANCELLED`) и текущий `expires_at`; при изменении запись заменяется новой (`dataclasses.replace`). Статус `EXPIRED` никогда не хранится, а вычисляется функцией из `reservations.py`: `ACTIVE` и `now >= expires_at` → `EXPIRED`. Альтернатива — хранить `EXPIRED` и переводить при обращении: это превращает чтение в запись и нарушает «истечение не пишется».
2. **Граница истечения: `now >= expires_at` — истёк.** Резерв действует на полуинтервале `[created_at, expires_at)`. В ТЗ не указано; полуинтервал согласуется с `movement_summary` (`[since, until)`).
3. **Снимок** `Reservation` строится из записи и текущего времени одной функцией; все публичные методы возвращают только снимки. `lines` хранятся кортежем `ReservationLine` в исходном порядке; кортежи-входы нормализуются в `ReservationLine`. Входной `Iterable` потребляется один раз.
4. **Порядок проверок в `reserve`** (всё до первой записи): `order_id` → `ttl` → материализация и разбор строк (форма, коды, `qty`, зарегистрирован ли SKU) → пустой список → дубликат `order_id` → достаточность по суммам позиций (`dict[(wh, sku)] -> sum`). Только после этого запись резерва и события `RESERVE` по строкам. `InsufficientStockError(requested=сумма по позиции, available=доступное)`; при нескольких проблемных позициях сообщается первая в порядке строк. `created_at = clock.now()` читается один раз и используется и для записи, и для журнала.
5. **`available`/`reserved`**: `reserved` суммирует строки активных (не истёкших) резервов по позиции — полный перебор резервов, O(N). Для хранилища в памяти это приемлемо; индекс по позициям — преждевременная оптимизация. `available = max(0, on_hand - reserved)`: после `adjust` вниз физический остаток может оказаться ниже резерва, отрицательное «доступное» не имеет смысла для вызывающих.
6. **`issue` и `transfer` сверяются с `available`**, а не с `on_hand`. В ТЗ упомянут только `issue`, но docstring `transfer` фиксирует «для склада-источника это обычный расход: проверки те же», а перемещение в обход резерва нарушило бы его цель. Целевая сторона не затрагивается. Без резервов `available == on_hand`, поведение прежнее. `adjust` остаётся фактом без проверок.
7. **`confirm`**: определить текущий статус (NotFound → Expired/State) → посуммировать строки по позициям → проверить **физический** остаток (`on_hand`), а не `available` (резерв самого заказа уже учтён в `reserved`) → затем записать новые остатки, `ISSUE` по каждой строке в исходном порядке с `ref=order_id`, статус `CONFIRMED`, `RESERVE_CONFIRM`. Запись остатков выполняется как «вычесть qty строки» последовательно по строкам; вся проверка уже выполнена, поэтому частичного применения нет. Публичный `issue` внутри не вызывается (он проверяет `available` и пишет `ISSUE` с другим контекстом); общий внутренний хелпер для списания и записи `ISSUE`. Если физического остатка не хватает (после `adjust`) — `InsufficientStockError(requested=сумма, available=on_hand)` без изменений.
8. **`cancel`**: `ACTIVE` → `CANCELLED` + `RESERVE_CANCEL`; `CANCELLED` → снимок без записи; `CONFIRMED` → `ReservationStateError`; `EXPIRED` (вычисленный) → возвращается снимок `EXPIRED` без изменений. Выбор для истёкшего — допущение: ТЗ молчит; ошибка противоречила бы духу идемпотентной отмены (клиент «отменяет» уже освободившийся резерв), а перевод в `CANCELLED` потребовал бы запись в журнал, которая для «истечения» запрещена.
9. **`extend`**: `new_expires = expires_at + ttl` (продление «на ttl» от текущего срока, а не от «сейчас»). Статусные ошибки как у `confirm`. Наличие товара не проверяется.
10. **Валидация `ttl`**: `isinstance(ttl, timedelta)` и `ttl > timedelta(0)`, иначе `ValidationError` (общий хелпер для `reserve` и `extend`). `ttl=None` допустим только в `reserve`. `order_id` проверяется существующим `_validate_code` во всех методах, включая `get_reservation`; все `Reservation*Error` принимают `order_id` и хранят его атрибутом.
11. **Журнал**: поле `expires` форматируется `format_timestamp(...)`, как время события (README), то есть с секундной точностью — реальное `expires_at` в снимке сохраняет микросекунды. `EventLog.append` может бросить `EventFormatError` на уже изменённом состоянии; чтобы это не ломало атомарность, все значения событий валидируются заранее (`order_id`, коды — через `_validate_code`, TTL-время — aware). Потому события строятся и пишутся после всех проверок, последним шагом.
12. **Структура кода**: модели в `models.py`, ошибки в `errors.py`, `reservations.py` — `DEFAULT_RESERVATION_TTL`, внутренняя запись резерва и чистые функции (нормализация строк, вычисление статуса, снимок, суммирование по позициям); оркестрация и журнал — методы `Inventory`. Новые публичные имена экспортируются из `warehouse/__init__.py`. Циклических импортов нет: `reservations.py` зависит от `models`/`errors`, а не от `inventory`.

## Риски / Trade-offs

- [`movement_summary` увидит `RESERVE` с полем `sku`] → отчёт заведёт для такого SKU запись с нулями. `reports.py` менять запрещено, а имена полей зафиксированы ТЗ; принимается, фиксируется тестом-характеристикой в задачах. Суммы `received/issued/adjusted` не искажаются, так как `RESERVE*` не попадают ни в одну ветку; `ISSUE` от `confirm` корректно считается расходом.
- [Допущения по неоднозначному ТЗ: `transfer` учитывает резервы, `cancel` истёкшего — без ошибки, граница `now >= expires_at`, `DuplicateReservationError` для любого статуса, `available` не ниже 0] → перечислены в спецификации сценариями, чтобы при несогласии менять одно место.
- [Строка журнала с секундной точностью и `expires_at` с микросекундами] → расхождение допустимо, формат журнала менять нельзя.
- [O(N) перебор резервов на каждый запрос] → приемлемо для масштаба хранилища в памяти.
- [Часы, идущие назад (`ManualClock.set`)] → «истёкший» резерв снова может стать `ACTIVE`, так как статус вычисляется; это следствие требования «по часам сервиса в момент обращения», специально не обрабатывается.

## Migration Plan

Миграции нет: хранилище в памяти, новые поля и методы добавляются без изменения существующих сигнатур. Откат — удаление добавленного кода; журнал с новыми типами событий внешней выгрузке нужно уметь пропускать.


### proposal.md

## Why

Товар списывается только при отгрузке, поэтому пока покупатель оформляет и оплачивает заказ, тот же товар успевают продать второй раз (WH-214). Нужно удерживать товар под заказ с момента оформления, а неоплаченные резервы должны сами переставать действовать по TTL — без фоновых задач, по часам сервиса в момент обращения.

## What Changes

- В `Inventory` добавляются резервы: `reserve`, `confirm`, `cancel`, `extend`, `get_reservation`, а также запросы `available` и `reserved`.
- Новые модели `ReservationStatus`, `ReservationLine`, `Reservation` (`warehouse/models.py`), ошибки `ReservationError` и наследники (`warehouse/errors.py`), константа `DEFAULT_RESERVATION_TTL = 15 минут` (`warehouse/reservations.py`; значение из обновления в обсуждении, а не 30 минут из исходного текста).
- Истечение вычисляется лениво при обращении, в журнал не пишется и физический остаток не трогает.
- Новые события журнала: `RESERVE`, `RESERVE_CONFIRM`, `RESERVE_CANCEL`, `RESERVE_EXTEND`; `confirm` дополнительно пишет обычные `ISSUE` по строкам.
- **Изменение поведения `issue`** (и `transfer` со склада-источника — см. design): они не могут забрать товар из активных резервов, при нехватке доступного — `InsufficientStockError`. Для кода без резервов поведение прежнее.
- Не меняются: формат строки журнала, конструктор `Inventory`, `receive/adjust/on_hand/stock_levels`, `cli.py`, `reports.py`, существующие тесты; новых зависимостей нет.

### specs/stock-reservations/spec.md

## Purpose

Удержание товара под заказ с ограниченным по времени сроком действия, чтобы один и тот же физический остаток не продавался дважды. Резервы не меняют физический остаток, пока не подтверждены.

## ADDED Requirements

### Requirement: Создание резерва
Система SHALL по `reserve(order_id, lines, ttl=None)` создать резерв под заказ сразу по всем строкам (строки могут относиться к разным складам) и вернуть снимок со статусом `ACTIVE`. `created_at` MUST быть текущим временем часов сервиса, `expires_at = created_at + ttl`. Если `ttl` не указан, MUST использоваться `DEFAULT_RESERVATION_TTL`, равный 15 минутам. Строки в снимке MUST сохраняться как переданы, в том же порядке, как `ReservationLine`; строки можно передавать кортежами `(warehouse, sku, qty)` или `ReservationLine`. Физический остаток MUST NOT меняться. Строки с одинаковой позицией (склад + SKU) MUST NOT склеиваться.

#### Scenario: Резерв по двум складам
- **WHEN** на складах A и B есть достаточно товара и вызывается `reserve("SO-1", [("A","BOLT",2),("B","NUT",3)])`
- **THEN** возвращается резерв `ACTIVE` с двумя строками в переданном порядке, `expires_at` на 15 минут позже `created_at`, а `on_hand` по обеим позициям не изменился

#### Scenario: Явный TTL
- **WHEN** вызывается `reserve` с `ttl=timedelta(minutes=5)`
- **THEN** `expires_at` равен `created_at + 5 минут`

#### Scenario: Повторяющаяся позиция хранится как пришла
- **WHEN** в заказе две строки `("A","BOLT",2)` и `("A","BOLT",3)`
- **THEN** снимок содержит обе строки без объединения, а в `reserved("A","BOLT")` попадает 5

### Requirement: Проверка входных данных резерва
Система SHALL отклонять `reserve` с `ValidationError`, если `ttl` не является положительным `timedelta`, если строк нет, если `order_id`, склад или SKU-код не проходят проверку кода (непустая строка без пробелов и `=`), или если строка не имеет вида `(warehouse, sku, qty)`/`ReservationLine`. Некорректное количество (не положительный `int`, `bool`, дробное, строка) MUST давать `InvalidQuantityError`. Незарегистрированный SKU MUST давать `UnknownSkuError`. Резерв с уже использованным `order_id` MUST давать `DuplicateReservationError`, независимо от статуса существующего резерва. Любая ошибка MUST оставлять состояние и журнал без изменений.

#### Scenario: Нулевой или отрицательный TTL
- **WHEN** вызывается `reserve` с `ttl=timedelta(0)` или отрицательным `ttl`
- **THEN** бросается `ValidationError`, резерв не создан, журнал не изменился

#### Scenario: Пустой заказ
- **WHEN** вызывается `reserve("SO-1", [])`
- **THEN** бросается `ValidationError`

#### Scenario: Повторный order_id
- **WHEN** резерв `SO-1` уже существует (в любом статусе) и вызывается `reserve("SO-1", ...)`
- **THEN** бросается `DuplicateReservationError` с `order_id == "SO-1"`

### Requirement: Доступный и зарезервированный остаток
Система SHALL предоставлять `reserved(warehouse, sku)` — сумму количеств по всем активным (не истёкшим) резервам для позиции, и `available(warehouse, sku)` — физический остаток минус `reserved`, но не менее 0. Для незарегистрированного SKU оба запроса MUST бросать `UnknownSkuError`. Резервировать MUST быть можно только из доступного: проверка выполняется по сумме количеств всех строк заказа с одной и той же позицией, и при нехватке бросается `InsufficientStockError` (`requested` — суммарное количество по позиции, `available` — доступное), без частичного резерва.

#### Scenario: Резерв уменьшает доступное
- **WHEN** на складе 10 единиц и создан резерв на 4
- **THEN** `on_hand` равен 10, `reserved` равен 4, `available` равен 6

#### Scenario: Нехватка по сумме дублирующихся строк
- **WHEN** доступно 5, а заказ содержит две строки той же позиции по 3
- **THEN** бросается `InsufficientStockError` с `requested == 6`, `available == 5`, и ни одна строка не зарезервирована

#### Scenario: Нехватка по одной из строк
- **WHEN** первая строка заказа укладывается в доступное, а вторая (другой склад) нет
- **THEN** бросается `InsufficientStockError`, резерв не создан, событий `RESERVE` в журнале нет

#### Scenario: Чужой резерв недоступен
- **WHEN** 10 единиц, из них 8 в активном резерве заказа `SO-1`, и `SO-2` просит 3
- **THEN** бросается `InsufficientStockError` с `available == 2`

### Requirement: Истечение резерва
Резерв со статусом `ACTIVE` SHALL считаться истёкшим, когда текущее время часов сервиса достигло или превысило `expires_at`; решение принимается в момент обращения, без фоновых задач. Снимок такого резерва MUST иметь статус `EXPIRED`, он MUST NOT учитываться в `reserved` и `available`. Истечение MUST NOT записываться в журнал и MUST NOT менять физический остаток. Статусы `CONFIRMED` и `CANCELLED` окончательные: истечение времени их не меняет.

#### Scenario: Резерв истёк
- **WHEN** после создания резерва часы продвинуты на TTL или больше
- **THEN** `get_reservation` возвращает статус `EXPIRED`, `reserved` равен 0, `available` равен физическому остатку, новых событий в журнале нет

#### Scenario: Резерв ещё действует
- **WHEN** текущее время строго меньше `expires_at`
- **THEN** статус `ACTIVE`

#### Scenario: Подтверждённый резерв после срока
- **WHEN** резерв подтверждён, затем время прошло `expires_at`
- **THEN** `get_reservation` возвращает `CONFIRMED`

#### Scenario: Отменённый резерв после срока
- **WHEN** резерв отменён, затем время прошло `expires_at`
- **THEN** `get_reservation` возвращает `CANCELLED`

#### Scenario: Освободившийся товар можно зарезервировать снова
- **WHEN** резерв истёк
- **THEN** другой заказ может зарезервировать этот товар

### Requirement: Подтверждение резерва
Система SHALL по `confirm(order_id)` для активного резерва уменьшить физический остаток по каждой строке на её количество и перевести резерв в `CONFIRMED`, вернув снимок. Нулевой `available` из-за самого этого резерва MUST NOT мешать подтверждению. Достаточность физического остатка проверяется по сумме строк одной позиции; если физического остатка не хватает (например, после инвентаризации), MUST бросаться `InsufficientStockError` без каких-либо изменений. Истёкший резерв MUST давать `ReservationExpiredError`, подтверждённый или отменённый — `ReservationStateError`.

#### Scenario: Подтверждение при нулевом доступном
- **WHEN** весь остаток (5) зарезервирован под `SO-1` и вызывается `confirm("SO-1")`
- **THEN** `on_hand` становится 0, статус `CONFIRMED`

#### Scenario: Дублирующиеся строки при подтверждении
- **WHEN** остаток 5, резерв состоит из двух строк одной позиции по 3 и 2
- **THEN** подтверждение проходит, остаток 0

#### Scenario: Недостаточный физический остаток
- **WHEN** после резерва инвентаризацией остаток уменьшен ниже зарезервированного и вызывается `confirm`
- **THEN** бросается `InsufficientStockError`, остатки, статус резерва и журнал не изменились

#### Scenario: Подтверждение истёкшего
- **WHEN** резерв истёк
- **THEN** `confirm` бросает `ReservationExpiredError`, остаток не изменён

#### Scenario: Повторное подтверждение
- **WHEN** резерв уже `CONFIRMED` или `CANCELLED`
- **THEN** `confirm` бросает `ReservationStateError`

### Requirement: Отмена резерва
Система SHALL по `cancel(order_id)` для активного резерва перевести его в `CANCELLED`, освободив товар, и вернуть снимок. Отмена MUST быть идемпотентной: повторная отмена уже отменённого резерва возвращает снимок `CANCELLED`, ничего не меняет и ничего не пишет в журнал. Подтверждённый резерв MUST NOT отменяться (`ReservationStateError`). Отмена истёкшего резерва — не ошибка и не действие: возвращается снимок со статусом `EXPIRED`, статус и журнал не меняются.

#### Scenario: Отмена освобождает товар
- **WHEN** отменяется активный резерв на 4 из 10
- **THEN** статус `CANCELLED`, `reserved` равен 0, `available` равен 10

#### Scenario: Повторная отмена
- **WHEN** `cancel` вызывается второй раз
- **THEN** возвращается `CANCELLED`, число событий в журнале не меняется

#### Scenario: Отмена подтверждённого
- **WHEN** резерв `CONFIRMED`
- **THEN** `cancel` бросает `ReservationStateError`

#### Scenario: Отмена истёкшего
- **WHEN** резерв истёк и вызывается `cancel`
- **THEN** ошибки нет, статус в снимке `EXPIRED`, журнал не изменился

### Requirement: Продление резерва
Система SHALL по `extend(order_id, ttl)` для активного резерва сдвинуть `expires_at` на `ttl` вперёд от текущего `expires_at` и вернуть снимок. `ttl` проверяется как в `reserve` (положительный `timedelta`, иначе `ValidationError`). Ошибки по статусам такие же, как у `confirm`: истёкший — `ReservationExpiredError` (истёкший резерв не оживляется), подтверждённый или отменённый — `ReservationStateError`. Продление MUST NOT проверять наличие товара, так как резерв уже его удерживает.

#### Scenario: Продление активного
- **WHEN** активный резерв с `expires_at = T` продлевается на 10 минут
- **THEN** `expires_at` становится `T + 10 минут`, остальные поля не меняются

#### Scenario: Продление истёкшего
- **WHEN** резерв истёк
- **THEN** `extend` бросает `ReservationExpiredError`

#### Scenario: Некорректный TTL при продлении
- **WHEN** `extend` вызывается с нулевым `ttl`
- **THEN** бросается `ValidationError`, `expires_at` не изменился

### Requirement: Поиск резерва и ошибки
Система SHALL по `get_reservation(order_id)` возвращать неизменяемый снимок резерва со статусом на текущий момент. Если резерва с таким `order_id` нет, `get_reservation`, `confirm`, `cancel` и `extend` MUST бросать `ReservationNotFoundError`. Все ошибки резервов MUST быть наследниками `WarehouseError` и иметь атрибут `order_id`. `order_id` проверяется как код (как SKU и склады), иначе `ValidationError`.

#### Scenario: Неизвестный заказ
- **WHEN** вызывается `get_reservation("NOPE")`
- **THEN** бросается `ReservationNotFoundError` с `order_id == "NOPE"`

#### Scenario: Снимок не меняется задним числом
- **WHEN** снимок получен, затем резерв отменён
- **THEN** ранее полученный снимок сохраняет прежний статус

### Requirement: Расход не забирает резервы
Система SHALL при `issue` сравнивать запрошенное количество с доступным (физический остаток минус активные резервы) и при превышении бросать `InsufficientStockError`, где `available` — доступное количество. Это же правило MUST действовать для склада-источника `transfer`. `receive`, `adjust`, `on_hand`, `stock_levels` и поведение без резервов MUST остаться прежними; `on_hand` и `stock_levels` показывают физический остаток.

#### Scenario: Расход из чужого резерва
- **WHEN** остаток 10, активный резерв 8, вызывается `issue` на 3
- **THEN** бросается `InsufficientStockError` (`available == 2`), остаток не изменён

#### Scenario: Расход доступной части
- **WHEN** остаток 10, активный резерв 8, вызывается `issue` на 2
- **THEN** расход проходит, остаток 8

#### Scenario: Расход после истечения
- **WHEN** резерв истёк
- **THEN** `issue` может забрать весь физический остаток

#### Scenario: Без резервов
- **WHEN** резервов нет
- **THEN** `issue`, `transfer`, `receive`, `adjust` ведут себя как прежде

### Requirement: События журнала резервов
Система SHALL писать в журнал: `RESERVE` на каждую строку резерва в порядке строк с полями `order`, `wh`, `sku`, `qty`, `expires`; при `confirm` — обычный `ISSUE` на каждую строку (в порядке строк, `ref` = номер заказа), затем `RESERVE_CONFIRM` с полем `order`; при фактической отмене — `RESERVE_CANCEL` (`order`); при продлении — `RESERVE_EXTEND` (`order`, `expires` — новый срок). Поле `expires` MUST быть записано в том же формате, что и время события. Операции, завершившиеся ошибкой, идемпотентная повторная отмена, отмена истёкшего и само истечение события MUST NOT создавать. Формат строки журнала не меняется.

#### Scenario: События резерва
- **WHEN** создан резерв из двух строк
- **THEN** в журнале два события `RESERVE` с `order`, `wh`, `sku`, `qty`, `expires` (например, `expires=2026-03-01T10:15:00Z`)

#### Scenario: События подтверждения
- **WHEN** подтверждается резерв из двух строк заказа `SO-1`
- **THEN** в журнале подряд: `ISSUE` (`ref=SO-1`) на первую строку, `ISSUE` на вторую, затем `RESERVE_CONFIRM order=SO-1`

#### Scenario: Продление пишет новый срок
- **WHEN** резерв продлён
- **THEN** появляется ровно одно событие `RESERVE_EXTEND` с `order` и новым `expires`
