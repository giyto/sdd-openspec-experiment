## Context

`Inventory` хранит физические остатки в `InMemoryStore`, пишет события в `EventLog`, время берёт из внедрённых часов. Правила из README: только stdlib, aware UTC, атомарность (проверки, потом изменения), frozen-модели и снимки наружу, формат журнала неизменен. Мотивация и требования: см. proposal.md и specs/order-reservations.

## Goals / Non-Goals

**Goals:**
- Резервы внутри `Inventory`, без фоновых задач; истечение вычисляется лениво.
- Старый API ведёт себя как раньше, пока резервов нет.

**Non-Goals:**
- Изменения `cli.py`, `reports.py`, существующих тестов; персистентность; потокобезопасность.
- Удаление/архивация старых резервов, кроме замены истёкшего или отменённого резерва новым на тот же `order_id`.

## Decisions

- **Хранение.** Внутренняя изменяемая запись резерва (order_id, lines, created_at, expires_at, внутренний статус ACTIVE/CONFIRMED/CANCELLED) лежит в `InMemoryStore` (словарь по `order_id`). Наружу всегда отдаётся frozen `Reservation`. Статус `EXPIRED` не хранится, а вычисляется: `ACTIVE` и `now >= expires_at`. Альтернатива (переписывать статус при обращении) отвергнута: это мутация на чтении.
- **Один `now` на операцию.** Каждая операция читает `clock.now()` один раз и использует его для проверки истечения, `created_at` и записи в журнал.
- **Граница истечения:** `now >= expires_at` означает истёк (допущение: тикет не уточняет).
- **Расчёт `reserved`:** сумма по активным не истёкшим резервам, проход по всем резервам (O(N), для памяти приемлемо). `available = max(0, on_hand - reserved)`; clamp нужен, т.к. `adjust` может опустить остаток ниже резерва (допущение).
- **Единая проверка достаточности.** Хелпер агрегирует строки по `(warehouse, sku)` и сравнивает сумму с `available` (reserve) или физическим остатком (confirm). `InsufficientStockError.requested` равен сумме по позиции; при нескольких нехватках сообщается первая в порядке строк.
- **`issue`/`transfer`.** Лимит меняется с `on_hand` на `available`; `adjust` не меняется. `transfer` включён, т.к. README определяет его источник как обычный расход, иначе резерв можно «увести» перемещением (допущение).
- **`confirm` не вызывает публичный `issue`** (лимит `available` заблокировал бы подтверждение). Он напрямую уменьшает остатки и пишет `ISSUE` с `ref=order_id` в том же виде, что и `issue`; запись и изменения идут только после всех проверок.
- **Порядок проверок `reserve`:** order_id → ttl → непустые строки → каждая строка (форма, код склада, qty, SKU) → дубликат order_id (только если прежний резерв действующий или подтверждённый; истёкший/отменённый молча заменяется новым) → достаточность. `lines` материализуется один раз (может быть итератором); кортеж или `ReservationLine` нормализуется в `ReservationLine`.
- **Порядок проверок `confirm`/`extend`:** найти → (ttl для extend) → истёк → статус не ACTIVE. `cancel`: найти → CANCELLED: снимок; EXPIRED: no-op со снимком (допущение); CONFIRMED: `ReservationStateError`; ACTIVE: отменить.
- **`extend`** считает новый срок от `now`: кандидат `now + ttl`. Если кандидат не позже текущего `expires_at`, ничего не меняется, в журнал ничего не пишется, ошибки нет, возвращается текущий снимок. Срок не сокращается.
- **Замена резерва.** При `reserve` на `order_id` с истёкшим или отменённым прежним резервом запись в словаре перезаписывается новой (решение автора: история не хранится).
- **`expires` в журнале:** `format_timestamp`, секундная точность; сравнения идут по точному значению.
- **Размещение кода:** модели в `models.py`, ошибки в `errors.py`, `reservations.py` — `DEFAULT_RESERVATION_TTL` и чистые функции (нормализация, агрегация, статус); оркестрация в `Inventory`.

## Risks / Trade-offs

- [Допущения про границу истечения, `cancel` истёкшего, `extend` от `now`, `transfer`, clamp `available`] → зафиксированы в спецификации и дизайне, покрываются тестами.
- [Секундная точность `expires` в журнале против точного хранимого значения] → допустимо по README; тест на субсекундный TTL.
- [Рост словаря резервов] → вне рамок.
- [`adjust` опускает остаток ниже резерва → `confirm` падает с `InsufficientStockError`] → намеренно, атомарно, резерв остаётся активным.
