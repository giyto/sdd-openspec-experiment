### design.md

## Context

Сейчас `calculate_total` чистая функция: суммы строк, налог по строкам, доставка по сумме товаров, `total = subtotal + shipping + tax`. `OrderService.quote` вызывает её, `place_order` сохраняет `Order`. Соглашения README: `Decimal` + `quantize_money` (ROUND_HALF_UP), только наследники `ShopError`, время через `Clock`, frozen-dataclass с инвариантами в `__post_init__`, коды людей через `normalize_key`, интервалы `[начало, конец)`, подарочные сертификаты никогда не получают скидок. Мотивация и состав изменений — в proposal.md, требования — в specs.

## Goals / Non-Goals

**Goals:**
- Скидка в итогах и построчно, сумма построчных равна общей, налог со строки после скидки.
- Счётчик использований меняется только при успешном `place_order`.
- Старые вызовы дают те же суммы.

**Non-Goals:**
- CLI и отчёты (отдельный тикет), изменение существующих тестов.
- Хранение реестра и счётчиков вне памяти, потокобезопасность между процессами.
- Комбинирование нескольких кодов в одном заказе.

## Decisions

1. **Нормализация везде через `normalize_key`.** `PromoCode.__post_init__` нормализует `code` (через `object.__setattr__`, как в `Product`) и отвергает пустой результат; `PromoRegistry.add/resolve/uses` нормализуют аргумент. `resolve("")` естественно даёт `UnknownPromoCodeError`. Пустой/пробельный код в `OrderService` отсекается до реестра: `_clean_code(raw) -> str | None` возвращает `None` для `None` и пустой после `strip` строки; нестроковый ввод даёт `ValidationError` из `normalize_key`.
2. **Проверка срока в реестре, условий заказа в `calculate_total`.** `resolve`: существует → `starts_at <= now < expires_at` (иначе `PromoExpiredError`, в т. ч. до начала) → `uses < max_uses` (иначе `PromoConditionsError`). Время только из `clock` реестра. `calculate_total(..., promo=)` реестр не знает и не проверяет срок/лимит, только `min_order_amount` и наличие участвующих строк.
3. **Участвующие строки:** категория не `GIFT_CARD` и не в `excluded_categories`. Сертификаты исключены жёстко (README), даже если код их не перечисляет.
4. **Что сравнивается с `min_order_amount`:** сумма участвующих строк до скидки, `>=`. Аргумент: сертификаты и исключённые товары не должны «добирать» минимум для скидки, на которую не имеют права. Альтернатива (весь `subtotal`) отвергнута.
5. **Размер скидки:** PERCENT — `quantize_money(base * value / 100)`; FIXED — `min(value, base)`, где `base` — сумма участвующих строк до скидки.
6. **Раскладка — метод наибольших остатков в целых копейках.** Для строки i: `share_i = D * a_i / S` (все в копейках, целочисленно), берём `floor`, остаток `D - sum(floor)` раздаём по одной копейке строкам по убыванию дробной части, при равенстве — по порядку в корзине. Гарантии: сумма в точности `D`; `d_i <= a_i`, потому что при `share_i = a_i` дробная часть 0 и добавки нет; детерминизм. Альтернатива «последней строке остаток» отвергнута: может превысить сумму строки и смещает копейки на одну строку.
7. **Налог:** `tax.tax_for(category, amount - discount)` на строку. `subtotal` остаётся суммой до скидки, `shipping.cost_for(subtotal, ...)` считается от него же (скидка на доставку не влияет и порог бесплатной доставки не двигает). `total = subtotal - discount + shipping + tax`.
8. **Обратная совместимость данных:** `LineTotal.discount` и `OrderTotal.discount` добавляются последними полями со значением по умолчанию `ZERO`; `Order.promo_code: str | None = None` — последним полем. Параметр `promo` в `calculate_total` keyword-only.
9. **Учёт использования.** `PromoRegistry` получает дополнительный метод `redeem(code)`, который под `threading.Lock` повторно выполняет `resolve` и увеличивает счётчик, возвращая `PromoCode`. `place_order`: пустая корзина → `EmptyCartError`; `resolve` и `calculate_total` (любая ошибка прекращает операцию без побочных эффектов); `redeem`; затем создание и сохранение `Order`. Так счётчик растёт только если заказ оформляется, а гонка двух оформлений на последнем использовании не превышает лимит. `quote` вызывает только `resolve` и `calculate_total`. Отмена заказа счётчик не уменьшает.
10. **Допущение о порядке ошибок:** `EmptyCartError` проверяется раньше ошибок промокода (существующее поведение пустой корзины не меняется); дальше порядок из тикета: неизвестен → не действует → лимит → условия заказа.
11. **Ошибки:** `PromoError(ShopError)` и три прямых наследника `PromoError`, не связанных между собой. `uses` для неизвестного кода — `UnknownPromoCodeError`. `ValidationError` для некорректного `PromoCode` и дубликата в реестре.
12. **Валидация `PromoCode`:** значения денег — только `Decimal`, конечные; FIXED и `min_order_amount` не более двух знаков (по образцу цены в `Product`); `max_uses` — `int`, не `bool`; даты aware; `starts_at < expires_at`; `excluded_categories` — набор `Category` (приводится к `frozenset`). Процент может иметь дробную часть (12.5).
13. **Экспорт:** новые публичные имена добавляются в `shop/__init__.py`; `cli.py` и `reports.py` не меняются (они не создают `LineTotal`/`OrderTotal` напрямую, значения по умолчанию сохраняют совместимость).
14. **Логирование:** модульный `logger`, без `print`; `info` при списании использования.

## Risks / Trade-offs

- [`min_order_amount` трактуется как сумма участвующих строк, маркетинг мог иметь в виду весь заказ] → зафиксировано как допущение; смена — локальная правка одной проверки и спеки.
- [Код без участвующих строк даёт `PromoConditionsError`, а не нулевую скидку] → пользователь получает понятный отказ вместо «успешного» кода без эффекта; отражено в спеке.
- [Реестр в памяти, лок защищает только один процесс] → в рамках проекта хранилище заказов тоже в памяти; при переходе на БД счётчик нужно делать атомарным в хранилище.
- [Часы реестра и сервиса могут быть разными объектами] → в тестах и композиции передаётся один `FixedClock`; расхождение не влияет на корректность проверок.
- [Расширение публичного API реестра методом `redeem` сверх списка в тикете] → метод минимален и нужен для атомарного учёта; существующие сигнатуры не меняются.

## Migration Plan

Миграция данных не нужна: изменения аддитивные, значения по умолчанию сохраняют прежние вызовы и суммы. Откат — revert коммита. Версию пакета можно поднять до 1.5.0 (не обязательно, решает релиз).


### proposal.md

## Why

Летняя кампания маркетинга (SHOP-412) идёт с промокодами, а сейчас скидки вручную проставляет поддержка, из-за чего суммы расходятся с чеками. Бухгалтерия считает налог по строкам, поэтому скидка должна быть честно разложена по строкам заказа и учтена в налоге.

## What Changes

- Новый модуль `shop/promo.py`: `DiscountKind`, `PromoCode` (процентный или фиксированный, минимальная сумма, срок действия, лимит использований, исключённые категории) и `PromoRegistry` (хранение кодов, проверка существования/срока/лимита по внедрённым часам, счётчик использований).
- Новые ошибки в `shop/errors.py`: `PromoError` и три независимых наследника `UnknownPromoCodeError`, `PromoExpiredError`, `PromoConditionsError`.
- `calculate_total` принимает необязательный `promo`; `LineTotal` и `OrderTotal` получают поле `discount`; скидка раскладывается по строкам с точным совпадением суммы, налог считается с суммы строки после скидки, доставка не скидывается.
- `OrderService` принимает необязательный `PromoRegistry`; `quote` и `place_order` принимают `promo_code`; `Order` хранит нормализованный `promo_code`. Использование засчитывается только при успешном `place_order`.
- Коды вводят люди, поэтому они регистронезависимы и обрезаются по краям (`normalize_key`). Пустой/пробельный `promo_code` в `quote`/`place_order` означает «без промокода» (решение тимлида в задаче); `resolve("")` — неизвестный код.
- Начало акции в будущем — тоже `PromoExpiredError` (решение маркетинга в задаче).
- Обратная совместимость: старые вызовы `calculate_total(cart[, shipping, tax])`, `quote(cart)`, `place_order(cart)` дают прежние суммы. Не **BREAKING**.

## Capabilities

### New Capabilities
- `promo-codes`: модель промокода, его валидация и нормализация, реестр (поиск, срок, лимит, счётчик использований) и иерархия ошибок.
- `promo-discounts`: расчёт скидки по промокоду в итогах заказа (участвующие строки, процент/фикс, построчная раскладка, налог после скидки, доставка), условия заказа и интеграция с оформлением заказа.

### Modified Capabilities

Нет: в `openspec/specs/` пока нет спецификаций, новое поведение описано новыми capability.

## Impact

- Код: `shop/promo.py` (новый), `shop/errors.py`, `shop/pricing.py`, `shop/orders.py`, `shop/__init__.py` (экспорт новых имён).
- Не трогаем: `shop/cli.py`, `shop/reports.py` (скидки в CLI и отчётах — отдельный тикет), существующие тесты. Новые тесты — отдельными файлами.
- Зависимости: новых нет, только стандартная библиотека.


### specs/promo-codes/spec.md

## Purpose

Описывает промокод как объект, правила его ввода и проверки, реестр кодов со счётчиком использований и ошибки, по которым вызывающий код отличает причину отказа.

## ADDED Requirements

### Requirement: Модель и валидация промокода
Промокод SHALL иметь непустой код, вид скидки (процент или фиксированная сумма) и значение; процентное значение MUST лежать в (0, 100], фиксированное MUST быть больше 0 и иметь не более двух знаков после запятой. Минимальная сумма заказа MUST быть не меньше 0 и иметь не более двух знаков; по умолчанию 0.00. `max_uses` MUST быть `None` (без лимита) или целым >= 1. `starts_at` и `expires_at` MUST быть aware-датами или `None`; если оба заданы, начало MUST быть строго раньше конца. Деньги MUST быть `Decimal` (не `float`). Любое нарушение SHALL приводить к `ValidationError`. Промокод SHALL быть неизменяемым.

#### Scenario: Корректный процентный код
- **WHEN** создаётся код с видом PERCENT и значением 15
- **THEN** объект создаётся, минимальная сумма равна 0.00, лимита и срока нет

#### Scenario: Процент вне диапазона
- **WHEN** значение PERCENT равно 0, отрицательно или больше 100
- **THEN** выбрасывается `ValidationError`

#### Scenario: Процент ровно 100
- **WHEN** значение PERCENT равно 100
- **THEN** код допустим

#### Scenario: Фиксированная сумма некорректна
- **WHEN** значение FIXED равно 0, отрицательно, `float` или имеет три знака после запятой
- **THEN** выбрасывается `ValidationError`

#### Scenario: Пустой код
- **WHEN** код пуст или состоит из пробелов
- **THEN** выбрасывается `ValidationError`

#### Scenario: Некорректные срок и лимит
- **WHEN** дата naive, либо `starts_at` не раньше `expires_at`, либо `max_uses` равен 0 или отрицателен
- **THEN** выбрасывается `ValidationError`

### Requirement: Нормализация кода
Код промокода SHALL храниться в нормализованном виде (без пробелов по краям, в верхнем регистре). Добавление, поиск и подсчёт использований в реестре MUST применять ту же нормализацию, так что `" summer10 "` и `"SUMMER10"` — один и тот же код.

#### Scenario: Ввод в другом регистре
- **WHEN** в реестр добавлен код `"Summer10"`, а ищется `"  SUMMER10 "`
- **THEN** находится тот же промокод, его код равен `"SUMMER10"`

#### Scenario: Дубликат
- **WHEN** в реестр добавляется код, совпадающий с существующим после нормализации
- **THEN** выбрасывается `ValidationError`, реестр не меняется

### Requirement: Поиск действующего кода в реестре
Реестр SHALL проверять по порядку: (1) код существует, иначе `UnknownPromoCodeError`; (2) код действует в текущий момент, иначе `PromoExpiredError`; (3) лимит не исчерпан, иначе `PromoConditionsError`. Текущее время MUST браться только из часов, переданных реестру. Срок действия — полуоткрытый интервал [`starts_at`, `expires_at`): начало включительно, конец исключительно, `None` — без ограничения. Время до `starts_at` MUST давать `PromoExpiredError`. Пустая или пробельная строка MUST давать `UnknownPromoCodeError`.

#### Scenario: Неизвестный код
- **WHEN** запрашивается код, которого нет в реестре, включая `""`
- **THEN** выбрасывается `UnknownPromoCodeError`

#### Scenario: Акция ещё не началась
- **WHEN** текущее время раньше `starts_at`
- **THEN** выбрасывается `PromoExpiredError`

#### Scenario: Начало срока включительно
- **WHEN** текущее время равно `starts_at`
- **THEN** код найден

#### Scenario: Конец срока исключительно
- **WHEN** текущее время равно `expires_at`
- **THEN** выбрасывается `PromoExpiredError`

#### Scenario: Порядок проверок
- **WHEN** код просрочен и при этом лимит исчерпан
- **THEN** выбрасывается `PromoExpiredError`, а не `PromoConditionsError`

#### Scenario: Лимит исчерпан
- **WHEN** число использований равно `max_uses`
- **THEN** выбрасывается `PromoConditionsError`

### Requirement: Счётчик использований
Реестр SHALL отдавать число использований кода (`uses`), изначально 0. Использованием MUST считаться только успешно оформленный заказ; `resolve`, расчёт итогов, `quote` и неудачные попытки оформления MUST NOT менять счётчик. Использование отменённого заказа SHALL оставаться засчитанным. `uses` для неизвестного кода MUST выбрасывать `UnknownPromoCodeError`.

#### Scenario: Новый код
- **WHEN** код только добавлен
- **THEN** `uses` равен 0

#### Scenario: Последнее использование по лимиту
- **WHEN** `max_uses` равен 1 и один заказ оформлен успешно
- **THEN** `uses` равен 1, повторный поиск кода выбрасывает `PromoConditionsError`

### Requirement: Иерархия ошибок промокодов
Ошибки промокодов SHALL наследоваться от общего `PromoError`, который наследуется от `ShopError`. `UnknownPromoCodeError`, `PromoExpiredError` и `PromoConditionsError` MUST быть независимыми: ни один не является подклассом другого. Голые `ValueError`/`KeyError` MUST NOT выпускаться наружу.

#### Scenario: Независимость классов
- **WHEN** перехватывается `PromoExpiredError`
- **THEN** `UnknownPromoCodeError` и `PromoConditionsError` им не перехватываются, но все три перехватываются как `PromoError` и как `ShopError`


### specs/promo-discounts/spec.md

## Purpose

Определяет, как промокод влияет на итоги заказа: какие строки участвуют, как считается и раскладывается скидка, как меняется налог и как промокод применяется при расчёте и оформлении заказа.

## ADDED Requirements

### Requirement: Участвующие строки
Скидка SHALL действовать только на участвующие строки. Строка не участвует, если её категория входит в исключённые категории кода, а также всегда, если это подарочный сертификат (скидки на него не распространяются независимо от настроек кода). Доставка MUST NOT участвовать в скидке.

#### Scenario: Исключённая категория
- **WHEN** код исключает категорию BOOKS, а в корзине есть книги и одежда
- **THEN** скидка начисляется только на строки одежды, у строк книг скидка 0.00

#### Scenario: Подарочный сертификат
- **WHEN** в корзине сертификат и обычный товар, а код не исключает категорий
- **THEN** скидка по сертификату равна 0.00

### Requirement: Размер скидки
Процентная скидка SHALL равняться сумме участвующих строк × процент / 100, округлённой через `ROUND_HALF_UP` до копеек. Фиксированная скидка SHALL равняться значению кода, но не больше суммы участвующих строк. Скидка MUST считаться от сумм строк до скидки.

#### Scenario: Процент с округлением
- **WHEN** сумма участвующих строк 100.05 и скидка 10 %
- **THEN** скидка равна 10.01 (10.005 округляется вверх)

#### Scenario: Фикс больше суммы
- **WHEN** фиксированная скидка 5000 при участвующих строках на 1200.00
- **THEN** скидка равна 1200.00 и участвующие строки стоят 0.00

#### Scenario: Сто процентов
- **WHEN** скидка 100 %
- **THEN** скидка равна сумме участвующих строк

### Requirement: Построчная раскладка скидки
Скидка SHALL раскладываться по участвующим строкам пропорционально их суммам с точностью до копейки; сумма построчных скидок MUST в точности равняться общей скидке, а скидка строки MUST NOT превышать сумму строки. Остаток копеек SHALL отдаваться строкам с наибольшей дробной долей, при равенстве — раньше стоящей в корзине строке; результат MUST быть детерминированным.

#### Scenario: Копейки не теряются
- **WHEN** фиксированная скидка 10.00 раскладывается на три строки по 10.00
- **THEN** построчные скидки 3.34, 3.33, 3.33, их сумма равна 10.00

#### Scenario: Скидка строки не больше строки
- **WHEN** любая корзина с любым допустимым кодом
- **THEN** для каждой строки 0.00 <= скидка <= сумма строки

### Requirement: Итоги и налог со скидкой
Каждая строка итогов и итог заказа SHALL иметь поле скидки (0.00, если скидки нет). `subtotal` MUST оставаться суммой строк до скидки; `total` MUST равняться `subtotal - discount + shipping + tax`. Налог строки MUST считаться по ставке её категории с суммы строки после скидки с округлением в строке; налог заказа — сумма налогов строк. Стоимость доставки и условие бесплатной доставки MUST считаться от суммы товаров до скидки и не меняться из-за промокода.

#### Scenario: Налог после скидки
- **WHEN** строка электроники 1000.00 получает скидку 100.00
- **THEN** налог строки 180.00 (20 % от 900.00), `total` на 120.00 меньше, чем без кода

#### Scenario: Доставка не зависит от скидки
- **WHEN** сумма товаров 3100.00 (доставка бесплатна), скидка уводит сумму ниже 3000.00
- **THEN** доставка остаётся 0.00

#### Scenario: Скидка полностью покрывает строку
- **WHEN** скидка равна сумме строки
- **THEN** налог этой строки равен 0.00

### Requirement: Условия заказа
Расчёт итогов с промокодом SHALL проверять только условия заказа (срок и лимит проверяет реестр). Сумма участвующих строк до скидки MUST быть не меньше минимальной суммы кода (граница включительно); если участвующих строк нет, заказ MUST считаться неподходящим. Нарушение условий SHALL приводить к `PromoConditionsError`. Расчёт итогов MUST NOT менять счётчик использований.

#### Scenario: Сумма ниже минимума
- **WHEN** сумма участвующих строк 499.99 при минимуме 500.00
- **THEN** выбрасывается `PromoConditionsError`

#### Scenario: Сумма ровно минимум
- **WHEN** сумма участвующих строк равна минимуму
- **THEN** скидка применяется

#### Scenario: Нет участвующих строк
- **WHEN** в корзине только подарочные сертификаты или товары исключённых категорий
- **THEN** выбрасывается `PromoConditionsError`

### Requirement: Обратная совместимость расчёта
Вызовы без промокода SHALL давать те же суммы, что и до изменения; скидка в них равна 0.00.

#### Scenario: Старые вызовы
- **WHEN** вызываются расчёт итогов с корзиной (с политиками или без) без промокода
- **THEN** суммы совпадают с прежними, `discount` равен 0.00 в заказе и во всех строках

### Requirement: Промокод при расчёте и оформлении заказа
Сервис заказов SHALL принимать необязательный реестр промокодов и необязательный код в `quote` и `place_order`. Код MUST нормализоваться. `None`, пустая и пробельная строка означают «без промокода» и не считаются ошибкой, даже без реестра. Непустой код без реестра MUST давать `UnknownPromoCodeError`. Проверки идут по порядку: код существует, действует, лимит, условия заказа. Пустая корзина по-прежнему даёт `EmptyCartError`. `quote` MUST NOT менять состояние. `place_order` MUST увеличивать счётчик ровно на 1 только после успешного оформления; при любой ошибке заказ не создаётся и счётчик не меняется. Заказ SHALL хранить нормализованный код или `None`; сохранённые итоги MUST включать скидку.

#### Scenario: Пустое поле формы
- **WHEN** `place_order(cart, "   ")` или `quote(cart, "")`
- **THEN** результат такой же, как без кода, `Order.promo_code` равен `None`

#### Scenario: Успешное оформление
- **WHEN** `place_order(cart, " summer10 ")` с действующим кодом `SUMMER10`
- **THEN** заказ содержит скидку, `promo_code` равен `"SUMMER10"`, `uses("SUMMER10")` равен 1

#### Scenario: Quote не расходует лимит
- **WHEN** выполняется `quote` с кодом, у которого `max_uses` равен 1
- **THEN** `uses` остаётся 0 и последующий `place_order` успешен

#### Scenario: Неудачная попытка
- **WHEN** `place_order` с кодом, не прошедшим условия заказа
- **THEN** выбрасывается `PromoConditionsError`, заказов в хранилище не прибавилось, `uses` не изменился

#### Scenario: Нет реестра
- **WHEN** сервис создан без реестра и передан код `"SUMMER10"`
- **THEN** выбрасывается `UnknownPromoCodeError`

#### Scenario: Лимит
- **WHEN** `max_uses` равен 1 и первый заказ с кодом оформлен
- **THEN** второй `place_order` с этим кодом выбрасывает `PromoConditionsError`
