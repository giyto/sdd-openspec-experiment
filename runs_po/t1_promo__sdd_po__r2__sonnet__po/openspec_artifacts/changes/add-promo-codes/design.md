## Context

Сейчас `calculate_total` чистая функция: суммы строк, налог по строкам, доставка по сумме товаров (порог — по сумме до скидки), `total = subtotal + shipping + tax`. `OrderService.quote` вызывает её, `place_order` сохраняет `Order`. Соглашения README: `Decimal` + `quantize_money` (ROUND_HALF_UP), только наследники `ShopError`, время через `Clock`, frozen-dataclass с инвариантами в `__post_init__`, коды людей через `normalize_key`, интервалы `[начало, конец)`, подарочные сертификаты никогда не получают скидок. Мотивация и состав изменений — в proposal.md, требования — в specs.

## Goals / Non-Goals

**Goals:**
- Скидка в итогах и построчно, сумма построчных равна общей, налог со строки после скидки.
- Счётчик использований меняется только при успешном `place_order`.
- Старые вызовы дают те же суммы.

**Non-Goals:**
- CLI и отчёты (отдельный тикет), изменение существующих тестов.
- Хранение реестра и счётчиков вне памяти, потокобезопасность между процессами.
- Комбинирование нескольких кодов в одном заказе.

## Decisions

1. **Нормализация везде через `normalize_key`.** `PromoCode.__post_init__` нормализует `code` (через `object.__setattr__`, как в `Product`) и отвергает пустой результат; `PromoRegistry.add/resolve/uses` нормализуют аргумент. `resolve("")` естественно даёт `UnknownPromoCodeError`. Пустой/пробельный код в `OrderService` отсекается до реестра: `_clean_code(raw) -> str | None` возвращает `None` для `None` и пустой после `strip` строки; нестроковый ввод даёт `ValidationError` из `normalize_key`.
2. **Проверка срока в реестре, условий заказа в `calculate_total`.** `resolve`: существует → `starts_at <= now < expires_at` (иначе `PromoExpiredError`, в т. ч. до начала) → `uses < max_uses` (иначе `PromoConditionsError`). Время только из `clock` реестра. `calculate_total(..., promo=)` реестр не знает и не проверяет срок/лимит, только `min_order_amount` и наличие участвующих строк.
3. **Участвующие строки:** категория не `GIFT_CARD` и не в `excluded_categories`. Сертификаты исключены жёстко (README), даже если код их не перечисляет.
4. **Что сравнивается с `min_order_amount`:** сумма участвующих строк до скидки, `>=`. Аргумент: сертификаты и исключённые товары не должны «добирать» минимум для скидки, на которую не имеют права. Альтернатива (весь `subtotal`) отвергнута.
5. **Размер скидки:** PERCENT — `quantize_money(base * value / 100)`; FIXED — `min(value, base)`, где `base` — сумма участвующих строк до скидки.
6. **Раскладка — метод наибольших остатков в целых копейках.** Для строки i: `share_i = D * a_i / S` (все в копейках, целочисленно), берём `floor`, остаток `D - sum(floor)` раздаём по одной копейке строкам по убыванию дробной части, при равенстве — по порядку в корзине. Гарантии: сумма в точности `D`; `d_i <= a_i`, потому что при `share_i = a_i` дробная часть 0 и добавки нет; детерминизм. Альтернатива «последней строке остаток» отвергнута: может превысить сумму строки и смещает копейки на одну строку.
7. **Налог:** `tax.tax_for(category, amount - discount)` на строку. `subtotal` остаётся суммой до скидки, `shipping.cost_for(subtotal - discount, ...)`: порог бесплатной доставки сравнивается с суммой товаров ПОСЛЕ скидки (иначе покупатели добирали бы до порога промокодом), а сама стоимость доставки скидкой не уменьшается (`fee` прежний). `total = subtotal - discount + shipping + tax`.
8. **Обратная совместимость данных:** `LineTotal.discount` и `OrderTotal.discount` добавляются последними полями со значением по умолчанию `ZERO`; `Order.promo_code: str | None = None` — последним полем. Параметр `promo` в `calculate_total` keyword-only.
9. **Учёт использования.** `PromoRegistry` получает дополнительный метод `redeem(code)`, который под `threading.Lock` повторно выполняет `resolve` и увеличивает счётчик, возвращая `PromoCode`. `place_order`: пустая корзина → `EmptyCartError`; `resolve` и `calculate_total` (любая ошибка прекращает операцию без побочных эффектов); `redeem`; затем создание и сохранение `Order`. Так счётчик растёт только если заказ оформляется, а гонка двух оформлений на последнем использовании не превышает лимит. `quote` вызывает только `resolve` и `calculate_total`. Отмена заказа возвращает использование: `OrderService.cancel` для заказа с `promo_code` вызывает `PromoRegistry.release(code)`, уменьшающий счётчик на 1 (под тем же локом, не ниже 0). Отмена возможна только из `PLACED`, поэтому возврат происходит не более одного раза на заказ. Формулировка замечания об отмене была обрезана; принято решение «отмена освобождает использование», в духе лимита как числа действующих заказов.
10. **Допущение о порядке ошибок:** `EmptyCartError` проверяется раньше ошибок промокода (существующее поведение пустой корзины не меняется); дальше порядок из тикета: неизвестен → не действует → лимит → условия заказа.
11. **Ошибки:** `PromoError(ShopError)` и три прямых наследника `PromoError`, не связанных между собой. `uses` для неизвестного кода — `UnknownPromoCodeError`. `ValidationError` для некорректного `PromoCode` и дубликата в реестре.
12. **Валидация `PromoCode`:** значения денег — только `Decimal`, конечные; FIXED и `min_order_amount` не более двух знаков (по образцу цены в `Product`); `max_uses` — `int`, не `bool`; даты aware; `starts_at < expires_at`; `excluded_categories` — набор `Category` (приводится к `frozenset`). Процент может иметь дробную часть (12.5).
13. **Экспорт:** новые публичные имена добавляются в `shop/__init__.py`; `cli.py` и `reports.py` не меняются (они не создают `LineTotal`/`OrderTotal` напрямую, значения по умолчанию сохраняют совместимость).
14. **Логирование:** модульный `logger`, без `print`; `info` при списании использования.

## Risks / Trade-offs

- [`min_order_amount` трактуется как сумма участвующих строк, маркетинг мог иметь в виду весь заказ] → зафиксировано как допущение; смена — локальная правка одной проверки и спеки.
- [Код без участвующих строк даёт `PromoConditionsError`, а не нулевую скидку] → пользователь получает понятный отказ вместо «успешного» кода без эффекта; отражено в спеке.
- [Реестр в памяти, лок защищает только один процесс] → в рамках проекта хранилище заказов тоже в памяти; при переходе на БД счётчик нужно делать атомарным в хранилище.
- [Часы реестра и сервиса могут быть разными объектами] → в тестах и композиции передаётся один `FixedClock`; расхождение не влияет на корректность проверок.
- [Расширение публичного API реестра методами `redeem`/`release` сверх списка в тикете] → методы минимальны и нужны для атомарного учёта; существующие сигнатуры не меняются.

## Migration Plan

Миграция данных не нужна: изменения аддитивные, значения по умолчанию сохраняют прежние вызовы и суммы. Откат — revert коммита. Версию пакета можно поднять до 1.5.0 (не обязательно, решает релиз).
