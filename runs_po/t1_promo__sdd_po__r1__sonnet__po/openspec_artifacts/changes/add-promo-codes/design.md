## Context

См. proposal.md (Why). Сейчас `calculate_total` считает строки, налог сверху по строкам и доставку; `OrderService.quote/place_order` вызывает его без промокодов. Соглашения README: `Decimal` и `quantize_money` (ROUND_HALF_UP), ошибки только от `ShopError`, время только через `Clock`, frozen-dataclass с проверкой в `__post_init__`, вводимые людьми коды нормализуются `normalize_key`, интервалы полуоткрытые, только stdlib. Подарочные сертификаты никогда не получают скидок.

## Goals / Non-Goals

**Goals:**
- Точная раскладка скидки по строкам (сумма == общая скидка), налог по строке после скидки.
- Обратная совместимость: новые поля `discount` имеют значение по умолчанию `ZERO`, новые параметры необязательны, `cli.py` и `reports.py` не меняются.

**Non-Goals:**
- Скидки в CLI/отчётах, комбинирование нескольких кодов, потокобезопасность хранилища заказов, персистентность реестра.

## Decisions

1. **`shop/promo.py` содержит `DiscountKind`, `PromoCode`, `PromoRegistry`** (по API тикета). `PromoCode.__post_init__` нормализует код через `object.__setattr__` (как `Product.sku`) и валидирует поля, ошибки — `ValidationError`. Деньги проверяются как в `Product`: `Decimal`, `to_money(v) == v`. Для PERCENT число знаков не ограничиваем (только конечность и диапазон `(0, 100]`).
2. **Реестр**: словарь `normalized code -> PromoCode` и счётчики. `resolve`: `normalize_key` → поиск (пусто или нет в словаре → `UnknownPromoCodeError`) → окно `[starts_at, expires_at)` по `clock.now()` (вне окна, включая «ещё не началось» → `PromoExpiredError`) → `uses >= max_uses` → `PromoConditionsError`. Добавлен публичный метод `record_use(code)`: под `threading.Lock` повторно проверяет лимит и увеличивает счётчик. Парный метод `release_use(code)` под тем же локом уменьшает счётчик на единицу, но не ниже 0 (для возврата при отмене заказа). Альтернатива «счётчик внутри resolve» отвергнута: тикет требует, чтобы использованием считался только успешный заказ.
3. **Ошибки** в `shop/errors.py`: `PromoError(ShopError)` и три прямых независимых наследника; не `ValidationError`, чтобы вызывающий код различал бизнес-отказ и кривой ввод.
4. **Пустой ввод**: в сервисе `promo_code` — `None` или `normalize_key(x) == ""` → промокода нет, реестр не вызывается; `resolve("")` → `UnknownPromoCodeError` (решение тимлида). Не-строка → `ValidationError` из `normalize_key`.
5. **Расчёт скидки в `pricing.py`**: `calculate_total(..., *, promo=None)`. Участвует строка, если категория не `GIFT_CARD` и не в `promo.excluded_categories`. База = сумма участвующих строк; если база == 0 (нет участвующих) или `< min_order_amount` → `PromoConditionsError`. Скидка: PERCENT → `quantize_money(base * value / 100)`; FIXED → `min(value, base)`. Срок и лимит здесь не проверяются.
6. **Раскладка — метод наибольших остатков в копейках**: целое число копеек скидки D, база B; доля строки `D * amount_i / B`; берётся floor в копейках, остаток копеек раздаётся по одной строкам с наибольшей дробной частью, при равенстве — раньше в корзине. Расчёт на целых (`Decimal`/`int`) без округления долей. Инвариант: сумма == D, `discount_i <= amount_i` (так как `D <= B`). Альтернатива «пропорция с округлением и остаток на последнюю строку» отвергнута: последняя строка может уйти в минус или получить перекос.
7. **Налог**: `tax.tax_for(category, amount - discount)`; `LineTotal.amount` остаётся суммой до скидки, добавляется `discount` (по умолчанию `ZERO`, последним полем). `OrderTotal.discount` тоже последним полем с умолчанием. `total = subtotal - discount + shipping + tax`.
8. **Доставка** считается по сумме товаров после скидки (`subtotal - discount`), чтобы покупатели не добирали до порога промокодом. Сама стоимость доставки скидкой не уменьшается.
9. **`OrderService`**: `promos` — keyword-параметр; приватный `_resolve_promo(promo_code)` → `PromoCode | None`. `quote(cart, promo_code=None)` = resolve + `calculate_total` (счётчик не трогает). `place_order`: resolve → `calculate_total` → создать `Order` (`promo_code=promo.code`) → `registry.record_use` → `store.add`. Все проверки, способные упасть, идут до `next_id()` и записи, чтобы неудача не меняла состояние; номер заказа берётся после расчёта. `Order.promo_code: str | None = None` последним полем. `cancel`: после проверки статуса, если у заказа есть `promo_code` и задан реестр, вызывается `release_use`, затем заказ сохраняется как отменённый. Повторная отмена падает с `InvalidOrderStateError` до возврата, поэтому возврат происходит ровно один раз. Без реестра возврат пропускается (решение: заказ с кодом без реестра возможен только при пересборке сервиса, отмена не должна из-за этого падать).
10. **Логирование** через `logger` модуля, без `print`.

## Risks / Trade-offs

- [Гонка: два параллельных заказа на последнее использование] → `record_use` перепроверяет лимит под локом; но `place_order` целиком не атомарен (хранилище заказов вне рамок). При отказе `record_use` заказ не сохраняется.
- [Часы реестра и сервиса могут различаться] → в продакшене используется один `Clock`; в тестах передавать один и тот же `FixedClock`.
- [Допущение «min_order_amount сравнивается с суммой участвующих строк»] → тикет говорит лишь «сумма заказа». Выбрана база скидки, чтобы сертификаты и исключённые категории не помогали набрать минимум. Изменить легко (одно сравнение).

## Assumptions (неоднозначности тикета)

- Заказ без участвующих строк с промокодом — `PromoConditionsError`, а не тихая нулевая скидка.
- Сравнение с `min_order_amount` нестрогое (равенство проходит).
- Отмена заказа с промокодом возвращает использование (счётчик −1, не ниже 0), даже если срок кода уже истёк.
- `uses` для неизвестного кода — `UnknownPromoCodeError`.
- Дубликат кода в реестре (после нормализации) — `ValidationError`.
- Если у кода есть `starts_at`, `expires_at`, они обязаны быть aware; naive → `ValidationError`.
