### design.md

## Context

См. proposal.md (Why). Сейчас `calculate_total` считает строки, налог сверху по строкам и доставку; `OrderService.quote/place_order` вызывает его без промокодов. Соглашения README: `Decimal` и `quantize_money` (ROUND_HALF_UP), ошибки только от `ShopError`, время только через `Clock`, frozen-dataclass с проверкой в `__post_init__`, вводимые людьми коды нормализуются `normalize_key`, интервалы полуоткрытые, только stdlib. Подарочные сертификаты никогда не получают скидок.

## Goals / Non-Goals

**Goals:**
- Точная раскладка скидки по строкам (сумма == общая скидка), налог по строке после скидки.
- Обратная совместимость: новые поля `discount` имеют значение по умолчанию `ZERO`, новые параметры необязательны, `cli.py` и `reports.py` не меняются.

**Non-Goals:**
- Скидки в CLI/отчётах, комбинирование нескольких кодов, возврат использования при отмене заказа, потокобезопасность хранилища заказов, персистентность реестра.

## Decisions

1. **`shop/promo.py` содержит `DiscountKind`, `PromoCode`, `PromoRegistry`** (по API тикета). `PromoCode.__post_init__` нормализует код через `object.__setattr__` (как `Product.sku`) и валидирует поля, ошибки — `ValidationError`. Деньги проверяются как в `Product`: `Decimal`, `to_money(v) == v`. Для PERCENT число знаков не ограничиваем (только конечность и диапазон `(0, 100]`).
2. **Реестр**: словарь `normalized code -> PromoCode` и счётчики. `resolve`: `normalize_key` → поиск (пусто или нет в словаре → `UnknownPromoCodeError`) → окно `[starts_at, expires_at)` по `clock.now()` (вне окна, включая «ещё не началось» → `PromoExpiredError`) → `uses >= max_uses` → `PromoConditionsError`. Добавлен публичный метод `record_use(code)`: под `threading.Lock` повторно проверяет лимит и увеличивает счётчик. Альтернатива «счётчик внутри resolve» отвергнута: тикет требует, чтобы использованием считался только успешный заказ.
3. **Ошибки** в `shop/errors.py`: `PromoError(ShopError)` и три прямых независимых наследника; не `ValidationError`, чтобы вызывающий код различал бизнес-отказ и кривой ввод.
4. **Пустой ввод**: в сервисе `promo_code` — `None` или `normalize_key(x) == ""` → промокода нет, реестр не вызывается; `resolve("")` → `UnknownPromoCodeError` (решение тимлида). Не-строка → `ValidationError` из `normalize_key`.
5. **Расчёт скидки в `pricing.py`**: `calculate_total(..., *, promo=None)`. Участвует строка, если категория не `GIFT_CARD` и не в `promo.excluded_categories`. База = сумма участвующих строк; если база == 0 (нет участвующих) или `< min_order_amount` → `PromoConditionsError`. Скидка: PERCENT → `quantize_money(base * value / 100)`; FIXED → `min(value, base)`. Срок и лимит здесь не проверяются.
6. **Раскладка — метод наибольших остатков в копейках**: целое число копеек скидки D, база B; доля строки `D * amount_i / B`; берётся floor в копейках, остаток копеек раздаётся по одной строкам с наибольшей дробной частью, при равенстве — раньше в корзине. Расчёт на целых (`Decimal`/`int`) без округления долей. Инвариант: сумма == D, `discount_i <= amount_i` (так как `D <= B`). Альтернатива «пропорция с округлением и остаток на последнюю строку» отвергнута: последняя строка может уйти в минус или получить перекос.
7. **Налог**: `tax.tax_for(category, amount - discount)`; `LineTotal.amount` остаётся суммой до скидки, добавляется `discount` (по умолчанию `ZERO`, последним полем). `OrderTotal.discount` тоже последним полем с умолчанием. `total = subtotal - discount + shipping + tax`.
8. **Доставка** считается по `subtotal` до скидки (скидка «не распространяется» на доставку; скидка не должна лишать бесплатной доставки).
9. **`OrderService`**: `promos` — keyword-параметр; приватный `_resolve_promo(promo_code)` → `PromoCode | None`. `quote(cart, promo_code=None)` = resolve + `calculate_total` (счётчик не трогает). `place_order`: resolve → `calculate_total` → создать `Order` (`promo_code=promo.code`) → `registry.record_use` → `store.add`. Все проверки, способные упасть, идут до `next_id()` и записи, чтобы неудача не меняла состояние; номер заказа берётся после расчёта. `Order.promo_code: str | None = None` последним полем.
10. **Логирование** через `logger` модуля, без `print`.

## Risks / Trade-offs

- [Гонка: два параллельных заказа на последнее использование] → `record_use` перепроверяет лимит под локом; но `place_order` целиком не атомарен (хранилище заказов вне рамок). При отказе `record_use` заказ не сохраняется.
- [Часы реестра и сервиса могут различаться] → в продакшене используется один `Clock`; в тестах передавать один и тот же `FixedClock`.
- [Допущение «min_order_amount сравнивается с суммой участвующих строк»] → тикет говорит лишь «сумма заказа». Выбрана база скидки, чтобы сертификаты и исключённые категории не помогали набрать минимум. Изменить легко (одно сравнение).

## Assumptions (неоднозначности тикета)

- Заказ без участвующих строк с промокодом — `PromoConditionsError`, а не тихая нулевая скидка.
- Сравнение с `min_order_amount` нестрогое (равенство проходит).
- Отмена заказа не возвращает использование.
- `uses` для неизвестного кода — `UnknownPromoCodeError`.
- Дубликат кода в реестре (после нормализации) — `ValidationError`.
- Если у кода есть `starts_at`, `expires_at`, они обязаны быть aware; naive → `ValidationError`.


### proposal.md

## Why

SHOP-412: маркетинг запускает летнюю кампанию с промокодами, а скидки сейчас вручную делает поддержка, из-за чего суммы расходятся с чеками. Нужна скидка, которая считается кодом, честно попадает в итоги и построчно в чек (бухгалтерия считает налог по строкам).

## What Changes

- Новый модуль промокодов: процентные и фиксированные коды, срок действия `[starts_at, expires_at)`, лимит использований, минимальная сумма заказа, исключённые категории; реестр кодов с внедрёнными часами и счётчиком использований.
- Три новых независимых исключения под `PromoError(ShopError)`: неизвестный код, код вне срока, нарушены условия (лимит или заказ не подходит).
- `calculate_total` принимает необязательный `promo`; скидка раскладывается по строкам с точной суммой, налог считается с суммы строки после скидки, доставка не скидывается. В `LineTotal` и `OrderTotal` появляется поле `discount`.
- `OrderService` принимает необязательный `PromoRegistry`; `quote` и `place_order` принимают необязательный `promo_code`; `Order` хранит нормализованный `promo_code`. Использование засчитывается только при успешном `place_order`.
- Старые вызовы без промокода дают те же суммы (обратная совместимость).
- Вне рамок: `shop/cli.py`, `shop/reports.py`, существующие тесты (не меняются), новые зависимости.

## Capabilities

### New Capabilities
- `promo-codes`: модель промокода, нормализация и валидация, реестр (поиск, срок, лимит, счётчик использований), иерархия ошибок.
- `order-discounts`: применение промокода при расчёте итогов, построчная раскладка скидки, налог после скидки, интеграция в `quote`/`place_order`, учёт использований.

### Modified Capabilities

(нет: в `openspec/specs/` пока нет спецификаций, правила README о расчёте формализуются в новых спецификациях)

## Impact

- Код: новый `shop/promo.py`; изменения в `shop/errors.py`, `shop/pricing.py`, `shop/orders.py`; новые тесты отдельными файлами. `shop/cli.py` и `shop/reports.py` не меняются, но продолжают работать (новые поля имеют значения по умолчанию).
- API: только обратно совместимое расширение. Зависимости не добавляются.
- README: желательно добавить в «Правила расчёта» строку про скидку (`total = subtotal - discount + shipping + tax`).


### specs/order-discounts/spec.md

## Purpose

Описывает, как промокод влияет на итоги заказа: расчёт скидки, раскладка по строкам, налог, доставка, а также передачу кода при расчёте и оформлении заказа и учёт использований.

## ADDED Requirements

### Requirement: Участвующие товары
Скидка SHALL действовать только на участвующие строки. Строка не участвует, если её категория — подарочный сертификат (всегда, независимо от настроек кода) или входит в исключённые категории кода. Базой скидки является сумма участвующих строк до скидки.

#### Scenario: Сертификат не получает скидку
- **WHEN** в корзине книга и подарочный сертификат, применён процентный код без исключений
- **THEN** скидка сертификата равна 0.00, база — только сумма книги

#### Scenario: Исключённая категория
- **WHEN** у кода исключена категория `FOOD`
- **THEN** скидка строк категории `FOOD` равна 0.00

### Requirement: Размер скидки
Процентная скидка SHALL равняться базе × процент / 100, округлённой до копеек через `ROUND_HALF_UP`. Фиксированная скидка SHALL равняться `min(значение, база)`. Скидка не превышает базу и не бывает отрицательной.

#### Scenario: Округление процента
- **WHEN** база равна 100.05, процент 10 (точное значение 10.005)
- **THEN** скидка равна 10.01

#### Scenario: Фиксированная скидка больше базы
- **WHEN** фиксированная скидка 500.00, а база 320.00
- **THEN** скидка равна 320.00

### Requirement: Условия заказа
Расчёт итогов с промокодом SHALL отклонять заказ с `PromoConditionsError`, если база скидки (сумма участвующих строк до скидки) меньше `min_order_amount` или участвующих строк нет. Равенство минимальной сумме допустимо. Расчёт итогов MUST NOT проверять срок и лимит — это делает реестр.

#### Scenario: База ниже минимума
- **WHEN** `min_order_amount` равен 1000.00, а база 999.99
- **THEN** возникает `PromoConditionsError`

#### Scenario: База равна минимуму
- **WHEN** `min_order_amount` равен 1000.00, а база 1000.00
- **THEN** скидка применяется

#### Scenario: Нет участвующих строк
- **WHEN** в корзине только подарочные сертификаты
- **THEN** возникает `PromoConditionsError`

### Requirement: Построчная раскладка скидки
Общая скидка SHALL раскладываться по участвующим строкам пропорционально их суммам с точностью до копейки так, что сумма построчных скидок точно равна общей скидке, а скидка строки не превышает её сумму. Остаток копеек SHALL получать строки с наибольшей дробной частью доли; при равенстве — строка, добавленная в корзину раньше. Результат детерминирован.

#### Scenario: Сумма совпадает
- **WHEN** скидка 10.00 раскладывается на три равные строки
- **THEN** построчные скидки равны 3.34, 3.33, 3.33 и дают в сумме 10.00

#### Scenario: Строка не уходит в минус
- **WHEN** фиксированная скидка равна всей базе
- **THEN** скидка каждой участвующей строки равна её сумме

### Requirement: Налог и итоги
Налог строки SHALL считаться с суммы строки после скидки по ставке её категории с округлением в каждой строке. Итоги: `subtotal` — сумма строк до скидки, `discount` — общая скидка, `total = subtotal - discount + shipping + tax`. Доставка не зависит от скидки: её стоимость определяется по сумме товаров до скидки, и скидка на неё не распространяется. Без промокода `discount` строк и заказа равен `0.00`.

#### Scenario: Налог после скидки
- **WHEN** строка стоит 1000.00 со ставкой 20 %, скидка строки 100.00
- **THEN** налог строки равен 180.00

#### Scenario: Бесплатная доставка сохраняется
- **WHEN** subtotal 3100.00, а скидка делает сумму товаров меньше 3000.00
- **THEN** доставка по-прежнему 0.00

#### Scenario: Итог
- **WHEN** применена скидка
- **THEN** `total` равен `subtotal - discount + shipping + tax`, а сумма `discount` строк равна `discount` заказа

### Requirement: Обратная совместимость расчёта
Вызовы `calculate_total(cart)`, `calculate_total(cart, shipping, tax)`, `quote(cart)`, `place_order(cart)` SHALL возвращать те же суммы, что и до изменения; `discount` равен `0.00`.

#### Scenario: Без промокода
- **WHEN** вызывается `calculate_total(cart)`
- **THEN** суммы совпадают с прежними, `discount == Decimal("0.00")` у заказа и строк

### Requirement: Промокод в quote и place_order
`quote` и `place_order` SHALL принимать необязательный `promo_code`. `None`, пустая и пробельная строка означают отсутствие кода (реестр не опрашивается, даже если он не задан). Непустой код SHALL разрешаться через реестр сервиса; при отсутствии реестра любой непустой код — `UnknownPromoCodeError`. Порядок проверок: существование, срок, лимит, условия заказа. `Order.promo_code` SHALL хранить нормализованный код или `None`. Не-строка MUST давать `ValidationError`.

#### Scenario: Пустое поле формы
- **WHEN** `place_order(cart, promo_code="   ")`
- **THEN** заказ оформляется без скидки, `Order.promo_code is None`

#### Scenario: Код в другом регистре
- **WHEN** `place_order(cart, promo_code=" summer10")`
- **THEN** скидка применена, `Order.promo_code == "SUMMER10"`

#### Scenario: Нет реестра
- **WHEN** сервис создан без реестра и передан непустой код
- **THEN** возникает `UnknownPromoCodeError`

#### Scenario: Порядок проверок
- **WHEN** код просрочен, а заказ ниже минимальной суммы
- **THEN** возникает `PromoExpiredError`

### Requirement: Учёт использований
Использование SHALL засчитываться ровно один раз и только при успешном `place_order` с промокодом. `quote`, `calculate_total` и любые неудачные попытки (ошибка до сохранения заказа) MUST NOT менять счётчик. Отмена заказа счётчик не уменьшает.

#### Scenario: quote не расходует лимит
- **WHEN** выполнен `quote` с кодом на одно использование, затем `place_order`
- **THEN** `place_order` успешен, `uses` равно 1

#### Scenario: Неудачная попытка
- **WHEN** `place_order` падает из-за суммы ниже минимальной
- **THEN** `uses` не меняется, заказ не сохранён

#### Scenario: Лимит исчерпан
- **WHEN** лимит 1 и один заказ уже оформлен
- **THEN** второй `place_order` вызывает `PromoConditionsError`


### specs/promo-codes/spec.md

## Purpose

Описывает промокоды: как задаётся код, как его вводят покупатели, как реестр проверяет существование, срок действия и лимит использований, и какие ошибки возвращаются.

## ADDED Requirements

### Requirement: Модель промокода и валидация
Промокод SHALL быть неизменяемым объектом с видом скидки (процент или фиксированная сумма), значением, минимальной суммой заказа (по умолчанию 0.00), необязательными началом и концом действия, необязательным лимитом использований и набором исключённых категорий. Код SHALL нормализоваться как другие вводимые людьми коды (обрезка пробелов по краям, верхний регистр). Некорректные данные MUST приводить к `ValidationError`: пустой (после нормализации) код; процент вне `(0, 100]`; фиксированная сумма не больше нуля или с более чем двумя знаками после запятой; отрицательная минимальная сумма; лимит меньше 1 или не целое число; naive `datetime`; начало не раньше конца; нефинитные значения и `float` вместо денег.

#### Scenario: Код нормализуется при создании
- **WHEN** создаётся промокод с кодом `"  summer10 "`
- **THEN** его код равен `"SUMMER10"`

#### Scenario: Процент вне диапазона
- **WHEN** создаётся процентный промокод со значением `0` или `100.01`
- **THEN** возникает `ValidationError`

#### Scenario: Процент 100 допустим
- **WHEN** создаётся процентный промокод со значением `100`
- **THEN** промокод создаётся

#### Scenario: Пустой код
- **WHEN** создаётся промокод с кодом `"   "`
- **THEN** возникает `ValidationError`

#### Scenario: Некорректный интервал
- **WHEN** `starts_at` равен `expires_at` или позже него
- **THEN** возникает `ValidationError`

#### Scenario: Лимит меньше единицы
- **WHEN** `max_uses` равен `0`
- **THEN** возникает `ValidationError`

### Requirement: Регистрация кодов без дублей
Реестр SHALL хранить промокоды по нормализованному коду. Повторное добавление кода, совпадающего после нормализации, MUST приводить к `ValidationError`.

#### Scenario: Дубль в другом регистре
- **WHEN** в реестр добавлены `SUMMER10`, затем `" summer10"`
- **THEN** второе добавление вызывает `ValidationError`, первый код остаётся без изменений

### Requirement: Поиск кода нечувствителен к регистру и пробелам
`resolve` и `uses` SHALL нормализовать переданную строку. Пустая или пробельная строка в `resolve` MUST давать `UnknownPromoCodeError` (не `ValidationError`). Не-строка MUST давать `ValidationError`.

#### Scenario: Ввод в другом регистре
- **WHEN** зарегистрирован `SUMMER10` и вызывается `resolve(" summer10 ")`
- **THEN** возвращается этот промокод

#### Scenario: Пустой ввод в resolve
- **WHEN** вызывается `resolve("")`
- **THEN** возникает `UnknownPromoCodeError`

#### Scenario: Неизвестный код в uses
- **WHEN** вызывается `uses` для незарегистрированного кода
- **THEN** возникает `UnknownPromoCodeError`

### Requirement: Порядок проверок и ошибки реестра
`resolve` SHALL проверять по порядку: существование (`UnknownPromoCodeError`), действие в текущий момент (`PromoExpiredError`), лимит использований (`PromoConditionsError`). Интервал действия полуоткрытый `[starts_at, expires_at)`; граница `None` означает отсутствие ограничения. Код, который ещё не начал действовать, MUST давать `PromoExpiredError`. Текущее время SHALL браться только из часов, переданных реестру. `PromoError` — общий предок трёх независимых классов ошибок; ни один из них не наследует другой и не является `ValidationError`.

#### Scenario: Начало включительно
- **WHEN** текущее время равно `starts_at`
- **THEN** `resolve` возвращает код

#### Scenario: Конец исключительно
- **WHEN** текущее время равно `expires_at`
- **THEN** `resolve` вызывает `PromoExpiredError`

#### Scenario: Акция ещё не началась
- **WHEN** текущее время раньше `starts_at`
- **THEN** `resolve` вызывает `PromoExpiredError`

#### Scenario: Просрочен и исчерпан одновременно
- **WHEN** код вне срока и его лимит исчерпан
- **THEN** `resolve` вызывает `PromoExpiredError`

#### Scenario: Лимит исчерпан
- **WHEN** число использований равно `max_uses`
- **THEN** `resolve` вызывает `PromoConditionsError`

#### Scenario: Ошибки независимы
- **WHEN** проверяется иерархия исключений
- **THEN** все три класса являются подклассами `PromoError` и `ShopError`, но ни один не подкласс другого

### Requirement: Счётчик использований
Реестр SHALL вести счётчик использований каждого кода, начинающийся с 0. `resolve`, `uses` и любые неудачные операции MUST NOT изменять счётчик. Фиксация использования SHALL повторно проверять лимит и при исчерпании вызывать `PromoConditionsError`, не увеличивая счётчик.

#### Scenario: Поиск не расходует лимит
- **WHEN** `resolve` вызван несколько раз подряд
- **THEN** `uses` остаётся равным 0

#### Scenario: Фиксация сверх лимита
- **WHEN** фиксируется использование кода с исчерпанным лимитом
- **THEN** возникает `PromoConditionsError`, счётчик не растёт
