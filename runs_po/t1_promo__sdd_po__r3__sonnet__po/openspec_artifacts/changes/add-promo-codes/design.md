## Context

См. proposal.md. Проект следует соглашениям README: `Decimal` + `quantize_money` (`ROUND_HALF_UP`), ошибки только от `ShopError`, внедряемый `Clock`, frozen-dataclass с инвариантами в `__post_init__`, `normalize_key` для вводимых людьми кодов, полуоткрытые интервалы `[начало, конец)`, только stdlib. Сертификаты (`Category.GIFT_CARD`) по README никогда не участвуют в скидках. `shop/cli.py` и `shop/reports.py` не меняются: новые поля имеют значения по умолчанию, чтобы они продолжали работать.

## Goals / Non-Goals

**Goals:** обратная совместимость API; точное совпадение суммы построчных скидок с общей; использование засчитывается только успешным заказом и возвращается при его отмене.

**Non-Goals:** скидки в CLI/отчётах; хранение промокодов вне памяти; комбинирование нескольких кодов.

## Decisions

1. **Размещение.** `shop/promo.py` содержит `DiscountKind`, `PromoCode`, `PromoRegistry`; расчёт скидки живёт в `shop/pricing.py` (чистая функция, без времени и состояния); исключения в `shop/errors.py`. `pricing` импортирует `PromoCode` из `promo`; `promo` не импортирует `pricing` (нет цикла).
2. **Разделение проверок.** Реестр проверяет существование → срок → лимит; `calculate_total` — только условия заказа (минимум, наличие участвующих строк). `OrderService` вызывает их в этом порядке.
3. **Нормализация.** `normalize_key` применяется в `PromoCode.__post_init__`, `add`, `resolve`, `uses`. Пустой после нормализации код в конструкторе — `ValidationError`, в `resolve` — `UnknownPromoCodeError`. Правило «пустой = нет кода» действует только в `OrderService` до обращения к реестру (решение Анны Лебедевой).
4. **Срок.** `starts_at <= now < expires_at`; вне интервала — `PromoExpiredError`, и до начала, и после конца (решение Ольги Смирновой). Проверки aware-дат и `starts_at < expires_at` в `__post_init__`.
5. **Распределение скидки.** Работаем в целых копейках: доля строки = D·aᵢ/S; берём floor, недостающие копейки отдаём строкам с наибольшей дробной частью, при равенстве — той, что раньше в корзине. Сумма точно равна D, скидка строки не больше её суммы (дробная часть > 0 означает floor+1 ≤ aᵢ). Альтернатива «округлить каждую строку, остаток на последнюю» отвергнута: ломает пропорциональность и может дать скидку больше суммы строки.
6. **Налог.** `tax_for(category, amount - discount)` построчно; `OrderTotal.tax` — сумма. `subtotal` — до скидки, `total = subtotal - discount + shipping + tax`.
7. **Доставка.** Порог бесплатной доставки сравнивается с суммой товаров после скидки (`subtotal - discount`), чтобы покупатели не добирали до порога промокодом. Сама стоимость доставки (`fee`) скидкой не уменьшается.
8. **Новые поля.** `LineTotal.discount` и `OrderTotal.discount` — последние поля с default `ZERO`, прямое создание в старом коде не ломается. `Order.promo_code: str | None = None` — тоже последним.
9. **Учёт использований.** В реестр добавляется публичный метод `redeem(code)` (под `threading.Lock`): повторно выполняет `resolve` и увеличивает счётчик. Для отмены добавляется `release(code)` (под той же блокировкой): уменьшает счётчик на один, не опуская ниже нуля; код нормализуется, неизвестный — `UnknownPromoCodeError`, срок и лимит не проверяются (код мог истечь после оформления заказа). Порядок в `place_order`: нормализация → `resolve` → `calculate_total` → `redeem` → `next_id` → `store.add`. Любая ошибка до `redeem` не меняет состояние и не расходует номер заказа; после `redeem` остаётся только запись в память.
10. **Отмена заказа.** `OrderService.cancel` после успешного перехода в `CANCELLED` вызывает `promos.release(order.promo_code)`, если у заказа есть `promo_code`. Повторная отмена невозможна (проверка статуса), поэтому возврат происходит не более одного раза на заказ. Если у сервиса нет реестра (заказ создан другим сервисом), возврат пропускается без ошибки; отмена заказа без кода счётчики не трогает.

## Risks / Trade-offs

- [Минимум заказа считается по участвующим строкам, а не по всей корзине] → не даёт добить сумму сертификатами; допущение, меняется в одном месте.
- [Возврат использования при отмене] → код с исчерпанным лимитом снова доступен для переоформления заказа поддержкой; `release` не проверяет срок, поэтому переоформление просроченного кода всё равно упрётся в `PromoExpiredError`.
- [Лимит и многопоточность] → `redeem` под блокировкой; `OrderStore` не потокобезопасен, как и раньше.
- [Фиксированная скидка с долями копейки] → `ValidationError` при более чем двух знаках.

## Допущения (неоднозначности тикета)

- `min_order_amount` сравнивается с суммой участвующих строк до скидки, нестрого (`>=`).
- Нет ни одной участвующей строки — `PromoConditionsError`.
- Порог бесплатной доставки сравнивается с суммой товаров после скидки; стоимость доставки скидкой не уменьшается.
- Непустой код без реестра — `UnknownPromoCodeError`; пустой код реестра не требует.
- `uses()` неизвестного кода — `UnknownPromoCodeError`.
- Отмена заказа с промокодом уменьшает счётчик использований на один (не ниже нуля); отмена заказа без кода счётчик не меняет.
- Процент допускает любое число знаков (результат округляется), фиксированная сумма — не более двух.
