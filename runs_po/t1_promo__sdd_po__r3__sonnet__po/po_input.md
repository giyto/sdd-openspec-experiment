### design.md

## Context

См. proposal.md. Проект следует соглашениям README: `Decimal` + `quantize_money` (`ROUND_HALF_UP`), ошибки только от `ShopError`, внедряемый `Clock`, frozen-dataclass с инвариантами в `__post_init__`, `normalize_key` для вводимых людьми кодов, полуоткрытые интервалы `[начало, конец)`, только stdlib. Сертификаты (`Category.GIFT_CARD`) по README никогда не участвуют в скидках. `shop/cli.py` и `shop/reports.py` не меняются: новые поля имеют значения по умолчанию, чтобы они продолжали работать.

## Goals / Non-Goals

**Goals:** обратная совместимость API; точное совпадение суммы построчных скидок с общей; использование засчитывается только успешным заказом.

**Non-Goals:** скидки в CLI/отчётах; хранение промокодов вне памяти; возврат использования при отмене заказа; комбинирование нескольких кодов.

## Decisions

1. **Размещение.** `shop/promo.py` содержит `DiscountKind`, `PromoCode`, `PromoRegistry`; расчёт скидки живёт в `shop/pricing.py` (чистая функция, без времени и состояния); исключения в `shop/errors.py`. `pricing` импортирует `PromoCode` из `promo`; `promo` не импортирует `pricing` (нет цикла).
2. **Разделение проверок.** Реестр проверяет существование → срок → лимит; `calculate_total` — только условия заказа (минимум, наличие участвующих строк). `OrderService` вызывает их в этом порядке.
3. **Нормализация.** `normalize_key` применяется в `PromoCode.__post_init__`, `add`, `resolve`, `uses`. Пустой после нормализации код в конструкторе — `ValidationError`, в `resolve` — `UnknownPromoCodeError`. Правило «пустой = нет кода» действует только в `OrderService` до обращения к реестру (решение Анны Лебедевой).
4. **Срок.** `starts_at <= now < expires_at`; вне интервала — `PromoExpiredError`, и до начала, и после конца (решение Ольги Смирновой). Проверки aware-дат и `starts_at < expires_at` в `__post_init__`.
5. **Распределение скидки.** Работаем в целых копейках: доля строки = D·aᵢ/S; берём floor, недостающие копейки отдаём строкам с наибольшей дробной частью, при равенстве — той, что раньше в корзине. Сумма точно равна D, скидка строки не больше её суммы (дробная часть > 0 означает floor+1 ≤ aᵢ). Альтернатива «округлить каждую строку, остаток на последнюю» отвергнута: ломает пропорциональность и может дать скидку больше суммы строки.
6. **Налог.** `tax_for(category, amount - discount)` построчно; `OrderTotal.tax` — сумма. `subtotal` — до скидки, `total = subtotal - discount + shipping + tax`.
7. **Доставка.** Считается по `subtotal` до скидки: скидка не влияет на доставку, в том числе на порог бесплатной.
8. **Новые поля.** `LineTotal.discount` и `OrderTotal.discount` — последние поля с default `ZERO`, прямое создание в старом коде не ломается. `Order.promo_code: str | None = None` — тоже последним.
9. **Учёт использований.** В реестр добавляется публичный метод `redeem(code)` (под `threading.Lock`): повторно выполняет `resolve` и увеличивает счётчик. Порядок в `place_order`: нормализация → `resolve` → `calculate_total` → `redeem` → `next_id` → `store.add`. Любая ошибка до `redeem` не меняет состояние и не расходует номер заказа; после `redeem` остаётся только запись в память.

## Risks / Trade-offs

- [Минимум заказа считается по участвующим строкам, а не по всей корзине] → не даёт добить сумму сертификатами; допущение, меняется в одном месте.
- [Отмена заказа не освобождает использование] → в тикете не требуется; вне рамок.
- [Лимит и многопоточность] → `redeem` под блокировкой; `OrderStore` не потокобезопасен, как и раньше.
- [Фиксированная скидка с долями копейки] → `ValidationError` при более чем двух знаках.

## Допущения (неоднозначности тикета)

- `min_order_amount` сравнивается с суммой участвующих строк до скидки, нестрого (`>=`).
- Нет ни одной участвующей строки — `PromoConditionsError`.
- Порог бесплатной доставки считается по сумме до скидки.
- Непустой код без реестра — `UnknownPromoCodeError`; пустой код реестра не требует.
- `uses()` неизвестного кода — `UnknownPromoCodeError`.
- Отмена заказа счётчик не уменьшает.
- Процент допускает любое число знаков (результат округляется), фиксированная сумма — не более двух.


### proposal.md

## Why

Маркетинг запускает летнюю кампанию с промокодами (SHOP-412). Сейчас скидки вручную делает поддержка, и суммы расходятся с чеками. Нужна поддержка промокодов в расчёте и оформлении заказа, чтобы скидка попадала в итоги и построчно в чек (бухгалтерия считает налог по строкам).

## What Changes

- Новый модуль `shop/promo.py`: `DiscountKind`, `PromoCode`, `PromoRegistry` (реестр с внедрёнными часами и счётчиком использований).
- Новые исключения `PromoError` → `UnknownPromoCodeError`, `PromoExpiredError`, `PromoConditionsError` (три независимых наследника).
- `calculate_total` принимает необязательный `promo`; `LineTotal.discount` и `OrderTotal.discount` (по умолчанию `0.00`); скидка раскладывается по строкам без остатка, налог считается с суммы строки после скидки.
- `OrderService` принимает `promos`, `quote`/`place_order` принимают `promo_code`; `Order.promo_code` хранит нормализованный код. Использование засчитывается только при успешном `place_order`.
- Обратная совместимость: старые вызовы дают прежние суммы. Не **BREAKING**.
- Вне рамок: `shop/cli.py`, `shop/reports.py` (отдельный тикет), существующие тесты не меняются.

## Capabilities

### New Capabilities
- `promo-codes`: определение промокода, его валидация, реестр, проверки существования/срока/лимита, учёт использований.
- `promo-pricing`: расчёт скидки, распределение по строкам, налог после скидки, условия заказа в `calculate_total`.
- `promo-orders`: передача кода в `quote`/`place_order`, обработка пустого кода, сохранение в заказе, учёт использования.

### Modified Capabilities

(нет: в `openspec/specs/` пока нет спецификаций; правила README остаются в силе)

## Impact

- Код: `shop/promo.py` (новый), `shop/errors.py`, `shop/pricing.py`, `shop/orders.py`.
- Тесты: новые файлы в `tests/`, существующие не меняются.
- Зависимости: нет (только стандартная библиотека). Публичный API расширяется обратно-совместимо.


### specs/promo-codes/spec.md

## Purpose

Описывает промокод и реестр промокодов: валидацию определения кода, поиск по вводу пользователя, проверки срока и лимита использований и учёт использований.

## ADDED Requirements

### Requirement: Определение промокода
Промокод SHALL иметь непустой код, тип скидки (процент или фиксированная сумма) и значение. Процентное значение MUST быть в диапазоне (0, 100]; фиксированное — больше 0, в рублях не более чем с двумя знаками после запятой. Минимальная сумма заказа MUST быть не меньше 0 (по умолчанию 0.00). `max_uses` MUST быть `None` (без лимита) или целым не меньше 1. Значения денег SHALL быть `Decimal`, `float` отвергается. Код SHALL нормализоваться как другие вводимые людьми коды (обрезка пробелов по краям, верхний регистр). Нарушение любого инварианта — `ValidationError`.

#### Scenario: Код нормализуется при создании
- **WHEN** создаётся промокод с кодом `"  summer10 "`
- **THEN** его код равен `"SUMMER10"`

#### Scenario: Пустой код отвергается
- **WHEN** создаётся промокод с кодом `""` или `"   "`
- **THEN** выбрасывается `ValidationError`

#### Scenario: Недопустимое значение
- **WHEN** процент равен 0, отрицателен или больше 100, либо фиксированная сумма не положительна, либо `max_uses` равен 0
- **THEN** выбрасывается `ValidationError`

### Requirement: Срок действия — полуоткрытый интервал
Срок действия SHALL быть интервалом `[starts_at, expires_at)`: начало включительно, конец исключительно; граница `None` означает отсутствие ограничения. Границы MUST быть aware-датами (UTC). Если оба заданы и `starts_at` не раньше `expires_at`, MUST выбрасываться `ValidationError`.

#### Scenario: Граница начала включительна
- **WHEN** текущее время равно `starts_at`
- **THEN** код действует

#### Scenario: Граница конца исключительна
- **WHEN** текущее время равно `expires_at`
- **THEN** `resolve` выбрасывает `PromoExpiredError`

#### Scenario: Некорректный интервал
- **WHEN** `starts_at` равен или позже `expires_at`, либо дата naive
- **THEN** выбрасывается `ValidationError`

### Requirement: Добавление в реестр
`PromoRegistry.add` SHALL регистрировать промокод под нормализованным кодом. Повторное добавление кода, совпадающего после нормализации, MUST приводить к `ValidationError`. Реестр SHALL получать часы через конструктор и не обращаться к системному времени напрямую.

#### Scenario: Дубликат в другом регистре
- **WHEN** добавлены `"SUMMER10"` и затем `"summer10 "`
- **THEN** второе добавление выбрасывает `ValidationError`

### Requirement: Поиск и проверки кода
`PromoRegistry.resolve(code)` SHALL нормализовать ввод и проверять по порядку: (1) код существует, иначе `UnknownPromoCodeError`; (2) код действует сейчас по часам реестра, иначе `PromoExpiredError` (в том числе когда акция ещё не началась); (3) лимит не исчерпан, иначе `PromoConditionsError`. Лимит исчерпан, когда число использований не меньше `max_uses`. Пустая или пробельная строка в `resolve` — `UnknownPromoCodeError`. Три исключения MUST быть независимыми наследниками `PromoError` (не наследуют друг друга), а `PromoError` — наследник `ShopError`.

#### Scenario: Ввод в произвольном регистре
- **WHEN** зарегистрирован `SUMMER10`, вызывается `resolve("  sUmmer10 ")`
- **THEN** возвращается этот промокод

#### Scenario: Неизвестный и пустой код
- **WHEN** вызывается `resolve("NOPE")` или `resolve("")`
- **THEN** выбрасывается `UnknownPromoCodeError`

#### Scenario: Акция ещё не началась
- **WHEN** текущее время раньше `starts_at`
- **THEN** выбрасывается `PromoExpiredError`

#### Scenario: Порядок проверок
- **WHEN** код просрочен и при этом лимит исчерпан
- **THEN** выбрасывается `PromoExpiredError`, а не `PromoConditionsError`

#### Scenario: Лимит исчерпан
- **WHEN** `max_uses=1` и код уже использован один раз
- **THEN** `resolve` выбрасывает `PromoConditionsError`

### Requirement: Учёт использований
`PromoRegistry.uses(code)` SHALL возвращать число успешных использований кода (0 для нового; код нормализуется; для неизвестного кода — `UnknownPromoCodeError`). Использование SHALL засчитываться только оформлением заказа; `resolve`, `quote` и `calculate_total` счётчик не меняют. Реестр SHALL давать атомарную операцию «проверить и засчитать использование», чтобы лимит не превышался.

#### Scenario: Чтение не меняет счётчик
- **WHEN** вызывается `resolve` несколько раз
- **THEN** `uses` остаётся равным 0


### specs/promo-orders/spec.md

## Purpose

Определяет работу промокодов в сервисе заказов: передачу кода при расчёте и оформлении, обработку пустого ввода, сохранение кода в заказе и момент учёта использования.

## ADDED Requirements

### Requirement: Промокод в расчёте и оформлении
`quote` и `place_order` SHALL принимать необязательный `promo_code`. Код нормализуется, разрешается через реестр (существование → срок → лимит), затем применяются условия заказа. Ошибки: `UnknownPromoCodeError`, `PromoExpiredError`, `PromoConditionsError`. Без реестра любой непустой код неизвестен. Вызовы `quote(cart)` и `place_order(cart)` дают те же суммы, что и раньше.

#### Scenario: Скидка в котировке
- **WHEN** вызывается `quote(cart, "summer10")` с действующим кодом
- **THEN** итоги содержат скидку, `uses` не меняется

#### Scenario: Нет реестра
- **WHEN** сервис создан без `promos` и передан код `"ANY"`
- **THEN** выбрасывается `UnknownPromoCodeError`

### Requirement: Пустой промокод означает «без промокода»
Если `promo_code` — `None`, пустая строка или только пробелы, `quote` и `place_order` SHALL вести себя как без промокода (в том числе когда реестра нет). Не-строковое значение — `ValidationError`.

#### Scenario: Пустое поле формы
- **WHEN** `place_order(cart, "   ")`
- **THEN** заказ оформлен без скидки, `Order.promo_code` равен `None`

### Requirement: Код в заказе
`Order.promo_code` SHALL хранить нормализованный код применённого промокода или `None`.

#### Scenario: Нормализованный код
- **WHEN** заказ оформлен с `" summer10"`
- **THEN** `Order.promo_code == "SUMMER10"`

### Requirement: Использование засчитывается только успешным заказом
Использование кода SHALL засчитываться ровно один раз при успешном `place_order`. `quote`, `calculate_total`, а также неудачные попытки (неизвестный/просроченный код, исчерпанный лимит, нарушенные условия, пустая корзина) MUST NOT менять счётчик и не создавать заказ. Лимит проверяется и засчитывается атомарно, поэтому число заказов с кодом не превышает `max_uses`. Отмена заказа счётчик не уменьшает.

#### Scenario: Успешный заказ
- **WHEN** `place_order` с кодом завершился успешно
- **THEN** `uses(code)` увеличился на 1

#### Scenario: Неудачная попытка
- **WHEN** `place_order` падает из-за условий (например, сумма ниже минимума)
- **THEN** `uses(code)` не изменился, заказ не сохранён

#### Scenario: Последнее использование
- **WHEN** `max_uses=1` и первый заказ оформлен
- **THEN** второй `place_order` с тем же кодом выбрасывает `PromoConditionsError`


### specs/promo-pricing/spec.md

## Purpose

Определяет, как промокод влияет на итоги заказа: какие строки участвуют, как считается и раскладывается скидка, как меняются налог и итог.

## ADDED Requirements

### Requirement: Участвующие строки
Скидка SHALL действовать только на участвующие строки. Строка не участвует, если её категория — подарочный сертификат (всегда, по правилам проекта) или входит в `excluded_categories` промокода. Неучаствующие строки получают скидку `0.00`.

#### Scenario: Сертификат не участвует
- **WHEN** в корзине книга и подарочный сертификат, применяется процентный код
- **THEN** скидка сертификата равна `0.00`, а процент считается только от книги

#### Scenario: Исключённая категория
- **WHEN** у кода `excluded_categories={FOOD}`
- **THEN** строки категории еды скидку не получают

### Requirement: Размер скидки
Процентная скидка SHALL равняться сумме участвующих строк (до скидки) × процент / 100, округлённой по `ROUND_HALF_UP` до копеек. Фиксированная скидка SHALL равняться значению кода, но не больше суммы участвующих строк. Скидка на доставку не распространяется: стоимость доставки и условие бесплатной доставки считаются по сумме товаров до скидки, как без промокода.

#### Scenario: Округление процента
- **WHEN** сумма участвующих строк 100.10, скидка 5 %
- **THEN** скидка равна 5.01 (5.005 округляется вверх)

#### Scenario: Фиксированная скидка больше суммы
- **WHEN** фиксированная скидка 1000.00, сумма участвующих строк 700.00
- **THEN** скидка равна 700.00

#### Scenario: Доставка не меняется
- **WHEN** сумма товаров до скидки 3100.00 (доставка бесплатна), скидка уменьшает её ниже 3000.00
- **THEN** доставка остаётся 0.00

### Requirement: Построчное распределение без остатка
Скидка SHALL раскладываться по участвующим строкам пропорционально их суммам до скидки, в копейках, методом наибольших остатков; при равных остатках лишняя копейка достаётся строке, идущей раньше в корзине. Сумма `LineTotal.discount` по всем строкам MUST в точности равняться `OrderTotal.discount`, а скидка строки MUST NOT превышать её сумму. `LineTotal.discount` и `OrderTotal.discount` равны `Decimal("0.00")`, если скидки нет.

#### Scenario: Сумма по строкам сходится
- **WHEN** скидка 10.00 раскладывается на три строки по 33.33
- **THEN** построчные скидки в сумме дают ровно 10.00, результат детерминирован

#### Scenario: Без промокода
- **WHEN** `calculate_total` вызван без промокода
- **THEN** все скидки равны `0.00` и суммы совпадают с прежними

### Requirement: Налог и итог
Налог строки SHALL считаться по ставке её категории с суммы строки после скидки и округляться отдельно в каждой строке; налог заказа — сумма налогов строк. `subtotal` остаётся суммой строк до скидки; `total = subtotal - discount + shipping + tax`.

#### Scenario: Налог после скидки
- **WHEN** строка 1000.00 с налогом 20 % и скидкой 100.00
- **THEN** налог строки равен 180.00

### Requirement: Условия заказа
`calculate_total` с промокодом SHALL проверять только условия заказа и при нарушении выбрасывать `PromoConditionsError`: сумма участвующих строк до скидки меньше `min_order_amount` (равенство допустимо), либо нет ни одной участвующей строки. Срок действия и лимит `calculate_total` не проверяет. Вызовы без `promo` работают как раньше; `promo` не `PromoCode` и не `None` — `ValidationError`.

#### Scenario: Сумма ниже минимума
- **WHEN** `min_order_amount=1000.00`, участвующие строки на 999.99
- **THEN** выбрасывается `PromoConditionsError`

#### Scenario: Сумма равна минимуму
- **WHEN** участвующие строки ровно на `min_order_amount`
- **THEN** скидка применяется

#### Scenario: Нет участвующих товаров
- **WHEN** в корзине только подарочные сертификаты
- **THEN** выбрасывается `PromoConditionsError`
