# Формат экспериментальной задачи

Эксперимент сравнивает, насколько хорошо ИИ-агент (Claude Code, headless) выполняет задачу по коду
в двух условиях: (A) агенту дают только тикет; (B) агент сначала пишет спецификацию по OpenSpec
(proposal/specs/design/tasks), а потом реализует её в новой сессии. Качество меряется скрытыми
тестами, которые агент не видит, плюс проверками на выход за рамки задачи.

## Структура каталога `experiment/tasks/<task_id>/`

```
repo/                 исходный («brownfield») проект, который получает агент
  README.md           краткое описание проекта и его соглашений (как в настоящем репо)
  <package>/...       код, только стандартная библиотека Python 3.13
  tests/...           существующие тесты проекта, все проходят (pytest)
ticket.md             текст задачи для агента, на русском, в стиле реального тикета
reference/            полная копия repo/ с эталонным решением (тесты проекта тоже проходят)
hidden_tests/
  conftest.py         (если нужен) — без зависимостей от reference/
  test_hidden.py      скрытые приёмочные тесты
requirements.json     список требований и привязка тестов
meta.json             рамки задачи
NOTES.md              коротко: какие ловушки заложены и почему задача не тривиальна
```

## Требования к проекту `repo/`

- Python 3.13, только stdlib + pytest для тестов. Никаких сторонних пакетов.
- Реалистичный размер: 400–900 строк кода в 4–8 модулях, плюс 15–40 существующих тестов.
- У проекта должны быть явные соглашения, которые видно в коде и README: например, деньги в `Decimal`,
  собственная иерархия исключений, внедрение часов (clock) вместо `datetime.now()`, логирование через
  модульный логгер, датаклассы, именование. Это нужно, чтобы оценивать «вписывается ли код в проект».
- Должны быть модули, которые к задаче не относятся (CLI, отчёты, хранилище и т.п.). Тикет запрещает их трогать.
- Никаких следов будущего решения: никаких TODO, заглушек с нужными именами, подсказок.
- Тесты запускаются командой `python -m pytest -q` из корня `repo/`. Добавь `pytest.ini` или
  `conftest.py` в корень, чтобы пакет импортировался без установки.

## Требования к `ticket.md`

- На русском, как тикет от тимлида/аналитика: контекст «зачем», затем требования.
- 10–14 проверяемых требований. Часть изложена списком, часть — в тексте («кстати, ...»),
  как в реальной жизни. Минимум 3 краевых случая, которые легко пропустить, упомянуты один раз.
- Явно названы все публичные имена, которые будут импортировать скрытые тесты: модули, классы,
  функции, сигнатуры, исключения, поля. Тесты не должны угадывать API — всё, что они вызывают, есть в тикете.
- 2–3 ограничения рамок: например «сигнатуру `X` не менять, старые вызовы должны работать»,
  «модуль `cli.py` и `reports.py` не трогаем», «новых зависимостей не добавлять».
- Задача не должна быть «напиши TODO-лист»: нужно встроиться в существующий код, учесть взаимодействие
  правил, состояния, время, деньги, ошибки.
- Сложность: сильный разработчик делает её за 2–4 часа. Модель уровня Claude Sonnet должна
  справляться частично, а не на 100 % «с ходу»: важны неочевидные взаимодействия требований.
- Не упоминай OpenSpec, спецификации, скрытые тесты и эксперимент.

## Требования к `hidden_tests/test_hidden.py`

- Каждый тест называется `test_R<NN>_<коротко>`, где `R<NN>` — id требования из requirements.json.
  На каждое требование 2–5 тестов. Плюс тесты `test_API_<...>` на сохранение старого публичного API
  (обратная совместимость), если тикет его требует.
- Тесты проверяют только поведение, описанное в тикете, через публичный API из тикета.
  Не проверяй внутренние детали, имена приватных функций, точные тексты сообщений (если тикет их не задаёт).
- Детерминированность: время только через внедряемые часы/параметры, случайность — через seed/внедрение.
- Скрытые тесты запускаются так: каталог `hidden_tests/` копируется в `repo/tests_hidden/`
  и запускается `python -m pytest -q tests_hidden`. Значит импорты пакета должны работать из корня repo.
- Проверка обязательна: на `reference/` проходят 100 % скрытых тестов и 100 % тестов проекта;
  на исходном `repo/` скрытые тесты в основном падают (кроме тестов обратной совместимости API).

## `requirements.json`

```json
[{"id": "R01", "text": "кратко требование", "kind": "functional|edge|constraint|compat"}]
```

## `meta.json`

```json
{
  "task_id": "...",
  "title": "...",
  "package": "имя пакета",
  "protected_paths": ["pkg/cli.py", "pkg/reports.py", "tests/"],
  "allowed_new_dependencies": false
}
```
`protected_paths` — файлы/каталоги, которые по тикету менять нельзя. Существующие тесты в `tests/`
агент может дополнять новыми файлами, но не должен менять существующие тестовые файлы — укажи
конкретные существующие файлы тестов в protected_paths, а не весь каталог.
